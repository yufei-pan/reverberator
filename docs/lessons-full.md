# Lessons: full entries

Why this project's APIs, formats and agreed behaviours had to change. `lessons.md` has one line per
entry: read that first, and look entries up here by date and name rather than reading this whole. New
entries go last, in the same commit as the change:

```markdown
## YYYY-MM-DD <short name>
- Changed: ...
- Why we had to change: ...
- Original design was wrong because: ...
- Lesson: ...
```

## 2026-10-23 reverberator: a vault link is told by the version's moves, not its text
- Changed: in 0.44 a symlink in a version is the vault's own chain link only when its version's move rows (or, with no move, its `../` count) say so. Absolute links are never chain links. Each version's monitored path is recorded in the manifest meta (`monitor_paths`).
- Why we had to change: a user's symlink whose text had the chain form was followed as the vault's own, so pruning could move another file's copy onto it or delete it.
- Original design was wrong because: it read meaning from a value anyone can write (a link's text), with nothing the daemon alone controls to tell its own links apart.
- Lesson: when a format holds both your own records and users' data of the same shape, mark yours with something only you write, from the first version.

## 2026-10-23 reverberator: pruning hard-links instead of moving, and keeps its books itself
- Changed: pruning hard-links the oldest version's copies into the next version and removes the oldest only at the end; size records are moved copy by copy instead of re-measured; a 0600 `.reverberator_prune_salt` names its temporaries.
- Why we had to change: moving copies one by one left the oldest version incomplete partway through, so a prune cut off (a kill, ENOSPC) could lose a copy that two links named; re-measuring by st_nlink was wrong on mergerfs, whose attribute cache shows a stale link count.
- Original design was wrong because: a destructive step ran before the step that made it safe, and the books trusted a filesystem value the live filesystem does not keep exact.
- Lesson: make the old state whole until the new state is complete, and keep counts you can compute yourself instead of reading them back from the filesystem.

## 2026-10-23 reverberator: the vault scan deletes nothing unless certain, and the commit order puts the commit point last
- Changed: the scan reads the whole vault first and fails the job (FAILED marker) on any error or doubt instead of deleting; an orphan is removed only when current_version or the manifest proves it a crashed attempt. A backup now writes its change list whole, commits the manifest, swaps current_version, then places the list (the commit point).
- Why we had to change: `os.path.exists` read any I/O error as "gone", and on mergerfs one disk out hid change lists while their folders showed, so 0.43 could rm -rf committed versions; the old order let current_version lag a committed list.
- Original design was wrong because: the absence of a marker file was taken as proof, though absence also comes from errors and hidden disks; and the records naming the newest version were written after the commit point.
- Lesson: delete only on positive evidence, never on a missing marker; and write every record that names a new state before the step that commits it.

## 2026-10-24 reverberator: the vault database keeps its journal file, in TRUNCATE mode
- Changed: in 0.45 the vault database runs SQLite `journal_mode = TRUNCATE`, and each job vault keeps a 0-byte `.reverberator_manifest.sqlite-journal` between backups, made and flushed once when the manifest opens.
- Why we had to change: in DELETE mode every commit creates and deletes the journal, and only a folder fsync makes that durable; mergerfs answers fsyncdir with ENOSYS, so after a power loss a stale hot journal could come back or a deletion could be lost.
- Original design was wrong because: it assumed a file name's creation and removal are durable once fsynced, on a stack (a FUSE union) that silently drops the one call that makes them so.
- Lesson: on a filesystem stack you do not control, prefer formats whose durability needs only file fsyncs; make a name once and keep it, rather than creating and removing it per transaction.

## 2026-10-24 reverberator: history and restore exit 1 when a vault disk is missing
- Changed: in 0.45, history and restore still run while a disk of the vault's mergerfs pool is missing, print `Warning: <reason>: <job vault> may be incomplete` on stderr, and exit 1 where they would have exited 0; 2 still means a usage error.
- Why we had to change: a missing disk hides part of every version, so a history or restore that exited 0 looked whole when it was not, and a script could take a partial restore for a full one.
- Original design was wrong because: exit 0 meant "nothing raised", not "the result is whole", and whether the vault could be read whole was never part of the answer.
- Lesson: an exit code should say whether the result is complete, not only whether the run failed; give an incomplete-but-useful result its own non-zero meaning from the start.

## 2026-10-24 reverberator: crash recovery lives in the job's scan only, not in the step that failed
- Changed: 0.45 drops the backup commit's own undo. The job's vault scan resolves every cut-off commit, once every disk of the vault's pool is there: a version whose change list is still in a private `.reverberator-change-list-*` folder is removed and current_version goes back. Two states that round 8 recorded as known limitations, which stopped a job until a hand clean-up, now clean themselves up.
- Why we had to change: the undo ran inside the failing step, where a missing disk could hide a committed list, so it could not tell a crash from a hidden list; and its own gaps left those two hand clean-ups.
- Original design was wrong because: recovery was split between the failing step and the next start, and the part in the failing step ran with the least information.
- Lesson: put crash recovery in one place that runs with full knowledge (the next start's scan), and let the failing step only fail.

## 2026-10-27 reverberator: any batch resumed after a restart is followed by a whole-tree comparison
- Changed: in 0.46 a pending batch resumed at a restart counts as round-tripped even when it holds only scans, so a full comparison follows it; before, a scans-only resume compared its scanned folders and nothing else.
- Why we had to change: a chmod, an xattr change or an mtime-keeping write made elsewhere while the daemon was down was never compared, and the new `matched` key (the time from which the vault matched the whole tree) would have advanced past it for good.
- Original design was wrong because: it judged what a resumed batch needs by the batch's own content ("scans compare their folders whole, so nothing is lost"), when what a restart cannot know is what changed outside the batch while nothing watched.
- Lesson: decide what a restart must compare from what was unwatched (the downtime), never from the shape of the work it resumes.

## 2026-10-27 reverberator: an attribute-only change whose mtime moved is copied
- Changed: under Only Sync Attributes, an attrib whose live mtime differs from the recorded one now copies the file. Round 9 synced the new times onto the old copy whenever its size and tail matched (touch -m).
- Why we had to change: an mmap write raises no event and moves the mtime. A chmod in the same batch then put the new mtime on the old bytes, and every later comparison took the copy as current.
- Original design was wrong because: it read a moved mtime as metadata only, while the mtime is the signal every comparison trusts for contents. Writing it onto bytes it did not come with made that signal lie.
- Lesson: never write a change signal (an mtime, a hash, a version stamp) onto data it did not come with; when in doubt, copy.

## 2026-10-28 reverberator: a vault folder is made only once its disk is there
- Changed: parse_rules no longer creates a missing Vault Path (nor ignores a row whose path cannot be created: the job fails and retries), and fills an auto Vault (or Monitoring) File System Signature only for a folder whose disk is there: the longest /etc/fstab mount point at or above it mounted, every disk of its mergerfs pool there. The backuper creates the path inside its vault wait once the disk is there, every vault wait (and every monitored wait) checks the disk, and a stop writes no pending file where it is not.
- Why we had to change: with the pool unmounted, a start made the Vault Path folder on the root disk under the bare mount point and recorded the root disk's signature for an auto cell, so the job then waited on the wrong disk once the pool mounted; a stop wrote its pending file there too.
- Original design was wrong because: it took "the folder exists, or can be made" for "the disk is there", and the one check that judged the disk (the signature) was itself filled from whatever the folder sat on.
- Lesson: before making or writing into a place that must live on a given disk, check that disk by a source that does not depend on the place (here fstab against the live mount table); never fill an identity check from the thing it is meant to check.

## 2026-10-29 reverberator: the rule-file write-back keeps lines that repeat a job name
- Changed: rewrite_rule_rows() no longer removes the earlier lines that carry the same job name as the row it writes
  back; parse_rules warns at each start, once per repeated name, naming the line used. A repeated name's row keeps its
  name cell as written.
- Why we had to change: the user wants a repeated name warned about with the file left as it is; the write-back
  silently deleted the user's lines whenever it filled in a cell of the winning row.
- Original design was wrong because: it took "TSVZ ignores the earlier lines" for "nobody needs them", and tidied the
  user's file as a side effect of a different job (filling in auto cells).
- Lesson: a write-back changes only the cells it exists to fill; anything else in a user's file it finds odd is
  reported, never edited away.

## 2026-11-03 reverberator 0.53: a prune on a mergerfs pool flushes every disk before it destroys the old state
- Changed: the agreed limitation "No flush before a prune's removal" (2026-10-23: a power loss mid-prune on mergerfs could only bring a link back in either form, no copy lost) is gone. On a pool, a prune makes `.reverberator_pruning` in the job vault say which version it walks (one JSON line, made once with a folder flush and kept, written in place and fsynced) before its walk, flushes every disk of the pool after the walk and the records, clears the marker, removes the oldest version, and flushes again before its change lists go. A prune that finds the marker naming its oldest version (or cannot read it) links back from that version whatever the next one lost; the next backup finishes such a prune before it compares. The scan flushes before it deletes a stale change list. A single filesystem gets none of it.
- Why we had to change: a study on a scratch pool showed one mergerfs request (a rename) lands on one disk and unlinks on another, and after a power loss each disk comes back at its own last checkpoint: unchanged files lost their copy in every later version, newest included, copies hid behind stale links, and the scan could stop with a hint to remove by hand the folder holding the only copies. Nothing detected it.
- Original design was wrong because: "a prune cut off anywhere loses nothing" was argued for one filesystem with one order of writes, and carried over to a union of disks that each keep their own order; the limitation was judged on the guess that the worst case was a link in its old form, never tested by cutting each disk at a different point.
- Lesson: on a union of disks, a step that destroys the old state waits for a flush of every disk the new state touched, and a record that the new state is under way is made durable before its first change. Test crash safety by putting each disk back at its own point, not the whole stack at one.

## 2026-11-04 reverberator 0.54.1: backups wait for restores; status says "waiting since", and `daemon.version` is a string
- Changed: a backup no longer runs while a restore of its job copies. Each job has three lock files in the state folder: `job-<name>.restore.lock` (restores shared while they copy; a batch exclusive from before its prune to its commit, and the job's start around its vault scan), `job-<name>.backup.lock` (new: a waiting batch exclusive; a restore shared only while it takes the restore lock, so restores cannot starve a waiting backup) and `job-<name>.history.lock` (new: history and a restore's picker and prompt shared; only the prune exclusive, non-blocking). A restore asks Continue? holding only the history lock, takes the job lock after, and reads the versions again. The daemon never blocks inside flock: it polls while the job runs, so a stop stays prompt. A lock that cannot be checked postpones the whole backup (FAILED marker after 15 min, "...; backup postponed"). `reverberator status` shows a waiting job as "waiting since <time>: <detail>" (was "waiting for disk since"), and a lock wait's detail is its reason alone ("a restore of <job> is copying"). `status --json` `daemon.version` is the string "0.54.1" (was the number 0.54).
- Why we had to change: the agreed 0.55 layout (the newest version is the one real tree, changed in place by each backup) makes a restore that runs during a backup read a tree being rewritten. The user chose "Backups wait" and to ship the locks first on today's layout.
- Original design was wrong because: the restore lock only kept prunes off a vault, on the assumption that a committed version never changes. That holds only for a layout where each backup builds a new tree beside the old ones. The status phrase assumed every wait is for a disk, and the version was a float, which no three-part version can be.
- Lesson: a lock that guards readers from writers is designed for the layout that will be changed in place, and it is taken after the reader's prompt, never around it: a prompt left open must not hold anything a background writer needs. A writer that waits polls with LOCK_NB under its own stop flag. A gate lock lets a waiting writer go first. A wait's status names its reason and is computed at the source, short enough for the card that shows it. Versions are strings.

## 2026-11-06 reverberator 0.55: the newest version is the one real tree, and older versions link forward
- Changed: a backup no longer builds each version as a whole tree of links to the previous one, and a prune no longer hard-links the oldest version's copies into the next one. The newest version is a plain tree. Before a backup changes a path of it, it records that path's old state in the version before (folders on the way made real with a link per entry pointing forward, a moved entry by hard links, a folder still forwarded whole by one RENAME_EXCHANGE), handing the tree to the new version's name with one RENAME_EXCHANGE first; on a mergerfs pool or a filesystem with no exchange, by renames with flushes between them. A prune renames the oldest away and removes it. A cut backup is rolled forward, never undone, and the manifest's commit is the commit point. Change-list sizes count each inode in the newest version holding it, so the inode estimate before a batch is the change alone. Chain Length and Copy threads have no effect, and Keep 1 Complete Backup False reads as True. One answer, `vault_layout()`, says which rules a vault gets, for the scan, the start and the commands alike. Each vault is converted once at its first 0.55 start, and there is no going back to 0.54.
- Why we had to change: on an f2fs vault SSD every inode a cycle touches costs a 4 KiB node block. A large job's hourly cycle touched about 650K inodes and wrote 2.7 GiB (about 64 GiB a day) to keep 6-9 MiB of changed data, with 2.6M calls. Measured after, on the real code with the same shape: 24 to 36 MiB a batch, and 59 MiB for one of about 17,000 changes.
- Original design was wrong because: a version cost the size of the tree, not of its change, and links pointed backward, from the most used version to the one about to be deleted, so every prune rewrote the next version first, with crash machinery (salt, marker, link-back, move tables) to match. Two things the new design nearly carried over wrong: the layout lived only in a manifest that is discarded when unreadable, and with it lost the 0.54 rules would have removed a cut batch's tree, the only real tree, as an orphan, so the staging folder, made after those rules ran and before anything else changes, now says they must never run again; and the inode estimate `latest.inode + change` was added to a vault count that now holds the tree already, so a job past half its inode limit would have pruned everything it may.
- Lesson: make a version's cost follow what changed: keep the current state as the one real copy, record the old state of only what changes before changing it, and point references from older to newer so removing the oldest touches nothing else. Record by same path only (hard-link a moved source), so no record needs a path map. Kill after every write and check every version against an oracle, readers beside writers too. Measure in the units the medium charges (inodes touched), not bytes. A marker that keeps old destructive rules from running gets a second witness on the disk, made before the first change. When a stored number changes meaning, rework every formula that reads it.

## 2026-11-06 reverberator 0.55: a commit flushes its copies first, and a link with no text is a real outcome
- Changed: a batch that placed a copy flushes the vault's disks before its change list is written, unless a comparison's clean sync came after the last copy; a roll-forward and a batch on two renames always flush, and a flush that fails commits nothing. The scan's test for a hand-over's leftover takes ENOENT from readlink as a link with no text and goes on to the next entry.
- Why we had to change: an f2fs checkpoint keeps a new file's size and not its data, and an fsync of a folder or a file can run one. With no flush, a power cut within the writeback window (about 30 to 45 s) after a commit left that batch's copies past the inline size all NUL in a committed version, on every commit and in 0.54 too, and nothing reported it. A checkpoint from any process that lands inside symlink(2) can also keep a link whose text never arrived: lstat works, readlink gives ENOENT, fsck sees nothing, and a later checkpoint heals it. The scan took that ENOENT for a failure and refused the vault on every attempt.
- Original design was wrong because: it took "the manifest's commit is durable" for "what the manifest names is durable". The rule "nothing is flushed when copies are written" rested on the claim that writeback usually loses a file's end, which the comparison catches, while on f2fs a checkpoint loses the whole file. The crash suite's power cuts could not show it, as its files were a few bytes, small enough to live inline in the inode. The scan assumed a name lstat sees has text to read.
- Lesson: a filesystem's journal or checkpoint guards its own structures, not your data: "committed" needs a flush of the data before the commit point, and a crash test needs files big enough to leave the filesystem's inline path, or it cannot see this. An outcome the man page does not list is still an outcome after a cut: judge it by what it proves, not as an error that stops the job for ever.

## 2026-11-06 reverberator 0.55: a rename moves more than a name, and a read after a change can be old
- Changed: a conversion saves every folder's times in the manifest before its first swap and gives them back after each one (`version_times`). On a pool, link counts are read by `links_now()`, a statx with FORCE_SYNC, and the pool is told to forget what it holds after a change made directly on one of its disks.
- Why we had to change: on f2fs an exchange across folders moves the mtime of the folder that moved, as its `..` changes, and ext4 does not, so a swap alone lost a version's folder times. mergerfs caches `st_nlink` per name for about a second, so an lstat misses a link or a removal made under another name, and reads after a change made directly on a branch are stale (an entry of another kind reads as EIO). ext4's `st_blocks` can read 0 for an instant during writeback, so a file's blocks say nothing about its contents while it is being written out.
- Original design was wrong because: it took a rename to change names alone, and an lstat to answer for now, on the strength of what one filesystem did.
- Lesson: save a value you must keep before any call that can move it, and give it back after; try each layer you read through for what it caches, and ask for a fresh read where a stale one gives a wrong answer. A union that is written around must be told to forget.

## 2026-11-06 reverberator 0.55: a change list is not a timeline
- Changed: history reads a version's move rows with `follow_moves()`, which takes the path's own row first wherever it stands and passes over the other half of a swap or rotation, instead of reading the rows in order.
- Why we had to change: a batch's collapse keeps a chain of moves as one row, standing at its last move's place with the source its first move left, so rows are not in event order and the name a row gives is not always one a version held. A rotation such as `mv site site.old; mv site.new site; mv site.old archive/site-1` read as moved from the wrong name, and a fuzz of 30,000 real batches found 42 names that a fix built on event order had broken.
- Original design was wrong because: the collapse was written for the replay, which needs only where things end up, and the reader took the same rows for a history of the batch.
- Lesson: a format that merges records must say what order is left. A reader that needs the order of events either gets it recorded or works from the rule the writer merged by; check any claim of order against real batches, not the common case.

## 2026-11-06 reverberator 0.55: a gate that passes by chance is no gate, and skipped tests rot
- Changed: the pool cut test, the release gate, gained a shape with file placement forced, and a small sample of double cuts on the conversion shapes. Its rig runs the real `sync_vault_filesystems()` and stubs one level lower. The full runs are repeated on merged code, not only on each branch, as the default suite skips them.
- Why we had to change: one cut in a conversion on a pool lost a version's names, and 16,174 runs passed it, as `category.create=pfrd` placed the files once per run's template and the template had not drawn the placement the bug needs. Forced, it failed 8 of 12 tries. Separately, a lock per disk gave a function a new argument on one branch while the rig's stand-in kept the old one on another: each branch was green, the default suite skips the rig, and after the merge all 12 cut tests stopped at their first flush.
- Original design was wrong because: the gate's count of runs was taken for coverage of shapes, though the shape depended on a random draw it did not control, and a stand-in with its own copy of a signature can only be checked by running what uses it.
- Lesson: a release gate whose verdict depends on what a random policy did proves nothing about the shapes it did not draw: force the placement in every shape that depends on it. Tests skipped by default run after every merge, as two green branches can break them between them; a stand-in goes as low in the stack as it can, so the code above it stays real and its signature cannot go stale.

## 2026-11-09 reverberator 0.55.2: a failure no rerun can fix does not hold a restore private
- Changed: a restore that meets a symlink the target's filesystem refuses as too long (its text or its path: on XFS a text of 1,024 bytes and up) names it, with the reason, as a failure that is not retried, and finishes: the folders are handed over and the marker goes, and the exit code stays 1, as 0 means everything asked for was restored. Only failures a run again may fix keep the target private with its marker, and the summary's offer of a run again counts only those. A backup leaves such a link out of the version, recorded as absent the way a delete is, with a warning, instead of failing every batch. A later change in 0.55.2 gave the same treatment to the other failures no run again can fix: a chain that leads nowhere, a link to the live file of a referenced backup, and an entry whose path the target's filesystem refuses as too long, at any step of restoring it. Before it, one of them met by a run again after a kill made the restore impossible to finish: the run again copied everything again, failed that entry, and so never cleared its record.
- Why we had to change: a backup of such a link failed every batch, so no version committed while the link existed, and a restore of one reported it, left the whole restored tree private (mode 0700) with its marker, and asked for a run again that could never succeed for that link, only `--accept` ending it. Both were shown by running the real 0.55.1 daemon in a container with an XFS vault and target.
- Original design was wrong because: it treated every failure of a restore as one a run again may fix, and every failure to write into the vault as a fault of the vault, so a property of the data (a link longer than one filesystem holds) was handled as a passing error, and the response to it, waiting for a retry, could never end.
- Lesson: sort failures by whether a retry can fix them before choosing what they hold back. One no retry can fix is reported once, by name, and the work goes on to its end; only a failure a retry may fix holds the result back for one, and the offer of a retry counts only those.

## 2026-11-09 reverberator 0.55.2: a sync proves only what its handle saw
- Changed: a restore syncs what it wrote through handles opened once, before its first copy: off a mergerfs pool the fd it claimed the target by (a file target's folder, opened before the copy), on a pool one fd per disk of the pool, opened at the claim, of a branch of that disk; never through a path opened at the sync. Its marker says "unsynced" from the claim until that sync succeeds, and any unsynced record, whatever its value, means a run again copies everything again, keeps a "recopy" record until every entry was copied again and a sync succeeded, and refuses `--accept` (exit 2) while it stands; a failed sync records "recopy" 'sync failed'; the marker also says "made" when a restore made the target. A stop (Ctrl-C, SIGTERM, SIGHUP) before the sync says "Stopping: writing what was restored into the target out to disk first, which takes as long as the disk needs", waits for that sync, which nothing cuts short, and then a run again keeps what is there. A disk that joins the pool during the run and holds the restore's folder fails it ("the disk D joined the pool while the restore ran"), and a recopy over a vault whose pool is missing a disk keeps its recopy and leaves the target private. A write error a sync meets on a disk that holds a vault of the rule file is recorded as the daemon records its own failed sync (a marker in the state folder, with the new field "restore": true, which the daemon logs once with VAULT WRITE ERROR when a comparison first reads it and then rewrites as its own marker), or warned of when that cannot be written. Output and exit codes changed since 0.55.1: the lines for a disk's write error (and after the hand-over, that the files restored are on disk and their folders' owners, modes and times and the marker's removal may not be), a branch that could not be opened, disks that could not be listed (and listed again), the joined disk, and "cannot write its marker and make it durable"; "N failed" counts only the failures a run again may fix, and the summary offers a run again for those alone; `--accept` exits 2 over a marker with a record; the recopy summary line and the Interrupted lines, the way-out sentence (fix the cause and run again, or remove the target and restore it fresh, or restore into a new folder when no restore made the target), `--accept`'s "Kept ... but not all of it is known to be on disk" and "Did not keep ..." heads; a signal ignored when the restore starts stays ignored.
- Why we had to change: a restore never synced, so one that said done could lose files at a power cut. The first design kept a stopped or killed run's copies when a run again in the same boot and mounts synced them through a handle it opened then, and that run could exit 0 over lost bytes when the daemon's vault flush or a `sync -f` had met the write error first.
- Original design was wrong because: it took "a sync returned 0" for "these bytes are on disk", though a handle opened after a write error hears of it only while no other sync has.
- Lesson: Linux reports a writeback error once to each handle that was open when it happened, and to a handle opened later only while no one has seen it. So a sync that must vouch for writes goes through a handle opened before the first of them, and "is it on disk?" cannot be answered after the fact, across a crash, a kill or another program's sync. Where that proof is missing, do the work again rather than keep it.

## 2026-11-10 reverberator: a write error is heard where it is needed, not remembered
- Changed: every vault sync of the daemon goes through handles a unit of its work (a batch, a scan, a conversion) opened before its first write into the job vault, one per filesystem holding it (on a mergerfs pool, one per branch's filesystem, picked at each sync by the job vault's st_dev on each branch); a branch holding the job vault on a filesystem the unit opened no handle of fails the sync. The failed-sync markers go: no vault-sync-failed-<disk> file is written in the state folder or read any more, and nothing waits for a reboot. The alert changes from "VAULT WRITE ERROR: disk D failed a sync (E); its copies stay unchecked until a reboot" (and its "its marker cannot be written" form) to "VAULT WRITE ERROR: disk D failed a sync (E): nothing is committed past it, and the next attempt copies again what this one changed", and from once per disk per boot to once per unit that hears the error: a disk that keeps failing alerts again at every retry of every job on it (after 60 s, doubling up to once an hour). A restore no longer records a write error for the daemon, so its warning "could not record the write error of disk ... for the daemon" goes. The comparison no longer syncs; the scan's removal of a stale change list now fails the attempt when its flush fails; the roll-forward copies again every file the cut batch recorded (and, over a rebuilt manifest, every file it made) instead of reading it back.
- Why we had to change: the daemon synced through a handle it opened at the sync, so when another program's sync (a `sync -f`, a restore's, another job's) met a vault disk's write error first, the daemon heard nothing and committed a version whose copies might not be on disk. The markers were there to remember an error the kernel reports once, and needed a lock per disk, a boot id, a restore's report and their own failure cases (a marker that cannot be written, one per mount point of one filesystem), each with a limitation of its own.
- Original design was wrong because: it remembered the error after the fact instead of arranging to hear it. A handle open since before the writes hears the error whoever saw it first, and a failed attempt that copies its work again needs nothing remembered.
- Lesson: an error the system reports once is not worth remembering in a record of your own (a marker, its locks, a report to another process): open the handle that must hear it before the work it vouches for, fail the attempt when it does, and redo the work. A record kept instead is a moving part with failure cases of its own, and still misses whoever saw the error first.

## 2026-11-12 reverberator 0.55.5: a record follows its inode through a rename
- Changed: a move keeps the records and unchecked marks of the manifest rows the version already holds (the committed ones), and the rows move only once the version's rename is made; a fallback to a copy leaves them where they were. A row the batch wrote (dirty) loses its record and mark when it moves, so the verification reads it back at its new place, as it did before: the copy it recorded may hold the monitored file of its old place, and the verification trusts a dirty row for presence only.
- Why we had to change: every rename made the batch's own verification read each moved file back (2,000 files: 263.3 MB read for 0.1 MB written), and rows moved ahead of a rename that then fell back to a copy left the target's rows gone, so the version before kept a change list that said too little.
- Original design was wrong because: it took a renamed entry for an unknown one, though a rename keeps the inode and its bytes, and it moved the records before the change they describe.
- Lesson: a record describes an object, not a name: move it with the object, and only once the object has moved.

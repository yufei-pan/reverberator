## 2. The walk (P10, P11, P12, D14, D13's watcher half)

All the walks of a tree go through two generators: `iter_tree_entries()` (the watcher's walk, every comparison's, the
first version's, the scan's and the roll-forward's walks of a version, `VaultManifest.rebuild()`) and
`iter_folder_entries()` (history and restore, through `iter_version_entries()`). Both recurse by `yield from`, one
Python frame a level.

**Today.**
- A tree deeper than about 1,000 levels hits Python's recursion limit (1,000 frames). Run in Docker on Python 3.13
  (2026-11-14, the walk copied from the code, a tree of 1,200 one-letter folders and a file at the bottom): the walk
  yields 999 of 1,201 entries and logs one ERROR line, "Error scanning <path, 998 levels down>: maximum recursion depth
  exceeded", as `except Exception` takes the RecursionError for an unreadable folder. So the deepest folders get no
  watch, every full comparison logs an UNREADABLE alert for them and keeps their rows, and the files below are never
  backed up. Restore stops at the same depth in `iter_folder_entries()` (history reads each version by lstat and walks
  none), and `WrittenFolders.settle()`'s `is_real()` recurses once per path component, which an event deep enough would hit
  (reasoned, not run).
- The walk lists a folder with `is_dir(follow_symlinks=False)`, then `os.scandir(entry.path)`, by path. A folder replaced
  by a symlink in between (`mv d d.old; ln -s /srv/other d`, a migration) is listed through the link: a full comparison
  copies the link's target's entries into that version under d, and the next batch puts the link there (reasoned, not
  run). The watcher's `add_watch()` follows it too: `watch_flags` have no IN_DONT_FOLLOW, and `watch()` adds the path with
  its trailing slash, which makes the kernel follow a link whatever the flags (`probe_at()` strips it for that reason).
- `except Exception` around the whole generator hides bugs: `tests/test_inner_mounts.py:91` uses `errno` without
  importing it, and passes because its NameError is swallowed as an unreadable folder (a root-only test).
- A folder gone when the walk reaches it is told by listing its parent (`folder_gone()`, on the error path only): a mass
  deletion of N siblings while a walk passes lists that parent N times (about 8 ms a listing at 100,000 names).
- The watcher's walk counts a folder unwatched only when its error is not ENOENT or ENOTDIR
  (`initializeFolderWatchers()`). A folder its parent lists and the kernel cannot open (FUSE, CIFS or sshfs name
  trouble, ENOENT every time) is not counted unwatched, so it does not hold the matched time, though no event reports a
  change in it.

**The change: one iterative walk that opens each folder without following a link.**
1. **A stack, not a call a level.** `iter_tree_entries()` keeps a stack of the folders it is in, each frame its path
   string, its rel and its listing; depth first, a folder right before what is in it, the same order and the same
   yields as today (folder paths end with /, links come out as files, `list_folders_first`, `skip`, `errors`). Each
   yielded path is the frame's path joined with the entry's name, as `DirEntry.path` of a listing of a handle is the bare
   name. `iter_folder_entries()` keeps a stack the same way and changes nothing else: it lists each folder where
   `walk_folder()` landed, by path, as today, since history and restore follow the vault's forward links. `is_real()`
   walks up its rel in a loop. No other walk of the tree's depth recurses (the end-to-end test below finds one that does).
2. **P11: each folder below the root is opened by its path, not following a link:** `os.open(path, O_RDONLY |
   O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC)`, then `os.scandir(fd)`, which lists through a duplicate of the handle (CPython);
   the walk keeps its own handle until the listing closes, as an entry of a listing by handle stats through it (R12): two
   handles a level while a folder is listed, where today's walk holds one. The walk's root is opened as today, following a
   link (a monitored path may be given through one), but for the root of a scope walk (`iter_scope_entries()`), whose
   lstat just said it is a folder: it takes O_NOFOLLOW too. What comes of each open:
   - ELOOP or ENOTDIR (a link or a file took the folder's place): the folder is gone as a folder; a FolderGone, with
     its INFO line, as L10 made of a folder gone mid-walk, with no listing of the parent. The entry now at that name is
     the comparison's to find, in its parent's next listing or its event.
   - ENOENT: gone unless the parent still lists it (D14's rule below).
   - Any other error, ENAMETOOLONG for a path of 4,096 bytes and more included: as today (ERROR, appended to errors,
     UNREADABLE at the comparison).
3. **Handles past 1,000 levels.** A walk holds two handles a level while a folder is listed (`iter_folder_entries()`, which
   lists by path, one), and now goes deeper than 1,000 levels. The daemon raises RLIMIT_NOFILE's soft limit to its hard one
   at start (`inotify_resource_manager`); `restore` does the same, one call at its start, and so does the suite's conftest;
   `history` holds no listing a level (it reads each version by lstat) and raises nothing. Past it, a folder the walk cannot
   open is unreadable, logged and left unwatched, and the walk goes on.
4. **D14: a kept listing per parent.** When a folder's open answers ENOENT, the walk asks its parent's frame for a kept
   set of the parent's names, listed by path (as `folder_gone()` lists it) the first time a child is not found. The
   folder is gone when the kept set does not name it; when it does, the parent is listed again and that set kept, as a
   set listed before the open cannot tell. A mass deletion of siblings lists the parent once per wave, not once per
   folder; a name the parent lists and the kernel cannot open costs one listing each time it is met, and keeps its ERROR
   and UNREADABLE lines at every walk, as today (L10's R32).
5. **P12: the walk catches OSError only, at the calls that read the tree** (the opens, the listing's next entry, an
   entry's `is_dir()`); `skip()` and the code that consumes the yields are outside the catch. A bug is raised to the
   caller with its traceback: in the backuper's walks it fails the attempt; in the watcher, `watcher()` catches an
   exception that leaves `watchFolder()`, logs it with its traceback and fails the job (`job.fail()`), as a failed watch
   init does, so the job is started again rather than left with no watcher. tests/test_inner_mounts.py imports errno.
   This comes with or after item 1: with the recursive walk, a deep tree's RecursionError would stop the job.
6. **P11, the watches:** every watch `initializeFolderWatchers()` adds below its root is added at the folder's path
   without its trailing slash, with IN_ONLYDIR and IN_DONT_FOLLOW, as `probe_flags` already are: a link at a folder's
   place is never watched (ENOTDIR, which `watch()` treats as gone, with its info line). The root's own watch is added
   as today, as a configured path may be given through a link. The watch is still added by path when the folder is
   yielded, before the walk opens it, so a folder made in it after its listing begins raises its create; a link swapped
   in between the watch and the open makes the open fail (ELOOP or ENOTDIR), and the walk's error loop removes the watch it added,
   as for any folder it could not read.
7. **D13, the watcher's half:** the error loop of `initializeFolderWatchers()` counts a folder unwatched unless its
   error is a FolderGone (`not isinstance(error, FolderGone)` in place of the errno test), so a folder the kernel cannot
   open holds the matched time as any unwatched folder does ("A paused inner mount or an unwatched folder holds the
   matched time").

**What it leaves, Not an issue.** The walk lists only a folder that was a folder at its open, and adds no watch through
a link at a folder's own place. What still follows a link by path, as today: the consumers of the yields (the
comparison's lstat of a folder's slash path, cp, the vault reads), for a folder replaced between its listing and that
lstat, which gets what any entry replaced in that window gets today (an attrib and copy_file_meta()'s "it is a symlink"
ERROR line for a link, "treating as create" for a file); the walk's open and its watch, for a folder above, replaced by a
link after the walk entered it; and a folder renamed after its open, listed under its old rel as today's
`os.scandir(path)` lists it. In the shape that happens (a folder moved to another disk and a link left at its place)
they read the same files through the link, and the next batch records the link; a link crafted to race a walk gets its
target's names into a change list and the vault with their owners and modes, which a restore by that user cannot read.
No real-world failure; a fix would be every consumer reading by handle.

**Why it is right.** The yields and every caller's contract are unchanged. O_NOFOLLOW on the folder's own name is the
check round 22 asked for, at the one call that lists it, with no handle kept for a parent; the kept listing of a parent
is only a cache of an answer the kernel gave after the child's open failed, and a name it holds is asked again.

## 3. The tail read: a leased file at the comparison, an unreadable one at the check (D2, D1)

Every comparison reads the last 64 KiB of each regular file whose size and mtime match its record (`hash_file()`, from
`compare_monitor_entry()`), through a non-blocking open, so a FIFO put at a file's place cannot hold the comparison.
Before the hand-over, 0.55.5's check (`entries_all_drop_out()`) opens each regular file of a batch whose entries may all
drop out, and stops at the first that opens.

**Today.**
- D2: a regular file another process holds a write lease on (an NFS write delegation, Samba's kernel oplocks, any
  `F_SETLEASE` caller) answers that open with EWOULDBLOCK: "Error comparing <path>: [Errno 11] Resource temporarily
  unavailable, treating as modify" at ERROR, and a version that changes nothing (with Keep N, the oldest pushed out).
- D1: a regular file that opens and whose read fails (a bad sector; an EIO from a FUSE or network filesystem), the only
  change of a batch or a full comparison (unchanged, its tail failing at the comparison: "Error comparing ..., treating
  as modify"; or changed since its record): the check opens it, which works; the tree is handed over; the copy's cp
  fails with its UNREADABLE line; a version that changes nothing commits, at every full comparison and every batch of
  its events.

**The change.**
- **D2:** in `hash_file()`, on EWOULDBLOCK from the non-blocking open, and only then: open the same path O_PATH |
  O_NOFOLLOW, `fstat` it, and when it is a regular file, open `/proc/self/fd/<fd>` O_RDONLY, blocking. That open waits for
  the lease to break (fs.lease-break-time, 45 s by default), as cp's open does, and the tail is read through it. Anything
  but a regular file is refused as today ("Not a regular file"). The O_PATH handle cannot block and is of the inode the
  reopen reads, so a swap to a FIFO between them cannot hold the comparison. No extra call unless the open answered
  EWOULDBLOCK.
- **D1:** the check reads, through the handle it opens, the file's last 64 KiB (the bytes the comparison's tail check
  reads; cp then reads them from the page cache). A read error drops the file out as a failed open does: its UNREADABLE
  line once per batch (`reported`), the file keeping its last copy, the matched time held. A file that opens and reads
  ends the check as today (False). The comparison's "Error comparing ..., treating as modify" line for an unreadable tail
  stays: it is true, and the check then drops the entry.

**Why it is right.** A file whose tail cannot be read would fail its copy, so the version keeps its last copy either
way: leaving it out at the check gives the same version with no empty one, and needs no change to the commit path. A
lease is no read error: the blocking reopen reads the file the way the copy would.

**D2's other route, weighed:** on EWOULDBLOCK, take the file as matching its record. It needs no
reopen and never waits, but it skips the tail check of a leased file, a new way past the approved "A rewrite made while
down that keeps size and mtime" (a wrong result), to save one O_PATH reopen that runs only for a leased file. Not taken.

**Tests.**
1. tests/test_io_errors.py, with its lease holder (around 970): a full comparison of a file whose size and mtime match
   its record, while another process holds a write lease and lets go 1 s after the break starts: no "Error comparing"
   line, no version, and the comparison took at least 1 s. Main logs the error and commits a version.
2. The same with a FIFO swapped in at the file's place between the EWOULDBLOCK and the O_PATH open (a stand-in on
   `os.open`): the comparison does not block.
3. A batch whose only entry is a file whose tail read fails with EIO (a stand-in on the check's read of that file),
   once changed since its record and once unchanged (the full comparison's case): no version, one UNREADABLE line, the
   matched time held. Main commits a version that changes nothing.
4. Pins: an unchanged readable file compares as unchanged; a file deleted between its lstat and its tail read is
   handled as today; a batch with a readable file beside the unreadable one commits, and the unreadable one keeps its
   last copy with its UNREADABLE line.

**Cost.** None on the normal path of the comparison. The check reads up to 64 KiB of one file per batch it runs on,
which cp then reads from the cache. A leased file costs the comparison up to the lease-break time, as cp's copy does.

## 5. A path the vault refuses (D4, Q3)

**Today.** Linux takes a path of at most 4,095 bytes (4,096 with its terminating NUL), whatever the filesystem. A path in
the vault is the Vault Path, the job name, the version folder's name (about 30 bytes) and the path below the monitored
root.
- A symlink whose own path in the vault passes 4,095 bytes fails at its record in the version before
  (`TreeWriter.record()` raises JobFailure, "FAILED: recording <rel> in <version> failed: [Errno 36] File name too
  long"), before any copy.
- A regular file in a folder whose path in the vault reaches 4,041 bytes fails at its copy: cp writes it under a
  temporary name in its folder (`partial_copy_path()`: a dot, 32 hex digits and `.reverberator-partial`, 54 bytes after
  its slash), that path passes the limit, and `copy_failure_side()` calls it the vault's failure (JobFailure).
- Either fails every attempt of the job for as long as the entry is in the monitored tree, retried with the growing delay;
  no version is made. A first version (V0) fails the same way, so such a job never gets one. A folder whose path passes
  the limit fails its mkdir the same way (reasoned, not run).

**The change: a length rule, before the vault is written.** An entry's path in the vault is measured in bytes
(`os.fsencode()`) in the new version: the version before's path is never longer, as the two names differ only in the
version number, whose digits never shrink, and the timestamp has a fixed width. For a copy (a file, a link, a folder's
own copy), the measure is the longer of that path and its temporary one (the folder's path plus 55). The rule sits
where the replay takes each entry (`do_reverb_backup()`, which a roll-forward's entries and the verification's fixes go
through too), in the first version's walk, and in the check before the hand-over; nothing else writes a new path into a
version. By event, when a path passes 4,095 bytes:
- a create, modify or attrib: nothing is recorded or copied, so the new version keeps what the tree holds there; the row
  is discarded when that is nothing (a new entry, the case the entry names), and kept otherwise;
- a folder left out takes everything under it out too (the first version's walk does not go into it; the replay's
  entries under it are left out by the same rule);
- a delete whose path passes: left out, its row kept: the tree keeps the entry, as its removal by path would fail, and
  its line says "this version keeps it" in place of "left out of this version";
- a move one of whose paths passes is replayed as the delete of its source and the create (a copy) of its destination,
  each under the rule;
- an entry the tree already holds at such a path (a folder renamed to a longer name, which moves no entry, or V99's
  entries one byte longer in V100) is backed up as it is; the rule applies when it changes.
Each entry left out gets one line per batch, through `reported`, the marker of a link whose text the vault refuses:
`reverberator job <name> NOT BACKED UP: <path>: its path in the vault would be longer than Linux takes (4,095 bytes);
left out of this version`. It alerts (firewatcher matches NOT BACKED UP).

**The check before the hand-over** (`entries_all_drop_out()`) takes the same rule first, with no syscall: an entry the
rule leaves out whole drops out (a delete or a move too), with its line. The new version's name is the newest's with the
number one higher, so its length is known before its timestamp is taken. Without this, every comparison that meets such
a file or folder would commit a version that changes nothing, as the check counts a readable file or a folder as a
change; with it, the approved "A batch whose only changes are left out can still commit a version" loses its first case
(the link at 4,041 bytes), whose pick, "Leave that case out (Recommended)" (2026-11-12), rested on "Catching that needs
extra path-length arithmetic", which this rule adds anyway (Calls to confirm).

A link whose text the vault's filesystem refuses (XFS: 1,024 bytes and up) stays with `link_too_long()`, after cp, as
that limit is the filesystem's own.

**Why it is right.** The limit is the kernel's, one number for every filesystem, so the rule is exact: an entry it
leaves out could never be written by path, and one it lets through is not refused for its length. Nothing is written
before the rule decides, so no cut leaves a part of such an entry.

**What it leaves out widens an approved known limitation** (a symlink only, 2026-11-09), and the deferred entry's plan
also named a shorter temporary name, whose form the restore (`remove_stale_partials()`) and the 0.54 prune reader
(`is_prune_temp()`) read back: both are Q3.

**Tests** (Docker, uid 65534; the Vault Path made deep in the basetemp, so a shallow monitored tree reaches the limit):
1. A symlink whose path in the vault is 4,096 bytes, in a batch beside a normal change: the version commits with the
   normal change, the link is not in it, one NOT BACKED UP line. Main fails every attempt with "FAILED: recording".
2. A regular file in a folder whose path in the vault is 4,041 bytes: the same. Main fails with "File name too long".
3. The same two in a first version: V0 commits without them. Main never commits V0.
4. A folder whose path passes the limit, with files in it: none of it in the version, one line for the folder.
5. A batch whose only entry is test 1's link, then test 2's file, then test 4's folder: no version. Main fails.
6. An entry at 4,095 bytes in V9 (the Vault Path sized for it), then V10: it stays in V10; its delete in a later batch
   keeps it, with its line, and makes no version that changes nothing.
7. Pins: a file in a folder at 4,040 bytes is backed up; a link whose text XFS refuses still takes `link_too_long()`'s
   line (marked real, an XFS basetemp, as today).

**Cost.** One length sum per entry the replay or the check takes, no syscall.

## 6. A lost manifest (D3, Q2)

The entry's three cases, each when the job's vault database is lost or unreadable (removed or damaged from outside; the
daemon's own messages suggest removing it in some cases).

**Today.**
1. **Inner mounts.** They are recorded in the manifest only (`VaultManifest.inner_mounts`). A rebuilt manifest has
   none, so an inner disk unmounted at that moment looks like an empty folder: the next comparison commits the version
   with it empty, with no "Inner mounts not mounted" line; when it is mounted again every file is copied back; under
   Keep N or a size limit the versions that hold its files can be pruned meanwhile, and a disk that never comes back
   loses its backup.
2. **A cut copy kept.** After a cut batch, `put_back_recorded()`'s pass 2 (remove what the cut batch made) runs only
   when the manifest describes the previous version, as it rests on `put_back_forward_links()`, which needs the rows. Over
   a lost manifest a file the cut batch copied in new, whose source cannot be read at the retry, keeps the cut copy as its
   backed-up copy, wrong bytes if the cut damaged it, with no line but its UNREADABLE one.
3. **A folder lost from the version before.** On two renames (a pool, or a filesystem with no RENAME_EXCHANGE), a batch
   cut between `TreeWriter.exchange_in()`'s two renames leaves the previous version with nothing at that folder and its
   forward link in staging. Over a lost manifest no row names it, so the start's `empty_staging()` removes the link, and
   what the batch deleted or replaced under that folder is in no version.

**The change.**
1. **The version folder's root-meta record carries its inner mounts.** ROOT_META_XATTR's record (`encode_root_meta()`,
   on each version's folder, read and compared at every batch already) gains a field under its "v": 1, which allows new
   fields: `"inner_mounts"`, the rels the commit remembers (`inner_mounts_to_remember()`), stored as the manifest
   stores them (`storable_name()`). 0.55.5's reader skips the field, and a whole-job restore ignores it.
   - **Written** with the record: `record_root_meta()` takes the set, and its call moves from the end of
     `do_reverb_backup()` to `do_backup()`'s commit, where `set_inner_mounts()` is called (the first version's too), the
     set computed once for both, before the manifest's commit. The record is still written only when it differs. The
     no-differences path writes no record: what it remembers differs from the newest version's set only for mounts
     whose folder the version holds as it is (`paused_inner_mounts()` pauses only a remembered folder that is empty).
     A record trimmed for size leaves the root's own extended attributes out first (about 2.9 KiB of them on ext4 or f2fs, less beside many inner mounts, hit it) and keeps
     the set; where that does not fit either (only the set's own size causes it: about 100 inner mounts), it leaves the set
     out too, keeping the owner, mode and times. Each trim logs once while it lasts, and a change from the first to the second logs again (its own
     state in `ROOT_META_TROUBLE`; the fix wave's FW7, 2026-11-22). A record that cannot be written logs once per trouble,
     as today, and that vault is as on main.
   - **Carried** by the hand-over, which already copies the record onto the version before: after a cut batch the newest
     committed version's folder holds the set as of its own commit.
   - **Read** whenever the manifest has no inner_mounts key: `VaultManifest.inner_mounts` returns None for "never
     recorded" (not []), and its three readers (`do_backup()`, `compare_scanned_folders()`,
     `delta_generate_backup_entries()`) then take the set from the newest version's record, through one helper, and
     the manifest's key otherwise, as today. A rebuild committed by a comparison (`delta_generate_backup_entries()`)
     leaves the key absent, so an attempt that fails after it still reads the record.
2. **A link a cut left in staging is put back without the manifest.** Over a manifest that does not describe the
   previous version, `prepare_roll_forward()` gives each symlink in staging back to the previous version (staging keeps the
   links of the forward form to the tree's folder until the scan after its commit, `empty_staging(keep_for=)`), when its text has the forward form to the tree's own version folder at a rel it names
   (`forwards_to_version()`'s rule: as many `../` as the rel has parts, then the tree's folder name, then the rel), the
   previous version holds nothing at that rel, the rel's parent is a real folder of it, and the tree holds the entry.
   On a pool the links due are judged first and `guard.require()` runs before the first is written, as
   `put_back_forward_links()` does, and the put-back ends with `forget_pool_cache()`. With the manifest standing,
   `put_back_forward_links()` runs by the rows as today. Whichever of the two wrote a link, the vault's disks are flushed
   at once (`flush_or_fail()`): a link a power cut left without its text would read as present at the next scan, and the
   commit would remove the staged copy.
   - Why the text can be trusted here: the text names the tree's own folder, whose name (its number and the batch's
     timestamp) this batch made. A user's link recorded into staging is an entry of version n, made before that name
     existed; only a link crafted after the batch began, by someone who reads the vault's folder names, could carry it
     (the names-chains spec's crafted link), with a cut and a lost manifest after it, and it would make the version
     before show, at the rel its text names, the entry the tree holds there, which that version may never have held.
     Not an issue: no real-world failure.
3. **Pass 2 runs over a lost manifest off a pool.** Once item 2 has run, the previous version lists every entry the tree
   should keep off a pool, which is what pass 2 rests on (0.55.5's spec, section 1), so pass 2 runs whenever the vault is
   off a pool. On a pool over a lost manifest it stays off, as on main: a cut can leave a folder's record on one disk and
   not another, and with no rows the repair cannot tell a removed entry from a new one (the approved known limitation "A
   manifest lost in the same cut as a split on a pool"). `new_in_tree()` stays for that case.

**What is left: Q2.** On a vault on a mergerfs pool, over a lost manifest, case 2 stays as on main. No vault here is on
a pool.

**Why it is right.**
- Case 1: the version's own state is kept with the version, which a lost database cannot take with it; the database
  stays the first source, so nothing changes while it stands.
- Case 3: the staged link is the daemon's own and names its place; putting it back restores exactly what the version
  held before the cut.
- Case 2: pass 2 removes only names the previous version does not list, and after item 2 that version lists everything
  version n held, off a pool.

**Crash safety.** Item 1 writes the record on a version folder before the commit, as today; a cut before the commit
leaves it on an uncommitted tree (rolled forward, and written again). Item 2 writes links the next scan would write
again (it is idempotent: a link there is no longer due). Item 3's removals are pass 2's, whose crash table is 0.55.5's.

**Tests.**
1. tests/test_inner_mounts.py (VM, privileged): a job with an inner mount (tmpfs), a backup, the manifest removed, the
   mount unmounted, a start: the version keeps the mount's files, "Inner mounts not mounted" is logged, and once mounted
   again nothing is copied. Main commits the folder empty and copies it all back.
2. The same with the manifest's rebuild committed by a comparison and the attempt failing after it: the next attempt
   still pauses the mount. And with the record's write failing (a stand-in on `os.setxattr`): one error line for the
   trouble, the backup commits, as on main.
3. Case 3 (Docker, the exchange faked away so the writer takes two renames): a batch cut between `exchange_in()`'s two
   renames (the crash harness's kill point there), the manifest removed, a start: the previous version holds the folder's
   link again and every version reads right by the oracle. Main loses what the batch deleted under it (the entry: run
   on 0.55.4 and 0.55.5).
4. Case 2 (Docker): 0.55.5's run N4 over a lost manifest off a pool: a create of the cut batch whose middle the cut copy
   lost, its source mode 000 at the retry (uid 65534), the manifest removed: the newest version holds nothing there, with
   one UNREADABLE line. Main keeps the damaged copy.
5. Pins: on FakePool, case 2 over a lost manifest keeps the cut copy (pass 2 stays off); 0.55.5's run N5 test (a forward
   link left in staging over a lost manifest keeps the file) still passes; a user's link in staging whose text has the
   forward form to another version's folder is not put back.
6. The crash harness's kill-point runs, with a variant that removes the manifest before each restart, pass the version
   oracle and the row oracle.

**Cost.** None per commit: the record is read and compared already, and written when the set or the root's metadata
changes. At a scan over a lost manifest only: one listing of staging and a readlink per link in it.

**API.** A storage format gains a field: the root-meta record's "inner_mounts" (a lessons entry, section 23). The
manifest is unchanged.

## 7. Disks that change under a step

### 7.1 A disk taken out of a pool (D5)

**Today.** `pool_problem(path, since)` looks for a disk of the pool that is missing or was mounted again since the step
began, not for one the pool stopped listing. A disk taken out of the pool through mergerfs's control file
(`user.mergerfs.branches`) while a batch runs is not seen: the batch's flush syncs only the disks the pool lists by then
(`VaultUnit.holding()`), and the batch commits with no alert though what it wrote there is not synced. The same removal
while the start after a cut puts the cut batch's tree back is seen by no guard either, and the scan's removals can take
an entry that a version's forward link names. Reasoned from the code, not run (the entry).

**The change.** `pool_problem()` with `since` also names each disk of `since.ids` the pool no longer lists: "disk <disk>
left pool <pool> during this step". Every guard check (the batch's polls and `require()`, the scan's checks before each
act of its repair) asks it, so the batch fails before its commit (the guard's `require()` comes after the flush and before
the commit) and the scan stops with nothing removed, as for a disk that drops. The next attempt begins with the pool as
it is now. `VaultUnit` is unchanged.

**Tests.**
1. Docker, on `harness.FakePool`: the branch list read through a stand-in that drops a branch after the batch's copies:
   the attempt fails with the new text, nothing commits. Main commits.
2. The same during the start's put-back of a cut tree: the scan stops before its first removal. Main goes on.
3. **The test VM, a real mergerfs pool** (the entry's "check it by a run"): a branch removed through the control file
   during a batch's copies (a hook between the copies and the flush): the attempt fails, the branch is added back, the
   next attempt rolls forward, and every version reads right.

**Cost.** A set difference per guard check.

### 7.2 A restore's filesystem changing under it (D6)

**Today.** A restore onto a pool checks at each of its syncs for a disk that joined the pool or a filesystem mounted at
its folder's place on a disk (`sync_restore()`, `disks.devs`), not for the pool itself unmounted (a lazy unmount) or
another filesystem mounted over it; off a pool it checks nothing (`devs` is None). Later copies then land on a filesystem
none of its handles is on, its syncs do not cover them, and it can say it is done for files no sync of its own wrote out.

**The change.**
- `open_restore_disks()` keeps the `st_dev` of the restore's folder as the run opened it (`fstat(fd)`, the folder fd it
  is given), on a pool and off one.
- At each `sync_restore()`, before its syncs, `os.stat(folder).st_dev` must be that one: otherwise the restore fails for
  `rel`, "the filesystem holding <folder> changed while the restore ran (unmounted, or another mounted over it): what was
  restored since is not on the disk it began on", a failure of the same kind as a disk that joined (`rerun=False`, with
  that check's reason).
- On a pool, a disk the pool listed at the claim with the folder on it and no longer lists fails the restore the same
  way ("the disk <disk> left the pool while the restore ran"), as a copy may have landed there. This is beyond the entry
  (Calls to confirm): it is D5's rule, in the restore.

**Tests** (Docker, uid 65534, with FakePool where a pool is needed):
1. Off a pool: the folder's place swapped for a symlink to a folder on /dev/shm between two copies (a stand-in for a
   filesystem mounted over it, as 0.55.5's F2 tests did): the restore fails, naming the folder. Main says done.
2. On FakePool: the pool's mount point swapped the same way: the restore fails. Main says done.
3. On FakePool: a branch dropped from the list during the restore: it fails, naming the disk. Main says done.
4. **The test VM:** a real lazy unmount of a tmpfs target during a restore: the restore fails.
5. Pins: 0.55.5's joined-disk tests.

**Cost.** One stat per sync of a restore.

### 7.3 A batch whose monitored disk goes while it waits for its locks (D7)

**Today.** A batch compares the tree, then waits for the job's locks (`locks.take()` in `do_backup()`, behind a restore
that copies, say). It looks for an unmounted disk after its walk (`drop_unmounted_entries()`), before that wait, and not
again after it. When the monitored disk is unmounted during the wait, the batch commits a version without the copies of
the files that vanished with it: a changed file keeps its older copy in that version, a new file is missing from it, with
no alert (at most "Not tracking <path>: source no longer exists"), until a comparison with the disk back. A first
version already reads its mount table after the locks (0.55.5's R37).

**The change.** In `do_backup()` the locks are taken right after the no-differences path, before the estimate (today
they come after the estimate and the filesystem's limits). Once they are held, the batch looks again:
`drop_unmounted_entries(..., 'wait for the locks')`, which reads the table, fails the attempt when the monitored root
shows another filesystem (`check_monitored_mount()`: the monitored disk itself unmounted), and drops the entries under an
inner mount that went, pausing it. A batch this look empties releases the locks and takes the no-differences path (its
code moves into a local function both places call). Then the estimate, the limits and the prunes, as today, from the
entries that are left.

**Why it is right.** The estimate and the prunes are made from what the batch will copy after the wait, so no version is
pruned to make room for files that are gone; the monitored disk unmounted fails the attempt as it does during a walk, and
the next attempt waits for it ("monitored filesystem not ready").

**Tests.**
1. The test VM (privileged): a monitored path on a tmpfs, a restore of the job holding the locks (the restore lock taken
   by the test, as tests/test_restore_lock.py does), a batch that has compared and waits, the tmpfs unmounted, the lock
   released: the attempt fails, no version. Main commits a version without the file.
2. The same for an inner mount: the version keeps the mount's last copies, "Inner mounts unmounted during the wait for
   the locks" is logged, and the matched time is held. Main commits without them.
3. A batch whose every entry is under that inner mount: no version, the locks released.
4. Pin: a batch whose disks stay commits as today, with one mount table read more after the locks: it adds to the
   commit's own, which must come after the copies (the counter tests of tests/test_jobs.py, `..._three_times` and
   `..._four_times`, change to four and five).

**Cost.** One mount table read per batch that reaches the locks (about 0.44 ms of CPU, L4's measure). The locks are held
for the estimate too (an lstat per entry), a few ms more of a restore's wait.

### 7.4 An inner disk unmounted while a first version walks (D8)

**Today.** The first version's walk (`do_backup()`, the V0 branch) copies as it walks and makes no look after it: a disk
mounted inside the tree and unmounted while the walk ran leaves out the files the walk had not reached, with no line,
and the matched time claims the whole tree. Later versions lack them while the disk stays away (paused, as an inner mount
remembered at the commit), until a comparison with the disk back copies them.

**The change.** After V0's walk and copies, `drop_unmounted_entries()` with no entries (`{}`) and the walk named "first
version's walk": the mount gone during the walk is paused, its line says the walk left out what it had not reached under
it (the V0 wording, as no last copy is kept there), and the commit holds the matched time (`paused`) and remembers it.

**Tests.** The test VM: a V0 walk with an inner tmpfs unmounted midway (a hook in the walk at a folder under it): one
line, the matched time not recorded, the mount remembered and paused at the next batch, and once mounted again the next
comparison copies what was missing. Main logs nothing and records the matched time.

**Cost.** One mount table read per first version.

### 7.5 A disk mounted under a pool's disk at the monitored path's place (D10)

**Today.** On a mergerfs pool, a disk mounted under one of the pool's disks below the monitored path's place on it (a
pool at /srv/pool of disk1 at /mnt/disk1, the monitored path /srv/pool/data, fstab mounting a disk at
/mnt/disk1/data/sub, which the pool shows at /srv/pool/data/sub) is not an inner mount of the monitored path:
`inner_mount_points()` looks for mount points under the monitored path in the mount table, where this one is under the
pool's disk. While it is not mounted, the pool shows the bare folder it covers, a full comparison takes its files as
deleted (routine lines only), and once it is mounted again they are copied again whole. Unmounted while a walk passes,
the folders after it read as gone, with INFO lines, and the matched time moves past them. No live job has such a disk
(checked 2026-11-13).

**The change.** When the monitored path is on a pool, its inner mount points also include each mount point under a disk
of the pool at or below the path's place on it, as the path it shows through the pool (/srv/pool/data/sub for
/mnt/disk1/data/sub). The pool's disks are the batch guard's (`PoolGuard.state_of(monitor_path).ids`, read when the
batch began), and the watcher's own read when the table changes; no extra read per batch. From there it is an inner
mount like any: remembered at the commit, paused when it is not mounted and its folder through the pool is empty, its
rows kept and the matched time held, and the watcher asks for a comparison of it when it is mounted again. Its
fingerprint for the watcher's remount check is the disk's own mount (at its place under the pool's disk), not the pool's.

**Why it is right.** The rule is the one for a disk inside the tree, with the place the mount table shows it at mapped
to the place the pool shows it at; what reads it afterwards is unchanged.

**Tests.**
1. Docker, on FakePool with a fake mount table naming a mount under a branch at the path's place: `inner_mount_rels()`
   names it; a full comparison with it unmounted and its folder empty keeps its rows. Main deletes them.
2. **The test VM, a real mergerfs pool** with a tmpfs mounted under one branch at the monitored path's place: a backup,
   the tmpfs unmounted, a full comparison: the version keeps its files, "Inner mounts not mounted" is logged; mounted
   again: nothing copied. Main takes them as deleted and copies them back.
3. Pin: off a pool, inner mounts as today.

**Cost.** On a pool only: a scan of the mount table against each disk's place, per call (the table is in memory).

## 8. fstab: one read per look, and a read error is a problem (D9, D11)

**Today.**
- D9: `fstab_mount_points()` returns [] for any OSError. A read error other than its absence (a failing root
  filesystem, in practice) is taken as fstab naming no mount point, with no line: a path under an unmounted fstab mount
  point counts as there, so a start makes the Vault Path and the job's own folder on the bare mount point and, with an
  N/A or auto Vault File System Signature, backs up there.
- D11: on a pool, each check of the pool reads /etc/fstab again (`pool_state()`'s rule for a disk fstab names under a
  pool's disk), and `vault_disk_problem()` reads it once more for its own rule: a one-file batch with its tree on a pool
  reads it 9 times (about 1.9 ms a batch on the mount table and fstab reads, where about 1.4 ms was within reach).

**The change.**
- `fstab_mount_points()` raises the OSError of a read that failed other than with ENOENT (no fstab is an answer: none
  named). Each caller that reads it turns that into a problem, "/etc/fstab cannot be read: <error>":
  `vault_disk_problem()` returns it as its reason, so the wait names it, waits, and alerts after its grace as for any
  disk not there (FAILED: waiting); `pool_state()`, read with no points given (the writer's pool checks, the hand-over,
  a step's later checks), returns it as its PoolState's problem, as its mount-table branch does. Every
  `wait_for_path()` asks `vault_disk_problem()`, so the monitored path's waits wait too, as for a disk not there.
- **One read per look.** The one-item list a batch's waits share (`wait_for_path(table=)`) holds the look: the mount
  table and the fstab points read with it. `vault_disk_problem()` and `pool_state()` take the points as they take the
  table (`fstab=`), and read fstab only when given none. `PoolGuard(mount_table=, fstab=)` keeps, from the look its batch
  began with, the points under its pools' disks, and its checks (polls, `require()`) use those: a change to /etc/fstab
  during a batch reaches the next batch's look.
- A wait that polls again reads the table and fstab again, as L4's waits read the table live.
- Worth its parts, though no vault here is on a pool: a guard's once-a-second polls during a long copy each read fstab
  today, and the points ride L4's parameters for the table.

**Why it is right.** An absence counts as evidence only when the source was asked and answered (RULES.md, APIs). fstab
is read by the look that decides, once, and what a guard compares against later is the state its step began from, as
it already does for the mount table.

**Tests.**
1. Docker: FSTAB_PATH pointed at a file whose read fails with EIO (a stand-in on `open` for that path): the job waits,
   its status names the problem, nothing is made under the Vault Path. Main makes the job's folder and backs up.
2. FSTAB_PATH missing: as today (no wait).
3. A one-file batch with its monitored tree and vault on FakePool: fstab is read once per look (a counter); the counts
   written in the handback, main's first.
4. Pins: 0.55.5's R40 tests (a disk fstab names under a pool's disk at the path's place makes the job wait), and
   tests/test_vault_disk.py's fstab tests.

**Cost.** On a pool, about seven fstab reads a batch fewer (about 0.5 ms); off a pool, one read per look as today.

## 9. An xattr change made while down, in a folder renamed during the start's walk (D12, Q4)

**What the operator sees.** An extended-attribute-only change made while the daemon is down, to an entry in a folder
renamed while the start's full comparison walks past it (between its parent's listing and its own), is never compared:
the walk finds the folder gone (FolderGone, INFO), and the rename's batch compares extended attributes only of entries
whose ctime is after its own start, then records its matched time past the change. Run on 0.55.5's code (the entry).

**Ladder.** An issue (an attribute lost from the versions), needing three things to meet: an xattr-only change made
while nothing watched, a rename of its folder, and that rename in the moment the walk passes it. The fixes:
- hold the matched time at a full comparison that met a folder gone mid-walk and run a second one right after, with the
  same old bound: one more whole-tree walk whenever a folder vanishes during a full comparison (0.55.5's L10 counted
  three such lines in a week of the live journal, from all walks);
- or carry the gone folders, with the comparison's bound, to the batch that brings their renames: a new part and its
  state, for this one order.
Proposed: a known limitation (Q4).

## 10. A name its parent lists and the kernel cannot look up, in a batch's scopes (D13's other half, Q5)

**What is left after section 2.** A batch's comparison takes a scope (an event's path) whose lstat answers ENOENT as gone
(`iter_scope_entries()`, `scope_path_entry()`): its rows are deleted. On a filesystem that lists a name it cannot look
up (CIFS or sshfs name trouble), a batch whose events name such a path removes it from the new version, with no line.

**Ladder.** An event's path is a name a local program used, and on such mounts the name the kernel cannot look up is the
one the server lists, which differs from the local one (a charset the server maps, a name it mangles); within a scope's
subtree the walk already tells a listed name from a gone one. So the failure needs an event naming the very name the
server lists and refuses: not seen, reasoned rare. The planned fix (one listing per parent of a gone scope) runs on the
path every delete takes, as each deleted file is compared as a path and as a subtree. Proposed: a known limitation
(Q5), the watcher's half built (section 2, item 7).

## 11. The footprint gate after a burst (D15)

**Today.** tests/test_footprint.py measures the daemon (a child process, Docker, uid 65534, 3,000 folders and 20,000
files) after a restart and one backup. The trim after each commit (`release_idle_memory()`) could go without a test
failing: the trim after the start covers that measurement. 0.55.5's footprint report measured, under churn, 57 to 75 MB
with the trims against 125 to 134 MB without.

**The change.** A second gate in the same file, in two steps:

## 16. The folder-metadata healing check (P16)

**The user's ask** (2026-11-03, "Not an issue, check healing (Recommended)"): a folder that keeps the setgid bit or the
default ACL it inherited from its parent in the vault when its own metadata copy fails (an ERROR line, the folder listed
as unsynced) is Not an issue; check whether later versions heal it.

**Today, from the code.** A folder made in a version inherits from its parent there what the kernel gives a new folder
(setgid, a default ACL). Its metadata copy (`copy_new_folder_meta()`, then `copy_file_meta()`) runs: the owner (a
failure is logged and the rest goes on); the extended attributes the source lacks removed (`drop_xattrs_missing_from()`,
which removes an inherited default ACL); then `shutil.copystat()`: times, the source's extended attributes, the mode
(Python 3.13). An exception stops the steps after it. It can fail at the first version's walk, at
`WrittenFolders.settle()`, or at the replay's attrib or move. The batch then holds the matched time (`unsynced`), and the
row records what the version holds (`settle()` marks it dirty; the first version records every row from the version; the
replay's case depends on the path, which step 1 reads). The next comparison that meets the folder compares its mode,
owner and group with that record, a full comparison its mtime too; extended attributes only for an entry whose ctime is
not before the bound (`compare_entry(xattrs_since=)`), which the next batch committing with nothing unsynced moves past
the folder's ctime. So, reasoned, not run:
- **setgid inherited** (stopped before the chmod): the record's mode differs from the monitored folder's, so the next
  comparison that walks it copies its metadata again: it heals then.
- **a default ACL inherited:** it stays only when the removal step fails, which also stops the times: the next full
  comparison sees the mtime differ and copies again. It heals there; until then each version holds the ACL.
- **the source's own extended attributes missing**, when `copystat()` fails once at them, after the times, on a folder
  made with the monitored folder's mode: the record matches, and once the matched time moves on nothing compares the
  attributes, so it does not heal until the metadata is copied again for another reason. The approved "A folder whose
  extended attributes alone fail to copy keeps the wrong ones" covers a failure that hits every time; this one would
  work if tried.

**The change, in two steps.**
1. **The check, as the user asked** (tests/test_io_errors.py, Docker, uid 65534; the vault on a filesystem with POSIX
   ACLs, the basetemp, skipped with its reason where none):
   - setgid: a monitored folder P with setgid and a folder C in it without (uid 65534 can set both on its own folders);
     C's metadata copy failing once before its chmod; then a batch that does not touch C, then a batch that touches it,
     then a full comparison. Read: C's mode in each version.
   - an inherited default ACL: P with a default ACL (`system.posix_acl_default`, written by `os.setxattr`), C without
     one; C's removal step failing once; then the same three. Read: C's ACL in each version.
   - the source's own attribute: C with a user attribute, `copystat()`'s attribute step failing once for C; then the same
     three. Read: C's attributes in each version.
   - each at the three places a folder's copy can fail: the first version, `settle()`, a batch's attrib. The stand-ins
     fail one step of the copy for C's vault path, once.
   The results, by case and place, go in the handback, run on main: which version heals, if any.
2. **Then a question (Q7), asked with step 1's results.** The user's 2026-11-03 answer was "Not an issue", and asked
   only for the check: a fix, or a widening of the approved entry "A folder whose extended attributes alone fail to copy
   keeps the wrong ones" to a failure that would work if tried, is the user's to pick. Nothing of step 2 is built
   before that answer. The design it would be, for the cases that did not heal:
   - a folder whose metadata copy failed gets, in the commit, a row whose record holds a mode no entry has (-1; the row's
     mode is read by `compare_monitor_entry()` and by the replay's attrib branch, which takes a folder whose row holds it as
     one the commit marks no more, and kept by `read_rows_from_tree()` where a cut batch's tree still holds
     the folder), wherever the copy failed; the next comparison that meets it (a full
     comparison, or a batch that compares the folder) finds an attrib, and the replay copies all of its metadata again,
     extended attributes included, then records it as usual;
   - a failure of a folder whose row already holds that mark records it from the version, as today, so a failure that
     hits every time is tried once more (one version that changes nothing) and then is the approved entry's ("logged with
     a traceback each time"), where the record then matches the monitored folder's mode, owner and mtime; a failed copy
     that leaves one of those different is found again at every comparison that compares it, as on 0.55.5;
   - no extended attributes are compared, so a row with no record (every row of a rebuilt manifest) costs nothing more.

**Tests** (for step 2, if taken): step 1's case that did not heal heals at the next full comparison and at the next
batch comparing C; a failure every time is tried once more (one version that changes nothing) and then left; pins: the setgid case
still heals; a folder whose copy works keeps its record.

**Cost.** None on a folder whose copy works; a failed one costs one attrib of that folder at the next comparison that

## 2026-11-14 reverberator 0.55.6: a comparison reopens a leased file blocking, through a handle that cannot block
- Changed: a comparison's tail read that its non-blocking open refuses with EWOULDBLOCK opens the file again through an O_PATH handle, and, once that handle says it is a regular file, reads it through a blocking open of that handle, which waits for the lease to break as cp does.
- Why we had to change: a file under another process's write lease (an NFS write delegation, Samba's oplocks) failed the comparison with an error line and was copied again, committing a version that changed nothing.
- Original design was wrong because: the non-blocking open was there for a FIFO put at a file's place, and it refuses a leased regular file the same way: one flag answered two questions.
- Lesson: when a flag guards against one hazard, check what else it refuses; tell the cases apart by a handle that cannot block before taking the one that can.

## 2026-11-14 reverberator 0.55.6: a version's root-meta record carries its inner mounts
- Changed: the commit writes the inner mounts it remembers into the version folder's root-meta record as well as into the manifest, and a manifest with no such key reads them from the newest version's record.
- Why we had to change: a lost or damaged manifest forgot which inner disks the job had seen, so one unmounted at that moment read as an empty folder, its files left the new version, and pruning could take the versions that held them.
- Original design was wrong because: state needed to read the tree right was kept only in a database that is rebuilt from the tree, and the tree cannot say it.
- Lesson: state a rebuild cannot recover from the data lives with the data, not only in the index rebuilt from it.

## 2026-11-14 reverberator 0.55.6: an entry whose path the vault refuses is left out, not a failed job
- Changed: an entry whose path in the vault, or its copy's temporary path, would pass Linux's 4,095 bytes is left out of the version before anything is written, with its NOT BACKED UP line; before, it failed every attempt of its job.
- Why we had to change: one deep entry stopped every backup of the job, a first version included, for as long as it stayed in the monitored tree.
- Original design was wrong because: a limit no retry can lift was handled as a failure a retry might fix.
- Lesson: a limit of the target that no retry lifts is met per entry, by a rule that decides before writing; the entry is reported, and the rest goes on.

## 2026-11-14 reverberator 0.55.6: an /etc/fstab that cannot be read is a problem, not an empty one
- Changed: a read of /etc/fstab that fails other than with ENOENT is a problem the job's wait names and waits on; before, it read as fstab naming no mount point.
- Why we had to change: with fstab unreadable, a path under an unmounted fstab mount point counted as there, and a start could make the vault on the bare mount point.
- Original design was wrong because: the rule took a failed read for an answer.
- Lesson: a source a safety rule reads either answers or is a problem; only its own "none" (no such file) is an empty answer.

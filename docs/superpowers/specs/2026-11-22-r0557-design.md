# Round 0.55.7: the fourteen entries 0.55.6 deferred

For the release after 0.55.6. Built later on a branch of its own from the merged 0.55.6 (branch `r0556`, version commit
e166baa; no build before the user's answer to Q19). "Fails on 0.55.6" below means on that code. Functions are named; line
numbers are of reverberator.py at 1eb4333 (18,251 lines) and only a guide.

The round takes every entry of docs/limitations.md whose "Revisit when" names the round after 0.55.6, fourteen of them.
Each was checked against the code first (the ladder's step 1): all fourteen are real as written; one was run (section 1),
the rest are read from the code. Where a fix that removes a part or a state works, it is taken over the one the entry
names, and the section says why. Revised four times after its checks. Sections 2 and 3.1 drew findings in every round, so
the third revision took the routes of the third check's step back, each with less state: section 2 looks at the folder on
each disk of the pool instead of storing where an inner disk sits, and section 3.1 remembers each pool mount's disks where
the pool's list is read instead of parsing fstab. The fourth took the final check's last fixes: section 2 keeps 0.55.6's
look beside the look at each disk, section 3.1's record is the daemon's alone, and section 3.2's flush raises the pool's own
problem.

## 1. An entry past the path limit inside a version

**Real, run.** A probe in the test container (the suite's own `held_at_4096_in_v10()`: a file at 4,095 bytes in V9, 4,096 in
V10) on 0.55.6's code: a file created beside it fails every attempt with `JobFailure: recording ... failed`
(`TreeWriter.record()` → `ensure_real()` → `unfold()` → `keep_entry()`'s lstat, ENAMETOOLONG); its top folder renamed to a
name of the same length fails the same way through `hard_link_tree()`; a full comparison with nothing changed commits.

Why: the length rule (`vault_path_too_long()`, `length_rule_bytes()`) measures an entry when it is written. The hand-over
moves the tree to the next version's folder each batch (`hand_over()`: exchange, or two renames), so at V9 to V10 every path
in the tree gains a byte; a folder renamed longer (`renamed_in_place()` measures the folder's own two paths only) lengthens
every path below it. The entry then sits in the tree past the limit, and everything that reaches it by path fails: the
writer's records, but also the roll-forward's `measure_previous()`/`measure_version()`, the start's repair walks,
`tree_totals()`, the restore and history. (`BatchSizes.result()` reads the previous version, a byte shorter there.)

**Fix: a version never holds an entry past the limit (Q22, option (a)).** Principle 2: remove the state the failure needs,
rather than reach it through handles at every site that reads a version (the check found eight such sites, and on a pool a
handle does not help at all: mergerfs makes each call with the whole path on its disk, reasoned, not run). The rule already
leaves out an entry whose path the vault cannot hold, with its NOT BACKED UP line; this extends it to an entry whose path
would grow past the limit, before it grows, while every path still fits:

- **The rule counts the version after the one written.** `length_rule_bytes()` takes how many numbers past the folder it
  is given it counts (its `after` becomes that count, and `next_version_bytes()` counts that many numbers on), so every
  write measures the length the entry will have at the next hand-over. Only at the version before a digit (V9, V99, ...)
  does this differ from today: by one byte. The sites:

  | Site | Folder given | Numbers on |
  |---|---|---|
  | the first version's walk (`do_backup()`) | the version written (V0) | 1 |
  | the estimate (`do_backup()`) | a roll-forward's tree; else the newest committed version | 1; else 2 |
  | `entries_all_drop_out()` | the newest committed version | 2 |
  | the replay (`do_reverb_backup()`; its `version_bytes` to `replay_ops()`, `settle_ops()`) | the version written | 1 |
  | a delete's kept test (`left_out(kept=True)`, the line ending `this version keeps it`: can it be reached now) | the version written | 0 |
  | the growth scan and a move's bound (below) | the version written | 1, and 0 to tell an entry already past |

- **When the version's path grows, what that puts past the limit leaves the version written.** The manifest keeps a meta
  key, `rule_bytes`, written in each version commit's transaction (`do_backup()`'s, a first version's and a roll-forward's;
  `no_differences()` writes nothing): the number of the version committed, and the length in bytes of the path of the
  version after it as spelled (`next_version_bytes()`, without the pool's surplus). At the start of `do_reverb_backup()`,
  inside its transaction, the scan runs when that length, taken for the version after the one written, is above the
  recorded one (the next version gains a digit, or the vault was moved or spelled longer), when none is recorded (a vault an
  older release wrote), or when the recorded number is not the version before the one written (an older release committed
  since). It selects the
  rows whose own path passes the limit at the rule's count (one number on, the pool's surplus included): one SQL scan with
  the stored path's byte length as a prefilter (`length(CAST(path AS BLOB)) > PATH_LIMIT - 1 - count`: a stored path is
  never shorter than its name's bytes, as `storable_name()` only lengthens), then `vault_path_too_long(count, rel, False)`.
  - A row past the limit at the version written itself (0 numbers on) can be neither recorded nor removed by path: it
    stays, with one NOT BACKED UP line per topmost such row (a folder's covering all below it), ending `this version keeps
    it, past the limit (left by an older release, or by a vault moved to a longer path): a change in its folder fails the
    job's backups until it is removed from the vault by hand`. A selected subtree holding one stays whole (its record would
    walk it: `hard_link_tree()` on two renames).
  - Each other topmost selected row is left out as the replay removes a delete: its parent marked written
    (`written.wrote_in()`, as `delete_path()` marks it), its record joining the replay's own `pre_record()` ops (one flush
    on two renames for both), then `TreeWriter.remove_queued()` and its rows dropped, each with `report_path_too_long(...,
    kept=False)` (`left out of this version`), waited for before the replay goes on.

  The pool's surplus is out of the trigger: a disk with a longer path joining the pool puts no entry already there out of
  reach, as mergerfs looks an entry up disk by disk and an error on the longer disk reads as absent there, and every write
  already counts the longest disk (`pool_surplus()`). Reasoned, not run: the VM run below settles it.
- **A folder moved to a longer place has its rows measured first.** In the replay's move branch, for a folder whose target
  is longer in bytes than its source, one range query, the longest stored path under the source
  (`max(length(CAST(path AS BLOB)))` over its key range), bounds its rows at the target: count + 1 + bytes(stored target) +
  (that longest - bytes(stored source)). Only when the bound passes the limit are the rows listed; each topmost row whose
  path at the target passes is left out the same way at its source place (its line names the monitored path at the
  target), waited for before `TreeWriter.rename()`. Its record costs no flush, as `replay_ops()` recorded the move's source
  whole. The rename and `move_tree()` then move the rest; the query reads the rows `move_tree()` rewrites right after.
- **History.** Each entry left out by the scan or a bound joins the batch's applied list as a 'delete' of its monitored
  path at its old place, as section 9 writes what the version applied; until section 9 is built, it has no row.

The previous version's folder is never longer than the tree's (a number has as many digits or fewer), and the writer's
staging names are shorter (`TreeWriter.staged()`'s 6 hex characters), so every record, and every older version, fits once
the tree does. A pruned version is renamed into staging under its own name (`prune_version()`), 22 bytes longer than its
folder: off a pool `rm -rf` removes it at any depth, through folder handles, but on a pool mergerfs makes each call with the
whole path on its disk, so an entry within 22 bytes of the limit stays there, its space never freed, with an error line at
each try (reasoned, not run). Deferred to the next round: a prune's staged name no longer than a version folder's (a new
docs/limitations.md entry).

What stays outside (Q22, each as on 0.55.6 and each needing a removal by hand):
- An entry a version already holds past the limit: left by an older release that crossed a digit with it, or by a vault
  moved or spelled longer (each lengthens every version at once, between runs; so does a longer link into a pool vault).
  The scan names it and leaves it (above); its delete keeps it, and a change in its folder fails every backup of the job.
  None of the live vaults holds one (the main session's check).
- An entry no row tracks that a longer rename or a digit puts past the limit: the rows do not show it. A move's copy
  fallback leaves such entries, but the move's own batch sweeps them (`touched_scopes()` makes both ends of a move subtrees
  of its verification), so one stays only where that sweep could not list its folder (its error line); the sweep that next
  meets it fails every attempt (`removing <path> from the version failed: File name too long`).

**Reaches:** `length_rule_bytes()`/`next_version_bytes()` and the sites above, `do_reverb_backup()` (the scan, the move
branch's bound, `left_out()` with two counts, the leave-outs' ops in its first `pre_record()`), `VaultManifest` (the
`rule_bytes` key; the two queries), `do_backup()`'s commits. `settle_ops()`'s docstring loses its digit-growth sentence.

**Behaviour:** a NOT BACKED UP line `left out of this version` for each entry left out at a growth or a longer rename, then
at every backup that meets it, as for any entry the rule leaves out; the versions before keep it until the prune takes
them. An entry already past: its own ending (above), at each scan that meets it.

**Docs:** docs/limitations.md drops the deferred entry and gains the staged-name one; "A symlink or a path the vault can't
hold is left out" replaces its sentence "An entry a version already holds past the limit ... (deferred: ...)" with two: an
entry whose path would grow past the limit is left out from that growth on, with its line, the versions before keeping it
(from the version before the one that gains a digit, from a folder's rename to a longer name, from the first backup after
the vault is moved or spelled longer); an entry a version already holds past the limit (Q22's two cases) stays, named by
the scan, and fails every backup of the job once a change reaches its folder, until it is removed from the vault by hand;
and it gains Q22's answer in its approved field. README: line 62 keeps the second sentence, without "(to be fixed in the
next round)"; line 23's "a delete of an entry already past the limit leaves it in the newest version" becomes the growth
sentence; line 92 gains the scan's ending.

**Tests (container, uid 65534; tests/test_long_paths.py):** a file at 4,095 bytes in V0 to V8: V9's batch (a change
elsewhere) leaves it out with its line, V8 reads it, V9 and V10 do not, a sibling created, changed and removed in its folder in
V10 and V11 commits, a full comparison logs its line and makes no version, and history says deleted at V9; a file created at
4,095 bytes in V9's batch is left out; a folder renamed to a longer name so one file below it passes: the rename is made, the
file left out (the version before holds it at the old place), the next batch in that folder commits; a vault with no
recorded count, and one whose `rule_bytes` names a version older than the newest (a downgrade), run the scan once;
`held_at_4096_in_v10()` builds its state with the rule counting the version written, as 0.55.6 did (a monkeypatched

**Cost:** nothing per batch but comparing two numbers. The scan runs at V9, V99, V999, after a vault is moved or spelled

## 2. An inner disk under one disk of a pool

**Real (read).** `paused_inner_mounts()` pauses a remembered, unmounted inner mount only while its folder reads empty or
cannot be looked at (an OSError of its lstat or listing other than ENOENT or ENOTDIR); on a pool it reads the folder
through the pool, the union of every disk's folder of that name, so another disk's entry there makes it non-empty: the mount
is not paused, its files leave each new version, and `inner_mounts_to_remember()` forgets it.

**Fix: keep that look; where it finds entries on a pool, look at the folder on each disk too. Nothing stored.** The three
callers of `paused_inner_mounts()` pass the batch's state of the monitored path's pool (`pool_guard.state_of(monitor_path)`).
For a remembered mount that is not mounted:
- the look through the monitored path, kept whole: an empty folder or one that cannot be looked at pauses it, one gone or no
  folder does not. It alone covers an inner disk mounted inside a filesystem that is mounted over the pool's own path,
  whose folder has no place on any disk (the disks alone would let its files leave the version with no line);
- when it finds entries and the pool's branches are known (`pool.ids`), the folder's place on every branch (mapped as
  `pool_inner_mounts()` maps one; a helper both share) is looked at: paused when one is an empty folder or cannot be looked
  at (the same errors); a place gone or no folder says nothing. Only then: a folder that reads empty or unlistable through
  the pool is paused already, and one gone through it has no place that is a folder, but for a copy hidden under a mount
  over the pool's path, which would pause a folder retired by removal. A stored place, the entry's named fix, goes stale
  when a disk is replaced or renamed (the third check's F1).

The helper gets the monitored path resolved (`os.path.realpath()`, once per call in `paused_inner_mounts()` as
`inner_mount_rels()` does; `pool_inner_mounts()` takes its root resolved): the callers pass it as the rule spells it, and one
given through a link would map to the wrong place against `pool.pool`.

**The alert.** A folder paused by its places has entries the pause hides: they landed on another disk through the pool.
`paused_inner_mounts()` fills an optional dict (rel: its pausing places, with the error of one that could not be looked at)
for those folders, from the answers it has (the through look is the emptiness check, one entry: no listing); its set stays
as its callers take it. At the batch's start (`do_backup()`, beside its `Inner mounts not mounted` line; the only caller
that passes the dict) each logs through `job_log()` (error level; NOT BACKED UP alerts): `NOT BACKED UP: <folder>: an inner
disk's folder, paused while <place> is empty, shows entries through the pool that are not backed up while it stays paused:
mount its disk again` (a place that cannot be looked at: `<place> cannot be looked at (<error>)`), and, for an empty place,
` (to retire the inner disk instead, whose files then leave the new versions, give <place> files of its own or remove it)`.
A folder a walk's look pauses (`drop_unmounted_entries()`) passes no dict and alerts at the next batch's start. A disk
retired by files of its own while another disk keeps an empty copy of its folder (mergerfs clones a folder's path onto the
disk a create lands on) stays paused with that line until the copy is removed, where 0.55.6 backed it up (the main session's
call), and the matched time is held meanwhile: the approved "A paused inner mount or an unwatched folder holds the matched
time" entry's revisit case, reached for as long as the copy stays. Nothing is lost. A disk out of the pool's list is section
3.1's wait.

**Reaches:** `paused_inner_mounts()` (the look at the disks, the dict, the resolved root), `pool_inner_mounts()` (the shared
place helper), `do_backup()` (the line). No stored data.

**Docs:** the deferred entry and its README line (63) go. README line 104's retire sentence adds, for a pool: remove the
folder through the pool (mergerfs's default rmdir policy removes it from every disk), or give the mount point folder on the
inner disk's own disk files of its own and remove any empty copy the NOT BACKED UP line names. The new ending joins README's
marker list (line 92's block); a lessons entry (section 11).

**Tests (VM, as root, real mergerfs; tests/test_pool_pause.py):** a pool of two loop disks, an inner loop disk mounted under
disk 1 at the monitored path's place, a file written straight onto disk 2 in a folder of that name. Unmount the inner disk:
paused, its files still in the versions after Keep N Versions more batches, the line naming disk 1's place. A file written
into disk 1's place: not paused, both files backed up. Disk 2's file removed, its folder left empty, disk 1's place holding
files: paused, the line naming disk 2's place; that folder removed: not paused. The folder removed through the pool:
forgotten. Disk 1 taken out of the pool's list: the job waits (section 3.1). A filesystem mounted over the pool's path with
a second one inside it, the second unmounted: paused, no line. **Container, uid 65534:** the same cases with a made-up
`PoolState` over plain folders (the mount-over case with a made-up mount table); a place that cannot be looked at (an
`os.scandir()` stand-in raising EIO): paused; the through look failing: paused, no line; no branches known: the through look
only; a monitored path given through a link: the right places.

**Cost:** none without a remembered unmounted inner mount. For each, at each of the batch's looks (its start, after each
walk, after the lock wait): 0.55.6's lstat and listing through the pool, and, when that shows entries on a pool, an lstat
and a listing per disk.

## 3. Disks out of a pool's list

### 3.1 The disks each pool mount has listed (the restart and idle entries)

**Real (read).** `JobControl.left` (filled by `PoolNotReady.left`, read by `JobControl.left_reason()` in `wait_for_path()`)
lives in memory and holds only disks a failed step saw leave; `PoolGuard` keeps a step's lists for that step alone. So a
restart forgets, and a disk taken out between steps is never seen leaving.

**Fix: one record, where a pool's list is read, in the daemon (Q21, option (a)).** `pool_state()` reads a pool's branch list
at every look: each wait's poll, a guard's start and its checks (at most
once a second in a step), and the mount monitor's pass (at each mount change and at least every 60 s, for every job's
paths). A process-wide record, `POOL_BRANCHES` (a lock of its own), keeps for each pool mount point its mount id
(`pool_id`) and every branch, resolved, that this mount has listed. `run_daemon()` sets it, beside `StatusBoard`; in every
other process it is None and `pool_state()` neither feeds nor asks it: the history and restore commands reach `pool_state()`
(through `vault_pool_warning()`) and would write the daemon's file with their own, empty view. With a record, `pool_state()` hands it each list it reads; a branch the record holds for this mount that the
list lacks is a problem of the pool, `disk <branch> left pool <pool>: waiting for it to be listed again (mount the pool again
if it was taken out for good)`, decided at the source (principle 10), so every wait, guard check and monitor flag of every
job on that pool sees it, until the pool lists the branch again or is mounted again (another id, whose record starts from
its list; when the entry it replaces holds a branch the new list lacks, one INFO line says the pool was mounted again and
that reverberator no longer waits for that disk). A look with no `pool_id` (the statx of the pool failed, its list may still
be read) is neither fed nor asked and returns its list as now: the record keeps the branch, and the next look with an id
asks as usual. Nothing is parsed: disks added through mergerfs's control file and pools mounted outside fstab are covered,
and a folder made where a glob matches changes nothing. 0.55.6's in-process wait and the guard's comparison of the lists
fold into it (a guard's start feeds the record), so `left` goes from every place that carries it (Reaches); the guard keeps
its other comparisons with `since` (the pool, or a disk, mounted again).

- **Across a restart:** the record is kept in the state folder (`state_dir_path()`), `pool-disks.json`, one line of JSON,
  `{"v": 1, "boot_id": ..., "pools": {<pool mount point>: {"id": <mount id>, "disks": [...]}}}`, so a daemon restarted within
  one boot goes on waiting for a disk that is still out. The default state folder, /run/reverberator, is tmpfs: a reboot
  empties it, and the boot id matters only for a state folder set elsewhere, on a disk. `run_daemon()` reads the file once,
  beside `StatusBoard`, keeping this boot's pools (`/proc/sys/kernel/random/boot_id`); another boot's file or none gives an
  empty record, and one that cannot be read or decoded an empty record and one error line. So the first 0.55.7 start, and
  the first after a reboot, begin empty, as 0.55.6 does: a disk already out then is not waited for.
- **The write** is made by a daemon thread of its own, which the load starts and `pool_state()` wakes (an event) whenever an
  entry is new, replaced or gains a branch. It writes the newest record outside the record's lock through `StatusBoard`'s
  writer (temp file and rename, no fsync: what a power cut leaves is another boot's; it never raises and logs its first
  error once per run), so no look, the monitor's thread among them, waits for the state folder, and a failed or slow write
  holds no job; a stop within a moment of a new branch loses it (that restart forgets it, as 0.55.6 does).
- **A kernel without unique mount ids** (before 6.8; `statx_mount('/')` gives none, asked once at the start): mountinfo
  reuses a freed id, so a remounted pool can come back with its old one, and a remount would let nothing go. There the record
  stays in memory, its text ending `restart reverberator if it was taken out for good`, as on 0.55.6: the restart entry stays
  on such kernels, which widens the approved "Kernels before 6.8 and the pool check" (Q21).
- **To let a disk go for good:** mount the pool again, or reboot; or, with reverberator stopped, remove `pool-disks.json`
  (every pool's disks go). A restart no longer does. Until then every job on that pool waits (Q21 (a) states the cost).

**Behaviour:** a disk taken out of a pool's list, in a step or between steps, makes every job on that pool wait with that
text (the FAILED: waiting marker after the wait's 15 min grace, repeated hourly, its timing unchanged), where 0.55.6 made
only the job whose step saw it leave wait; a step that meets it fails with it. A wait reads the pool at each poll
(`POLL_WAIT_SECONDS`), so it sees a disk gone again or listed again at its next poll; it ends once its poll finds the disk
listed and the monitor's flag is set (the monitor's next pass: within about a minute). A job with no wait learns of a disk
taken out at the monitor's pass, within a minute.

**Reaches:** `POOL_BRANCHES` and `pool_state()` (feed and ask); `run_daemon()` (the load, the writer thread, `statx_mount('/')`
asked once; the one place that sets the record, so the commands never write the file); `JobControl` (`left`, `fail()`,
`left_reason()`), `wait_for_path()`, the backuper's hand-over of `PoolNotReady.left`, `pool_problem()` (`left` and the
`during this step` comparison of `since`'s list), `PoolGuard.problem()` and `require()`, `read_vault_whole()`,
`decrement_stepper()`'s `require_pools()`, tests/prune_oracle.py's copy of it; section 3.2's flush asks `pool_problem()`.

**Docs:** both deferred entries and their README lines (61, 64) go. README line 76 says: every job on a pool waits for a disk
the pool listed since it was mounted and lists no more, until it is listed again; to let one go for good, mount the pool
again (or reboot), or remove pool-disks.json from the state folder while reverberator is stopped; a restart does not (on a
kernel before 6.8 it does, as now), and the first start after the upgrade begins empty; its example texts take placeholder
disks (section 11).

**Tests (container, uid 65534, the stand-in pool; tests/test_pool_guards.py, tests/test_pool_pause.py):** tests/conftest.py's

### 3.2 The flush that lists the pool once

**Real (read).** `VaultUnit.holding()` reads the pool's branch list once and syncs the job vault's filesystem on each
branch listed then; a branch out of the list at that moment is skipped, and if it is back by `pool_guard.require()` at the
commit, the commit goes through with its copies there unsynced. The prune's flush is the same call.

**Fix: the flush asks the pool's own check.** On a pool, `holding()` first asks `pool_problem()` for the job vault (with the
state the guard held when the unit began, which `VaultUnit.__init__()` keeps, and the guard's fstab points) and raises
`PoolNotReady` with its text. That text includes section 3.1's, so a branch the pool listed since it was mounted that the
list lacks fails the step (`disk <branch> left pool <pool>: waiting for it to be listed again ...`), and the next wait waits
while it is out. The entry's own fix, `VaultUnit` keeping the branches it opened and comparing them with the resolved list (a
`user.mergerfs.srcmounts` entry can be spelled through a link or end with `/`), was weighed and left: a second branch set, a
second comparison and a text helper shared with the record, to answer again what the pool's check answers once, at the
source (principle 10). The check also names a disk not mounted at the flush, which `holding()` gave as an OSError about a
filesystem the step did not open. Its cost is a mount-table read and a statx per
branch at each flush on a pool vault, which the guard's check at the commit already makes (the build times it against a
flush's own `syncfs`). The exception is no OSError, so it goes through `flush_or_fail()` and `sync_vault_filesystems()` to
fail the step (a backup's commit, `TreeWriter.flush()`, a prune, a scan's repair), and the next attempt redoes the work (the
lesson of 2026-11-10). Not a sync of every disk the step began with: a removed disk that hangs would stall it with no
timeout, where today it fails at the check.

`decrement_stepper()`'s `flush_disks()` (the 0.54-layout prune on a pool) catches only OSError: it takes the `PoolNotReady`
too, keeps the oldest version with its reason (`keep_oldest()`) and raises it again, as `require_pools()` does. It runs on
two paths, and `keep_oldest()` says and keeps the same on both: an error line (`Aborting removal of <version> because
<text>`), the job's FAILED line (`cannot remove <version>, as <text>; it is kept, and the vault keeps growing`, once an hour
at most: `PRUNE_ABORTED`), the records written, and the version back at the front of `vault_info_dict`. Before the removal
(after the walk's links and the records, before the marker is cleared) its folder is whole and the marker still names it:
the next attempt waits, then prunes it again. In `remove_lists()`, after `folder_gone()`, only its change lists are left,
and the version is kept as a record: the next attempt waits, then finds the folder gone and removes what is left, as the
prune does for a folder that went before. The raise leaves the caller's own `keep_oldest()` (`what was left of it cannot be
removed`) unrun, so the line is said once. The 0.54 conversion's `flush_vault_disks()` call (`migrate_job_vault()`) lets it
through as the JobFailure its docstring names: that version is not marked converted, and the next attempt waits, then
resumes from it.

**Reaches:** `VaultUnit.__init__()` (keeps the state) and `holding()`; `decrement_stepper()`'s `flush_disks()`; the
docstrings of `holding()`, `sync_vault_filesystems()` and `flush_vault_disks()`, which name `PoolNotReady` beside OSError.

**Docs:** the deferred entry and its README line (60) go.

**Tests (container, stand-in pool; VM, real mergerfs):** a branch taken out of the list just before the commit's flush and
put back before the commit's check: the step fails naming it, nothing is committed, the next attempt commits once it is
listed; the same for a prune's flush, and for the 0.54-layout prune on each of its two paths (the oldest kept, its FAILED
line once, the attempt failed; with the folder gone, the next prune removes the lists); a branch listed through a link or
with a trailing `/`: no failure.

**Cost:** one mount-table read and a statx per branch at each flush on a pool vault; none off a pool.

## 4. The inner mount set

### 4.1 Where the set is kept (the record entry)

**Real (read).** `record_root_meta()` puts the set in the root-meta record (one attribute of the version's folder); on ext4
and f2fs every extended attribute of an inode shares one block of about 4 KiB (xattr(7)), so the set and the root's own
extended attributes trade room, and about 100 mount points do not fit even alone. A failed write keeps the version before's
record, whose set can be older.

**Fix: the set out of the record.** The manifest keeps the set as now (`inner_mounts`). A file of the job vault,
`.reverberator_inner_mounts`, holds it for a lost manifest: one line of JSON (`{"v": 1, "inner_mounts": [...]}`, each rel as
`storable_name()` writes it), written by temp file, fsync and rename before the version's record (`record_root_meta()`) and
the commit's flush. Each commit that records the set (a version commit, `no_differences()`) reads the file and writes it when
its content differs from what that commit records, or it is not there or cannot be read: so a vault's first commit after the
upgrade writes it, even empty, and a stale one (an attempt that failed after its rename, a commit by an older release, a cut
on a pool that kept the old one) is written again at the next commit. It holds the newest committed or attempted set: one
attempt ahead is harmless (an added mount pauses an empty folder at worst; a dropped one was dropped because its folder holds
entries), and in `no_differences()`, where no flush follows, a power cut can keep the old file, which matters only with the
manifest lost too. A write that fails fails the attempt (JobFailure naming the file and the error). A separate attribute was
the entry's plan; it shares the same block, so it buys no room.

The record keeps the root's owner, mode, times and extended attributes, and `"inner_mounts": []` only when the commit's
set is empty (`record_root_meta()`'s `inner_mounts` parameter becomes that marker, `[]` or None). It loses its second trim,
with its `'trimmed mounts'` state and line: a record with the marker and no attributes (about 160 bytes) fits wherever one
fits at all. Its one trim, a root whose extended attributes alone do not fit (about 2.9 KiB on an ext4 or f2fs vault),
stays: Q20. Every new record says which in a field added under `"v": 1`, `"xattrs_left_out": true` or `false` (a 0.55.6
reader ignores it), which section 8 reads.

`remembered_inner_mounts()` gives the manifest's set; with none, the file's; with none, the newest version's record's: a
0.55.6 record's `inner_mounts` field, as now; a 0.55.7 record's (it holds `xattrs_left_out`) `[]` as none, while one without
the field says the set lived in the file, so the file's absence stops the backup: FAILED, `<file> is not there and the vault
database lost the inner mount points it held: which inner disks are unmounted cannot be told; mount the job's inner disks,
then write {"v": 1, "inner_mounts": []} into it to go on` (an inner disk left unmounted would read as emptied). A file that
cannot be read or decoded stops it the same way, naming the file and the error. So most jobs, which have no inner mount, go
on with both lost.

**Reaches:** `record_root_meta()` (the marker; no second trim), `encode_root_meta()`/
`decode_root_meta()`, `remembered_inner_mounts()` (the file in its order), `do_backup()`'s commit and `no_differences()` (both
write the set and the file; the commit passes the marker), the job vault's scan (`read_job_vault()`/`get_vault_info()` know
the file and remove a temp a kill left, as they do `PRUNE_SALT_TEMP_INFIX`'s), the 0.54 conversion's listing of the job vault
if it reads names. Stored data: a new file; the record's `inner_mounts` only as the marker; old records still read; a
downgrade to 0.55.6 reads the manifest's `inner_mounts` as it always did.

**Docs:** the deferred entry goes, its README line (69) goes; README's record paragraph (line 82) drops the inner mount
points from the record and the second trim, and names the file. A lessons entry (section 11).

**Tests:** the file written and read back, a set of 500 mounts, a write that fails (a folder at the temp's place: the attempt
fails, the next commits), the file written at a vault's first commit with an empty set, a stale file (written by hand with
another set) written again at the next commit, the read order over a lost manifest, a 0.55.6 record with the set read; with
the manifest and the file lost, a 0.55.7 record with `[]`: the backup goes on; one without the field: FAILED, then the empty
set written by hand goes on (container, uid 65534, except what writes trusted.*). tests/test_inner_mounts.py:1146 reads the
set from the file, not the record; the second trim's tests (tests/test_restore_in_place.py, near lines 1545-1580) go. A root
with 2 KiB of extended attributes and 200 inner mount points keeps its attributes in the record (VM, as root: trusted.* needs
root).

**Cost:** per commit, one read of a small file; the key and the file are written only when they change (`_set_meta()`).

### 4.2 A disk mounted and unmounted within one backup

**Real (read).** `inner_mounts_to_remember()` takes the mounts of the batch's table and of the one read at the commit; a disk
mounted after the first and gone by the second is in neither, while the backup's walks or copies may have put its files in
the version. The next batch's comparison of that folder then finds it empty.

**Fix: every mount table the mount monitor reads feeds the set.** The mount monitor (`fs_signature_monitor`) reads the table
at every change of it (POLLPRI on mountinfo) and hands each to its subscribers first; the watcher's subscription
(`store_mount_table()`) keeps only the newest for the watcher's loop, which is why a busy watcher misses one. With a job, it
also adds the inner mounts of each table it is handed (`inner_mount_rels()`, the mounts under the pool's disks among them) to
a set on the job's `JobControl`, under its lock, by string work alone, as a subscriber must not block: from the watcher's
resolved root (`root_real`) and the pool's disks it read last (`pool_seen`), skip-filtered, so `inner_mount_points()` and
`inner_mount_rels()` can be given the root already resolved (a keyword; their other callers unchanged) instead of calling
`os.path.realpath()`.
- **Emptied** by `backuper()` right before a batch's waits, so every mount seen from the look whose table the batch takes
  counts, and none seen and gone before it (no walk of the batch met it); a first version, which reads the table again
  after its scan (`do_backup()`), empties it again just before that read. Emptied before the look rather than after it,
  no mount can come between the two.
- **Read**, under the lock, by every `drop_unmounted_entries()` (its seen mounts: the remembered ones, the batch table's and
  these, so a disk mounted during a comparison's walk and gone by the look after it has what the walk found under it
  dropped), and by both commits, which pass it to `inner_mounts_to_remember()` as a new parameter joining `kept` (also where
  no table could be read). A rel only the set holds (in neither of the commit's tables, not remembered) is passed only when
  the manifest, as the commit leaves it, holds rows under it (`VaultManifest.has_rows_under()`, new, a one-row range query
  like `has_unrecorded_under()`): a disk whose files a walk or copy put in the version has rows, the entry's case; one no
  walk met (a stick in and out during a long wait for a pool) has none, so it is not paused for good with the matched time
  held. The next batch then finds the folder of a disk that is gone empty and remembered: paused, with its line, its files
  kept.
- With no job (tests, outside the daemon), nothing is fed or read, as on 0.55.6.

The entry named the walks and copies: a comparison's lstat gives each folder's st_dev at no cost, but the replay's folder
copies and a first version's walk read none, a `cp` cannot tell, and on a pool an inner disk shown through the pool has the
pool's st_dev (FUSE gives every entry its own superblock's). The monitor's tables see every mount wherever a walk is.

Not an issue, each needing a disk mounted, met by a walk or copy and unmounted within one gap no table reaches the set in:
- a signature check (df, lsblk) the monitor runs after a mount change: a change during it is read right after it;
- a watcher starting again after an overflow: it subscribes before adding any watch (one table read); one whose root went
  away waits for the root, as the batches do;
- a mount table the monitor could not read (the kernel's own text, which fails only when it cannot allocate): the next
  pass comes at the next change or within 60 s;
- a disk that joined the pool since the watcher read `pool_seen`: its joining fails any step running then (the guard), so no
  version keeps what a walk met under it.

**Reaches:** the watcher's subscription, `JobControl` (the set; emptying and reading it), `backuper()` (the emptying before
the waits), `inner_mount_points()`/`inner_mount_rels()` (a resolved root), `drop_unmounted_entries()` and
`inner_mounts_to_remember()` (the new parameter, with a default), `do_backup()` (the rows check at both commits),
`VaultManifest.has_rows_under()`. `follow_inner_mounts()` is unchanged (tests/test_jobs.py:809 keeps its call). Tests that
run the watcher or the backuper with no job keep passing (tests/test_restore_lock.py:411, tests/test_r_scan.py:786,
tests/test_crash_safety.py:71 and 135). A mount kept so that never comes back stays remembered as any inner disk does,
until its folder is removed (README's retire sentence).

**Docs:** the deferred entry and its README line (67) go.

**Tests (VM, as root; tests/test_inner_mounts.py):** a loop disk mounted inside the tree after a batch's look and unmounted
before its commit, with the walk made to meet it (a hook after the walk) and the watcher held in a walk of its own: the next
batch keeps its files, with the `Inner mounts not mounted` line; one mounted during a comparison's walk (a hook in the walk)
and unmounted before the look after it: what the walk found under it dropped, and not remembered (no rows); one mounted and
unmounted during a batch's waits, no walk meeting it: not remembered; one mounted and unmounted between two batches, before
the next batch's waits: not remembered. Container: the set fed by a subscription call with a made-up table (a pool's disks
among it), emptied before the waits, a rel only the set holds kept with rows under it and not without, and a run with no
job.

**Cost:** one pass over each mount table per job, at each mount table change only; no syscall; at a commit, one query per
rel only the set holds (usually none).

## 5. A link given back after a cut, on f2fs

**Real (read).** `put_back_forward_links()` and `put_back_staged_links()` judge a link due when `kind_at()` finds nothing at
its place; a link a power cut left with no text (readlink answers ENOENT) is found, so it is never written again, and that
version keeps a broken link.

**Fix: the entry's own, with the put-back's own text.** At a place the put-back judges (a row, or a staged link's rel, under
real folders of the previous version, the tree holding the entry), an entry whose lstat says link and whose `readlink()`
answers ENOENT is due too: unlinked and written again with the text the put-back computes for that place. For a row of a
link (kind 'l'), that is the row's own text (the manifest's link column: version n's link, which a forward link to the
unchanged tree reads the same): a user's link that a record copied with `cp -af` on a vault that refuses hard links keeps
its text, never a forward text naming the tree's newer entry; a link row with no recorded text (a manifest listed again from
the tree) is left as now. For any other row, and for a staged rel, it is the forward text, as only a forward link stands at
such a place. Nothing else reads or rewrites a textless link.

**Reaches:** `put_back_forward_links()`, `put_back_staged_links()` (one helper they share). `prepare_roll_forward()`'s flush
after a link written already covers a rewrite.

**Docs:** the deferred entry and its README line (68) go.

**Tests:** container: a put-back place whose link reads ENOENT (`os.readlink` stood in for that path alone), for a file row
(rewritten with the forward text) and a link row (with the row's text): the roll-forward commits, the version reads right.
VM, as root: the power-loss sweep on an f2fs vault gains the kill point between the put-back's symlink and its flush
(tests/test_crash_power_loss.py).

**Cost:** a `readlink()` per link at a place the put-back judges, at a start after a cut only.

## 6. A restore's look, once per batch of copies

**Real (read).** `sync_restore()` reads the pool's list only at a sync: a disk that joined and left between the claim and the
last sync is seen by neither its join look nor its left look. It checks the folder's filesystem only at a sync too, so a
restore whose target moved (a lazy unmount, a mount over it) copies on until its walk ends; `accept_restore()`'s walk
likewise.

**Fix: the entries' own, one look.** In `restore_entry()`'s `finish_batch()`, once a batch's copies are in place (every
`RESTORE_COPY_BATCH`, 1,000):
- the folder's filesystem: `os.stat(folder).st_dev` against `disks.dev`, an OSError counting as moved (as `moved_now()`).
  Moved: the moved line (`say_moved()`, lifted out of `sync_restore()` so both say it once), then a stop raised from the
  look, as `check_stop()` raises KeyboardInterrupt: a new exception, caught around the walk, after which no copy starts,
  the sync runs as now through its handles, no marker is written by path (`report.moved`), and the run exits 1.
- on a pool, its branch list: one `getxattr` of the control file of the pool the claim found (its mount point kept in
  `RestoreDisks`, a new field its three constructors in `open_restore_disks()` fill). Each branch listed gets its place's
  nearest existing folder's st_dev at this look (None when it cannot be looked at), kept in a set of branches seen. A list
  that cannot be read (the pool unmounted, EIO, ENOTSUP) fails the restore, `report.fail(rel, 'the disks of pool <pool>
  could not be listed while the restore ran: <error>', rerun=True)` (a run again lists the pool at its own claim and goes
  on), and stops it the same way, except that `report.moved` stays unset: the folder is still on its filesystem, so the
  marker is written by path as after any failure, and the sync after the stop makes its own look at the pool, whose
  failures count as now.
At the sync, the left look covers every branch seen, not only the claim's: one the pool no longer lists fails the restore as
left the pool when the folder is on it now (stat finds it, or cannot tell), or when its place's nearest existing folder is
on another filesystem than the look found (unmounted or replaced since), as `replaced()` judges the claim's branches; else
it is passed over. `--accept` looks at the folder's filesystem once per that many folders, in its partial-file walk and its
hand-over (it copies nothing, so it reads no pool list), and stops the same way.

What is left: a disk that joins and leaves between two looks, within one batch of copies: Q23.

**Reaches:** `open_restore_disks()`, `RestoreDisks`, `restore_entry()` (`finish_batch()`, the catch around the walk),
`accept_restore()`, `sync_restore()` (`say_moved()`, the left look).

**Docs:** both deferred entries and their README lines (65, 66) go; Q23's answer may add one entry.

**Tests (VM, as root, real mergerfs; tests/test_restore_pool.py, tests/test_restore_sync.py, with a small batch):** a branch
added through the control file after the first batch and removed before the sync, a copy placed on it: FAILED, left the
pool; the same with that branch's disk unmounted before the sync: FAILED; the target's loop disk unmounted lazily after the
first batch: FAILED at the second batch, nothing more written on the filesystem under it, no marker there; the pool's
control file made unreadable at a look (a stand-in for that `getxattr`): FAILED with its line, no traceback, its marker
written, and a run again goes on; `--accept` with
the target moved: ends at its first look.

**Cost:** one stat per 1,000 copies; on a pool one `getxattr` and one stat per branch per 1,000 copies.

## 7. An error read as "not there" in the replay

**Real (read).** The steps that act on an answer "not there" use a look that answers "no" for any error: `real_folders_to()`
without `strict` and `os.path.lexists()`/`isdir()`/`islink()`.

**Fix: the entry's own, one rule.** A look at the version is `kind_at()` or `real_folders_to(strict=True)`. Its strict

the lstat finds a file; ENOENT keeps answering True with `missing_ok`), where today it raises NotADirectoryError (only
FileNotFoundError is caught before it), and raises any other error, which fails the attempt as a JobFailure naming the
path and the error (`cannot look at <path> in the version: <error>; the next attempt goes on with it`): the version cannot be trusted there, and the next
attempt redoes the batch. A look at the monitored tree goes through a new helper, `monitored_there(path)`: False only for
ENOENT or ENOTDIR, True for anything else, so the copy is tried and its own failure keeps the last backed-up copy with its
UNREADABLE line (`finish_copies()`, `copy_failure_side()`), as an unreadable file does now. The sites:
- version side: `do_reverb_backup()`'s `delete_path()` (its `real_folders_to()` and the kind of what is at the entry), its
  attrib and move branches (the kind at the target, `real_folders_to()` of both paths); `TreeWriter.remove_queued()`,
  `rename()`, `make_folders()`, `_folders_for_copy()`, `staged()` (a staging name taken: `kind_at()`); `finish_copies()`

  `_folders_for_copy()`'s source, `copy_failure_side()` (an error is 'source', not 'vanished');
- left as they are: `roll_forward_entries()`'s `real_folders_to(monitor_path, ...)` (monitored side: an error there leaves
  the file out of the trusted list, so the comparison reads it, which is no drop); `file_in_place_of_folder()` (it runs only

## 8. The monitored folder's own metadata

**Real (read).** The watcher drops every nameless event (`Event name not found`, DEBUG); for a watched folder its parent's
watch gets the change with its name, but nothing watches the monitored root's parent, and an inner disk's top folder's parent
is told nothing. `touched_scopes()` and `change_events_to_backup_entries()` leave the root out, and a comparison compares
the root only as the tree, so a root-only change makes no version.

**Fix: the entry's own.**
- The watcher queues a nameless IN_ATTRIB on the monitored root's own watch, or on an inner disk's top folder's (a path of
  its `inner_mounts`), as an 'attrib' event of that folder. An inner disk's top folder is then an ordinary folder attrib, its
  metadata copied by the replay, as any folder's.
- For the root: `touched_scopes()` sets a new `TouchedScopes.root` when an event names the root, and `batch_scopes()` keeps
  such scopes, so a root-only batch compares nothing else (not a full comparison).
- The check, at both places that commit no version (`do_backup()`'s `no_differences()` before the locks, and after the look
  under them, where it runs before `locks.release()`): the root's owner, mode, mtime and extended attributes (its
  `trusted.reverberator.*` names left out; atime left out, as relatime moves it) against the newest version's record
  (`load_root_meta()`). It runs at a full comparison, and at a batch that holds the root's own nameless event
  (`TouchedScopes.root`); a batch without that event checks nothing of the root. A create and a delete in the top folder
  move its mtime and raise only named events, and a batch's comparisons leave folder mtimes out
  (`compare_monitor_entry()`), so such a batch makes no version, as the approved entry "A batch whose only changes are left
  out can still commit a version" keeps it; a change of the root's owner, mode or attributes always raises that event on its
  own watch (inotify(7)), and a lost one is an overflow, which makes a full comparison. A full comparison compares the root's
  mtime as `folder_times` compares every folder's. The attributes are left out when the record says `"xattrs_left_out":
  true`.
- Different: the batch goes on as a version with no entries, whose commit writes the new record. No difference when there
  is no record or it cannot be read (a vault filesystem without extended attributes), when the root's attributes cannot be
  read (an error other than ENODATA for a name removed since its listing: the next commit's `record_root_meta()` says it),
  and while the job's last record write failed (`ROOT_META_TROUBLE`), as the record then says nothing of what was kept; so
  a vault that cannot keep the record makes at most one such version per daemon run. A record 0.55.6 trimmed for room reads
  as a root without attributes: the first full comparison after the upgrade makes one version for a top folder whose
  attributes did not fit (Calls to confirm).
- That version's change list holds one 'attrib' row for the monitored root (section 9).

**Reaches:** the watcher loop's nameless branch, `TouchedScopes`, `touched_scopes()`, the backuper's `batch_scopes()`,
`do_backup()` (the check at both `no_differences()` sites, and an empty version through `hand_over()` and
`do_reverb_backup()` with no entries, which the replay and the commit must take), `change_events_to_backup_entries()`'s
docstring (the root's attrib now reaches the batch, through its scopes, not as an entry), the change list rows. Under Keep N
Versions such a version pushes the oldest out, as any version does.

**Behaviour:** a chmod, chown, touch or setfattr of the top folder makes a version within the job's delays, with one INFO line
(`The monitored folder's own metadata changed: making a version of it`); one reverted before the batch makes none.

**Docs:** the deferred entry and its README line (59) go.

**Tests (container, uid 65534, the real watcher):** a chmod of the root: a version whose record holds the new mode, and a
whole-job restore gives it; a chmod and its reversal in one batch: none; a file made and removed in the root, and a file in
the root the length rule leaves out: no version; a chmod while the daemon is down: a version at the start; a root whose
record left its attributes out: no version for an unchanged root; a record write that fails (a stand-in): one version, then
none. VM, as root: a chmod of an inner disk's top folder alone: a version with the folder's new mode.

**Cost:** for a batch holding the root's event, or a full comparison, that finds nothing: one lstat, the root's attribute
names and values, and one `getxattr` of the record. Nothing for any other batch.

## 9. History from what the replay applied

**Real (read).** `do_backup()` writes the change list from every entry of the batch (`content_file_content`) and the
verification's applied fixes; the replay's own result (`replay()`'s applied map) is dropped. So a modify whose copy was left
out or failed (the version keeps the old copy) reads as "modified", and a move whose target was left out reads as "moved to"
a place the version lacks.

**Fix: the entry's own, by the rule the verification already uses.** `applied_fixes()` moves out of `verify()` into
`do_reverb_backup()`'s scope, beside `replay()`, and judges the batch's own entries as it judges the verification's: the
replay's flag, and the manifest's row agreeing with the event (tracked, or for a delete untracked), with one addition, a copy
not put in place. The mapping: `wait_for_async_commands()` gathers the rels `finish_copies()` returns (the copies it put in
place) into one set for the batch, across every wait; the replay records the rel of each entry whose own copy it queued
(the rel `writer.copy()` was given for that entry; a folder create's copies below it are not its own); an entry whose own
rel was queued and is not in that set at the end was not applied. The move branch records whether a move was applied
(today every move stays applied): a fallback's result (`copy_instead_of_move()`, `delete_and_copy()`) where it falls back.
A move not applied whose source the manifest no longer tracks is written as the delete of its source.
`do_reverb_backup()` hands the applied entries to its caller through a new list parameter, as `verified` (its two returns
unchanged), section 1's leave-outs among them as deletes; `do_backup()` writes the change list from that list, then the
verification's fixes (judged the same way), then section 8's root row.

The root row is `[<monitored path>/, time, 'attrib', None]`, as `entry_row()` writes a folder. `path_changes()` takes it as the
top folder's own row (its path without the / is the monitored path, which `find_job()` gives as rel '' and history passes
whole) and counts nothing below for it; the 0.54 readers (`read_change_list_moves()`, `rows_dropping()`) map the monitored
path to '' already and read only lists written before the conversion.

**Reaches:** `do_reverb_backup()` (`replay()`, the move branch, `wait_for_async_commands()`, `applied_fixes()`, the new
parameter), `do_backup()`'s `content_file_content`. History reads the lists as before; old lists keep what they say.

**Docs:** the deferred entry and its README line (71) go.

**Tests (container, uid 65534; tests/test_history.py):** a modify left out by the length rule; a modify whose source is
unreadable (mode 000); a move whose target the rule leaves out: history names no "modified", and "deleted" for the moved
source; a batch of only left-out entries makes no version (as now); a root chmod: history of the top folder says
"attributes changed".

**Cost:** none measurable: a set lookup per entry.

## 10. A walk inside a folder whose subfolders are being deleted

**Real (read).** `iter_tree_entries()`'s `child_gone()` keeps the names of a parent listed after an open in it failed; a name
those names hold is listed for again. While a deletion runs beside the walk, each name was there at the last listing and is
gone at its open, so each failure lists the parent again: quadratic in the folders deleted.

**Fix: the entry's own, one listing per wave.** An open of a folder below the walk's root that answers ENOENT is set aside on
its parent's frame (`frame[5]` holds the set-aside names in place of the kept listing), with no listing. The set-aside names
are judged together, with one listing of the parent, at the first of: the parent's next entry that is no folder (before it
is yielded), its next folder whose open works (right after that open), and the end of its listing. Each is gone (a
FolderGone and its INFO line) when that listing lacks it, and keeps its error (`Error scanning`) when it holds it; a listing
that fails with ENOENT or ENOTDIR (the parent gone too) takes every one for gone, and one that fails otherwise leaves each
its own error, as `child_gone()` judges now. So a run of failed opens, a deletion ahead of the walk, costs one listing,
and a single failure is judged at its next sibling, within moments as now. ENOTDIR and ELOOP below the root stay gone at
once with no listing; the walk root is unchanged (`folder_gone()`).

The other route, judging every set-aside name at the parent's end by its inode (`DirEntry.inode()`), was weighed: in a
depth-first walk the parent's end comes after every later sibling's subtree, and a folder removed and made again in that
time (`rm -rf build; mkdir build`) often gets the same inode number back on ext4 or XFS, which would keep a false error
(ERROR, an unwatched folder, UNREADABLE). The wave keeps today's short window and needs no inode.

**Reaches:** `iter_tree_entries()` only, and its docstring ("lists their parent once" becomes "once per run of failed
opens").

**Docs:** the deferred entry and its README line (72) go.

**Tests (container, uid 65534; tests/test_version_walk.py or test_r_scan.py):** a walk inside a folder of 2,000 subfolders
deleted after the walk's listing began (in a hook at the first yield): the parent is listed once for the judgement, and every
folder is yielded or judged gone; a name the parent lists that cannot be opened (a stand-in for the open of that name) keeps
its error; a folder replaced by a file (ENOTDIR) is gone at once. The build measures a walk of 10,000 folders deleted
alongside, before and after (the entry's "tens of seconds").

**Cost:** fewer listings.

## Questions for the user

**Q20. A monitored folder with more than about 2.9 KiB of extended attributes, on an ext4 or f2fs vault.** With the inner
mount points moved out of the record (section 4.1), the record still holds the root's own owner, mode, times and extended
attributes in one attribute of the version's folder, and on ext4 and f2fs all of a folder's attributes share about 4 KiB. A
top folder whose own attributes take more than about 2.9 KiB there (an XFS top folder can hold up to 64 KiB) keeps them out of
its record, with one line in the log: a whole-job restore gives the top folder none of them (its owner, mode and times it
gets). Files and other folders are not affected. This is part of the deferred entry "A top folder with many inner disks loses
its own extended attributes from its record", so leaving it is a known limitation that needs your OK.
- (a) Known limitation (Recommended): top folders with that many attributes are rare (ACLs and security labels take tens of
  bytes); the README's record paragraph already says so.
- (b) Store the root's attributes raw, one attribute each, beside the record: room up to about 4 KiB of them on ext4 and
  f2fs, and as much as XFS takes on an XFS vault; a second record form, read and restored for good, for that case.
- What waits on it: the limitations entry for the case, and section 4.1's trim text. The words it would narrow: "Fixes round
  (Recommended)" (2026-11-14), which put the whole deferred entry in the round after 0.55.6.

**Q21. Whether a job still waits, after reverberator restarts, for a disk taken out of its mergerfs pool.** From this round
each look at a pool, in the daemon, remembers the disks that pool mount has listed, and every job on the pool waits for one
it lists no more until it is listed again (section 3.1): the idle entry is fixed for every pool, disks added through
mergerfs's control file and pools mounted outside fstab included. Open is the restart entry: 0.55.6 forgets such a disk at
a restart, and the backup after it can make the version before show another version's bytes for a file on that disk, a
wrong result.
- (a) Keep the record in the state folder too (Recommended, what is built): `pool-disks.json` in /run/reverberator, with
  the boot id; both entries fixed, across daemon restarts within one boot (/run is tmpfs: a reboot, and the first 0.55.7
  start, begin empty, as 0.55.6 does). What it costs an operator: a disk taken out of the pool's list on purpose (through
  mergerfs's control file) blocks every job on that pool, whatever files it holds, with FAILED: waiting lines from 15 min
  on, until the pool is mounted again, the machine rebooted, or pool-disks.json removed while reverberator is stopped; a
  restart no longer lets it go. On a kernel before 6.8 (no unique mount ids, so a remounted pool can keep its old id) the
  record stays in memory and a restart lets a disk go: the restart entry stays there, which widens the approved known
  limitation "Kernels before 6.8 and the pool check" (2026-10-26, "Known limitation (Recommended)").
- (b) In memory only: the restart entry stays, a known limitation, and a restart or a remount lets a disk go (a remount
  starts the record again at a new id).
- What waits on it: section 3.1's file and README line 76 (built on (a) when not answered by then). The words it would
  narrow: "Fixes round (Recommended)" (2026-11-14), which put the restart entry in this round: (b) leaves it, a wrong result
  the agent rules call always worth fixing; (a) leaves it on kernels before 6.8, and for a disk already out when 0.55.7 first starts. "Support pools with a limitation"
  (2026-11-04) covers a limitation on pools, so chief may decide it.

**Q22. An entry whose path grows past Linux's 4,095-byte limit after it was backed up.** A version's path grows when the
version number gains a digit (V9's 4,095 bytes are V10's 4,096), when a folder above an entry is renamed longer, and when
the vault is moved to a longer path or its Vault Path spelled longer. Today such an entry stays in the version past the
limit, and every backup of the job fails once a change reaches its folder, until it is removed from the vault by hand.
Section 1 fixes this by never letting it get there.
- (a) Leave it out before it grows (Recommended, what is built): from that growth on, the entry is in no new version, with
  its NOT BACKED UP line at every backup that meets it; the versions before keep it until the prune takes them, and then no
  version holds it. At a digit it is left out one version early (V9 leaves out what V10 could not hold). It costs nothing
  per batch: one scan of the vault database at each growth, and one range query for each folder moved to a longer place.
  Left as on 0.55.6, each failing every backup of the job until it is removed by hand: an entry a version already holds
  past the limit (left by an older release at a digit, or by a vault moved or spelled longer, which lengthens every
  version at once), which the next scan names with its own NOT BACKED UP line; and an entry no row tracks that a rename or a
  digit puts past the limit (one stays only where a batch's sweep could not list its folder). It extends the approved known
  limitation "A symlink or a path the vault can't hold is left out" from an entry written past the limit to one whose path
  grows past it, and writes those two cases into it.
- (b) Keep it, reaching it through folder handles (the fix the deferred entry named): the entry stays backed up, but every
  part that reads a version by path must change, the writer, its size counts, the start's repair walks, the restore and
  history among them (eight sites found so far, and each missed one stops the job one version later with no way out from
  the monitored tree); on a vault on a mergerfs pool it cannot work at all, as mergerfs makes each call with the whole path
  on its disk (reasoned, not run), so pool vaults keep the failure; and a restore of such an entry fails until the restore
  takes handles too.
- What waits on it: section 1, the second step of the build. The user's words: the pick of 2026-11-09, "Accept: leave it out,
  warn (Recommended)", which (a) extends to the growing case, as chief extended it on 2026-11-15 to every entry whose path
  passes the limit; (a) also narrows "Fixes round (Recommended)" (2026-11-14), which put the deferred entry's handle fix in this
  round, and leaves the entry's failure in place for the two cases above. Chief may decide it under that pick.

**Q23. A disk that joins a pool and leaves it again within one batch of a restore's copies.** From this round a folder
restore on a mergerfs pool reads the pool's list once per 1,000 copies and fails when a disk it saw has left the pool by the
sync (section 6). A disk added through mergerfs's control file and taken out again between two of those looks is still not
seen: copies that landed on it are out of the pool's view, and the restore says done.
- (a) Known limitation (Recommended): it needs an operator to add a disk to the pool and take it out again within one
  batch of copies of a restore they run; a look per copy would narrow the window, not close it.
- (b) Close it: before its sync, the restore looks up every entry it copied through the pool (one lstat each, mostly from
  cache; a million for a whole job of a million files) and fails for any it cannot find.
- What waits on it: the limitations entry, or section 6's last check. The words it would narrow: "Fixes round
  (Recommended)" (2026-11-14), for the deferred entry "A disk that joins a pool and leaves it within one restore is not
  seen".

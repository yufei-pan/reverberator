## 1. An entry past the path limit inside a version

**Real, run.** A probe in the test container (the suite's own `held_at_4096_in_v10()`: a file at 4,095 bytes in V9, 4,096 in
V10) on 0.55.6's code: a file created beside it fails every attempt with `JobFailure: recording ... failed`
(`TreeWriter.record()` → `ensure_real()` → `unfold()` → `keep_entry()`'s lstat, ENAMETOOLONG); its top folder renamed to a
name of the same length fails the same way through `hard_link_tree()`; a full comparison with nothing changed commits.

Why: the length rule (`vault_path_too_long()`, `length_rule_bytes()`) measures an entry when it is written. The hand-over
moves the tree to the next version's folder each batch (`hand_over()`: exchange, or two renames), so at V9 to V10 every path
in the tree gains a byte; a folder renamed longer (`renamed_in_place()` measures the folder's own two paths only) lengthens
every path below it. The entry then sits in the tree past the limit, and everything that reaches it by path fails: the
writer's records, but also `BatchSizes.result()`, the roll-forward's `measure_previous()`/`measure_version()`, the start's
repair walks, `tree_totals()`, the restore and history.

**Fix: a version never holds an entry past the limit (Q22, option (a)).** Principle 2: remove the state the failure needs,
rather than reach it through handles at every site that reads a version (the check found eight such sites, and on a pool a
handle does not help at all: mergerfs makes each call with the whole path on its disk, reasoned, not run). The rule already
leaves out an entry whose path the vault cannot hold, with its NOT BACKED UP line; this extends it to an entry whose path
would grow past the limit, before it grows, while every path still fits:

- **The rule counts the version after the one written.** `length_rule_bytes()` adds the digits the next number gains
  (`next_version_bytes()` of the version written), in its one place, so every write (the first version's walk, the
  replay's copies, folders and renames' targets, the estimate, `entries_all_drop_out()`, `replay_ops()`, `settle_ops()`)
  counts the length the entry will have at the next hand-over. A delete's "kept" test (`left_out(kept=True)`, the line
  ending `this version keeps it`) still counts the version written, as it asks whether the entry can be reached now. The
  sites that pass the newest version's path for the version to be written (the estimate, `entries_all_drop_out()`) count
  two numbers on. Only at the version before a digit (V9, V99, ...) does this differ from today: by one byte.
- **When the count grows, what it puts past the limit leaves the version written.** The manifest keeps the count of its
  last version commit (a meta key, `rule_bytes`, written in the commit's transaction by `do_backup()`, a first version and
  a roll-forward too; `no_differences()` writes nothing). At the start of `do_reverb_backup()`, inside its transaction and
  before the replay's records, a count above the recorded one (or none recorded: a vault an older release wrote) selects the
  rows whose own path passes the limit under the new count: one SQL scan with the stored path's byte length as a prefilter
  (`length(CAST(path AS BLOB)) > PATH_LIMIT - 1 - count`: a stored path is never shorter than its name's bytes, as
  `storable_name()` only lengthens), then `vault_path_too_long(count, rel, False)` exactly. The topmost of each subtree is
  removed as the replay removes a delete (`TreeWriter.remove_queued()`: recorded in the previous version first, then `rm`
  in the tree; its rows dropped), each with `report_path_too_long(..., kept=False)` (`left out of this version`), and
  waited for before the replay goes on. The count grows at three events: the next version gains a digit (so V9's batch
  leaves out what V10 could not hold, and V8 keeps it); on a pool, a disk with a longer path joins (`pool_surplus()`); the
  first version-making batch after the upgrade (no count recorded).
- **A folder moved to a longer place has its rows measured first.** In the replay's move branch, for a folder whose target
  is longer in bytes than its source: one range query, the longest stored path under the source
  (`max(length(CAST(path AS BLOB)))` over the source's key range), bounds it; only when the bound passes at the target are
  the rows listed, and each topmost row whose path at the target passes is left out the same way at its source place (its
  line names the monitored path at the target), waited for before `TreeWriter.rename()`. The rename and `move_tree()` then
  move the rest. The query reads the rows `move_tree()` rewrites right after, so it costs no more than the move already does.

The previous version's folder is never longer than the tree's (a number has as many digits or fewer) and staging is
shorter, so every record, and every older version, fits once the tree does. A pruned version renamed into staging is
past no reader but `rm -rf`, which does not care about depth.

What stays outside: an entry an older release left past the limit (a vault that crossed a digit with one, before this
round): the scan passes over a row past the limit in the version written too, which it could not remove by path, so that
entry keeps 0.55.6's behaviour (its delete keeps it, a change in its folder fails the backups until it is removed from the
vault by hand). None of the live vaults holds one (the main session's check), and none can get one from this round on:
Not an issue (Calls to confirm). An entry no row tracks (what a move's copy fallback left, until a sweep of a scope above it)
is not found by the scan; for one to sit exactly at a digit's boundary needs both at once.

**Reaches:** `length_rule_bytes()` (and through it the four rule sites), `do_reverb_backup()` (the growth's scan, the move
branch's bound, `left_out()` with two counts), `VaultManifest` (the `rule_bytes` key; the two queries), `do_backup()`'s
commits. `settle_ops()`'s docstring loses its digit-growth sentence.

**Behaviour:** a NOT BACKED UP line `left out of this version` for each entry left out at a growth or a longer rename, then
at every backup that meets it, as for any entry the rule leaves out; no change-list row for it (section 9: no entry of the
batch). The versions before keep it, until the prune takes them.

**Docs:** docs/limitations.md drops the deferred entry; "A symlink or a path the vault can't hold is left out" replaces its
sentence "An entry a version already holds past the limit ... (deferred: ...)" with: an entry whose path would grow past the
limit is left out from that growth on, with its line, the versions before keeping it: at a version number's growth from the
version before the one that gains a digit, at a folder renamed longer from that rename, on a pool from the first backup after
a disk with a longer path joins; and gains Q22's answer in its approved field. README: line 62 goes; line 23's "a delete of
an entry already past the limit leaves it in the newest version" becomes the growth sentence; line 92's `this version keeps
it` stays, for an entry an older release left.

**Tests (container, uid 65534; tests/test_long_paths.py):** a file at 4,095 bytes in V0 to V8: V9's batch (a change
elsewhere) leaves it out with its line, V8 reads it, V9 and V10 do not, a sibling created, changed and removed in its folder in
V10 and V11 commits, a full comparison logs its line and makes no version; a file created at 4,095 bytes in V9's batch is left
out; a folder renamed to a longer name so one file below it passes: the rename is made, the file left out (the version before
holds it at the old place), the next batch in that folder commits; a vault with no recorded count runs the scan once;
`held_at_4096_in_v10()` builds its state with the rule counting the version written, as 0.55.6 did (a monkeypatched
`length_rule_bytes()`), and its three tests pin that such an entry keeps 0.55.6's behaviour; the stand-in pool (`fake_pool`)
with a longer branch added between batches leaves out what it puts past the limit. A cut at each step (the crash sweep's
kill points: the leave-out's record, its removal, the rename after it): the roll-forward commits and the oracle reads every
version. **VM, as root:** the boundary and rename shapes on ext4 and f2fs loop vaults and on a real mergerfs pool.

**Cost:** nothing per batch but comparing two integers. The scan runs at V9, V99, V999, at a longer pool disk and once
after the upgrade; the bound only for a folder moved to a longer place. The build times the scan on a manifest of a million
rows, and the bound on a moved folder of 100,000 rows against `move_tree()` on the same rows.

## 2. An inner disk under one disk of a pool

**Real (read).** `paused_inner_mounts()` pauses a remembered, unmounted inner mount only while its folder reads empty, and
on a pool it reads the folder through the pool: the union of every disk's folder of that name. Another disk holding an entry
there makes the folder non-empty, so the mount is not paused, its files leave each new version, and
`inner_mounts_to_remember()` forgets it.

**Fix: the entry's own.** The set of remembered inner mounts (section 4.1) records, for one under a disk of the monitored
path's pool, that disk: the branch whose place matched it in `pool_inner_mounts()` (the index it already finds), carried by
`inner_mount_rels()`/`inner_mounts_to_remember()` as {rel: branch, or None off a pool}. A remembered mount that is not
mounted, with a branch recorded, is looked at on that disk: its place there (the branch joined with the monitored path's
place below the pool's mount point and the rel, which is the mount point the table showed), whether or not the pool lists
the branch now. There and empty, or not to be looked at (any OSError of the lstat or the listing): paused. Gone, not a folder,
or holding entries: not paused, as now, which is how a user retires an inner disk (README's procedure stays as it is). With
no branch recorded (off a pool, or a set 0.55.6 wrote, until the table shows that mount again) the folder is looked at
through the monitored path, as now. The place is the mount point Linux took, so it cannot pass the path limit.

**Reaches:** `pool_inner_mounts()` (the branch with each mount), `inner_mount_rels()`, `inner_mounts_to_remember()`,
`paused_inner_mounts()`, and through them `do_backup()`, `drop_unmounted_entries()`, `compare_scanned_folders()`; the stored
set (section 4.1).

**Behaviour:** such a disk is paused, with its `Inner mounts not mounted` line, and its files stay in every version. On a
pool, files put into a retired inner disk's folder through the pool that land on another disk leave it paused until its
own folder is removed (Calls to confirm).

**Docs:** the deferred entry and its README line (63) go.

**Tests (VM, as root, real mergerfs; tests/test_pool_pause.py):** a pool of two loop disks, an inner loop disk mounted under
disk 1 at the monitored path's place, a file written straight onto disk 2 in a folder of the same name; unmount the inner
disk: paused, its files in the next version, and still in the vault after Keep N Versions more batches; disk 1 taken out of
the pool's list through the control file (with no fstab line naming it, section 3.1): still paused. Its folder removed
through the pool: not paused; files written into it that land on disk 1: not paused. The place's listing stood in for (an
`os.scandir()` of that path raising EIO; root reads a mode-000 folder): paused. Container, uid 65534: the {rel: branch}
set through `pool_inner_mounts()` with a made-up table, and a 0.55.6 set with no branches read as now.

**Cost:** none: the same lstat and listing per remembered unmounted mount, at another path.

## 3. Disks out of a pool's list

### 3.1 The pool's fstab line is the list waited for (the restart and idle entries)

**Real (read).** `JobControl.left` (filled by `PoolNotReady.left`, read by `JobControl.left_reason()` in `wait_for_path()`)
lives in memory and holds only disks a failed step saw leave; `PoolGuard` keeps a step's lists for that step alone. So a
restart forgets, and a disk taken out between steps is never seen leaving.

**Fix: compare the pool with what fstab says it is (Q21, option (a)).** Weighed against a state file of the disks each pool
mount has listed (Q21's (b)): this keeps no state (principle 2), uses the file the operator declares the pool in, which the
code reads at every look already (principle 3), survives restarts, reboots, remounts and every kernel with nothing to clear,
and its way out is the edit an operator makes anyway to take a disk out for good, or the next boot mounts the pool with it
(or its bare folder) again.

- `parse_fstab()` also gives each line's source and type. For a mergerfs line (type `fuse.mergerfs` or `mergerfs`) whose
  source is a `:`-list of absolute paths, each with an optional `=` suffix (`=RW`, `=NC,100G`) that is dropped, each part's
  glob is expanded as mergerfs expands it at mount (`glob.glob()`, sorted) and resolved (`os.path.realpath()`): the pool's
  configured disks, keyed by the line's resolved mount point. Any other source (a name, a part that is no absolute path)
  names no disks, with one warning per pool per daemon run (as `F2FS_UNTOLD` keeps its warnings). `fstab_mount_points()`
  and the `Look` it fills carry these beside the points, so a guard's checks read no fstab of their own.
- `pool_state()`: a configured disk of the pool that its branch list lacks is a problem of the pool, `disk <disk> of pool
  <pool> is not in the pool's list (/etc/fstab names it)`. So every wait, every guard check, the mount monitor's flags, and
  the restore's and history's pool warnings (`vault_pool_warning()`, whose history exits 1) see it: one answer at the source.
- What goes: `JobControl.left` and `left_reason()`, `PoolNotReady.left` and its parameter, the `left` parameter of
  `pool_problem()` and `PoolGuard.problem()`, the third argument of `job.fail()` from the backuper's `except JobFailure`. A
  step's own check that a disk left during it (`pool_problem()` with `since`) stays: it fails the step, and the next wait
  waits while fstab names the disk.
- Not covered (Q21): a disk added to a pool only through mergerfs's control file and taken out again, and a pool mounted
  outside fstab (by hand, a systemd .mount unit): no list names their disks, so one taken out is not waited for, as on 0.55.6
  between steps.

**Behaviour and lines:** the wait's reason above, with the FAILED: waiting marker and its timing unchanged, whatever the job
was doing when the disk left. Editing the fstab line (or, for a glob, removing or renaming the disk's mount point folder)
ends the wait at the next look, with no restart. A disk mounted at a folder a glob matches before it is added to the pool
makes the job wait too (the alert comes after the 15-minute grace).

**Docs:** both deferred entries and their README lines (61, 64) go; README line 76: the job waits for a disk its pool's
fstab line names and the pool does not list, whenever that happens, and the way out is the fstab edit (or the folder, for a
glob), in place of "restarting reverberator lets a disk taken out for good go"; its example texts take placeholder disks
(section 11). Q21's answer may add one limitations entry (the cases not covered), next to "Vault disks mounted outside
fstab".

**Tests (container, uid 65534, stand-in pool with an fstab line written to `rv.FSTAB_PATH`; tests/test_pool_guards.py):** a
branch taken out of the stand-in's list between batches: the next wait waits, names it, goes on once it is listed again; the
same with a new `JobControl` (a restart: nothing carried); the fstab line edited to drop it: the wait ends with no restart;
a glob line, the folder renamed: the wait ends; a source the parser does not read: no wait, one warning; a disk listed only
through the stand-in's control file and taken out: not waited for (Q21's case, pinned). `parse_fstab()` doctests: `=RW`,
`=NC,100G`, a glob, an octal escape, a source that is a name. tests/prune_oracle.py (`require_pools()`) and
tests/test_pool_guards.py:421-427 and tests/test_pool_pause.py's `left_reason()` tests lose `left`. **VM, as root, real
mergerfs (tests/test_pool_cut.py):** a pool mounted from a glob line (the expansion agrees with mergerfs's own branch list);
a branch taken out through the control file between batches, then the daemon restarted as a process: it waits, no version
or prune until the branch is listed again; the fstab line edited: it goes on, and the vault's versions read whole after.

**Cost:** none per wait: fstab is read at every look already; a glob adds one listing of its folder.

### 3.2 The flush that lists the pool once

**Real (read).** `VaultUnit.holding()` reads the pool's branch list once and syncs the job vault's filesystem on each
branch listed then; a branch out of the list at that moment is skipped, and if it is back by `pool_guard.require()` at the
commit, the commit goes through with its copies there unsynced. The prune's flush is the same call.

**Fix: the entry's own.** `VaultUnit` keeps the branches it opened (its state's `ids`); `holding()` raises `PoolNotReady`,
`disk <branch> left pool <pool> during this step`, for one of them the list it reads lacks. It is no OSError, so it goes
through `flush_or_fail()` and `sync_vault_filesystems()` to fail the step (a backup's commit, `TreeWriter.flush()`, a
prune, a scan's repair), and the next attempt redoes the work once the next wait (section 3.1) lets it, as the lesson of
2026-11-10 says (a write error is heard where it is needed: fail the attempt and redo the work). Not a sync of every disk
the step began with: a removed disk that hangs would stall that sync with no timeout, where today it fails at the check.

**Reaches:** `VaultUnit.__init__()` and `holding()`. Its callers are unchanged.

**Docs:** the deferred entry and its README line (60) go.

**Tests (container, stand-in pool; VM, real mergerfs):** a branch taken out of the list just before the commit's flush and
put back before the commit's check: the step fails naming it, nothing is committed, the next attempt commits once it is
listed; the same for a prune's flush.

**Cost:** none: the same listing.

## 4. The inner mount set

### 4.1 Where the set is kept (the record entry)

**Real (read).** `record_root_meta()` puts the set in the root-meta record (one attribute of the version's folder); on ext4
and f2fs every extended attribute of an inode shares one block of about 4 KiB (xattr(7)), so the set and the root's own
extended attributes trade room, and about 100 mount points do not fit even alone. A failed write keeps the version before's
record, whose set can be older.

**Fix: the set out of the record.** The manifest keeps the set as now (`inner_mounts`, the rels) and each one's disk in a
new key (`inner_mount_disks`, {rel: branch}, written on every commit that writes the set, `{}` when none), in the same
transaction. A file of the job vault, `.reverberator_inner_mounts`, holds the same for a lost manifest: one line of JSON
(`{"v": 1, "inner_mounts": [...], "disks": {...}}`, each rel as `storable_name()` writes it), written by temp file, fsync and
rename before the commit's flush, when its contents differ from the set the batch began with or the file is not there (so a
vault's first commit after the upgrade writes it, even empty). It holds the newest committed or attempted set: an attempt
that fails after the rename leaves it one attempt ahead, which is harmless (an added mount pauses an empty folder at worst;
a dropped one was dropped because its folder holds entries), and in `no_differences()`, where no flush follows, a power cut
can keep the old file, which matters only with the manifest lost too. A write that fails fails the attempt (JobFailure
naming the file and the error). A separate attribute was the entry's plan; it shares the same block, so it buys no room.

`remembered_inner_mounts()` reads the manifest's keys; with none, the file; with none, for a vault 0.55.6 wrote, the newest
version's record's `inner_mounts` field, as now (no disks). An unreadable file stops the backup as an unreadable record
does now (FAILED, naming the file, and how to go on: remove it).

The record keeps the root's owner, mode, times and extended attributes only: `encode_root_meta()` writes no `inner_mounts`
(`decode_root_meta()` still reads one), and `record_root_meta()` loses its second trim (`'trimmed mounts'`). Its one trim, a
root whose extended attributes alone do not fit (about 2.9 KiB on an ext4 or f2fs vault), stays: Q20. Every new record says
which in a field added under `"v": 1`, `"xattrs_left_out": true` or `false` (a 0.55.6 reader ignores it), which section 8
reads.

**Reaches:** `record_root_meta()`, `encode_root_meta()`/`decode_root_meta()`, `remembered_inner_mounts()`,
`VaultManifest.inner_mounts`/`set_inner_mounts()` and the new key, `do_backup()`'s commit and `no_differences()` (both write
the set), the job vault's scan (`read_job_vault()`/`get_vault_info()` know the file and remove a temp a kill left, as they do
`PRUNE_SALT_TEMP_INFIX`'s), the 0.54 conversion's listing of the job vault if it reads names. Stored data: a new file and
a new manifest key; old records still read; a downgrade to 0.55.6 reads the manifest's `inner_mounts` as it always did.

**Docs:** the deferred entry goes, its README line (69) goes; README's record paragraph (line 82) drops the inner mount
points from the record and the second trim, and names the file. A lessons entry (section 11).

**Tests:** the keys and the file written and read back, a set of 500 mounts with their disks, a write that fails (a folder
at the temp's place: the attempt fails, the next commits), the file written at a vault's first commit with an empty set, the
read order over a lost manifest, a 0.55.6 record with the set read (container, uid 65534, except what writes trusted.*);
tests/test_inner_mounts.py:1146 reads the set from the file, not the record. A root with 2 KiB of extended attributes and
200 inner mount points keeps its attributes in the record (VM, as root: trusted.* needs root).

**Cost:** none per batch: the keys are written only when they change (`_set_meta()`), the file the same.

### 4.2 A disk mounted and unmounted within one backup

**Real (read).** `inner_mounts_to_remember()` takes the mounts of the batch's table and of the one read at the commit; a disk
mounted after the first and gone by the second is in neither, while the backup's walks or copies may have put its files in
the version. The next batch's comparison of that folder then finds it empty.

**Fix: every mount table the mount monitor reads feeds the set.** The mount monitor (`fs_signature_monitor`) reads the table
at every change of it (POLLPRI on mountinfo) and hands each to its subscribers first; the watcher's subscription
(`store_mount_table()`) keeps only the newest for the watcher's loop, which is why a busy watcher misses one. It also adds the
inner mounts of each table it is handed (`inner_mount_rels()` with the pool's disks the watcher read last, `pool_seen`, no
read of its own; skip-filtered) to a set on the job's `JobControl`, under its lock. The backup resets that set to the inner
mounts of the table it reads after its locks (`drop_unmounted_entries()`'s look after the wait; a first version's read after
its scan), so only mounts seen from there on count: one seen and gone between batches, which no copy met, is not
remembered. The version commit passes it to `inner_mounts_to_remember()` as a new parameter that joins `kept` (also where no
table could be read); `no_differences()` does not (no copy ran). The next batch then finds the folder of a disk that is gone
empty and remembered: paused, with its line, its files kept.

The entry named the walks and copies: a comparison's lstat gives each folder's st_dev at no cost, but the replay's folder
copies and a first version's walk read none, a `cp` cannot tell, and on a pool an inner disk shown through the pool has the
pool's st_dev (FUSE gives every entry its own superblock's). The monitor's tables see every mount wherever a walk is.

What is left: a disk mounted and unmounted between two of the monitor's reads. It reads within moments of each change,
unless it is in a signature check (df, lsblk) after a change of a mount holding a job's path; a walk or copy cannot meet a
disk that briefly. Not an issue (Calls to confirm).

**Reaches:** the watcher's subscription, `JobControl` (the set, its reset, its take), `inner_mounts_to_remember()` (the new

**Docs:** the deferred entry and its README line (67) go.

**Tests (VM, as root; tests/test_inner_mounts.py):** a loop disk mounted inside the tree after a backup's locks and unmounted

## 5. A link given back after a cut, on f2fs

**Real (read).** `put_back_forward_links()` and `put_back_staged_links()` judge a link due when `kind_at()` finds nothing at
its place; a link a power cut left with no text (readlink answers ENOENT) is found, so it is never written again, and that
version keeps a broken link.

**Fix: the entry's own, with the put-back's own text.** At a place the put-back judges (a row, or a staged link's rel, under
real folders of the previous version, the tree holding the entry), an entry whose lstat says link and whose `readlink()`
answers ENOENT is due too: unlinked and written again with the text the put-back computes for that place. For a row of a
link (kind 'l'), that is the row's own text (the manifest's link column: version n's link, which a forward link to the
unchanged tree reads the same): a user's link that a record copied with `cp -af` on a vault that refuses hard links keeps
its text, never a forward text naming the tree's newer entry; a link row with no recorded text (a manifest listed again from
the tree) is left as now. For any other row, and for a staged rel, it is the forward text, as only a forward link stands at
such a place. Nothing else reads or rewrites a textless link.

**Reaches:** `put_back_forward_links()`, `put_back_staged_links()` (one helper they share). `prepare_roll_forward()`'s flush
after a link written already covers a rewrite.

**Docs:** the deferred entry and its README line (68) go.

**Tests:** container: a put-back place whose link reads ENOENT (`os.readlink` stood in for that path alone), for a file row
(rewritten with the forward text) and a link row (with the row's text): the roll-forward commits, the version reads right.
VM, as root: the power-loss sweep on an f2fs vault gains the kill point between the put-back's symlink and its flush
(tests/test_crash_power_loss.py).

**Cost:** a `readlink()` per link at a place the put-back judges, at a start after a cut only.

## 6. A restore's look, once per batch of copies

**Real (read).** `sync_restore()` reads the pool's list only at a sync: a disk that joined and left between the claim and the
last sync is seen by neither its join look nor its left look. It checks the folder's filesystem only at a sync too, so a
restore whose target moved (a lazy unmount, a mount over it) copies on until its walk ends; `accept_restore()`'s walk
likewise.

**Fix: the entries' own, one look.** In `restore_entry()`'s `finish_batch()`, once a batch's copies are in place (every
`RESTORE_COPY_BATCH`, 1,000):
- the folder's filesystem: `os.stat(folder).st_dev` against `disks.dev`, an OSError counting as moved (as `moved_now()`).
  Moved: the moved line (`say_moved()`, lifted out of `sync_restore()` so both say it once), then a stop raised from the
  look, as `check_stop()` raises KeyboardInterrupt: a new exception, caught around the walk, after which no copy starts,
  the sync runs as now through its handles, no marker is written by path (`report.moved`), and the run exits 1.
- on a pool, its branch list: one `getxattr` of the control file of the pool the claim found (its mount point kept in
  `RestoreDisks`, a new field its three constructors in `open_restore_disks()` fill). Each branch listed gets its place's
  nearest existing folder's st_dev at this look (None when it cannot be looked at), kept in a set of branches seen. A list
  that cannot be read (the pool unmounted, EIO, ENOTSUP) fails the restore with its line (`the disks of pool <pool> could not
  be listed while the restore ran: <error>`) and stops it the same way.
At the sync, the left look covers every branch seen, not only the claim's: one the pool no longer lists fails the restore as
left the pool when the folder is on it now (stat finds it, or cannot tell), or when its place's nearest existing folder is
on another filesystem than the look found (unmounted or replaced since), as `replaced()` judges the claim's branches; else
it is passed over. `--accept` looks at the folder's filesystem once per that many folders, in its partial-file walk and its
hand-over (it copies nothing, so it reads no pool list), and stops the same way.

What is left: a disk that joins and leaves between two looks, within one batch of copies: Q23.

**Reaches:** `open_restore_disks()`, `RestoreDisks`, `restore_entry()` (`finish_batch()`, the catch around the walk),
`accept_restore()`, `sync_restore()` (`say_moved()`, the left look).

**Docs:** both deferred entries and their README lines (65, 66) go; Q23's answer may add one entry.

**Tests (VM, as root, real mergerfs; tests/test_restore_pool.py, tests/test_restore_sync.py, with a small batch):** a branch
added through the control file after the first batch and removed before the sync, a copy placed on it: FAILED, left the
pool; the same with that branch's disk unmounted before the sync: FAILED; the target's loop disk unmounted lazily after the
first batch: FAILED at the second batch, nothing more written on the filesystem under it, no marker there; the pool's
control file made unreadable at a look (a stand-in for that `getxattr`): FAILED with its line, no traceback; `--accept` with
the target moved: ends at its first look.

**Cost:** one stat per 1,000 copies; on a pool one `getxattr` and one stat per branch per 1,000 copies.

## 7. An error read as "not there" in the replay

**Real (read).** The steps that act on an answer "not there" use a look that answers "no" for any error: `real_folders_to()`
without `strict` and `os.path.lexists()`/`isdir()`/`islink()`.

**Fix: the entry's own, one rule.** A look at the version is `kind_at()` or `real_folders_to(strict=True)`. Its strict
branch answers False for ENOTDIR as for ENOENT (today it raises NotADirectoryError: only FileNotFoundError is caught
before it), and raises any other error, which fails the attempt as a JobFailure naming the path and the error (`cannot look
at <path> in the version: <error>; the next attempt goes on with it`): the version cannot be trusted there, and the next
attempt redoes the batch. A look at the monitored tree goes through a new helper, `monitored_there(path)`: False only for
ENOENT or ENOTDIR, True for anything else, so the copy is tried and its own failure keeps the last backed-up copy with its
UNREADABLE line (`finish_copies()`, `copy_failure_side()`), as an unreadable file does now. The sites:
- version side: `do_reverb_backup()`'s `delete_path()` (its `real_folders_to()` and the kind of what is at the entry), its
  attrib and move branches (the kind at the target, `real_folders_to()` of both paths); `TreeWriter.remove_queued()`,
  `rename()`, `make_folders()`, `_folders_for_copy()`, `staged()` (a staging name taken: `kind_at()`); `finish_copies()`
  (the metadata-only case, the three `real_folders_to()`, the lexists before a row is dropped); `discard_copies()`;
  `failed_removal()`; `sweep_version_folder()`'s look at tracked rows; `cp_af_copy_path()`'s destination; `replace_entry()`;
  `entries_all_drop_out()`'s `under_untracked_folder()` (ENOENT or ENOTDIR: no folder, as now; another error fails the
  attempt instead of counting as a change); `new_in_tree()`'s `real_folders_to()` of the tree;
- monitored side (`monitored_there()`): `copy_path()` (the source and each entry of a folder's walk),
  `copy_instead_of_move()`, the move branch's look at its source after the rename, `cp_af_copy_path()`'s source,
  `_folders_for_copy()`'s source, `copy_failure_side()` (an error is 'source', not 'vanished');
- left as they are: `roll_forward_entries()`'s `real_folders_to(monitor_path, ...)` (monitored side: an error there leaves
  the file out of the trusted list, so the comparison reads it, which is no drop); `file_in_place_of_folder()` (it runs only
  after the strict look answered "not a real folder", so an error there is a race, and None drops only the rows that look
  already decided go).

A look that fails inside a clean-up (`discard_copies()` from `stop_copies()` in a `finally`) leaves the partial file and does
not replace an exception already on its way up: it is raised after, or logged when one is.

**Docs:** the deferred entry and its README line (70) go.

**Tests (container, uid 65534; tests/test_io_errors.py):** a folder of the version made mode 000 by the test user (a real
EACCES) under a delete, a finished copy, a failed copy and a folder to be made: the attempt fails with the line, no row is
dropped, the next attempt with the mode back commits right; a monitored file in a folder made mode 000 after its event: its
UNREADABLE line, the last copy kept, no "source no longer exists"; a strict look meeting a file in a folder's place
(ENOTDIR): no failure. EIO at the same sites through a stand-in for `os.lstat` on one path (an error a test user cannot make
for real), and in the VM a dm-error device if the suite's VM tools have one.

**Cost:** none: the same call per look.

## 8. The monitored folder's own metadata

**Real (read).** The watcher drops every nameless event (`Event name not found`, DEBUG); for a watched folder its parent's
watch gets the change with its name, but nothing watches the monitored root's parent, and an inner disk's top folder's parent
is told nothing. `touched_scopes()` and `change_events_to_backup_entries()` leave the root out, and a comparison compares
the root only as the tree, so a root-only change makes no version.

**Fix: the entry's own.**
- The watcher queues a nameless IN_ATTRIB on the monitored root's own watch, or on an inner disk's top folder's (a path of
  its `inner_mounts`), as an 'attrib' event of that folder. An inner disk's top folder is then an ordinary folder attrib, its
  metadata copied by the replay, as any folder's.
- For the root: `touched_scopes()` sets a new `TouchedScopes.root` when an event names the root, and `batch_scopes()` keeps
  such scopes, so a root-only batch compares nothing else (not a full comparison).
- The check, at both places that commit no version (`do_backup()`'s `no_differences()` before the locks, and after the look
  under them, where it runs before `locks.release()`): the root's owner, mode, mtime and extended attributes (its
  `trusted.reverberator.*` names left out; atime left out, as relatime moves it) against the newest version's record
  (`load_root_meta()`). It runs at a full comparison, and at a batch that holds the root's own nameless event
  (`TouchedScopes.root`); a batch without that event checks nothing of the root. A create and a delete in the top folder
  move its mtime and raise only named events, and a batch's comparisons leave folder mtimes out
  (`compare_monitor_entry()`), so such a batch makes no version, as the approved entry "A batch whose only changes are left
  out can still commit a version" keeps it; a change of the root's owner, mode or attributes always raises that event on its
  own watch (inotify(7)), and a lost one is an overflow, which makes a full comparison. A full comparison compares the root's
  mtime as `folder_times` compares every folder's. The attributes are left out when the record says `"xattrs_left_out":
  true`.
- Different: the batch goes on as a version with no entries, whose commit writes the new record. No difference when there
  is no record or it cannot be read (a vault filesystem without extended attributes), when the root's attributes cannot be
  read (an error other than ENODATA for a name removed since its listing: the next commit's `record_root_meta()` says it),
  and while the job's last record write failed (`ROOT_META_TROUBLE`), as the record then says nothing of what was kept; so
  a vault that cannot keep the record makes at most one such version per daemon run. A record 0.55.6 trimmed for room reads
  as a root without attributes: the first full comparison after the upgrade makes one version for a top folder whose
  attributes did not fit (Calls to confirm).
- That version's change list holds one 'attrib' row for the monitored root (section 9).

**Reaches:** the watcher loop's nameless branch, `TouchedScopes`, `touched_scopes()`, the backuper's `batch_scopes()`,
`do_backup()` (the check at both `no_differences()` sites, and an empty version through `hand_over()` and
`do_reverb_backup()` with no entries, which the replay and the commit must take), `change_events_to_backup_entries()`'s
docstring (the root's attrib now reaches the batch, through its scopes, not as an entry), the change list rows. Under Keep N
Versions such a version pushes the oldest out, as any version does.

**Behaviour:** a chmod, chown, touch or setfattr of the top folder makes a version within the job's delays, with one INFO line
(`The monitored folder's own metadata changed: making a version of it`); one reverted before the batch makes none.

**Docs:** the deferred entry and its README line (59) go.

**Tests (container, uid 65534, the real watcher):** a chmod of the root: a version whose record holds the new mode, and a
whole-job restore gives it; a chmod and its reversal in one batch: none; a file made and removed in the root, and a file in
the root the length rule leaves out: no version; a chmod while the daemon is down: a version at the start; a root whose
record left its attributes out: no version for an unchanged root; a record write that fails (a stand-in): one version, then
none. VM, as root: a chmod of an inner disk's top folder alone: a version with the folder's new mode.

**Cost:** for a batch holding the root's event, or a full comparison, that finds nothing: one lstat, the root's attribute
names and values, and one `getxattr` of the record. Nothing for any other batch.

## 9. History from what the replay applied

**Real (read).** `do_backup()` writes the change list from every entry of the batch (`content_file_content`) and the
verification's applied fixes; the replay's own result (`replay()`'s applied map) is dropped. So a modify whose copy was left
out or failed (the version keeps the old copy) reads as "modified", and a move whose target was left out reads as "moved to"
a place the version lacks.

**Fix: the entry's own, by the rule the verification already uses.** `applied_fixes()` moves out of `verify()` into
`do_reverb_backup()`'s scope, beside `replay()`, and judges the batch's own entries as it judges the verification's: the
replay's flag, and the manifest's row agreeing with the event (tracked, or for a delete untracked), with one addition, a copy
not put in place. The mapping: `wait_for_async_commands()` gathers the rels `finish_copies()` returns (the copies it put in
place) into one set for the batch, across every wait; the replay records the rel of each entry whose own copy it queued
(the rel `writer.copy()` was given for that entry; a folder create's copies below it are not its own); an entry whose own
rel was queued and is not in that set at the end was not applied. The move branch records whether a move was applied
(today every move stays applied): a fallback's result (`copy_instead_of_move()`, `delete_and_copy()`) where it falls back.
A move not applied whose source the manifest no longer tracks is written as the delete of its source.
`do_reverb_backup()` hands the applied entries to its caller through a new list parameter, as `verified` (its two returns
unchanged); `do_backup()` writes the change list from that list, then the verification's fixes (judged the same way), then
section 8's root row.

The root row is `[<monitored path>/, time, 'attrib', None]`, as `entry_row()` writes a folder. `path_changes()` takes it as the
top folder's own row (its path without the / is the monitored path, which `find_job()` gives as rel '' and history passes
whole) and counts nothing below for it; the 0.54 readers (`read_change_list_moves()`, `rows_dropping()`) map the monitored
path to '' already and read only lists written before the conversion.

**Reaches:** `do_reverb_backup()` (`replay()`, the move branch, `wait_for_async_commands()`, `applied_fixes()`, the new
parameter), `do_backup()`'s `content_file_content`. History reads the lists as before; old lists keep what they say.

**Docs:** the deferred entry and its README line (71) go.

**Tests (container, uid 65534; tests/test_history.py):** a modify left out by the length rule; a modify whose source is
unreadable (mode 000); a move whose target the rule leaves out: history names no "modified", and "deleted" for the moved
source; a batch of only left-out entries makes no version (as now); a root chmod: history of the top folder says
"attributes changed".

**Cost:** none measurable: a set lookup per entry.

## 10. A walk inside a folder whose subfolders are being deleted

**Real (read).** `iter_tree_entries()`'s `child_gone()` keeps the names of a parent listed after an open in it failed; a name
those names hold is listed for again. While a deletion runs beside the walk, each name was there at the last listing and is
gone at its open, so each failure lists the parent again: quadratic in the folders deleted.

**Fix: the entry's own, one listing per wave.** An open of a folder below the walk's root that answers ENOENT is set aside on
its parent's frame (`frame[5]` holds the set-aside names in place of the kept listing), with no listing. The set-aside names
are judged together, with one listing of the parent, at the first of: the parent's next entry that is no folder (before it
is yielded), its next folder whose open works (right after that open), and the end of its listing. Each is gone (a
FolderGone and its INFO line) when that listing lacks it, and keeps its error (`Error scanning`) when it holds it; a listing
that fails with ENOENT or ENOTDIR (the parent gone too) takes every one for gone, and one that fails otherwise leaves each
its own error, as `child_gone()` judges now. So a run of failed opens, a deletion ahead of the walk, costs one listing,
and a single failure is judged at its next sibling, within moments as now. ENOTDIR and ELOOP below the root stay gone at
once with no listing; the walk root is unchanged (`folder_gone()`).

The other route, judging every set-aside name at the parent's end by its inode (`DirEntry.inode()`), was weighed: in a
depth-first walk the parent's end comes after every later sibling's subtree, and a folder removed and made again in that
time (`rm -rf build; mkdir build`) often gets the same inode number back on ext4 or XFS, which would keep a false error
(ERROR, an unwatched folder, UNREADABLE). The wave keeps today's short window and needs no inode.

**Reaches:** `iter_tree_entries()` only, and its docstring ("lists their parent once" becomes "once per run of failed
opens").

**Docs:** the deferred entry and its README line (72) go.

**Tests (container, uid 65534; tests/test_version_walk.py or test_r_scan.py):** a walk inside a folder of 2,000 subfolders
deleted after the walk's listing began (in a hook at the first yield): the parent is listed once for the judgement, and every
folder is yielded or judged gone; a name the parent lists that cannot be opened (a stand-in for the open of that name) keeps
its error; a folder replaced by a file (ENOTDIR) is gone at once. The build measures a walk of 10,000 folders deleted
alongside, before and after (the entry's "tens of seconds").

**Cost:** fewer listings.

## Questions for the user

**Q20. A monitored folder with more than about 2.9 KiB of extended attributes, on an ext4 or f2fs vault.** With the inner
mount points moved out of the record (section 4.1), the record still holds the root's own owner, mode, times and extended
attributes in one attribute of the version's folder, and on ext4 and f2fs all of a folder's attributes share about 4 KiB. A
top folder whose own attributes take more than about 2.9 KiB there (an XFS top folder can hold up to 64 KiB) keeps them out of
its record, with one line in the log: a whole-job restore gives the top folder none of them (its owner, mode and times it
gets). Files and other folders are not affected. This is part of the deferred entry "A top folder with many inner disks loses
its own extended attributes from its record", so leaving it is a known limitation that needs your OK.
- (a) Known limitation (Recommended): top folders with that many attributes are rare (ACLs and security labels take tens of
  bytes); the README's record paragraph already says so.
- (b) Store the root's attributes raw, one attribute each, beside the record: room up to about 4 KiB of them on ext4 and
  f2fs, and as much as XFS takes on an XFS vault; a second record form, read and restored for good, for that case.
- What waits on it: the limitations entry for the case, and section 4.1's trim text. The words it would narrow: "Fixes round
  (Recommended)" (2026-11-14), which put the whole deferred entry in the round after 0.55.6.

**Q21. What a job waits for when a disk is taken out of its mergerfs pool, and how an operator lets one go for good.** From
this round the job waits, before any backup, prune or scan, for a disk its pool should have and does not list, across
restarts of reverberator (section 3.1). Today the way out is to restart reverberator, and the job forgets a disk at a restart
and never sees one taken out between backups: those are the two deferred entries.
- (a) The pool's line in /etc/fstab is the list (Recommended, what is built): the job waits for a disk that line names
  (its globs expanded) and the pool does not list. To let a disk go for good, edit the line (or, for a glob, remove or rename
  the disk's mount point folder), which an operator does anyway, or the next boot puts the disk, or its bare folder, back in
  the pool; the job goes on at its next look, with no restart. No state is kept. Not covered, a known limitation beside
  "Vault disks mounted outside fstab": a disk added only through mergerfs's control file and taken out again, and a pool
  mounted outside fstab (by hand, a systemd .mount unit): one taken out is not waited for, as on 0.55.6 between backups.
  Also, a disk mounted at a folder a glob matches before it is added to the pool makes the job wait until it is (alerting
  after 15 minutes).
- (b) A state file of the disks each pool mount has listed (in the daemon's state folder, read at every wait, with the
  boot id): covers those cases too. To let a disk go: mount the pool again, reboot, or remove the file, which lets every
  pool's disks go at once; one more file format, its failure policy, and its lessons entry.
- What waits on it: section 3.1, its wait text and README line 76 (section 3.1 is built on (a) when not answered by then;
  (b) would be built in its place). The words it would narrow: (a) narrows "Fixes round (Recommended)" (2026-11-14) for the
  two cases it does not cover; (b) narrows nothing. "Support pools with a limitation" (2026-11-04) covers a limitation on
  pools, so chief may decide it.

**Q22. An entry whose path grows past Linux's 4,095-byte limit after it was backed up.** A version's path grows when the
version number gains a digit (V9's 4,095 bytes are V10's 4,096), when a folder above an entry is renamed longer, and on a
pool when a disk with a longer path joins. Today such an entry stays in the version past the limit, and every backup of the
job fails once a change reaches its folder. Section 1 fixes this by never letting it get there.
- (a) Leave it out before it grows (Recommended, what is built): from that growth on, the entry is in no new version, with
  its NOT BACKED UP line at every backup that meets it, and the versions before keep it, as for an entry the vault cannot
  hold when it is written; at a digit it is left out one version early (V9 leaves out what V10 could not hold). It costs
  nothing per batch: one scan of the vault database at each such growth. It extends the approved known limitation "A
  symlink or a path the vault can't hold is left out" from an entry written past the limit to one whose path grows past it.
- (b) Keep it, reaching it through folder handles (the fix the deferred entry named): every part that reads a version by
  path must change, the writer, its size counts, the start's repair walks, the restore and history among them (eight sites
  found so far, and each missed one stops the job one version later with no way out from the monitored tree); on a vault on
  a mergerfs pool it cannot work at all, as mergerfs makes each call with the whole path on its disk (reasoned, not run), so
  pool vaults keep the failure; and a restore of such an entry fails until the restore takes handles too.
- What waits on it: section 1, the second step of the build. The user's words: the pick of 2026-11-09, "Accept: leave it out,

## 1. An entry past the path limit inside a version

**Real, run.** A probe in the test container (the suite's own `held_at_4096_in_v10()`: a file at 4,095 bytes in V9, 4,096 in
V10) on 0.55.6's code:
- a file created beside it: `JobFailure: recording ... failed`, from `TreeWriter.record()` → `ensure_real()` → `unfold()`
  → `keep_entry()`'s `os.lstat()` (ENAMETOOLONG), at every attempt;
- its top folder renamed to a name of the same length: the same failure, through `TreeWriter.rename()` → `hl_record()` →
  `hard_link_tree()` → `keep_entry()`;
- a full comparison with nothing changed commits; with the sibling made, it fails as the first.

Why: `unfold()` holds an entry real when its forward text is too long for a link (the rel plus three bytes a level: on the
container's XFS anything past 1,023 bytes, on ext4 and f2fs past 4,095), and `keep_entry()`, `hard_link_tree()`,
`record()`'s look into folders both versions hold real and `tree_usage()` (for `folder_usage()`) all pass full paths.
The length rule measures every batch entry before it is written (0.55.6, `vault_path_too_long()`); what it cannot measure
is an entry that grows past the limit afterwards: the version number gains a digit at a hand-over, or a folder above it is
renamed longer (`renamed_in_place()` measures the folder's own two paths only).

**Fix: the entry's own.** The writer never passes a path built from the version's folder:
- `TreeWriter` opens the tree's folder, the previous version's folder and staging (when first needed) once, keeps the
  handles for the batch, and passes every path relative to one of them (`dir_fd`, `src_dir_fd`/`dst_dir_fd`, a
  `renameat2()` with handles in `rename_exchange()`). A rel is never longer than the monitored path it comes from, which
  Linux takes, so this alone covers every entry a version number's growth put past the limit.
- Its walks (`unfold()`, `hard_link_tree()`, `record()`'s look into a folder both versions hold real, `tree_usage()` as
  `folder_usage()` uses it) open each folder below their start through its parent's handle (O_DIRECTORY | O_NOFOLLOW),
  list it by that handle, and act on each entry by (handle, name): lstat, link, readlink, symlink, mkdir, rename. So a rel
  longer than 4,095 bytes (a folder renamed so that the monitored paths below it pass Linux's limit) is walked as well.
- A folder's metadata copied by `copy_folder_meta_onto()` goes from handle to handle (fchown, fchmod, futimens, the
  extended attributes by handle): a small helper beside `copy_file_meta()`, which keeps its path form for its other
  callers.
- `link_or_copy()` takes handles; its `cp` fallback (a vault that refuses hard links) is given
  `/proc/<the daemon's pid>/fd/<handle>/<name>` for an entry whose path does not fit, which the kernel resolves from the
  handle (`cp` inherits no handle, so not `/proc/self`).
- `sweep_version_folder()` lists a folder below its scope through its parent's handle the same way, so a folder past the
  limit holding tracked entries is not "Cannot list" at every sweep.

The alternative weighed, a margin in the rule (counting the version number as if it had nine digits, and a rename's whole
subtree), does not cover a folder renamed longer without a manifest query per rename, nor the entries 0.55.6 vaults hold
already, so it removes no part.

What stays outside the writer: the copies (`cp`) and removals (`rm -rf`, `shutil.rmtree()`) take the paths the rule
measured; the prune renames a whole version and removes it with `rm -rf`, which does not care about depth.

**Reaches:** `TreeWriter` (`__init__`, `path()`, `kept_path()`, `staged()`, every verb), `hand_over()` and `do_backup()`'s
roll-forward writer (they make writers; the handles close in `do_backup()`'s `finally`, and a writer made alone for one
copy by `cp_af_copy_path()`, `finish_copies()` or `discard_copies()` opens its handle when first used and closes it with the
call), `link_or_copy()`, `rename_exchange()`/`exchanged()`, `tree_usage()`, `sweep_version_folder()`/`sweep_entry()`. A walk
holds one handle a level on each side, as the 0.55.6 walk does (R12): deep trees need the raised open-file limit the daemon
already sets. Nothing stored changes.

**Behaviour:** such an entry stays in every new version, unchanged, while backups go on around it; a change to it is still
left out with its NOT BACKED UP line (`this version keeps it` for its delete). No log line changes. A restore of it is
outside this round (see the report's "found outside").

**Docs:** docs/limitations.md drops this deferred entry, and "A symlink or a path the vault can't hold is left out" drops
its sentence "but a change in its folder, or a rename of a folder above it, fails every backup ... (deferred: ...)",
keeping that the entry stays as it is. README: the "(to be fixed in the next round)" line goes.

**Tests (container, uid 65534; tests/test_long_paths.py):** on `held_at_4096_in_v10()`, a file created, changed and removed
beside it; its top folder renamed to a name of the same length and to a longer one; a folder past the limit holding a file,
with a sibling changed (the sweep: no "Cannot list" line); its parent folder deleted (`folder_usage()`'s walk); a full
comparison after each. Each commits, keeps the entry readable through a handle (`read_in()`), and the next batch commits too.
The same shapes on the stand-in pool (`fake_pool`, every record a keep). **VM, as root:** the sibling and rename shapes on
ext4 and f2fs loop vaults (a 4,095-byte link text: the forward link of a shallower entry fits there, where XFS's 1,023
refuses it) and on a real mergerfs pool. The tree-writes guard (tests/test_tree_writes.py) keeps passing: every write still
goes through a verb.

**Cost:** no syscall more on any path: an open through a handle replaces an open by path. The build times a batch that
unfolds a folder of 10,000 entries on 0.55.6 and on the branch; they should match within the spread of five runs.

## 2. An inner disk under one disk of a pool

**Real (read).** `paused_inner_mounts()` pauses a remembered, unmounted inner mount only while its folder reads empty, and
on a pool it reads the folder through the pool: the union of every disk's folder of that name. Another disk holding an entry
there makes the folder non-empty, so the mount is not paused, its files leave each new version, and
`inner_mounts_to_remember()` forgets it.

**Fix: look at the folder on each disk of the pool.** On a pool (`pool`, the batch's `pool_state()` of the monitored path),
a remembered inner mount that is not mounted is paused when, through the pool, it is a folder, and on some disk of the pool
its folder is there and empty (the mount point a disk leaves), or cannot be looked at. Through the pool gone, or not a
folder, it is not paused, as now. Off a pool nothing changes.

The entry named recording the disk each mount sits under. That is a new field in the manifest's set and in the record, with
its compatibility, for an answer the disks give themselves: the bare mount point is on the disk the inner disk was mounted
under, and nowhere else is an empty folder of that name likely. Both rules keep a retired disk's folder paused while it
stays empty on its disk, so neither is better at a retirement.

**Reaches:** `paused_inner_mounts()` (the folder's place below the pool's mount point, joined to each branch of
`pool.ids`), and through it `do_backup()`, `drop_unmounted_entries()`, `compare_scanned_folders()`. Nothing stored changes.

**Behaviour:** such a disk is paused, with its `Inner mounts not mounted` line, and its files stay in every version. On a
pool, retiring an inner disk is done by removing its folder: files written into it through the pool can land on another
disk while its own folder stays empty (Calls to confirm).

**Docs:** the deferred entry goes; README: its line goes, and the inner-mounts paragraph's retire sentence says "on a mergerfs
pool, remove the folder".

**Tests (VM, as root, real mergerfs; tests/test_pool_pause.py):** a pool of two loop disks, an inner loop disk mounted under
disk 1 at the monitored path's place, a file written straight onto disk 2 in a folder of the same name; unmount the inner
disk: paused, its files in the next version, and still in the vault after Keep N Versions more batches. A folder removed
through the pool: not paused. A disk's folder that cannot be looked at (a stand-in for that one lstat, as root reads mode
000): paused.

**Cost:** an lstat and a listing per disk of the pool, for each remembered inner mount that is not mounted, once per look.

## 3. Disks out of a pool's list

### 3.1 One record of the disks a pool mount has listed (the restart and idle entries)

**Real (read).** `JobControl.left` (filled by `PoolNotReady.left`, read by `JobControl.left_reason()` in `wait_for_path()`)
lives in memory and holds only disks a failed step saw leave; `PoolGuard` keeps a step's lists for that step alone. So a
restart forgets, and a disk taken out between steps is never seen leaving.

**Fix: one record, kept by the daemon, per pool mount.** For each mergerfs pool mount (its unique mount id, as
`pool_state()` reads it into `PoolState.pool_id`), the set of branches the daemon has seen it list. `wait_for_path()`, for a
path on a pool, reads the pool's branch list (one `getxattr` of its control file, as `left_reason()` reads today), adds
what it lists to the record, and while the record holds a branch the list lacks, waits, with that as its reason. The record:
- **Where:** in memory, shared by the jobs (`PoolDisks`, one lock), and in one file of the daemon's state folder
  (`pool-disks.json`: `{"v": 1, "pools": {"<mount point>": {"mount": <id>, "disks": [...]}}}`), written whole by temp file and
  rename when a pool's set grows or its mount changes, which is rare: a disk added, a pool mounted. The state folder is
  tmpfs by default, so a reboot clears it, when every mount id changes anyway.
- **What clears it:** a disk listed again leaves no gap; a pool mounted again has a new id, so its record starts from the
  list it has then. That is how mergerfs itself works: a list changed through the control file lasts as long as that mount.
- **How an operator lets a disk taken out for good go:** Q21. Recommended: mount the pool again (or reboot), or remove the
  file; the wait's reason says so.
- **What a restart reads:** the file, once, at the daemon's start; an entry whose mount id is not the pool's now is dropped
  at its first check. On a kernel without unique mount ids (before 6.8) the record stays in memory only, so a restart lets a
  disk go there, as 0.55.6 does: mountinfo ids are reused by a remount, and a remembered id could hold a disk taken out by one.

What goes: `JobControl.left` and `left_reason()`, `PoolNotReady.left`, the `left` parameter of `pool_problem()` and
`PoolGuard.problem()`, the third argument of `job.fail()` from the backuper. A step's own check that a disk left during it
(`pool_problem()` with `since`) stays: it fails the step, and the record then makes the next wait wait.

The record is broader than `JobControl.left`: it waits for any disk the pool listed and then stopped listing, not only one a
failed step saw go. That is the idle entry's point, and it holds for both pools of a job, the vault's and the monitored
path's (Calls to confirm).

**Reaches:** `wait_for_path()` (the record's check where `left_reason()` was), the daemon's start (load), `JobControl`,
`PoolNotReady`, `pool_problem()`, `PoolGuard`, the backuper's `except JobFailure`. The state folder's readers
(`read_status()` and the status board) must pass over the new file. Tests outside the daemon (`job=None`) have no record.

**Behaviour and lines:** the wait's reason becomes `disk <branch> left pool <pool>: waiting for it to be listed again (if
it was taken out for good, <what Q21 picks>)`, once a disk is out, whatever the job was doing when it left. The FAILED:
waiting marker and its timing are unchanged. An upgrade from 0.55.6 while a disk is out forgets it once, as a restart does
now (the 0.55.6 memory is not carried).

**Docs:** both deferred entries go; README: their lines go, and the mergerfs paragraph says the job waits for a disk taken
out of the pool's list whenever that happens, and names the way out Q21 picks, in place of "restarting reverberator lets a
disk taken out for good go".

**Tests (container, stand-in pool; tests/test_pool_guards.py):** a branch taken out of the stand-in's list between two
batches: the next batch's wait waits, names it, and goes on once it is listed again; the same across a new `PoolDisks`
loaded from the file (a restart); a new mount id (the pool mounted again) lets it go; Q21's other way lets it go; a disk
added is recorded without a wait. **VM, as root, real mergerfs (tests/test_pool_cut.py):** a branch taken out through the
control file between batches, then the daemon restarted as a process: it waits, and no version or prune happens until the
branch is listed again; the vault's versions read whole after.

**Cost:** one `getxattr` of the control file and one statx of the pool's mount point (its id) per wait for a path on a
pool. A wait with nothing wrong returns at its first poll, so a batch pays it once per such path (the vault path, the job
vault, the monitored path: at most three).

### 3.2 The flush that lists the pool once

**Real (read).** `VaultUnit.holding()` reads the pool's branch list once and syncs the job vault's filesystem on each
branch listed then; a branch out of the list at that moment is skipped, and if it is back by `pool_guard.require()` at the
commit, the commit goes through with its copies there unsynced. The prune's flush is the same call.

**Fix: sync the disks the step began with too.** `holding()` takes the union of the branches the unit opened at its start
(`state.ids`, kept as `self.branches`) and the ones listed now. A branch out of the list but still mounted is synced through
the handle opened before the batch's first write, so its copies are on its disk and any write error is heard. One that was
unmounted is not there to sync: the pool check at the commit fails the step as a disk that left or was mounted again, as
now.

The entry named raising the disk through the flush so the backup fails and waits. Syncing the disk instead leaves nothing to
raise: the backup that would have failed is right, and commits.

**Reaches:** `VaultUnit.__init__()`, `VaultUnit.holding()`. Its callers (`flush_vault_disks()`, the commit's
`flush_copies()`, `prune_version()`'s flush, `TreeWriter.flush()`) are unchanged.

**Docs:** the deferred entry and its README line go.

**Tests (container, stand-in pool; VM, real mergerfs):** a branch taken out of the list at the flush's listing and put back
before the commit's check: the backup commits, and the branch's handle was synced (each `syncfs_fd()` call's handle
recorded); a branch left out until the check: the step fails as before.

**Cost:** none: the same stat per branch.

## 4. The inner mount set

### 4.1 Where the set is kept (the record entry)

**Real (read).** `record_root_meta()` puts the set in the root-meta record (one attribute of the version's folder); on ext4
and f2fs every extended attribute of an inode shares one block of about 4 KiB (xattr(7)), so the set and the root's own
extended attributes trade room, and about 100 mount points do not fit even alone. A failed write keeps the version before's
record, whose set can be older.

**Fix: the set in a file of the job vault.** `.reverberator_inner_mounts` beside the manifest, one line of JSON
(`{"v": 1, "inner_mounts": [...]}`, each rel as `storable_name()` writes it), written by temp file, fsync and rename before
the commit's flush, and only when its contents change (rarely: an inner disk mounted or retired). A write that fails fails
the attempt (JobFailure naming the file and the error): no version commits while the set cannot be kept, so the file always
holds the set of the newest committed version, and the next attempt writes it again. A separate attribute was the entry's
plan; it shares the same block, so it buys no room. A file has no such limit and is read only when the manifest is lost.

`remembered_inner_mounts()` reads the manifest, then this file, then, for a vault 0.55.6 wrote and no commit has rewritten
since, the newest version's record's `inner_mounts` field, as now. An unreadable file stops the backup as an unreadable
record does now (FAILED, naming the file, and how to go on: remove it).

The record keeps the root's owner, mode, times and extended attributes only: `encode_root_meta()` writes no
`inner_mounts`, and `record_root_meta()` loses its second trim (`'trimmed mounts'`). Its one trim, a root whose extended
attributes alone do not fit (about 2.9 KiB on an ext4 or f2fs vault), stays: Q20. That record says so in a new field,
`"xattrs_left_out": true` (a field added under `"v": 1`, which a 0.55.6 reader ignores), which section 8 reads.

**Reaches:** `record_root_meta()`, `encode_root_meta()`/`decode_root_meta()`, `remembered_inner_mounts()`, `do_backup()`'s
commit and `no_differences()` (both write the set), the job vault's scan (`read_job_vault()`/`get_vault_info()` must know the
file and remove a temp a kill left, as it does `PRUNE_SALT_TEMP_INFIX`'s), the 0.54 conversion's listing of the job vault
if it reads names. Stored data: a new file; old records still read; a downgrade to 0.55.6 reads the manifest's set, and only
over a lost manifest would it find none (two faults).

**Docs:** the deferred entry goes, its README line goes; README's record paragraph (line 82) drops the inner mount points
from the record and the second trim, and names the file. A lessons entry (section 11).

**Tests:** the file written and read back, a set of 500 mounts, a write that fails (a folder at the temp's place: the
attempt fails, the next commits), the read order over a lost manifest, a 0.55.6 record with the set read (container, uid
65534, except what writes trusted.*). A root with 3 KiB of extended attributes and 200 inner mount points keeps its
attributes in the record (VM, as root: trusted.* needs root).

**Cost:** none per batch: the file is compared with the set in memory and written only when they differ.

### 4.2 A disk mounted and unmounted within one backup

**Real (read).** `inner_mounts_to_remember()` takes the mounts of the table read after the locks and of the one read at the
commit; a disk mounted between them and gone by the commit is in neither, while the backup's walks or copies may have put
its files in the version. The next batch's comparison of that folder (the watcher's 'scan' events for it) then finds it empty.

**Fix: the watcher tells the backuper of every inner mount it sees.** `follow_inner_mounts()` already sees each mount table
change and logs `Inner mount <path> mounted`; for a 'mounted' or 'replaced' change it adds the mount's rel to a set on the
job's `JobControl` (in memory). The next commit (`do_backup()`'s version commit and `no_differences()`) takes that set into
`inner_mounts_to_remember()` (with the skip list's filter) and removes what it took once the commit stands. The next batch
then finds the folder of a disk that is gone empty and remembered: paused, with its line, its files kept.

The entry named the walks and copies; telling a mount from the walk needs an fstat per folder on every walk, and a copy
cannot tell at all. The watcher already follows every mount change, at no cost to the walks.

A mount that came and went between two of the watcher's reads of the mount table (the watcher takes the newest table when its
loop turns) is still missed; for a walk to meet such a disk in that time is the same race (Calls to confirm).

**Reaches:** `follow_inner_mounts()` (it is given the job), `JobControl`, `inner_mounts_to_remember()`, `do_backup()`. A
remembered mount that is never mounted again stays paused while its folder is empty, as any retired disk's does (README's
retire sentence).

**Docs:** the deferred entry and its README line go.

**Tests (VM, as root; tests/test_inner_mounts.py):** a loop disk mounted inside the tree after a backup's locks and
unmounted before its commit, with the walk made to meet it (a hook after the walk): the next batch keeps its files, with
the `Inner mounts not mounted` line; never met by the walk: the next batch pauses an empty folder, nothing lost.

## 5. A link given back after a cut, on f2fs

**Real (read).** `put_back_forward_links()` and `put_back_staged_links()` judge a link due when `kind_at()` finds nothing at
its place; a link a power cut left with no text (readlink answers ENOENT) is found, so it is never written again, and that
version keeps a broken link.

**Fix: the entry's own.** At a place the put-back judges (a row, or a staged link's rel, under real folders of the previous
version, the tree holding the entry), a link whose `readlink()` answers ENOENT is due too: it is unlinked and written again
with the forward text. Only freshly written links can lose their text this way, and every link the writer writes in the
previous version at such a place is a forward link; a user's recorded link is a hard link to an old inode, written long
before.

**Reaches:** `put_back_forward_links()`, `put_back_staged_links()` (one helper they share). `prepare_roll_forward()`'s flush
after a link written already covers a rewrite.

**Docs:** the deferred entry and its README line go.

**Tests:** container: a put-back place whose link reads ENOENT (`os.readlink` stood in for that path alone): it is
rewritten, the roll-forward commits, the version reads right. VM, as root: the power-loss sweep on an f2fs vault gains the
kill point between the put-back's symlink and its flush (tests/test_crash_power_loss.py); the oracle's links read through
its guard (the 0.55.6 Call to confirm about `entry_view()`).

**Cost:** a `readlink()` per link at a place the put-back judges, at a start after a cut only.

## 6. A restore's look, once per batch of copies

**Real (read).** `sync_restore()` reads the pool's list only at a sync: a disk that joined and left between the claim and the
last sync is seen by neither its join look nor its left look. It checks the folder's filesystem only at a sync too, so a
restore whose target moved (a lazy unmount, a mount over it) copies on until its walk ends; `accept_restore()`'s walk
(removing partial files) likewise.

**Fix: the entries' own, one look.** `restore_entry()`'s `finish_batch()` (every `RESTORE_COPY_BATCH`, 1,000, copies), and
`accept_restore()` once per that many folders, look once:
- the folder's filesystem (`os.stat(folder).st_dev` against `disks.dev`), once the batch's copies are in place: moved, the
  restore says so (`say_moved()`'s line), starts no more copies, writes no marker by path, and ends as one whose sync
  failed, so at most one batch lands on the other filesystem;
- on a pool, its branch list (one `getxattr` of the control file of the pool the claim found, now kept in `RestoreDisks`),
  every branch listed added to a set of branches seen. At the sync, the left look covers every branch seen, not only the
  claim's: one seen and no longer listed fails the restore as left the pool, when the folder is on it (or cannot be told);
  one seen after the claim whose folder is not there held nothing of the restore, and is passed over.

**Reaches:** `open_restore_disks()` (the pool's mount point, the seen set), `RestoreDisks`, `restore_entry()`'s
`finish_batch()`, `accept_restore()`'s walk, `sync_restore()`'s left look.

**Docs:** both deferred entries and their README lines go.

**Tests (VM, as root, real mergerfs; tests/test_restore_pool.py, tests/test_restore_sync.py, with a small batch):** a branch
added through the control file after the first batch and removed before the sync, a copy placed on it: FAILED, left the
pool; the target's loop disk unmounted lazily after the first batch: FAILED at the second batch, nothing more written on the
filesystem under it, no marker there; `--accept` with the same: ends at its first look.

**Cost:** one stat, and on a pool one `getxattr`, per 1,000 copies.

## 7. An error read as "not there" in the replay

**Real (read).** The steps that act on an answer "not there" use a look that answers "no" for any error: `real_folders_to()`
without `strict` and `os.path.lexists()`/`isdir()`/`islink()`.

**Fix: the entry's own, one rule.** Where an error is a "no": a look at the version is `kind_at()` or
`real_folders_to(strict=True)`, which raise any error but ENOENT and ENOTDIR, and the error fails the attempt, as a JobFailure
naming the path and the error (`cannot look at <path> in the version: <error>; the next attempt goes on with it`): the
version cannot be trusted there, and the next attempt redoes the batch. A look at the monitored tree answers "there" on such
an error, so the copy is tried, and its own failure keeps the last backed-up copy with its UNREADABLE line
(`finish_copies()`, `copy_failure_side()`), as an unreadable file does now. The sites:
- version side: `do_reverb_backup()`'s `delete_path()` (its `real_folders_to()` and the kind of what is at the entry), its
  attrib and move branches (the kind at the target, `real_folders_to()` of both paths); `TreeWriter.remove_queued()`,
  `rename()`, `make_folders()`, `_folders_for_copy()`; `finish_copies()` (the metadata-only case, the three
  `real_folders_to()`, the lexists before a row is dropped); `discard_copies()`; `failed_removal()`;
  `sweep_version_folder()`'s look at tracked rows; `cp_af_copy_path()`'s destination; `replace_entry()`;
- monitored side: `copy_path()` (the source and each entry of a folder's walk), `copy_instead_of_move()`, the move branch's
  look at its source after the rename, `cp_af_copy_path()`'s source, `copy_failure_side()` (an error is 'source', not
  'vanished').

A look that fails inside a clean-up (`discard_copies()` from `stop_copies()` in a `finally`) leaves the partial file and does
not replace an exception already on its way up: it is raised after, or logged when one is.

**Docs:** the deferred entry and its README line go.

**Tests (container, uid 65534; tests/test_io_errors.py):** a folder of the version made mode 000 by the test user (a real
EACCES) under a delete, a finished copy, a failed copy and a folder to be made: the attempt fails with the line, no row is
dropped, the next attempt with the mode back commits right; a monitored file in a folder made mode 000 after its event: its
UNREADABLE line, the last copy kept, no "source no longer exists". EIO at the same sites through a stand-in for `os.lstat`
on one path (an error a test user cannot make for real), and in the VM a dm-error device if the suite's VM tools have one.

**Cost:** none: the same call per look.

## 8. The monitored folder's own metadata

**Real (read).** The watcher drops every nameless event (`Event name not found`, DEBUG); for a watched folder its parent's
watch gets the change with its name, but nothing watches the monitored root's parent, and an inner disk's top folder's parent
is told nothing. `touched_scopes()` and `change_events_to_backup_entries()` leave the root out, and a comparison compares
the root only as the tree, so a root-only change makes no version.

**Fix: the entry's own.**
- The watcher queues a nameless IN_ATTRIB on the monitored root's own watch, or on an inner disk's top folder's (a path of
  its `inner_mounts`), as an 'attrib' event of that folder. An inner disk's top folder is then an ordinary folder attrib, its
  metadata copied by the replay, as any folder's.
- For the root: `touched_scopes()` sets a new `TouchedScopes.root` when an event names the root, and `batch_scopes()` keeps
  such scopes, so a root-only batch compares nothing else (not a full comparison).
- One check, wherever a batch or a comparison finds nothing to back up (`do_backup()`'s `no_differences()` path): the root's
  owner, mode, mtime and extended attributes (its `trusted.reverberator.*` names left out) against the newest version's record
  (`load_root_meta()`), atime left out, as relatime moves it; the extended attributes left out too when the record says
  `"xattrs_left_out"` (section 4.1). Different: the batch goes on as a version with no entries, whose commit writes the new
  record. No record, one that cannot be read (a vault filesystem without extended attributes, a failed write), is no
  difference: the next version made for another reason writes it. It covers a change made while the daemon was down, as
  every start's full comparison reaches it.
- That version's change list holds one 'attrib' row for the monitored root, so `history` of the top folder lists it as
  "attributes changed".

**Reaches:** the watcher loop's nameless branch, `TouchedScopes`, `touched_scopes()`, the backuper's `batch_scopes()`,
`do_backup()` (the check before `no_differences()`, and an empty version through `hand_over()` and `do_reverb_backup()` with
no entries, which the replay and the commit must take), the change list rows. Under Keep N Versions such a version pushes
the oldest out, as any version does.

**Behaviour:** a chmod, chown, touch or setfattr of the top folder makes a version within the job's delays, with one INFO line
(`The monitored folder's own metadata changed: making a version of it`); one reverted before the batch makes none.

**Docs:** the deferred entry and its README line go.

**Tests (container, uid 65534, the real watcher):** a chmod of the root: a version whose record holds the new mode, and a
whole-job restore gives it; a chmod and its reversal in one batch: none; a chmod while the daemon is down: a version at the
start; a root whose record left its attributes out: no version for an unchanged root. VM, as root: a chmod of an inner disk's
top folder alone: a version with the folder's new mode.

**Cost:** for a batch or comparison that finds nothing: one lstat, the root's attribute names and values, and one `getxattr`
of the record. Nothing for a batch that makes a version anyway.

## 9. History from what the replay applied

**Real (read).** `do_backup()` writes the change list from every entry of the batch (`content_file_content`) and the
verification's applied fixes; the replay's own result (`replay()`'s applied map) is dropped. So a modify whose copy was left
out or failed (the version keeps the old copy) reads as "modified", and a move whose target was left out reads as "moved to"
a place the version lacks.

**Fix: the entry's own, by the rule the verification already uses.** `do_reverb_backup()` returns the batch's own entries the
replay applied, judged as `applied_fixes()` judges the verification's: the replay's flag, and the manifest's row agreeing with
the event (tracked, or for a delete untracked), with one addition: a create, modify or attrib copy that the replay queued and
`finish_copies()` did not put in place (its source gone or unreadable, a link too long) is not applied. A move not applied
whose source the version no longer holds is written as the delete of its source. `do_backup()` writes the change list from
those, then the verification's fixes (which take the same addition), and section 8's root row.

**Reaches:** `do_reverb_backup()` (the main `replay()` result, the copies placed, a list for the caller), `applied_fixes()`,
`finish_copies()` (its placed rels are what `wait_for_async_commands()` returns), `do_backup()`'s `content_file_content`.
History reads the lists as before; old lists keep what they say.

**Docs:** the deferred entry and its README line go.

**Tests (container, uid 65534; tests/test_history.py):** a modify left out by the length rule; a modify whose source is
unreadable (mode 000); a move whose target the rule leaves out: history names no "modified", and "deleted" for the moved
source; a batch of only left-out entries makes no version (as now).

**Cost:** none measurable: a set lookup per entry.

## 10. A walk inside a folder whose subfolders are being deleted

**Real (read).** `iter_tree_entries()`'s `child_gone()` keeps the names of a parent listed after an open in it failed; a name
those names hold is listed for again. While a deletion runs beside the walk, each name was there at the last listing and is
gone at its open, so each failure lists the parent again: quadratic in the folders deleted.

**Fix: judge them at the end of the parent's listing, all at once.** An open of a folder below the walk's root that answers
ENOENT or ENOTDIR is set aside on its parent's frame, with no listing; when the parent's listing ends, the parent is listed
once, and each set-aside name is gone (a FolderGone and its INFO line) or keeps its error (`Error scanning`), as the parent's
listing says. A parent that cannot be listed then (deleted too) takes every set-aside name for gone, as now. The kept names
(`frame[5]`) go: one state less. The walk root is unchanged (`folder_gone()`).

The lines and the `errors` entries come at the parent's end instead of at the name's place; every caller reads `errors` after
the walk.

**Reaches:** `iter_tree_entries()` only.

**Docs:** the deferred entry and its README line go; the docstring's "lists their parent once" becomes true as written.

**Tests (container, uid 65534; tests/test_version_walk.py or test_r_scan.py):** a walk inside a folder of 2,000 subfolders
while another process deletes them: the parent is listed at most twice (its listing and the judgement), and every folder is
yielded or judged gone; a name the parent lists that cannot be opened (a stand-in for the open of that name) keeps its error.
The build measures a walk of 10,000 folders deleted alongside, before and after (the entry's "tens of seconds").

**Cost:** fewer listings.

## Questions for the user

**Q20. A monitored folder with more than about 2.9 KiB of extended attributes, on an ext4 or f2fs vault.** With the inner
mount points moved out of the record (section 4.1), the record still holds the root's own owner, mode, times and extended
attributes in one attribute of the version's folder, and on ext4 and f2fs all of a folder's attributes share about 4 KiB. A
top folder whose own attributes take more than about 2.9 KiB there (an XFS top folder can hold up to 64 KiB) keeps them out of
its record, with one line in the log: a whole-job restore gives the top folder none of them (its owner, mode and times it
gets). Files and other folders are not affected. This is part of the deferred entry "A top folder with many inner disks loses
its own extended attributes from its record", so leaving it is a known limitation that needs your OK.
- (a) Known limitation (Recommended): top folders with that many attributes are rare (ACLs and security labels take tens of
  bytes); the README's record paragraph already says so.
- (b) Store the root's attributes raw, one attribute each, beside the record: room up to about 4 KiB of them on ext4 and
  f2fs, and as much as XFS takes on an XFS vault; a second record form, read and restored for good, for that case.
- What waits on it: the limitations entry for the case, and section 4.1's trim text. The words it would narrow: "Fixes round
  (Recommended)" (2026-11-14), which put the whole deferred entry in the round after 0.55.6.

**Q21. How an operator lets go a disk taken out of a pool for good.** From this round the job waits for any disk its pool
listed and then stopped listing, across a restart of reverberator (section 3.1). Today the way out is to restart
reverberator; that is what the entry fixes, so the round needs another.
- (a) Mount the pool again, or reboot, or remove the state folder's `pool-disks.json` (Recommended): a list changed through
  mergerfs's control file lasts as long as that mount anyway, and fstab mounts the pool with its configured disks; removing
  the file is one `rm`, with no remount. The wait's reason names both.
- (b) A new command that lets one disk go (`reverberator release-disk <pool> <disk>`, say): exact, and one more command to
  build, document and keep.
- (c) Keep "restart reverberator" as the way out: the restart entry becomes a known limitation; only the idle entry is fixed.
- What waits on it: section 3.1's release, the wait's text, README line 76. Nothing the user said is narrowed by (a) or (b);
  (c) narrows "Fixes round (Recommended)" (2026-11-14) for the restart entry.

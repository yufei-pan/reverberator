0.55.2 is 0.55.1 (main 6726e75) with three fixes that don't touch the watcher, and the suite's tests made to hold on XFS. The watcher's redesign (round 22) ships later, on its own schedule. The fixes come from round 22's design work: its spec, docs/superpowers/specs/2026-11-08-round22-watcher-design.md on the round22 branch, section 10, tasks 2 to 4. A fresh spec check read this spec, and its points are settled below.

## Why now

On 2026-11-08 the filesystem holding /mnt/optane, and with it /tmp and two live jobs' trees (work, docker_volumes), moved from ext4 to XFS. That brought two daemon findings and 17 suite failures. A durability check for that move also found an older gap in the restore. The same check confirmed that the status files in /run/reverberator need no fsync, as that folder is tmpfs. Nothing changes there.

## 1. A restore syncs before it ends

**Today:** a restore puts new files in place and syncs nothing. A hard reset within the writeback window can leave restored files empty, with no marker to say the restore did not finish. ext4 and XFS have the same window. This is older than 0.55.

**The fix:**
- **Before the marker goes.** A folder restore syncs the target's filesystem after its copies finish, before `hand_over_folders()` runs.
  - In `restore_entry()`, that is after `finish_batch()` and before the call to `hand_over_folders()`.
  - In `accept_restore()`, it is before its call to `hand_over_folders()`, since a killed run's copies may still be dirty when `--accept` removes the marker.
- **Before the command returns.** After the hand-over, a second sync covers the folders' metadata and the marker's unlink, so a restore that reports done is on disk. A file target has no marker: one sync after the file and its metadata are in place, before the command returns.
- **What gets synced.**
  - `syncfs_folder()` of the target's folder; for a file target, of the folder that holds it.
  - On a mergerfs target, whose own sync does not reach the disks, each branch holding the target, found as `vault_disks()` finds a vault's.
  - Call `syncfs_folder()` per disk. Not `sync_vault_filesystems()`, which records a vault's sync failures (`record_failed_sync()`); a restore must not write vault markers.
- **A sync error is a failure of the restore.** It goes through the restore's report as a failure: the marker stays, and the folders are not handed over.
  - The message says the target's disk reported a write error and names the disk.
  - It does not offer a rerun as the fix, since a rerun keeps the entries already there.
  - A failure of the second sync, after the hand-over, is reported the same way, with exit 1.

**Tests:** record the calls. Check that the first sync comes before the hand-over and the marker's unlink, the second after them, and that both come before the command returns. Cover a folder target, a file target, `--accept`, and a sync that raises.

## 2. The size estimate counts what the vault grows by, on XFS too

**Today:** both routes of the estimate count the source's blocks: the walk (`get_unskipped_size_inodes()`, `lstat().st_blocks`) and `get_path_size()` (`du --block-size=1`).
- XFS's speculative preallocation can show a file just appended to at about 2.6 times its size in blocks, for minutes.
- Under a Backup Size Limit, the prune before a batch would then remove versions the limit didn't need gone.
- The two live jobs on XFS have limits (work 50G, docker_volumes 5G), and both are far from them today.

**The rule the suite already checks:** written ≤ estimate ≤ what the vault grew by. The estimate leaves out the folders' own blocks, a known limitation ("Size estimates leave out a version's own small blocks"), which stays as it is.

**The fix:**
- A regular file is charged what its copy takes in the vault: the smaller of its blocks on the source (holes stay holes) and its size rounded up to the vault's block size.
- The vault's block size is read once per batch, with `statvfs` of the job vault.
- Other entries are charged as today.
- **The walk replaces `du` on the other route,** so there is one route and one rule. That also closes the deferred entry "One du process per batch for the size estimate"; the main session removes it.
- It costs no more than today: no read of file contents, and no call on a file beyond today's.
- **The size records don't change.** A version's recorded size and the prune's books keep their measure.
- Tests that pin the estimate itself to the source's `st_blocks * 512` move to the new charge. Tests of the records stay as they are.

**Tests that fail on XFS today.** Some fail only some of the time, because the preallocation comes and goes with timing:
- `tests/test_estimate_through_a_take.py::test_file_rows_through_a_take[folder carried, file moved over-du]` and its `-walk` twin;
- `tests/test_moves_into_new_folders.py::test_the_size_estimate_counts_what_is_written_under_a_folder_moved_into_a_new_one[one file rewritten-walk]`;
- `tests/test_moves_then_changes.py::test_the_estimate_puts_back_what_is_written_under_a_folder_it_took_out[du]`.

The `-du`/`-walk` parameters may become one, as the routes do.

**Acceptance:** every test selected by `-k estimate` over the whole suite, plus every test in tests/test_estimate_through_a_take.py and tests/test_r_sizes.py, passes 20 runs in a row:
- on an XFS basetemp, in Docker;
- on an ext4 basetemp, in Docker with the basetemp under /srv/<run> on the host's root filesystem (ext4), removed after, or in the test VM.

A new test makes a file whose source blocks run well past its size, the way an append on XFS does, and checks the charge. A sparse file and a file smaller than a block are checked too.

## 3. A link the vault's filesystem refuses does not stop the job

**Today:** a source link whose text the vault's filesystem refuses (on XFS, 1,024 bytes and up, `ENAMETOOLONG`) fails every batch.
- `cp_af_copy_path()` runs the copy, `copy_failure_side()` gives `'vault'`, and `finish_copies()` raises a job failure.
- The job retries with waits doubling to 3,600 s, so no version commits while the link exists. The job recovers once the link is gone.
- A restore of such a link onto such a filesystem reports `FAILED <rel>` and exits 1. Everything else is restored, but the target stays private (mode 0700) and keeps its marker until a rerun with `--accept`. A rerun can never succeed for that link.
- This was shown by running the real 0.55.1 daemon in a container.

**The fix covers symlinks only.** A regular file whose vault path is too long still fails as today; it is no part of what the user approved.

**How the refusal is recognized:**
- cp's error line names the copy's partial file and ends with `os.strerror(errno.ENAMETOOLONG)`. cp runs with LC_ALL=C, and `cp_error()` gives that text.
- `lstat` of the source shows a symlink.
- This test runs before `copy_failure_side()` gives `'vault'`.

**Backup:**
- **One warning.** It names the link and says why: its text or its path is longer than the vault's filesystem takes. It comes whenever a batch meets the link, as for an unreadable file. A full comparison meets it again.
- **The batch goes on.** The new version records the link as absent, the way a delete in the tree is recorded, through the `TreeWriter` verb a delete uses. The previous version then keeps its own link, if it had one, and history stays browsable.
- **The row is discarded.** The manifest's row for it goes (`manifest.discard()`), as for a source that vanished.

**Restore:**
- The same refusal while a restore copies is reported by path with the reason: the target's filesystem can't hold a link that long. It does not get the rerun advice.
- The restore then finishes. The folders are handed over and the marker goes, so the target is not left private.
- The exit code stays 1. The README says 0 means everything asked for was restored, and this link was not.
- When the target is the link itself, nothing is put there, the line says why, and the exit code is 1.
- The README's restore paragraph says this in one sentence. The exit codes line stays true as written.

**This is a change to the restore's output and behaviour, so it is an API change.** In the same commit, add the entry to docs/lessons-full.md and its one line to docs/lessons.md. The design was wrong because a failure that no rerun can fix held the restored tree private, waiting for a rerun.

**Tests:**
- a backup with such a link, among other changes;
- the same with a stale entry of that name in the previous version, which keeps its link;
- a full comparison meeting the link;
- a folder restore and a file restore of such a link to a filesystem that refuses it.

Make the refusal with a fake where a real filesystem is not at hand. An XFS basetemp is the real one.

The live vaults are f2fs, which takes link texts up to 4,095 bytes, so no live backup meets this today.

## 6. Where tests run

Pytest never runs as root on the host. A host hook enforces it, and the rule holds for scripts the hook can't see.
- **Unprivileged and repeated runs: Docker.**
  - Flags: `--rm --init`; `--memory=24g` with no `--memory-swap` for a suite run with `-n auto`, or `--memory=8g` for a few test files or one probe; `--pids-limit=8192`. These are the values the round 22 and XFS-fix runs used without reaching them.
  - The code mounted read-only.
  - As uid 65534, or as root inside the container where a test needs chown. Never `--privileged` or `--cap-add`.
  - Tests that need `trusted.*` xattrs, mounts or scratch images are out of reach there.
  - The runner `<scratchpad>/xfs/run.sh` is an example; copy it before changing it.
- **Root, loop and mount tests: the reverberator test VM** (VM 904, reverb-test, being set up now; /root/.config/reverb-test/README says how to use it). That covers chown, `trusted.*` xattrs, tmpfs mounts, the `REVERB_SCRATCH` scratch images, mergerfs, and the `f2fs_io` power-loss tests.

## 9. A stop syncs on its way out, a kill copies everything again (fix round 6)

**Before this round:** the marker's "unsynced" held this boot's id and the target's mount ids, and a run again of the same boot and mounts kept what an earlier stopped or killed run had copied, syncing it with the rest through a newly opened fd. That is not safe. Linux reports a writeback error to an fd opened after the error only while no syncfs has seen it yet: `do_dentry_open()` samples `sb->s_wb_err`, and any syncfs by any process (the daemon's own vault flush on that disk, a `sync -f`) marks it seen. The run again then handed over, and exited 0, over a file whose bytes were lost. The same hole was in one run on a mergerfs pool, whose syncs opened each branch's folder at sync time.

**The user's picks, verbatim:**
- "Recopy after a kill (Recommended)": "Ctrl-C syncs through the restore's own open handle on the way out again (it waits for the disk; a second Ctrl-C stops at once). A kill, crash or power cut always means the rerun copies everything again. The boot and mount record goes: less code, never wrong data. This replaces the remount entry you just approved with "a killed restore copies everything again"."
- Then a correction, as "a second Ctrl-C stops at once" was wrong (the kernel finishes a syncfs's writeback waits, which are uninterruptible, before any signal acts, SIGKILL included): "Wait for the disk (Recommended)": "The first Ctrl-C prints that it is writing what was restored out to disk, waits for that, then stops; a rerun keeps what is there. Nothing cuts the wait short. Simplest: no new parts."

**What it is now:**
- Every sync of a run goes through handles opened once, before the first copy: off a pool the claim fd (a file target's folder, opened before the copy); on a pool an fd of a branch of each disk, the branch itself and not the target's folder on it, so a copy that lands on a disk the target was not on at the claim is covered. A disk none of whose branches the user can open is the existing warning, once per restore.
- A run stopped by a signal before its own sync, and not a recopy, says on stderr that it is writing what was restored out to disk, syncs through those handles, and drops the record on success (a run again keeps what is there) or records recopy 'sync failed' on failure. A stopped recopy keeps its recopy and needs no sync.
- "unsynced" is written as `true`, and any value reads as unsynced (the boot-and-mount strings of earlier 0.55.2 builds too): a run again reads it as recopy 'cut', and --accept is refused with exit 2.
- The Interrupted line says what a run again does: pick it up or --accept after a stop whose sync succeeded (or right after the run's own sync), copy everything again after a stop whose sync failed or a stopped recopy.

**Why:** an fd opened before the first copy always hears of a writeback error since, once; no run can tell afterwards whether a killed run's copies reached the disk. The cost of a kill is the time of a full copy, never wrong data; docs/limitations.md, "A killed restore copies everything again", has it with the user's OK. 0.55.1 never wrote "unsynced", so nothing released changes.

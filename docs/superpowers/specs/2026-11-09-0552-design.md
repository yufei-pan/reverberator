## Why now

On 2026-11-08 the filesystem holding /mnt/optane, and with it /tmp and two live jobs' trees (work, docker_volumes), moved from ext4 to XFS. That brought two daemon findings and 17 suite failures. A durability check for that move also found an older gap in the restore.

## 1. A restore syncs before it ends

**Today:** a restore puts new files in place and syncs nothing. A hard reset within the writeback window can leave restored files empty, with no marker to say the restore did not finish. ext4 and XFS have the same window. This is older than 0.55.

**The fix:**
- At the end of each restore, one `syncfs` of the target's filesystem (`syncfs_folder()`).
- For a folder target, it comes before the restore marker is removed in `hand_over_folders()`. For a file target, it comes before the command returns.
- On a mergerfs target, whose own sync does not reach the disks, it syncs each branch holding the target, as `sync_vault_filesystems()` does for a vault.
- A `syncfs` error is a failure of the restore: the marker stays, as for any failure.

**Test:** record the calls, and check that the sync comes before the marker's unlink and, for a file target, before the command returns.

## 2. The size estimate counts what the vault grows by, on XFS too

**Today:** both routes of the estimate count blocks: the walk (`get_unskipped_size_inodes()`, `lstat().st_blocks`) and `get_path_size()` (`du --block-size=1`).
- XFS's speculative preallocation can show a file just appended to at about 2.6 times its size in blocks, for minutes.
- Under a Backup Size Limit, the prune before a batch would then remove versions the limit didn't need gone.
- The two live jobs on XFS have limits (work 50G, docker_volumes 5G), and both are far from them today.

**What the build must keep:**
- The estimate is at or above what the vault grows by, for sparse files and small files too.
- The inode count is exact.
- It costs no more than today: no read of file contents, and no call on a file beyond today's.

One way, the fixer's proposal:
- On the walk route, charge a regular file the smaller of its blocks and its size rounded up to the block.
- On the other route, use `du --apparent-size`, or the walk in place of `du`.

The builder picks, with the reason.

**Tests that fail on XFS today.** Some fail only some of the time, because the preallocation comes and goes with timing:
- `tests/test_estimate_through_a_take.py::test_file_rows_through_a_take[folder carried, file moved over-du]` and its `-walk` twin;
- `tests/test_moves_into_new_folders.py::test_the_size_estimate_counts_what_is_written_under_a_folder_moved_into_a_new_one[one file rewritten-walk]`;
- `tests/test_moves_then_changes.py::test_the_estimate_puts_back_what_is_written_under_a_folder_it_took_out[du]`.

**Acceptance:** every estimate test in the suite holds on XFS every time, not only these. Run each 20 times on XFS and on ext4, in containers, with no failure.

## 3. A link the vault's filesystem refuses does not stop the job

**Today:** a source link whose text the vault's filesystem refuses (on XFS, 1,024 bytes and up, `ENAMETOOLONG`) fails every batch.
- `cp_af_copy_path()` runs the copy, `copy_failure_side()` gives `'vault'`, and `finish_copies()` raises a job failure.
- The job retries with waits doubling to 3,600 s, so no version commits while the link exists. The job recovers once the link is gone.
- A restore of such a link onto such a filesystem reports `FAILED <rel>` and exits 1. Everything else is restored, and the target stays at mode 0700 until a rerun with `--accept`.
- This was shown by running the real 0.55.1 daemon in a container.

**The fix.** The user approved leaving the link out as a known limitation.
- **Backup:** a source link whose copy into the version is refused with `ENAMETOOLONG` is left out of the version, and the batch goes on.
  - One warning names it and says why: its text or its path is longer than the vault's filesystem takes.
  - The warning comes whenever a batch meets the link, as for an unreadable file.
  - If an earlier version held that name, the new version does not show the old link: the entry is absent from the new version.
- **Restore:** the same refusal during a restore is a warning in its report, as for metadata it cannot keep. The restore finishes and exits 0.
- **Tests:** both sides, with a stale entry of that name in the previous version among them.

The live vaults are f2fs, which takes link texts up to 4,095 bytes, so no live backup meets this today.

## 6. Where tests run

Pytest never runs as root on the host. A host hook enforces it, and the rule holds for scripts the hook can't see.
- **Unprivileged runs and repeated runs:** Docker, with `--rm --init --memory=Xg` and no `--memory-swap`, `--pids-limit`, `--user 65534:65534`, the code mounted read-only, and the basetemp on XFS.
- **Root, loop and mount tests:** the reverberator test VM (VM 904, being set up now). That covers chown, `trusted.*` xattrs, tmpfs mounts, the `REVERB_SCRATCH` scratch images, mergerfs, and the `f2fs_io` power-loss tests. Until the VM is ready, the builder runs what Docker can and says what is left for the VM.

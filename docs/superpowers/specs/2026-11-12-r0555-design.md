## 1. A cut batch's tree is made version n's again, at the scan (F1)

**Today.**
- `prepare_roll_forward()` (7022), at the scan, returns what the cut batch recorded in the previous version, version n (`give_back_folder_times()`, 6894: real folders, files and links, each of the kind it was), and marks the rows of the recorded files unchecked in a transaction of its own (`VaultManifest.mark_unchecked()`, 9072).
- `roll_forward_entries()` (7080) copies again each recorded name whose monitored path is a regular file now (`again`), trusted by the comparison and replayed as a modify.
- A recorded name it does not copy again keeps the cut batch's copy in the tree with an unchecked row: a file under an inner mount paused at the retry, one whose mount goes during the roll-forward's walk (`drop_unmounted_entries()`, 5769, drops the forced modify), one in a folder the walk cannot read (its rows are kept), and a name of another kind under a paused mount.
- The next full comparison that can see it reads it back by size, mtime and last 64 KiB. A copy all NUL that ends in 64 KiB of zeros passes; so does a page lost before the tail, and without a reboot the read comes from the page cache. Those are the three entries.
- What the cut batch made (a create, a move's target) has no record. The comparison finds it in the monitored tree and copies it again; when its source cannot be read at the retry, the cut copy stays as its last backed-up copy, its row recorded from it, and a damaged middle is never seen (the design re-check's run N4 on main).

**The change: make the tree version n's again before anything is compared.**
- A new scan step, `put_back_recorded(previous, tree, recorded)`, runs in `prepare_roll_forward()` right after `give_back_folder_times()`. It runs under the scan's locks and inside its VaultUnit (`get_vault_info()`, 7518), at every scan that finds a tree, before the attempt reads a row. In three passes:
  1. **Every recorded name gets version n's entry back,** in `recorded`'s order (a folder right before what is in it):
     - **a file or a link of version n:** whatever the tree holds there goes (`remove_entry()`), and `link_or_copy(kept, tree's place)` (12618) puts version n's entry there, a link as itself. Off a pool, nothing is done when the tree's entry is that inode already (same `st_dev` and `st_ino`). On a pool there is no such shortcut: every recorded file and link is unlinked and linked again, as mergerfs computes the `st_ino` it shows, and after a cut each disk comes back at its own point, so the cut copy can stay on one disk behind version n's link on another;
     - **a real folder of version n:** nothing when the tree holds a real folder there; otherwise whatever the tree holds there goes, and a folder is made there (`os.mkdir()`). Its entries are recorded names of their own, which come back one by one after it: `record()` (13111) recorded such a folder whole (exchanged in, or every entry kept by a link) before the tree's folder could be replaced or removed.
  2. **What the cut batch made goes, when the manifest describes the previous version.** In each recorded folder of the tree, and in its root, every entry whose name the previous version's folder does not list goes (`remove_entry()`): a create, or a move's target. A real folder of the previous version lists every entry the tree held when it was made real, and every new entry has one as its parent (`TreeWriter.make_folders()` makes it real first, as `new_in_tree()`, 7150, already relies on). Pass 2 rests on the previous version listing every entry the tree should keep. That holds once `put_back_forward_links()` (7000) has given back a forward link that a cut between two renames left in staging (`TreeWriter.exchange_in()`, 12996, on a pool or a filesystem with no exchange), and that step needs the manifest's rows: it runs only when the manifest describes the previous version (7039-7040). So pass 2 runs only then. Over a lost manifest the tree's entry at such a name is version n's own, which pass 2 would remove, with all under it for a folder (the re-check's run N5), so `new_in_tree()` stays, as on main.
  3. **Then, innermost first,** each recorded folder in the tree gets version n's folder's metadata (`copy_file_meta()` from the previous version's folder), as the links made in it moved its times and the cut batch may have changed its owner or mode. Version n's folder metadata is the previous version's, whose mtime `give_back_folder_times()` has just given back. A metadata copy that fails raises JobFailure, as `copy_folder_meta_onto()` (13018) makes of `copy_file_meta()`'s `failed` list, and the next attempt puts back again.
- On a pool the put-back ends with `forget_pool_cache(tree)` when it changed anything, as `remove_mixed_names()` and `put_back_forward_links()` do (6918-6923), so the next look at the tree (`read_rows_from_tree()`, the comparison) does not see an entry as it was for about a second.
- So once the scan returns, with the manifest standing, the tree holds what version n holds, and the comparison finds every change since version n, what the cut batch did included. A create whose source cannot be read at the retry is left out with its UNREADABLE line, as an unreadable file is, not kept as a possibly damaged cut copy (run N4). Over a lost manifest the tree keeps what the batch made, `new_in_tree()` finds it and the roll-forward copies it again, as on main; one whose source cannot be read keeps the cut copy, as on main: deferred with "A lost manifest stops an unmounted inner disk being paused" (section 10).
- **No staging and no rename.** The tree is no version until its commit; between the scan and the commit nothing reads it but the scan and the batch after it, and a restore of version n never reaches a recorded name through a forward link, as every folder above one is real in version n (status, history and restore never run the scan: `list_versions()`, 14266). A cut during the put-back leaves the previous version as it was, so the next scan computes the same `recorded` and puts back again; a name left empty between its removal and its link is linked then. A cut later, during the roll-forward's replay, may have recorded more names in the previous version (the replay records before it changes the tree: `TreeWriter.copy()`, 13209), each of them version n's own entry, which the next scan puts back too. A tree whose only entry was unlinked and not linked yet is judged a skeleton by the scan (7400) and removed, and version n stands whole (the re-check's run N2). On a pool the link goes through the pool, as `put_back_forward_links()`'s links do, and `link_or_copy()` copies where the pool answers EXDEV between its disks.
- **Where hard links are refused** (`NO_HARD_LINK_ERRNOS`, 11401: EMLINK, a FUSE or network filesystem, EXDEV between a pool's disks), `link_or_copy()` copies: a new inode holding the record's bytes. When any put-back copied, the scan flushes the vault's disks through its own unit (`flush_or_fail()`) before it returns, so those copies are on the disk, heard through handles opened before they were written, before the attempt goes on. A failed flush raises JobFailure, which fails the scan and the attempt with it, and the next attempt puts back again. What this costs on such a vault is in the widened entry "A copy made where the vault refused a hard link" (section 10).
- **Order in `prepare_roll_forward()`:** `remove_shadowed_links()`, `put_back_forward_links()`, `remove_mixed_names()`, `give_back_folder_times()`, `put_back_recorded()`. The transaction with `mark_unchecked()` goes, and `VaultManifest.mark_unchecked()` with it. `prepare_roll_forward()` returns `recorded` as before.
- **tests/test_tree_writes.py:** `USERS` gains `'put_back_recorded': {'remove_entry', 'copy_file_meta'}`, a scan step that writes the tree directly before any writer runs, as `remove_mixed_names()` does.
- **What stays in the roll-forward:**
  - `read_rows_from_tree()` (7048), which now reads the tree after the put-back: the row of each recorded name reads version n's entry, so nothing reads rows a second time;
  - the forced modify of each recorded name whose monitored path is a regular file (7123-7127): only it carries a change of the cut batch that a comparison cannot see (a rewrite at its size with its mtime set back);
  - the trusted set for those names (7117): it leaves their contents to that copy. Without it an attribute difference found at one would take the copy's place in `found` (the `again` loop passes over a path already found), and under Only Sync Attributes the replay would sync its metadata only.
- **What goes from the roll-forward:** with F3, the saved entries `given` (7128-7135, section 3). `new_in_tree()` (7150) stays, for a lost manifest (pass 2 above).
- **What it covers, with no case of its own:** a paused mount at the retry, a mount gone during the walk, a folder the walk cannot read, a name of another kind (a link, or a folder, that a file replaced, or the other way round), a move under a paused mount (the design review's probe B: `mv disk/a disk/b`, cut, retried paused, left the version with neither), a create whose source cannot be read at the retry (run N4, the manifest standing), and any later reason a recorded name is not replayed. Each holds version n's entry, under version n's row, or nothing where version n held nothing.
- **What it does not cover.** A change only the watcher saw, at a name the retry does not copy again: a rewrite under an inner mount that keeps its size, mtime and last 64 KiB, its batch cut, the mount paused at the retry. The newest version keeps version n's bytes until the file changes again, with no line (the re-check's finding 1; main kept the cut copy). The user's pick: a sentence in "A rewrite made while down that keeps size and mtime" (section 10). Over a rebuilt manifest no inner mount is remembered, so none is paused (the deferred entry of section 10).

**Why it is right (crash safety).**

| State a stop, a kill or a power cut leaves | How the next start finishes it |
|---|---|
| Cut inside the put-back: a name emptied and not linked yet, a folder made and partly filled, its metadata not given yet, or a create not yet removed | The previous version is unchanged, so `recorded` is the same; the next scan links what is missing, leaves what is version n's already (off a pool), removes what the batch made, and gives every recorded folder its metadata again |
| Cut after the put-back, before the commit | The next scan finds version n's entries there; off a pool it leaves them, on a pool it links them again |
| Cut during the roll-forward's replay, with more names recorded | The next scan puts back those too, each version n's own entry |
| Power cut with some of the put-back lost | One of the states above |
| Committed | Each recorded name the roll-forward does not copy again holds version n's inode, whose bytes version n's commit flushed (or, on a vault that refuses hard links, a copy of the record the scan flushed), under version n's row, read from that entry; each one it copies again holds the new copy, flushed by the roll-forward's commit flush |

- Version n keeps its record at a name put back: a real entry, the tree's inode (or the copy's original where hard links are refused). It reads right, and `measure_previous()` (7199) counts a shared inode for the tree only. V(n+1)'s change list does not name it, as V(n+1) holds there what version n held; the roll-forward's own entries, copies again included, are listed as today.
- The roll-forward always runs the commit flush (`do_backup()`, 6134).
- Nothing vouches for bytes no flush of their own unit covered, so a write error another program's sync saw has nothing left to hide.

## 2. A pool vault's handles open where the job vault is (F2)

**Today.** `VaultUnit.__init__()` (1967) opens, on a pool, an fd of each branch's root (`open_branch()`, 2019). `holding()` (2035) picks a handle by the `st_dev` of the job vault's folder on each branch, and raises `not_opened()` when no handle has it. A job vault folder on a branch that sits on a filesystem of its own (a mount nested under the branch, a btrfs subvolume) has a `st_dev` no handle has, so every sync raises and every attempt fails.

**The change.**
- `open_branch()` opens `os.path.join(branch, self.rel)`, or, when that is not there, its nearest existing parent, never above the branch.
- Branches whose handles share a `st_dev` keep one fd, as today.
- `holding()` is unchanged. A job vault folder made on a branch later lands on the filesystem of the nearest parent that existed, so its `st_dev` matches. A mount made at a folder on the way since the unit began has a `st_dev` no handle has, and `holding()` raises, as it does for a joined disk.
- **The restore takes the same rule.** `open_restore_disks()` (16095) opens each disk's branch root (`vault_disks(folder, roots=True)`), one handle per disk name. For a target whose folder on a branch is a nested mount, `syncfs` writes out the branch root's filesystem, not the one holding the target, and the restore says done. Now:
  - on each branch it opens the restore folder's place, or its nearest existing parent, never above the branch;
  - it keeps one handle per filesystem, by `fstat().st_dev`, as the daemon's unit does, with a disk's name kept for its messages (a disk whose branches lead to two filesystems gets two handles);
  - **`sync_restore()` syncs every handle,** in the daemon's shape (`sync_vault_filesystems()`, 2118, which keys the handles by their index for `sync_each_disk()`). Today `sync_each_disk()` (1941) groups the handles by disk name and `sync()` takes only `handles[0]` (16170): with two filesystems under one disk name, the second is never synced, and an OSError after an fd is never seen (the re-check's finding 3);
  - a branch the user cannot open is warned of once (`report.cannot_sync()`) and left out, and one that fails otherwise keeps its OSError for its syncs to fail with, as today;
  - `sync_restore()`'s check for a disk that joined goes by filesystem too, as `holding()` does: each branch the pool lists at the end whose folder is there (`os.stat()`) on a filesystem no handle is of fails the restore, as a joined disk does today. A branch left out at the claim as one the user cannot open is passed over, as today. This also catches a mount made at the folder's place on a branch while the restore ran, which today's check by disk name misses.
  - This is beyond the entry: Calls to confirm.

**Why it is right.** Linux reports a filesystem's writeback error to a syncfs through any fd of that filesystem opened before the error (the flush spec, section 2). An fd at the job vault's own folder, or at its nearest existing parent, is an fd of the filesystem that holds or will hold it. Nothing is stored; a cut closes the fds with the process.

**Tests** (each fails on main):
1. tests/test_pool_writer.py (or the flush round's tests/test_vault_units.py), on `harness.FakePool` with the errseq stand-in: a branch whose job vault folder is a symlink to a folder on /dev/shm, a stand-in for a nested mount, as `os.open()` and `os.stat()` follow it to another `st_dev`.
   - A batch commits (main fails with "is not on a filesystem this step opened").
   - `fail()` and `seen_elsewhere()` on the /dev/shm folder between the copies and the commit flush: VAULT WRITE ERROR, nothing commits. This pins that the handle is on that filesystem.
2. A branch whose folder above the job vault (`<branch>/mnt`) is a symlink to a folder on /dev/shm, the job vault below it missing on that branch when the unit opens, then a copy landing there: the sync goes through the handle opened at `<branch>/mnt`, with no error. Main raises, as its handle is the branch root's, on another filesystem.
3. A restore onto a FakePool target whose folder on a branch is such a symlink: `fail()` on /dev/shm, and the restore's sync reports the write error. Main says done.
4. Two branches under one mount point (one disk name), the restore folder's place on the second a symlink to a folder on /dev/shm, `fail()` there: the restore reports the write error. It fails with a sync that takes a disk's first handle only.
5. A restore during which the restore folder's place on one branch becomes a symlink to a folder on /dev/shm, a copy landing there: the restore fails, naming the disk. Main says done.
6. **The test VM:** the same as test 1 with a real tmpfs mounted at the job vault's folder on a branch of a real mergerfs pool; and test 3 likewise.

**Cost.** None off a pool. On a pool of B branches: B opens at a deeper path (a few more path components looked up), once per unit; a restore's check stats the folder on each branch once, as today.

## 3. Every start is one full comparison: the pending file goes (F3)

**Today.**
- At a stop, the backuper hands the batch it has not committed back to the queue (its `finally`, 5150-5159: `prepend()` of `backup_entries_to_change_events()` and `scan_events()`, or a full scan request), and writes the queue to `.reverberator_pending_transactions.nsv` in the job vault (`persist_pending_transactions()`, 6345, through `pending_transaction_rows()`, 6317; called at 5165-5166). A failed job's queue is saved as a full scan request at the daemon's stop (`persist_failed_job_queue()`, 1518, run by `run_job()`'s `persist_pending`, 1416-1417).
- At a start, once the skip list is loaded and the watches are in place, `load_pending_transactions_for_resume()` (3786) walks the whole monitored tree (`get_monitor_path_most_recent_change_time()`, 3884) and replays the file when the tree's newest mtime is at least 1 s older than it, as a `round_tripped` batch (4992-5014). Its version commits, and `follow_up` (5088-5100) then compares the whole tree, a second version when anything changed while the daemon was down. Without a pending file, the start appends a full scan (5012-5014), one version.

## 4. A batch whose every entry drops out is compared as one with none (F4)

**Today.** An entry the replay cannot apply is left out at the copy (`finish_copies()`, 8108):
- an unreadable file keeps its last copy, with an UNREADABLE line;
- a symlink whose text or path the vault's filesystem refuses is left out, with a NOT BACKED UP line (`link_too_long()`, 8088).

By then the tree is handed over, so the batch commits a version that changes nothing. A full comparison meets the same entries every time (the unreadable file's row keeps its old record; the left-out link has no row), so each start, interval or overflow makes one more empty version. Under Keep N each pushes the oldest out. An event batch of such a file alone does the same at every write.

**The order of `do_backup()`'s drops,** for every batch with no tree to roll forward (with F3, every such batch is a fresh one: an event batch, a collapsed one, a batch from compared scan folders, or a full comparison). Today the paused drop is an `elif` after the comparison of an empty batch (6004-6011), so a batch it emptied returned "No differences" with nothing compared:
1. the paused drop (`drop_entries_under()` of the paused folders), moved up from its `elif`;
2. `drop_untracked_deletes()` (4577), after the paused drop, as that drop can add a delete: a move into a paused folder deletes its source (4613), which may be a path with no row. Over a manifest that does not describe the newest version (the first batch after a lost manifest; today step 2 does not run then, 5966), a delete is dropped when the newest version holds nothing at its path (an lstat there: the newest version is the real tree);
3. the check below; a batch whose every entry drops out is cleared;
4. a batch with no entries. One that came with no entries is compared as today: the places it touched, or the whole tree for a full comparison (no touched scopes). One that came with entries and lost them all at any of steps 1 to 3 is compared at the places it touched, when it came with touched scopes, or takes the no-differences path at once when it came with none (a batch of compared scan folders, `compare_scanned_folders()`, 4834, whose entries were a comparison's result already; main takes no-differences there too, the re-check's run N3). `drop_unmounted_entries()` and the check follow a comparison, and a batch whose every entry it then drops is cleared;
5. only then the no-differences path.

**The check.** The check stops at the first entry that would change the version, in three passes, cheapest first:
1. A delete or a move: it changes the version. No syscall.
2. Every other entry (a create, a modify or an attrib, of a folder too): an lstat of its monitored path:
   - a folder: it changes the version (a folder's entry makes it or gives it its metadata; a file's entry whose path is a folder now is replayed as that folder);
   - a regular file `source_readable()` (7885) opens, or an entry of another kind (a FIFO, a socket, a device, which cp -a copies as itself): it changes the version;
   - a regular file it cannot open, or a path that cannot be looked at: it drops out, as the copy keeps the last copy. Under Only Sync Attributes an attrib of such a file drops out the same way: its record cannot vouch (the tail cannot be read), so the replay copies it, and the copy keeps the last copy (the design review's probe D);
   - a path gone: it drops out, as the replay passes over it; what it touched is compared at step 4;
   - a symlink: pass 3.
3. Only if every entry is still in doubt, each symlink entry is probed. It changes the version when the newest version (`latest_version_info.path`, the tree before the hand-over) holds an entry at its place, as leaving it out then removes that entry. Otherwise it changes the version unless the vault refuses its text: `os.symlink(text, <staging>/.link-probe-<uuid>)` answers ENAMETOOLONG. Before its first write the probe calls `pool_guard.require()`; staging is made when it is not there (`os.makedirs(exist_ok=True)`), and the probe is unlinked at once. Any other error counts as "would change", and the copy says what it is.
- **When none would:** each entry is logged as the copy or the replay would log it, with the same UNREADABLE or NOT BACKED UP line (once per batch through `reported`), or, for a path gone, the replay's own line, and the batch is cleared (steps 3 and 4 above). The no-differences path, with `reported` set, leaves the matched time where it is and, after L1, writes nothing.
- When one would, nothing changes from today: the others drop out at the copy as before.
- **A link whose path the vault refuses is left out of the check.** The copy writes a link under a temporary name in its folder (`partial_copy_path()`, 7728: a dot, 32 hex digits and `.reverberator-partial`, 54 bytes), and the vault refuses that path once the folder's full path in the vault reaches 4,041 bytes (measured on the host: Linux's path limit is 4,096 bytes with its terminating NUL, and the name adds 55 with its slash), whatever the link's own name. The probe sits in staging, at a shorter path, and the user's pick keeps a length check out ("Leave that case out (Recommended)"). Such a link, in a folder that holds no regular file (one would fail every backup, 8093), still makes one empty version per full comparison: the narrowed known limitation of section 10.

**Why it is right.**
- Each dropped entry is one the replay would have left as the version holds it. An unreadable file keeps its last copy, and a refused link with nothing at its place leaves nothing.
- A batch whose entries all dropped out is still compared where it touched: a change its collapse hid is found there, as main's verification finds it. The design review's probe H: a create of a file gone since, beside `create tmp; mv tmp f; rm f` with f in the vault, collapses to the create alone; the comparison of the touched places finds f deleted.
- A batch of compared scan folders whose entries all drop out is not compared again: its entries were that comparison's, and comparing it again as a batch with no touched scopes would walk the whole tree (the re-check's finding 5).
- A file readable at the check and unreadable or gone at its copy still makes one empty version: the narrowed known limitation the user accepted ("Accept the race (Recommended)", section 10).
- The probe writes only into staging, and only for a batch made of unreadable files and links. No restore reads staging; the scan's pool repair lists it (`repair_pool_vault()`, 7328) and `empty_staging()` (6875) clears it, and both take a probe as any leftover. The probe, and staging's mkdir, come after `pool_guard.require()`, as the no-differences path's first write does (6016), so nothing is written while a disk of the vault's pool is out; they change the vault before `locks.take()` (6040), as the comparison's manifest commit does already. The locks keep restores from reading the versions while they change, which the probe does not touch; the comment at 5854, "held from before anything in the vault is changed", is reworded to say that.
- No state is kept.

**Tests** (each fails on main unless marked a pin), in tests/test_long_links.py and tests/test_io_errors.py:

**Docs.** The entry narrows (section 10). ## 5. The lightness items

### 5.1 A batch with nothing to do commits nothing (L1)

**Today.** A batch whose events collapsed makes two sqlite commits and 10 fdatasyncs, in 321 syscalls:
- `delta_generate_backup_entries()` commits naming the version (10818), and `VaultManifest.commit()` (8809) always writes the `version` meta row;
- the no-differences path (6012-6023) then writes the skip fingerprint, the inner mounts and the matched time and commits again, whether they changed or not. `record_matched()` (8857) carrying the time over rewrites the same row.

**The change.**
- `VaultManifest.commit(version_path)` writes the `version` row only when it names another version. A transaction that wrote nothing to the main database then commits with no I/O: a probe with Python's sqlite3 in TRUNCATE mode left the header's change counter (bytes 24 to 27) and the journal file as they were across a transaction of reads and writes to a temp table (as `seen` is), and moved the counter for an `INSERT OR REPLACE` of the same value, which is what `commit()` does today (run again on sqlite 3.46.1 by the design review and a second opinion). Test 1 checks it on the real path.
- `set_skip_fingerprint()`, `set_inner_mounts()` and `record_matched()` write only a value that differs from the one recorded.
- **The matched time.** On the no-differences path it moves only when a full comparison ran: the batch came with no entries and no touched scopes, and step 4 of section 4 compared the whole tree. A batch of compared scan folders cleared by section 4's check has no touched scopes either, and does not move it. A collapsed batch with no difference leaves it where it is: an older matched time is always true, and only widens the next full comparison's extended-attribute bound to the entries changed since then. Any committed version moves it as today.
- So a collapsed batch that reads nothing back commits nothing. One that reads a copy back commits that record, as it must.

**Why it is right.** Fewer writes, nothing new kept. A cut finds what the last commit left, and every value it carries is still true. The matched key's rule stays: "written only by `do_backup()`'s commits" (8852-8856).

**Tests** (each fails on main unless marked a pin):
1. A batch whose events collapsed (a file made and removed): the header change counter unchanged, and the journal file's size and mtime unchanged.
2. A full comparison with no difference: one commit moves the header change counter, the matched time's, and the matched time moves. Main makes two that move it (the comparison's commit rewrites the `version` row, then the no-differences commit).
3. Pin: a collapsed batch whose scope holds an unchecked copy commits its record.
4. Pin: a skip list change still commits its new fingerprint on the no-differences path.

**Cost.** Two commits (about 10 fdatasyncs) less for each collapsed batch, one for a no-difference full comparison.
- **Measure in the test VM:** `strace -f -c -e trace=fsync,fdatasync,syncfs` over 20 collapsed batches of the daemon, main against the branch.
- 20 batches show that the count per batch is the same every time, as it should be: it is set by the code path, not by timing.

### 5.2 No folder fsyncs off a pool after the commit point (L2)

**Today.** After the manifest's commit (6167), `do_backup()` fsyncs the job vault after `swap_current_version()` (6172), and `place_change_list()` (2155) fsyncs it after the rename. Each is an f2fs checkpoint: a one-file batch writes 455 KiB with 5 checkpoints, 418 KiB with 3 without them. A failure of the first fails the attempt with the list still in its private folder.

**The change.**
- In `do_backup()`, both fsyncs run only when the job vault is on a pool. `on_pool` (`pool_guard.covers(job_vault)`) is asked once, before the split between the first version's path (5898-5951) and the others, as both reach the commit section (today it is asked inside the second only, at 6066).
- Off a pool there is no fsync, and with it no mount table read (`fsync_vault_folder()`, 1878, reads one through `vault_disks()`).
- `place_change_list()` takes `sync`, which `do_backup()` passes as `on_pool`.
- `finish_r_commit()` (6851), the scan's finish of a commit a cut stopped, keeps both fsyncs on every filesystem: it runs once after a crash, and on a pool it is the step that puts the swap on its disk before the list is placed.

**Why it is right.** Once the manifest has committed V(n+1), a power cut can leave any mix of these, and the scan settles each:

| After the power cut | The scan |
|---|---|
| current_version still names V(n) | `move_current_version_forward()` |
| the list still in its private folder | `finish_r_commit()` places it |
| the previous list under its old name | `finish_previous_list()` renames it |

- The one state the scan refuses is a list that is nowhere: the private folder's removal kept and the rename that placed the list lost.
- A power cut leaves the state of one instant, a prefix of the batch's steps, and the removal comes after the rename. Keeping the removal without the rename would be the filesystem losing a file from a folder in use. On one filesystem that cannot happen:
  - ext4's and XFS's journals commit metadata in order;
  - an f2fs checkpoint is a snapshot of one instant, and its roll-forward recovery replays only fsynced files, never a folder's removal.
  - The sweeps below run it on all three.
- The manifest's commit stays durable without the folder fsync: sqlite syncs its journal file itself, as the vault database is opened (8657; reasoned by the re-check, and the `just_before` sweep runs it).
- Before the commit point nothing changes: the change list's fsync, in a new private folder, is an f2fs checkpoint, which puts every change of the tree on the disk before the manifest's commit, as today.
- On a pool each disk keeps its own order, so both fsyncs stay.
- A vault on btrfs stays under its known limitation, "Vaults on btrfs": the crash promise does not cover it today, and nothing here is run there.

**What the operator sees: a known limitation, approved** (the user's pick of 2026-11-13, "Accept it (Recommended)"; the entry in section 10). Off a pool nothing after the commit point is fsynced. After a power cut within the filesystem's checkpoint interval (measured in the test VM, task 6; f2fs's default is 60 s):
- that backup's version is missing from status, history and restore until the job's next start scans the vault and places its list (`finish_r_commit()`): `list_versions()` (14266) leaves out a version folder with no change list;
- a restore run by hand offers the version before as the newest, and it reads right, through its forward links;
- status reads the vault's size low until then;
- a write error on that last sync is reported at a later sync instead of failing that batch (a sync through a handle opened later hears an error no other sync saw first: VaultUnit's docstring);
- a job that never starts again (removed from the rules, its disk read on another system) never lists it;
- at most one version is hidden, as each batch's list fsync puts the one before on the disk. Nothing is lost.
- A kill at that step leaves the same state today; L2 widens it to a power cut.

**Tests:**
1. Docker (fails on main): an off-pool one-file batch makes no `fsync_vault_folder()` call and no mount table read after the manifest's commit; a first version (V0) off a pool makes none either.
2. Pins: on FakePool both are made, a first version's included; a scan finishing a commit a cut stopped (`finish_r_commit()`) makes both, off a pool too.
3. **Power-loss, the test VM:**
   - `REVERB_CRASH_FULL=1` over `test_every_step_survives_a_power_loss` and `test_every_step_survives_a_power_loss_after_a_checkpoint` (`midway` and `just_before`), both `only_sync` values, every step, including the ones after the commit;
   - plus `test_a_power_loss_that_keeps_the_placement_and_loses_the_rename_is_finished`;
   - all must pass, with the row oracle of 5.3.
   - Over all its steps, the `just_before` sweep checkpoints the disk at every point of the batch and cuts one step later, so each state a checkpoint taken at any moment can keep is met, the ones after the commit point included.
4. **The same sweep on ext4 and on XFS, the test VM,** a gate of its own. The sweep takes the image's filesystem as a parameter (tests/scratch_images.py's `LoopImage` gains `mkfs.ext4` and `mkfs.xfs` beside `mkfs.f2fs`; only `LoopImage` and `needs_f2fs` there are bound to f2fs). The shutdown ioctl, `_IOR('X', 125, u32)` with flag 2 (no log flush), is the same call on all three, as the design review found. These runs also test design R's premise that the manifest's fsync carries the earlier renames on ext4 and XFS, which 5.3 leans on and the README so far only reasons.
5. Pin: the pool cut test (tests/test_pool_cut.py, the VM) still passes.

**Cost.** Two checkpoints and 37 KiB of the 455 KiB less for each committed batch on the live vaults.

### 5.3 A move keeps its rows' records, and moves them only once the rename is made (L3, L7)

**Today.**
- `VaultManifest.move_tree()` (9029) and `move_file()` (9044) leave the moved rows unverified (`UNVERIFIED`, 8714, which also clears the dirty mark), so the verification reads each moved file back: lstat and 64 KiB. A rename of a folder of 2,000 files read 263.3 MB for a change that wrote 0.1 MB.
- `do_reverb_backup()`'s move branch moves the rows before `TreeWriter.rename()` (13238): "the move's rows are at dst already", so `rename()` records dst with `rows=False`. For a file moved onto an empty folder it also removes that folder's rows before the rename (`manifest.remove_tree()`, 14008-14009).
- When the rename falls back to a copy, the target's rows are already gone. A record of the target, or of a folder above it, sized from its rows (`folder_usage()`, 13101, `rows=True`, as `remove_now()` from the sweep and `remove_queued()` call it) then counts too little, and the version before keeps a change list that says too little. The design review's run of fuzz seed 254, lists checked, shows it: `move_tree(c/n1/t/a/t/n2/n1/ -> c/n1/t/a/t/s/b/)` found no row under the source and wiped 6 under the target, the rename fell back, and `c/n1/t/a` was sized from its rows at 31,712 bytes and 48 inodes, where a walk gives 42,908 and 55; V20's list was short by 10.93 KiB and 7 inodes. Seed 4444 fails the same way; 372, 4492 and 14224 passed in that run.

**The change.**
- **Records follow their inode.** `move_tree()` and `move_file()` change the path. A row the batch has not written (not dirty) keeps its record and its unchecked flag. A row the batch wrote (dirty: a copy's row with no record, or one the replay vouched for with `mark_vouched()`, 9000) loses its record and dirty mark when it moves (`UNVERIFIED`), so the verification reads it back at its new place, as on main (ruling R36, which replaced R34's narrower rule: a copy's dirty row kept its mark and the verification, which trusts a dirty row for presence only, never read it back, so fuzz seeds 614 and 483 put wrong bytes in the version; and a vouched row's mark carried through a move is reached by no collapse order, and kept old bytes when the order was forced). A moved file whose attributes the replay syncs after its move is marked vouched there. A moved folder's own row is still added again (`manifest.add()` after the move), as its metadata is synced. `mark_vouched()`'s docstring changes: `add()` and a move of a dirty row wipe a record, a move of a committed row carries it.
- **Rows move, and are removed, only after the rename.** The replay calls `move_tree()` / `move_file()`, and the removal of an empty folder's rows that a file's move replaces (14008-14009), only after `writer.rename()` returned True.
  - `rename()` records dst with its own rows (`rows=True`, the default).
  - A fallback leaves the rows where they are. The undo branch after `copy_instead_of_move()` (which removed the rows `move_tree` put at the target) goes.
- **A moved file whose attributes the replay syncs** under Only Sync Attributes (`writer.file_meta()` after the rename) is marked vouched (`mark_vouched()`). The commit then reads its new metadata and keeps its hash (`take_dirty_records()`). Without Only Sync Attributes such a file is copied, as today.
- **`attribs_to_copy()` (10180)** passes the record of the row at the entry's place in the latest version, moved or not (today `record = None if moved`, 10221), as that row now travels with the inode to where the attrib applies.
- **Comments that said "a moved row is unverified"** are rewritten: `record_vouches()` (10158), `attribs_to_copy()`, the attrib replay's (13953-13955) and `move_tree()`'s docstring. A swap's leftover now carries the record of the inode actually at its place, as rows move with renames and only with them, so it vouches only when the monitored file matches that inode.
- **The fuzz checks lists again.** tests/test_watcher_fuzz.py drops `says_too_little()` and its filter (REVERB_WATCH_FUZZ_LISTS goes).

**Why it is right.**
- **The invariant:** every row's record describes the inode at its path in the version.
  - A rename keeps the inode, its bytes and its metadata.
  - The record moves with it, and only when it moved.
  - What the replay writes onto it afterwards is recorded at the commit (vouched, or dirty for a copy), wherever the row is by then.
- **The unchecked flag moves with the record,** so a copy not yet read back is read back at its new path.
- **After a cut before the commit,** the cut batch's rows roll back, and the roll-forward reads rows from the tree (`read_rows_from_tree()`).
- **After the commit point, a power cut cannot leave a committed record whose rename was lost:**
  - on f2fs the change list's fsync (a checkpoint, in its new private folder) put the renames on the disk before the manifest's commit;
  - on two renames the commit flush did;
  - on ext4 and XFS the manifest's fsync carries the earlier metadata in the journal, which the ext4 and XFS sweeps of 5.2 now run.
  - The row oracle below checks it under real power cuts.

### 5.4 No mount table read before a wait, and none twice for one look (L4)

**Today.** A one-file batch through `backuper()` reads the mount table at:
- each of the two waits (`wait_for_path()`, 1229, through `vault_disk_problem()`, 4318);
- `PoolGuard()` (4356), once per path, as `pool_state()` (4210) reads it;
- `do_backup()` (5860);
- `drop_unmounted_entries()` after the verification (5777);
- `set_inner_mounts()` at the commit (6127, `current_mount_table()`);
- each `fsync_vault_folder()`.

Reading the code gives about nine; the entry says seven. Task 4 counts main's reads first, off a pool and on one, before any saving is quoted. The entry's measurement, of `do_backup()` alone with eight reads before 0.55.3, is 0.44 ms of CPU a read at 162 mounts.

**The change.**
- **One read before the batch's work, the latest.** Each batch, the backuper keeps a one-item list, empty at the top of its loop, which both waits take (`wait_for_path(..., table=)`; `vault_disk_problem()` takes a table). A wait's first poll uses the table in the list, or reads it when the list is empty and puts it there. A wait that has to poll again reads the table live and puts that read in the list. Once both waits returned, `PoolGuard(paths, mount_table=...)` (a keyword: the second positional parameter is `clock`, 4364) and `compare_scanned_folders()` take the table the list holds: the latest read, with no wait after it.
  - A table read before a wait that blocks would be stale. A pool unmounted when the loop began and mounted while the vault's wait polls would read as no pool: the guard would not cover the job vault, the unit would open one fd on the pool's mount, and L2 would drop a pool's fsyncs.
- **One read after a scans walk.** When `compare_scanned_folders()` walked scanned folders, the table is read again after it, and that read goes to `do_backup(mount_table=...)`; otherwise `do_backup()` takes the list's. The read `do_backup()` makes today (5860) is what notices an inner disk unmounted while the scanned folders were walked, so the paused drop keeps their deletes out (the re-check's run N3).
- **One read after the walk, and one at the commit.** The no-differences path remembers inner mounts from the table `drop_unmounted_entries()` reads after the walk: nothing looks at the tree after it. The commit reads the table itself, as main does (ruling R35): the copy phase and the verification's fix replay look at the tree after the last walk, and a disk mounted then is in the version, so it must be remembered; remembered from the walk's table, it would be unknown to the next batch, which would read it, unmounted, as its files deleted, and copy them again when it comes back. A disk mounted after the commit is remembered by the next batch.
- **The first version's check follows its locks.** `do_backup()` on a vault with no version takes the locks and scans the vault before it checks the monitored mount and sets the paused inner mounts, and when it took them it reads the table after them (ruling R37). The table it was given was read before `compare_scanned_folders()`'s own lock wait (when the job has scanned folders) and before its own; an unmount in either wait would otherwise commit an empty first version. Main has the second window.
- Off a pool a committed one-file batch reads the table three times, a batch with scans four times (the commit's read, R35); a batch with no differences one fewer. On a pool `PoolGuard.require()` and `poll()` read it live for each pool path (they ask whether a disk dropped since), and the commit's two folder fsyncs read it through `vault_disks()`, as today: L4 changes none of those.

**Why it is right.** Without a wait that blocks, the reads it replaces were a few milliseconds apart, so the shared table says the same. With one, the table taken is the wait's last read. Every check that must see the table after a walk still reads it then.

**Tests.**
- Docker (fails on main): a counter on `read_mount_table()` over one one-file batch through `backuper()` (the harness's job runner), off a pool, counts 2; a batch with a scanned folder counts 3.
- Pin (passes on main; fails with a table read before the waits): a batch whose vault pool (FakePool) is unmounted when the loop begins and mounted while the vault's wait polls. The batch's guard covers the job vault, and its unit opens a handle per branch.
- Pin, the re-check's run N3 (passes on main; fails with the waits' table handed to `do_backup()`): an inner disk unmounted while `compare_scanned_folders()` walks: no version, and its files stay in the vault.

**Cost.** Off a pool, the reads main makes less two (three with scans), for each batch: about 0.44 ms of CPU each at 162 mounts.
- **Measure:** the counter on main and the branch, and `timeit` of 1,000 `read_mount_table()` calls on the host's table for the cost of one (the median).

### 5.5 The inode estimate counts what design R adds, so no du (L5)

**Today.** `get_backup_size_inode()` (10916):
- subtracts, for each deleted folder, its inode count from `du --inodes -csP` (`get_path_inodes()`, 8456, one process per batch), and 1 for each deleted file;
- counts an inode for a create only: "we do not count inode change for attrib / modify / move events".

That rule comes from 0.54, whose versions were whole trees of links: a delete made the next version smaller, and a modify put a copy where a link was.

**On design R a delete frees nothing, and a copy adds an inode.**
- A deleted entry goes into the previous version as its record, and stays in the vault until that version is pruned.
- A modify's copy, and an attribute change that copies, puts a new inode in the tree, while the old one stays in the previous version as its record (`TreeWriter.copy()` records by a hard link first).
- A move keeps its inode, but for a moved file whose attributes differ and that the replay copies with Only Sync Attributes off (14034-14037).
- So the vault's inode count rises by one for each copy and each folder the batch makes, plus the links it makes, and falls by nothing. Today's estimate undercounts a batch by what it deletes and by what it modifies.

**The change.**
- Deletes count no inode.
- Each entry the replay copies (`copies()` in `get_backup_size_inode()`) counts its inodes wherever it counts its bytes: one for a file, a walk's for a folder, with the same nesting rule as the bytes (`sized_folders`). The carried-in and written adjustments below it follow the same rule.
- `copies()` takes no move, as today (ruling R38). Build A counted a plain file's move with Only Sync Attributes off whose monitored mode, owner or mtime differed from its source row's record, but the source row is looked up at the move's path in the batch, before the replay moves any row: it finds none when a folder above moved earlier in the batch (`mv d x; mv x/m a`), and another file's row when the batch refilled that path (`mv x y; mv d x; mv x/m a`, the old x holding an m), which counted a full copy the replay never makes and pruned 12 of 13 versions in the review's probe. A pruned version is gone for good; an estimate too low passes the limit until the next prune. So a moved file that the replay copies is left out of the estimate, as on main, and no lstat is made for it. A move into a folder made at its own old place (`mv D x; mkdir D; mv x D/D`) is not subtracted as carried into that folder: the replay copies it.
- `get_path_inodes()` leaves reverberator.py, and with it the batch's du process and `ARGUMENT_LIMIT` (1204), which has no other user. The tests that call it as their vault oracle (tests/harness.py 173, tests/test_crash_safety.py 299, 305, 306 and 366, tests/test_user_links.py 1691) take a helper of their own in tests/harness.py, which keeps du (a test tool).
- **Hard links.** The replay copies each name on its own: a created folder is made folder by folder and each file in it is copied alone (`get_unskipped_size_inodes()`'s docstring, 10894), so a copied folder's hard-linked files become separate inodes in the vault, and the walk's count by name is what the copy adds. du's count by inode, which the entry's "Why" weighed, was of a deleted folder, which now counts nothing.

**Why it is right.** It is the change-list rule of docs/lessons.md 2026-11-06 ("When a stored number changes meaning, rework every formula that reads it"), applied to the formula 0.55 missed. The suite asserts written ≤ estimate ≤ what the vault grew by for bytes (tests/test_estimate_through_a_take.py, 71); the tests below assert it for inodes too, as the links stay left out. Nothing is stored.

**Tests.**
- Fails on main: a batch that deletes a folder of K entries, creates M files and modifies P files estimates M + P inodes (main: M - K), and runs no du (a recorder on `multiCMD.run_command()`).
- Fails on main: the inodes that batch wrote, its new inodes in the tree (by `st_ino` against the version before, links left out), are at most the estimate: M + P, where main estimates M - K.
- Pin (R38): a chmod then a mv of one file in one batch, Only Sync Attributes off: the replay copies it and the estimate counts nothing for it, as on main (`test_the_estimate_leaves_out_a_moved_file_the_replay_copies`). Fails on build A before R38: the refilled-path shape `mv x y; mv d x; mv x/m a` counted a copy never made and pruned 5 of 6 versions.
- Pin: the estimate is at most what the vault's inode count grew by.
- Tests that pin the old rule move to these, tests/test_estimate_through_a_take.py's exact inode count (20, 73) among them.

**Cost.** One process (fork, exec, a walk of the deleted folder) less per batch that deletes a folder.

**Docs.**
- The entry goes.
- "Size estimates leave out a version's own small blocks" is unchanged: the links stay left out.
- Calls to confirm: under an inode limit, a batch that deletes or modifies prunes when it should, which can be a batch earlier than before.

### 5.6 The root's metadata is written only when it changed (L6)

**Today.** `record_root_meta()` (12545), through `TreeWriter.root_meta()` (13291), calls `setxattr` on the tree's folder every batch.

**The change.**
- It reads the folder's `ROOT_META_XATTR` first and skips the write only when the value is byte for byte the full record it would write (owner, mode, times and every extended attribute). Anything else, a failed read included, goes through the write as today.
- A trimmed record never equals the full one, so a root whose extended attributes do not fit goes through the write and its line as today, once per run (`ROOT_META_TROUBLE`, which a restart empties). A skip ends a trouble state with its line, as a write does.
- `hand_over()`'s copy of the record to the skeleton stays.

**Why it is right.** A record equal byte for byte is the same record. A skip never stands for a trimmed write, so the "trimmed" line after a restart is said as today. Nothing is stored.

**Tests.**
- Fails on main: a batch that leaves the root's owner, mode, times and xattrs as they were makes no `setxattr` of `ROOT_META_XATTR` from `record_root_meta()` or `TreeWriter.root_meta()` (a recorder on those two; `hand_over()` writes the record onto the skeleton every batch and stays).
- Pins: a chmod of the root writes it; a record too big still writes the trimmed one once and says so once; after a restart (`ROOT_META_TROUBLE` emptied) with a trimmed record on the tree, the trimmed line is said once.

**Cost.** One `setxattr`, and the inode write it can cause, less for nearly every batch, for one `getxattr`. The record holds the root's atime: on a filesystem mounted relatime (the default) a walk moves it at most once a day, so the skip holds on all other batches; on one mounted strictatime every walk moves it, the skip never holds, and the cost is today's.
- **Measure:** the recorder's count over 20 one-file batches, on relatime.

### 5.7 The restore marker's recopy field and `--accept`'s first sync stay (L8)

Both exist: `recopy_way_out()` (15480), `refuse_accept_unsynced()` (16764), `marker_recopy()` (16750), and the sync before `hand_over_folders()` in `accept_restore()` (16546). Both still do a job, so neither goes.

- **"recopy" is still needed.** "unsynced" lasts from the claim to the run's sync. "recopy" lasts until every entry was copied again and a sync of them succeeded (`restore_entry()`'s docstring, 16240-16256).
  - A recopy run that fails one entry, say B, syncs and clears "unsynced", while B still holds what the killed run wrote, which nothing vouches for. "recopy" makes the next run copy everything again.
  - It also holds a recopy while a disk of the vault's pool is missing.
  - The two keys could become one with that longer lifetime, but that saves no I/O and rewrites the restore's most-reviewed code. Not this round.
- **`--accept`'s first sync is still needed on a pool.**
  - Its copies need no sync: `--accept` runs only over a marker with no record, so the run that wrote them synced them through handles open since its claim.
  - A 0.55.1 marker carries no record either, but no 0.55.1 restore can still be running, and a handle opened at `--accept` could not vouch for its copies anyway.
  - What the sync still does: a run stopped during its hand-over leaves folders' owners, modes and times unsynced (its stop syncs only before its own sync). On one filesystem the marker's removal cannot reach the disk before them. On a mergerfs pool each disk keeps its own order, and without this sync a power cut could keep the marker's removal on one disk and lose those folders' metadata on another, silently.
  - Off a pool it costs one syncfs per `--accept`, a command run by hand, and keeping one path for both is simpler than a branch.

**Docs.** No change.

### 5.8 A copy is recorded checked once its commit flushed it (L9)

**Today.** `record_dirty_entries()` records each file a batch copied as unchecked (`read_copied_record()`, 10262, unchecked 1). The next comparison that walks it reads it back (`compare_entry()`, 10327: an lstat and its last 64 KiB) and records it checked, a row write per copy. The mark stood for a copy whose bytes a crash could keep from the disk.

**Why it can go, after F1.** A pass over every writer of the flag:
- `read_copied_record()` through `record_dirty_entries()` at each commit (5950 for a first version, 14165 for the others, both before the commit flush at 6134): the only writer that sets it to 1 once F1 is built;
- `mark_unchecked()` at the scan: F1 removes it;
- `read_vault_record()`: 0 for every read-back (10322, 10329, 10518), an unverified row's (moved rows on 0.55.4, a rebuilt or converted manifest's) among them; the known-record path (10256), `read_rows_from_tree()` and `take_dirty_records()` keep the flag they read;
- a copy made where hard links are refused (`keep_entry()`, 13026) is a record in the previous version, with no row of its own, and sets `copies_unsynced`, so it is flushed like any copy;
- the conversion's copies are flushed before its commit (13524), and the 0.54 prune's copy touches no row.

Since 0.55 every copy a version commits is flushed before its commit (6134-6140), through the handles its unit opened before the copy was written (VaultUnit), which hear every writeback error of the filesystem since. After F1 no cut copy stands at any name: each recorded name is copied again or holds version n's entry, what the cut batch made is removed before the comparison, and the scan flushed any put-back copy. So a mark is only ever written on a copy already on the disk, heard through such handles, and the read-back it asks for can find nothing the flush did not.

**The change.**
- `record_dirty_entries()` records each row with unchecked 0; `read_copied_record()` goes. A vouched row keeps its record's flag, as today.
- The read side stays: rows that 0.55.4 and older marked are read back once, as before, so the marks drain.
- The manifest's docstring ("A file copied by a backup stays unchecked until delta generation reads the copy back") and `compare_scopes()`'s are rewritten, and so is README line 4.

**Why it is right (crash safety).** A power cut after the commit cannot take a flushed copy's bytes: the disks' flush is the barrier. With L9 the row oracle (5.3), which checks rows with unchecked 0, covers every copy a batch made, so the power-loss sweeps of 5.2 (every step, f2fs, ext4 and XFS) and the kill points prove it.

**Tests.**
- Docker (fails on main): a batch that copies N files records them checked; the next full comparison reads none of them back (a recorder on `read_vault_record()`) and writes no row for them.
- Pin: a row marked unchecked as 0.55.4 marks it (set by hand) is read back once and recorded checked.
- Gate: the power-loss sweeps of 5.2 and the kill points, with the row oracle.
- The tests that pin a fresh copy unchecked change: tests/test_verify_replay.py's `test_fresh_copies_keep_unchecked` (364-369), and tests/test_moves_then_changes.py around 1592-1599, 1618 and 1632 (`test_a_vouched_chmod_of_an_unchecked_copy_keeps_it_unchecked` and its neighbours), which then seed the unchecked row by hand.

**Cost.** Per copied file, at the next comparison that walks it: one lstat, one 64 KiB read and one row write less.
- **Measure:** `read_vault_record()` calls and `rchar` of a full comparison after a batch of 1,000 copies, main against the branch.

**API.** The manifest's `unchecked` column keeps its meaning for a reader ("read this copy back"); the writer stops setting it. A 0.55.4 daemon reading a 0.55.5 manifest trusts its checked rows, as it trusts any. A lessons entry (section 11).

### 5.9 A folder gone mid-walk is no error (L10)

**Today.** `iter_tree_entries()` (3724) logs every folder its scandir cannot read with an ERROR line, "Error scanning <path>: <error>" (3768, through `watcherTeeLogToTl()`), and hands the error to its caller. A folder made and removed while a walk passes (a `.git/objects/xx` folder, a build's scratch) gives "[Errno 2] No such file or directory": three such lines in the live journal since 2026-11-06, more in the week's log by the main session's count.
- The watcher's walk does not mark such a folder unwatched (3599-3600), but its error loop still logs "Not watching unreadable folder <path>: <error>" at ERROR for it (3610), and that walk runs for each new folder (3381, 3404, 3486, 3493).
- The comparison keeps the folder's rows. When the folder was watched, its delete comes as an event; under a folder left unwatched (an unreadable one, 3534-3535), no event comes, and the next full comparison finds it (each start's, after F3). The comparison's `log_unreadable()` (3774) would also raise an UNREADABLE alert for it, though it is not unreadable; none was seen in the journal.

**The change.**
- When a folder's own scandir fails to open with ENOENT or ENOTDIR (gone, or no longer a folder, since its parent listed it, or since a scope's lstat saw it, 10385), `iter_tree_entries()` lstats the folder. Only when that lstat agrees it is gone (ENOENT or ENOTDIR again) does it log one INFO line, "<path> was gone when the walk reached it: <error>", in place of the ERROR line, at every level, the walk's own root included, and mark the error as one of a folder gone. A folder the lstat still finds, whose scandir cannot open it, keeps its ERROR line and its UNREADABLE line, as on main. Either way the error is appended to `errors`, so every caller decides as today. An error met while listing, past the open, keeps its ERROR line. The lstat costs one call, on the error path only.
- The monitored root still fails the attempt through its callers' checks of an error at rel '' (`compare_scopes()`, 10571; `check_walk_errors()`, 5788).
- `log_unreadable()` passes over the errors marked as a folder gone, so the race raises no UNREADABLE alert; the rows stay, as today.
- The watcher's error loop (3600-3610) passes over them too: no "Not watching unreadable folder" line for them.
- EBADF does not join: a real error can show as EBADF, and mergerfs's EBADF during an rm stays its own entry ("mergerfs answers EBADF to a lstat during an rm"). Every other error keeps its ERROR line and its UNREADABLE line.
- A folder its parent lists and the kernel cannot open, every time, while an lstat still finds it (name trouble on a FUSE, CIFS or NTFS mount), keeps its ERROR and UNREADABLE lines at every walk, as on main: its contents are not backed up, and the alert says so (the re-check's finding 3, R32).
- Nothing depends on the lines: no test greps them, and firewatcher/reverberator.regex matches only the marker lines (FAILED, UNREADABLE, STOPPED, VAULT WRITE ERROR, NOT BACKED UP, EXITING), of which this change removes only false UNREADABLE ones.

**Tests.**
- Fails on main: a full comparison during which a folder below the root is removed between its parent's listing and its own (a stand-in on `os.scandir`): one INFO line, no "Error scanning" ERROR line, no UNREADABLE line, and its rows kept.
- Fails on main: a touched folder removed between `iter_scope_entries()`'s lstat and its scandir: one INFO line, no ERROR line.
- Fails on main: the watcher's walk of a new folder whose subfolder goes before its turn: no "Not watching unreadable folder" line.

**A deferred entry** (the lost manifest and an unmounted inner disk, confirmed by the design review's probe A; and, by R33, the cut copy a lost manifest keeps, F1's run N4 route over a lost manifest):

> ### A lost manifest stops an unmounted inner disk being paused
>
> - **Kind:** deferred.
> - **What the operator sees:** when a job's vault database is lost or unreadable (removed or damaged from outside; the daemon's own messages suggest removing it in some cases), two things go wrong. An inner disk unmounted at that moment then looks like an empty folder: the next comparison commits a version with that folder empty, with no "Inner mounts not mounted" line, and when the disk is mounted again every file is copied back. Under Keep N Versions or a size limit, the versions holding the disk's files can be pruned meanwhile, so a disk that never comes back can lose its backup. Second, when a batch was cut (a kill or a power loss) before the database was lost, a file the cut batch had just copied in new, whose source cannot be read at the retry, keeps the cut copy as its backed-up copy: if the cut damaged that copy, the newest version holds wrong bytes for it, with no line but the file's UNREADABLE one, until the file changes again. With the database standing, the start removes such a copy and the file is left out with its line.
> - **Why:** the inner mounts are recorded in the database only, so a rebuilt database has none to pause. And without the database the start cannot tell a file the cut batch made from one of the version before whose forward link a cut between two renames left in staging (on a pool, or a filesystem with no exchange): removing the first would remove the second, which is data loss (the design re-check's run N5), so the start keeps both, as 0.55.4 does. > - **Revisit when:** the round after 0.55.5.

## 2026-11-13 reverberator 0.55.5: every start compares the whole tree, and the pending file goes
- Changed: a stop no longer writes the queued changes to .reverberator_pending_transactions.nsv, and a start no longer replays them: every start runs the one full comparison it ran anyway, and makes one version. A file an older release left is removed at the first start.
- Why we had to change: since 0.46 every replayed batch was followed by a full comparison (2026-10-27), so the replay only kept the pending moves as renames, and for that it cost a second version at every restart with changes pending (a live job's restart, 2026-11-10), a walk of the whole tree for its resume check, a file format with its own escaping, time offsets and memory checks, a hand-back path, and five entries of limitations.
- Original design was wrong because: the replay was designed before the rule that every restart compares the whole tree; once the rule came, the saved state answered a question the comparison already answered, and was kept for the one thing only it did.
- Lesson: when a restart redoes the work in full anyway, drop the saved state that would resume it: a second path to the same result costs a format, its checks and its bugs, for the little only it does.

## 2026-11-12 reverberator 0.55.5: a record follows its inode through a rename
- Changed: a move keeps its committed manifest rows' records and unchecked marks (rows the batch wrote are read back at their new place), and the rows move only once the version's rename is made; a fallback to a copy leaves them where they were.
- Why we had to change: every rename made the batch's own verification read each moved file back (2,000 files of 128 KiB: 2,001 vault reads and 262.3 MB read where the branch reads 131.3 MB), and rows moved ahead of a rename that then fell back to a copy left the target's rows gone, so the version before kept a change list that said too little.
- Original design was wrong because: it took a renamed entry for an unknown one, though a rename keeps the inode and its bytes, and it moved the records before the change they describe.
- Lesson: a record describes an object, not a name: move it with the object, and only once the object has moved.

## 2026-11-12 reverberator 0.55.5: a copy flushed before its commit is recorded checked
- Changed: the commit records each copy checked; before, it marked each unchecked, and the next comparison that walked it read its last 64 KiB back and wrote its row again.

- Original design was wrong because: the mark stood in for a flush the commit did not make yet; once the flush came, the mark stayed.
- Lesson: when a guarantee moves upstream, remove the downstream check that stood in for it, or every write pays twice.

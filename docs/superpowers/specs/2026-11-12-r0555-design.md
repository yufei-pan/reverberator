## 1. A cut batch's file the roll-forward cannot copy again gets version n's entry back (F1)

**Today.**
- `prepare_roll_forward()` (7022) returns what the cut batch recorded in the previous version, version n (`give_back_folder_times()`, 6894: real folders, files and links, each of the kind it was), and marks the rows of the recorded files unchecked (`VaultManifest.mark_unchecked()`, 9072).
- `roll_forward_entries()` (7080) copies again each recorded name whose monitored path is a regular file now (`again`), trusted by the comparison and replayed as a modify.
- A recorded name it does not copy again keeps the cut batch's copy in the tree with an unchecked row. That covers a file under an inner mount paused at the retry, one whose mount goes during the roll-forward's walk (`drop_unmounted_entries()`, 5769, drops the forced modify), and one in a folder the walk cannot read (its rows are kept).
- The next full comparison that can see it reads it back by size, mtime and last 64 KiB. A copy all NUL that ends in 64 KiB of zeros passes; so does a page lost before the tail, and without a reboot the read comes from the page cache. Those are the three entries.

**The change: put version n's entry back.**
- A new TreeWriter verb, `put_back(rel)`, makes the tree's entry at rel version n's again, from the record in the previous version (`kept_path(rel)`, 12881):
  - a file or a link there: hard linked into staging (`link_or_copy()`, 12618, which copies where hard links are refused), then renamed over the tree's entry;
  - a real folder there, while the tree holds no real folder at rel (a file took its place): built in staging by `hard_link_tree()` (13082), then renamed in. Such a folder holds no forward link: `record()` (13111) recorded all of it before the tree's folder could be replaced, as it recurses into a previous folder that is already real;
  - a real folder there and a real folder in the tree: nothing, as its entries are names of their own;
  - a file or link there whose inode the tree's entry already is (same `st_dev` and `st_ino`): nothing, as a rename onto a hard link of the same inode does nothing and would leave the staged link behind;
  - whatever else the tree held at rel goes first (`remove_entry()`), as a create of the cut batch (a folder that took a file's place) is no entry of version n.
- **Who calls it.** `do_backup()` (5795), in the roll-forward branch, once `drop_unmounted_entries()` has run after `roll_forward_entries()` (around 5974-5982) and the writer exists (6071), before `do_reverb_backup()` (6089):
  - for each name of `vaultInfo.recorded` that `backup_entries` does not name, in either form, at it or at a folder above it;
  - in the order `recorded` lists them, a folder before what is in it;
  - then the rows at and under each name put back are read again from the tree, as `read_rows_from_tree()` (7048) reads them, as that read ran before the put-back.
- **What it covers, with no case of its own:** a paused mount at the retry, a mount gone during the walk, a folder the walk could not read, and any later reason a recorded name is not replayed. A name the comparison found gone, skipped or of another kind has an entry, so the replay takes it and nothing is put back.
- **What goes:** the transaction in `prepare_roll_forward()` and `VaultManifest.mark_unchecked()`. Every recorded name is now copied again or holds version n's entry, so no row needs the mark. `prepare_roll_forward()` returns `recorded` as before.
- **What it does not touch.** Creates of the cut batch have no record. With the manifest standing they have no row, and the roll-forward's sweep (`sweep_version_folder()`, 10607) removes them. Over a rebuilt manifest no inner mount is remembered, so none is paused.

**Why it is right (crash safety).**

| State a stop, a kill or a power cut leaves | How the next start finishes it |
|---|---|
| Cut inside a put-back: a link or a tree in staging, the tree's entry the cut copy | The scan empties staging (`empty_staging()`); the previous version is unchanged, so `recorded` is the same and the next roll-forward puts it back again |
| Cut after a put-back's rename, before the commit | The next roll-forward finds version n's inode there already and leaves it |
| Power cut with the put-back's link or rename lost | One of the two states above |
| Committed | The newest version's entry is version n's inode, whose bytes were flushed at version n's commit through that batch's handles; its row is version n's, checked or not as it was |

- The roll-forward always runs the commit flush (`do_backup()`, 6134), so the put-backs are on the disk before the commit point.
- On a pool the record was on every disk before the cut batch changed the tree (`pre_record()`), and the put-back reads it only.
- Nothing vouches for bytes no flush of their own unit covered, so a write error another program's sync saw has nothing left to hide.

**Tests** (each fails on main):

   - right after the roll-forward, before the mount is back: the newest version's file has the previous version's record's `st_ino` and version n's bytes (main: the cut copy, all NUL);
   - its row is version n's record, with the unchecked flag version n had;
   - the next full comparison, with the mount back, reads nothing back for that rel (a recorder on `read_vault_record()`), copies it, and the newest version holds the file's bytes.
2. The same, for a recorded name of another kind, under a paused mount: a user's link the cut batch replaced by a file (the link comes back), a folder replaced by a file (the folder comes back whole), a file replaced by a folder holding a new file (the file comes back, the folder goes).
3. tests/test_crash_harness.py, `test_no_copy_again_and_no_unchecked_marks_fails_the_oracle` becomes "no copy again and no put-back fails the oracle": with `roll_forward_entries()`'s copy again and the put-back both stubbed out, the oracle fails.

**Cost.** Only at a roll-forward: one link and one rename for each recorded name not replayed (a folder's: one link per entry), and a removal where the tree held something there. Nothing on any other path. `prepare_roll_forward()` loses one transaction (about 5 fdatasyncs) per roll-forward.

## 2. A pool vault's handles open where the job vault is (F2)

**Today.** `VaultUnit.__init__()` (1967) opens, on a pool, an fd of each branch's root (`open_branch()`, 2019). `holding()` (2035) picks a handle by the `st_dev` of the job vault's folder on each branch, and raises `not_opened()` when no handle has it. A job vault folder on a branch that sits on a filesystem of its own (a mount nested under the branch, a btrfs subvolume) has a `st_dev` no handle has, so every sync raises and every attempt fails.

**The change.**
- `open_branch()` opens `os.path.join(branch, self.rel)`, or, when that is not there, its nearest existing parent, never above the branch.
- Branches whose handles share a `st_dev` keep one fd, as today.
- `holding()` is unchanged. A job vault folder made on a branch later lands on the filesystem of the nearest parent that existed, so its `st_dev` matches. A mount made at a folder on the way since the unit began has a `st_dev` no handle has, and `holding()` raises, as it does for a joined disk.
- **The restore takes the same rule.** `open_restore_disks()` (16095) opens each disk's branch root (`vault_disks(folder, roots=True)`). For a target whose folder on a branch is a nested mount, `syncfs` writes out the branch root's filesystem, not the one holding the target, and the restore says done. It now opens the folder's place on each branch, or its nearest existing parent, never above the branch. The disk names, the `listed` set and the joined-disk check stay. This is beyond the entry: Calls to confirm.

**Why it is right.** Linux reports a filesystem's writeback error to a syncfs through any fd of that filesystem opened before the error (the flush spec, section 2). An fd at the job vault's own folder, or at its nearest existing parent, is an fd of the filesystem that holds or will hold it. Nothing is stored; a cut closes the fds with the process.

**Tests** (each fails on main):
1. tests/test_pool_writer.py (or the flush round's tests/test_vault_units.py), on `harness.FakePool` with the errseq stand-in: a branch whose job vault folder is a symlink to a folder on /dev/shm, a stand-in for a nested mount, as `os.open()` and `os.stat()` follow it to another `st_dev`.
   - A batch commits (main fails with "is not on a filesystem this step opened").
   - `fail()` and `seen_elsewhere()` on the /dev/shm folder between the copies and the commit flush: VAULT WRITE ERROR, nothing commits. This pins that the handle is on that filesystem.
2. The same with the job vault folder missing on a branch when the unit opens, and a copy landing there: the sync goes through the nearest parent's handle, with no error.
3. A restore onto a FakePool target whose folder on a branch is such a symlink: `fail()` on /dev/shm, and the restore's sync reports the write error. Main says done.
4. **The test VM:** the same as test 1 with a real tmpfs mounted at the job vault's folder on a branch of a real mergerfs pool; and test 3 likewise.

**Cost.** None off a pool. On a pool of B branches: B opens at a deeper path (a few more path components looked up), once per unit.

**Docs.** The entry goes. README line 54 goes.

## 3. One version per start (F3)

**Today.** In `backuper()` (4895):
- a batch resumed from the pending transactions, or handed back after a failed attempt, is `round_tripped`;
- it is replayed and verified on its own touched scopes, and commits a version;
- then `follow_up` (5095) runs a full comparison, which commits a second version when anything changed while the daemon was down.

The live job's restart of 2026-11-10 made two versions a second apart. Round 7's rule, a resumed batch is always followed by a full comparison, decides from the downtime and not from the batch (docs/lessons.md, 2026-10-27).

**The change.** A round-tripped batch is verified against the whole tree, in the same version:
- **`backuper()`.** For a round-tripped batch:
  - `touched` is the whole tree, `TouchedScopes([''], [])`;
  - `scan_folders` is emptied, as the whole tree covers them;
  - `matched_since` is `time.time_ns()`, taken before `do_backup()`, as for a full comparison;
  - `follow_up` goes.
- **`do_backup()`.**
  - A whole-tree `touched` whose batch has no entry left (after `drop_untracked_deletes()`, 4577, and the paused drops) is a full comparison: `touched` is set to `None`, so `delta_generate_backup_entries()` (10761) compares once, with folder times and `full_comparison_since()`, and nothing is verified twice.
  - With entries left, it replays them and the verification compares the whole tree.
- **`do_reverb_backup()`'s `verify()` (14077).** A whole-tree `touched` compares what a full comparison compares:
  - extended attributes by `full_comparison_since(vault_info_dict, manifest.matched)` (10730) as its `changed_since_wall`, which `do_backup()` fills in;
  - folders' mtimes, but not those of the folders the replay wrote into (`written.rels` at the time of the comparison). `settle()` gives those the monitored folders' times anyway, and a time compare would add an attrib row to the change list for each.
  - The roll-forward's verification, already whole-tree, gets the same.
- The sweep (`sweep_version_folder()`) covers what the comparison covers, the whole version, as for a roll-forward.

**Why it is right.**
- Round 7's rule stays met: every resumed or handed-back batch has the whole tree compared before its version commits, with the bounds a full comparison uses. The replay first keeps the batch's moves as renames, which a comparison alone would turn into copies.
- `matched_since` taken before the batch holds: every change made before it is in the tree when the verification walks it, and every one after it comes as an event (the watcher is watching before the batch is taken: `startup.watching`).
- **No new state, one removed (`follow_up`).** A stop, a kill or a power cut mid-batch leaves what it leaves today:
  - before the hand-over, the batch goes back to the queue, round-tripped, then to the pending file, and the next attempt applies the same rule;
  - after it, the roll-forward compares the whole tree.

**Tests** (each fails on main unless marked a pin):
1. tests/test_job_startup.py: a start with a pending batch (a file moved, a file written) and, made while the daemon was down, a chmod, an xattr-only change, a new file and a removed file. Expect:
   - one version holding all of it;
   - the move as a rename (the moved file shares its inode with the previous version's record, as `TreeWriter.rename()` leaves it);
   - the manifest's matched time names that version.
2. The same for a batch handed back after a failed attempt (a JobFailure injected at the commit flush, then the retry).
3. A folder whose mtime alone changed while down (a file made and removed in it): the version holds the new mtime (needs the folder times of the verification).
4. A pending file of a carried move-out's late delete only: one whole-tree walk (a counter on `compare_scopes()` with subtree `''`), and no version when nothing else changed. This closes "A resumed batch of only untracked deletes walks the tree twice".
5. A resumed batch of scans only: one version, no second walk.
6. Pin: no attrib row in the change list for a folder the resumed replay wrote into.

**Cost.**
- **At a start with a batch pending:**
  - Saved: one version's hand-over (a skeleton with one forward link per root entry and the exchange), its change list (whose fsync is an f2fs checkpoint), its manifest commit (about 5 fdatasyncs), the current_version swap and the list's placement, and, under a Keep count, one prune.
  - Added: the sweep's walk of the newest version folder.
  - Also after a failed attempt's retry.
- **Measure in the test VM:**
  - an f2fs loop image, with a tree of the larger live job's shape (about 19,000 folders and 123,000 files, sized as the footprint run counted them);
  - a start with a one-file pending batch and one file changed while down;
  - main against the branch, alternating, three runs each, as round 22's benches ran;
  - wall time, the start's `lifetime_write_kbytes` delta and its foreground checkpoints (`cp_foreground_calls`).
  - Three runs, because the alternation is what cancels host drift.
- If the sweep's walk costs more wall time than the version it saves, the build reports it before going on (Review focus 3).

**Docs.**
- "A start with changes pending makes two versions" goes, and so does "A resumed batch of only untracked deletes walks the tree twice".
- "An older pending file replayed after a stop dropped changes" narrows. The whole-tree verification puts the dropped attribute-only and mtime-keeping changes in the replayed batch's own version, so what is left is the same-size rewrite that kept its mtime. Section 10 has the text.
- README line 16 becomes: "a batch resumed after a restart (one of scans only too), or put back after a failed backup, is checked against the whole tree, as a full comparison checks it, before its version commits: one version holds the batch and what changed while the daemon was down." Line 38 goes; line 39 follows the narrowed entry.
- A lessons entry (section 11).

## 4. A batch whose every entry drops out commits nothing (F4)

**Today.** An entry the replay cannot apply is left out at the copy (`finish_copies()`, 8108):
- an unreadable file keeps its last copy, with an UNREADABLE line;
- a symlink whose text or path the vault's filesystem refuses is left out, with a NOT BACKED UP line (`link_too_long()`, 8088).

By then the tree is handed over, so the batch commits a version that changes nothing. A full comparison meets the same entries every time (the unreadable file's row keeps its old record; the left-out link has no row), so each start, interval or overflow makes one more empty version. Under Keep N each pushes the oldest out.

**The change.** In `do_backup()`, once `backup_entries` is final, before the size estimate (6028), the prunes and the hand-over, for a batch with no tree to roll forward:
- **Would any entry change the version?** The check stops at the first entry that would, in three passes, cheapest first:
  1. Any entry that is not a create or a modify of a file, nor a file's attrib under Only Sync Attributes off (a delete, a move, an attrib under Only Sync Attributes, a folder's entry, whose path ends with /): it changes the version. No syscall.
  2. For each other entry, an lstat of its monitored path:
     - a regular file `source_readable()` (7885) opens, or an entry of another kind (a FIFO, a socket, a device, which cp -a copies as itself): it changes the version;
     - a regular file it cannot open, or a path that cannot be looked at: it drops out, as the copy would keep the last copy;
     - a path gone: it drops out, as the replay would find the source gone and keep what the version holds;
     - a symlink: pass 3.
  3. Only if every entry is still in doubt, each symlink entry is probed. It changes the version when the tree already holds an entry at its place, as leaving it out then removes that entry. Otherwise it changes the version unless one of these refuses it:
     - its text: `os.symlink(text, <staging>/.link-probe-<uuid>)` answers ENAMETOOLONG; the probe is unlinked at once;
     - its path: the bytes of `partial_copy_path()` of its place in the new version reach `os.pathconf(job_vault, 'PC_PATH_MAX')`. The new folder's name is `V<n+1>--` and a timestamp of `VAULT_TIMESTAMP_FORMAT`'s fixed width, so its length is known before the folder is named.
- **When none would:** each entry is logged as the copy or the replay would log it, with the same UNREADABLE or NOT BACKED UP line (once per batch through `reported`), or, for a path gone, the replay's own line. The batch then takes the no-differences path (6012), which, with `reported` set, leaves the matched time where it is and, after L1, writes nothing.
- When one would, nothing changes from today: the others drop out at the copy as before.

**Why it is right.**
- Each dropped entry is one the replay would have left as the version holds it. An unreadable file keeps its last copy, and a refused link with nothing at its place leaves nothing.
- A file readable at the check and not at the copy is today's case: one empty version, rare and right.
- The probe writes only into staging, which the scan empties after a cut, and only for a batch made of unreadable files and symlinks.
- No state is kept.

**Tests** (each fails on main unless marked a pin), in tests/test_long_links.py and tests/test_io_errors.py:
1. A full comparison whose only difference is an unreadable file, its size changed, as uid 65534 with mode 000:
   - no version;
   - the manifest's header change counter (bytes 24 to 27) unchanged;
   - one UNREADABLE line.
2. The same for an unchanged unreadable file, which the comparison calls a modify when its hash cannot be read.
3. A full comparison whose only difference is a link the vault refuses:
   - the probe is faked as `refuse()` fakes cp;
   - and, marked real, a long link on /dev/shm with the vault on an XFS basetemp;
   - no version, one NOT BACKED UP line.
4. A link whose path in the new version reaches PC_PATH_MAX (a deep tree in the basetemp): no version.
5. Pins:
   - an unreadable file beside a real change commits, as today;
   - a long link at a place where the tree holds an older short link commits, the link gone from the new version (test_the_previous_version_keeps_its_own_link_of_that_name);
   - an attrib under Only Sync Attributes of an unreadable file commits its metadata;
   - `test_a_full_comparison_meets_the_link_again_and_warns_again` still passes.
6. A one-file batch makes no lstat or open of its file before the estimate beyond the one lstat and one open of pass 2 (a recorder), and no probe.

**Cost.** On a normal batch: none when its first entry is not a create or modify; an lstat, an open and a close when it is. The probe runs only in a batch made of unreadable files and links. An empty version is saved wherever one was made.

**Docs.** The entry goes. README line 24 gains: "a full comparison that meets only such a link (or only files it cannot read) makes no version".

## 5. The lightness items

### 5.1 A batch with nothing to do commits nothing (L1)

**Today.** A batch whose events collapsed makes two sqlite commits and 10 fdatasyncs, in 321 syscalls:
- `delta_generate_backup_entries()` commits naming the version (10818), and `VaultManifest.commit()` (8809) always writes the `version` meta row;
- the no-differences path (6012-6023) then writes the skip fingerprint, the inner mounts and the matched time and commits again, whether they changed or not.

**The change.**
- `VaultManifest.commit(version_path)` writes the `version` row only when it names another version. A transaction that wrote nothing to the main database then commits with no I/O: a probe with Python's sqlite3 in TRUNCATE mode left the header's change counter (bytes 24 to 27) and the journal file as they were across a transaction of reads and writes to a temp table (as `seen` is), and moved the counter for an `INSERT OR REPLACE` of the same value, which is what `commit()` does today. Test 1 checks it on the real path.
- `set_skip_fingerprint()` and `set_inner_mounts()` write only a value that differs from the one recorded.
- **The matched time.** On the no-differences path it moves only after a full comparison (`touched is None`). A collapsed batch with no difference leaves it where it is: an older matched time is always true, and only widens the next full comparison's extended-attribute bound to the entries changed since then. Any committed version moves it as today.
- So a collapsed batch that reads nothing back commits nothing. One that reads a copy back commits that record, as it must.

**Why it is right.** Fewer writes, nothing new kept. A cut finds what the last commit left, and every value it carries is still true. The matched key's rule stays: "written only by `do_backup()`'s commits" (8852-8856).

**Tests** (each fails on main unless marked a pin):
1. A batch whose events collapsed (a file made and removed): the header change counter unchanged, and the journal file's size and mtime unchanged.
2. Pin: a full comparison with no difference makes one commit, the matched time moves.
3. Pin: a collapsed batch whose scope holds an unchecked copy commits its record.
4. Pin: a skip list change still commits its new fingerprint on the no-differences path.

**Cost.** Two commits (about 10 fdatasyncs) less for each collapsed batch, one for a no-difference full comparison.
- **Measure in the test VM:** `strace -f -c -e trace=fsync,fdatasync,syncfs` over 20 collapsed batches of the daemon, main against the branch.
- 20 batches show that the count per batch is the same every time, as it should be: it is set by the code path, not by timing.

### 5.2 No folder fsyncs off a pool after the commit point (L2)

**Today.** After the manifest's commit (6167), `do_backup()` fsyncs the job vault after `swap_current_version()` (6172), and `place_change_list()` (2155) fsyncs it after the rename. Each is an f2fs checkpoint: a one-file batch writes 455 KiB with 5 checkpoints, 418 KiB with 3 without them.

**The change.**
- Both fsyncs run only when the job vault is on a pool (`pool_guard.covers(job_vault)`, which `do_backup()` asks once as `on_pool` at 6066; the first version's path asks the guard the same way).
- Off a pool there is no fsync, and with it no mount table read (`fsync_vault_folder()`, 1878, reads one through `vault_disks()`).
- `place_change_list()` takes `on_pool`.

**Why it is right.** Once the manifest has committed V(n+1), a power cut can leave any mix of these, and the scan settles each:

| After the power cut | The scan |
|---|---|
| current_version still names V(n) | `move_current_version_forward()` |
| the list still in its private folder | `finish_r_commit()` (6851) places it |
| the previous list under its old name | `finish_previous_list()` renames it |

- The one state the scan refuses is a list that is nowhere: the private folder's removal kept and the rename that placed the list lost.
- On one filesystem that state cannot arise, as the removal comes after the rename:
  - ext4's and XFS's journals commit metadata in order;
  - an f2fs checkpoint is a snapshot of one instant, and its roll-forward recovery replays only fsynced files, never a folder's removal.
  - That is reasoned; the run below proves it on f2fs.
- Before the commit point nothing changes: the change list's fsync, in a new private folder, is an f2fs checkpoint, which puts every change of the tree on the disk before the manifest's commit, as today.
- On a pool each disk keeps its own order, so both fsyncs stay.

**Tests:**

### 5.3 A move keeps its rows' records, and moves them only once the rename is made (L3, L7)

**Today.**
- `VaultManifest.move_tree()` (9029) and `move_file()` (9044) leave the moved rows unverified (`UNVERIFIED`), so the verification reads each moved file back: lstat and 64 KiB. A rename of a folder of 2,000 files read 263.3 MB for a change that wrote 0.1 MB.
- `do_reverb_backup()`'s move branch moves the rows before `TreeWriter.rename()` (13238): "the move's rows are at dst already", so `rename()` records dst with `rows=False`.
- When the rename falls back to a copy, the target's rows are already gone. A record of the target, or of a folder under it, sized from its rows (`folder_usage()`, 13101, `rows=True`, as `remove_now()` from the sweep and `remove_queued()` call it) then counts nothing. That is the reading behind L7, not yet verified: the version before keeps a change list that says too little.

**The change.**
- **Records follow their inode.** `move_tree()` and `move_file()` change the path and keep each row's record and unchecked flag. A moved folder's own row is still added again (`manifest.add()` after the move), as its metadata is synced.
- **Rows move only after the rename.** The replay calls `move_tree()` / `move_file()` only after `writer.rename()` returned True.
  - `rename()` records dst with its own rows (`rows=True`, the default).
  - A fallback leaves the rows where they are. The undo branch after `copy_instead_of_move()` (which removed the rows `move_tree` put at the target) goes.
- **A moved file whose attributes the replay syncs** under Only Sync Attributes (`writer.file_meta()` after the rename) is marked vouched (`mark_vouched()`, 9000). The commit then reads its new metadata and keeps its hash (`take_dirty_records()`). Without Only Sync Attributes such a file is copied, as today.
- **Comments that said "a moved row is unverified"** are rewritten: `record_vouches()` (10158), `attribs_to_copy()` (10180) and `move_tree()`'s docstring. A swap's leftover now carries the record of the inode actually at its place, as rows move with renames and only with them, so it vouches only when the monitored file matches that inode.
- **The fuzz checks lists again.** tests/test_watcher_fuzz.py drops `says_too_little()` and its filter (REVERB_WATCH_FUZZ_LISTS goes).

**Why it is right.**
- **The invariant:** every row's record describes the inode at its path in the version.
  - A rename keeps the inode, its bytes and its metadata.
  - The record moves with it, and only when it moved.
  - What the replay writes onto it afterwards is recorded at the commit (vouched, or dirty for a copy).
- **The unchecked flag moves with the record,** so a copy not yet read back is read back at its new path.
- **After a cut before the commit,** the cut batch's rows roll back, and the roll-forward reads rows from the tree (`read_rows_from_tree()`).
- **After the commit point, a power cut cannot leave a committed record whose rename was lost:**
  - on f2fs the change list's fsync (a checkpoint, in its new private folder) put the renames on the disk before the manifest's commit;
  - on two renames the commit flush did;
  - on ext4 and XFS the manifest's fsync carries the earlier metadata in the journal (reasoned, as the README says of design R).
  - The row oracle below checks it under real power cuts.

**Tests:**
1. Docker (fails on main): a rename of a folder of 2,000 files reads none of them back (a recorder on `read_vault_record()`), and their rows keep their records and unchecked flags.
2. Docker (fails on main), for L7: a whole-tree comparison between `mv A B` and the watcher's read of it, then the batch with the move, which falls back to a copy. `view_truth.wrong_lists()` is empty: the version before says the right size.
   - If this test does not fail on main, the cause read above is wrong, and the build reports back before fixing.
3. **A row oracle,** `rows_match_vault(job_vault)` in tests/vault_oracle.py. For each row of the newest version with a record and `unchecked = 0`, the entry at its path matches it:
   - kind, mode, uid and gid;
   - for a file: size, mtime and tail hash;
   - for a link: its text;
   - a folder's mtime is left out, as its row records the monitored one.
   - It runs after every retry in tests/test_crash_harness.py's kill points (Docker) and in the power-loss sweeps (the VM). It passes on main, where moved rows hold no record.
4. Pins: a swap in one batch (`mv a t; mv b a; mv t b`) still copies both and comes out right; an attrib after a move in the same batch, under Only Sync Attributes, is right in the version and its row.
5. **The fuzz, lists checked:**
   - seeds 254, 372, 4444, 4492 and 14224 (round 22's teardown errors of this class) pass 3 of 3 alone, in containers;
   - seeds 0 to 5,999 run with no list error. Round 22's run of those seeds met 11 of this class.

**Cost.** A moved file is read back no more: 0 bytes where 263.3 MB was read for 2,000 files.
- **Measure:** `read_vault_record()` calls and `/proc/self/io` `rchar` of the batch, main against the branch, for that rename of a folder of 2,000 files.

**API.** The manifest's format does not change. The meaning of a moved row does:
- A 0.55.4 manifest's moved rows hold no record and are read back once, as before.
- A 0.55.4 daemon reading a 0.55.5 manifest finds records that describe their entries, which it trusts as any record.

A lessons entry (section 11).

### 5.4 One mount table for the batch, one after its walk (L4)

**Today.** A one-file batch through `backuper()` reads the mount table about 9 times, by reading the code:
- each of the two waits (`wait_for_path()`, 1229, through `vault_disk_problem()`, 4318);
- `PoolGuard()` (4356), once per path, as `pool_state()` (4210) reads it;
- `do_backup()` (5860);
- `drop_unmounted_entries()` after the verification (5777);
- `set_inner_mounts()` at the commit (6127, `current_mount_table()`);
- each `fsync_vault_folder()`.

The entry's measurement, of `do_backup()` alone with eight reads before 0.55.3, is 0.44 ms of CPU a read at 162 mounts.

**The change.** Two reads a batch:
- **At the batch's start.** `backuper()` reads the table once, at the top of its loop. Both waits take it for their first poll and read it live on every later poll. `PoolGuard(paths, mount_table)`, `do_backup(mount_table=...)` and `compare_scanned_folders()` take it.
- **After the walk.** The table `drop_unmounted_entries()` reads after the walk is the one `set_inner_mounts()` takes at the commit. A disk mounted after the walk is remembered by the next batch.
- The fsyncs off a pool go with L2.

**Why it is right.** The reads it replaces were a few milliseconds apart, so the shared table says the same. Every check that must see the table after a walk still reads it then.

**Tests.** Docker (fails on main): a counter on `read_mount_table()` over one one-file batch through `backuper()` (the harness's job runner) counts 2. The task first counts main's number and writes it in the handback.

**Cost.** About 7 reads, about 3 ms of CPU, less for each batch at 162 mounts.
- **Measure:** the counter, and `timeit` of 1,000 `read_mount_table()` calls on the host's table for the cost of one (the median).

### 5.5 The inode estimate counts what design R adds, so no du (L5)

**Today.** `get_backup_size_inode()` (10916):
- subtracts, for each deleted folder, its inode count from `du --inodes -csP` (`get_path_inodes()`, 8456, one process per batch), and 1 for each deleted file;
- counts an inode for a create only: "we do not count inode change for attrib / modify / move events".

That rule comes from 0.54, whose versions were whole trees of links: a delete made the next version smaller, and a modify put a copy where a link was.

**On design R a delete frees nothing, and a copy adds an inode.**
- A deleted entry goes into the previous version as its record, and stays in the vault until that version is pruned.
- A modify's copy, and an attribute change that copies, puts a new inode in the tree, while the old one stays in the previous version as its record (`TreeWriter.copy()` records by a hard link first).
- A move keeps its inode.
- So the vault's inode count rises by one for each copy and each folder the batch makes, plus the links it makes, and falls by nothing. Today's estimate undercounts a batch by what it deletes and by what it modifies.

**The change.**
- Deletes count no inode.
- Each entry the replay copies (`copies()` in `get_backup_size_inode()`) counts its inodes wherever it counts its bytes: one for a file, a walk's for a folder, with the same nesting rule as the bytes (`sized_folders`). The carried-in and written adjustments below it follow the same rule.
- `get_path_inodes()` goes, and with it the batch's du process and `ARGUMENT_LIMIT`'s use here.
- tests/harness.py's own use of du stays (a test tool).

**Why it is right.** It is the change-list rule of docs/lessons.md 2026-11-06 ("When a stored number changes meaning, rework every formula that reads it"), applied to the formula 0.55 missed. The suite's rule for the estimate (written ≤ estimate ≤ what the vault grew by) holds for inodes too, as the links stay left out. Nothing is stored.

**Tests.**
- Fails on main: a batch that deletes a folder of K entries, creates M files and modifies P files estimates M + P inodes (main: M - K), and runs no du (a recorder on `multiCMD.run_command()`).
- Fails on main: the vault's inode count after that batch, by the change lists, is at least the estimate above what it was before.
- Tests that pin the old rule move to this one.

**Cost.** One process (fork, exec, a walk of the deleted folder) less per batch that deletes a folder.

**Docs.**
- The entry goes.
- "Size estimates leave out a version's own small blocks" is unchanged: the links stay left out.
- Calls to confirm: under an inode limit, a batch that deletes or modifies prunes when it should, which can be a batch earlier than before.

### 5.6 The root's metadata is written only when it changed (L6)

**Today.** `record_root_meta()` (12545), through `TreeWriter.root_meta()` (13291), calls `setxattr` on the tree's folder every batch.

**The change.**
- It reads the folder's `ROOT_META_XATTR` first, and writes only when the encoded record differs, or when the read fails.
- A trimmed record (no xattrs) compares as the trimmed bytes it would write.
- The lines and `ROOT_META_TROUBLE` states are unchanged. `hand_over()`'s copy of the record to the skeleton stays.

**Why it is right.** A record equal byte for byte is the same record. Nothing is stored.

**Tests.**
- Fails on main: a batch that leaves the root's owner, mode, times and xattrs as they were makes no `setxattr` of `ROOT_META_XATTR` on the tree (a recorder).
- Pins: a chmod of the root writes it; a record too big still writes the trimmed one once and says so once.

**Cost.** One `setxattr`, and the inode write it can cause, less for nearly every batch, for one `getxattr`.
- **Measure:** the recorder's count over 20 one-file batches.

### 5.7 The restore marker's recopy field and `--accept`'s first sync stay (L8)

Both exist: `recopy_way_out()` (15480), `refuse_accept_unsynced()` (16764), `marker_recopy()` (16750), and the sync before `hand_over_folders()` in `accept_restore()` (16546). Both still do a job, so neither goes.

- **"recopy" is still needed.** "unsynced" lasts from the claim to the run's sync. "recopy" lasts until every entry was copied again and a sync of them succeeded (`restore_entry()`'s docstring, 16240-16256).
  - A recopy run that fails one entry, say B, syncs and clears "unsynced", while B still holds what the killed run wrote, which nothing vouches for. "recopy" makes the next run copy everything again.
  - It also holds a recopy while a disk of the vault's pool is missing.
  - The two keys could become one with that longer lifetime, but that saves no I/O and rewrites the restore's most-reviewed code. Not this round.
- **`--accept`'s first sync is still needed on a pool.**
  - Its copies need no sync: `--accept` runs only over a marker with no record, so the run that wrote them synced them through handles open since its claim.
  - A 0.55.1 marker carries no record either, but no 0.55.1 restore can still be running, and a handle opened at `--accept` could not vouch for its copies anyway.
  - What the sync still does: a run stopped during its hand-over leaves folders' owners, modes and times unsynced (its stop syncs only before its own sync). On one filesystem the marker's removal cannot reach the disk before them. On a mergerfs pool each disk keeps its own order, and without this sync a power cut could keep the marker's removal on one disk and lose those folders' metadata on another, silently.
  - Off a pool it costs one syncfs per `--accept`, a command run by hand, and keeping one path for both is simpler than a branch.

**Docs.** No change.

   - the sweep runs every step (`REVERB_CRASH_FULL=1`) with the checkpoint variants, not a stride;
   - the first version's path asks the guard;
   - a pool keeps both fsyncs.
7. **L3/L7:**
   - every exit from the replay's move branch (renamed, NotARealFolder, NotRenamed, any other exception) leaves rows that describe what the version holds;
   - `attribs_to_copy()`'s look back through moves still reads the right row;
   - the vouched mark after a moved file's attribute sync;
   - the row oracle runs in both the kill and the power-loss runs.
8. **L4:**
   - a wait that polls more than once reads the table live after its first poll;
   - the table after the walk is the one the commit remembers inner mounts from.
9. **L5:** every test that pinned the old rule (deletes subtracted, creates alone counted), and the nesting of the inode count under created, modified and carried folders.
10. **L6:** the comparison is of the exact bytes the write would write, the trimmed form included.

## 14. Questions for the user

1. **Known limitation? A lost manifest stops an unmounted inner disk being paused.** Found while tracing F1; outside the round.
   - **What the operator sees:** when a job's vault database is lost or unreadable (removed or damaged from outside), it forgets which inner mounts it had seen. An inner disk that is unmounted at that moment then looks like an empty folder. The next comparison records its files as deleted in the newest version (older versions keep them), and when the disk is mounted again they are all copied back.
   - **Why not fix it:** remembering inner mounts outside the database is new state for a case that needs two faults at once, and no live job has an inner mount.
   - **Revisit when:** a job gets an inner mount, or a vault database is ever lost on a live vault.
   - The user has not asked for this.
   - Options:
     1. "Known limitation (Recommended)": the entry as above.
     2. "Fix it in a later round": keep the inner mounts in a second place (the job vault's own folder, say).

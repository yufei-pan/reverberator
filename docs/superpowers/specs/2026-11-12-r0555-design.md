# Round 0.55.5: four deferred fixes and the lightness round

For the release after 0.55.4. Branch r0555, from main ca260eb (0.55.4, live). Every "fails on main" below means on ca260eb.
The round closes the deferred entries of docs/limitations.md that name it, three of them through one fix at source, and
the lightness items whose "Revisit when" names the lightness round. The no-copy move into a new folder is not in it: it
gets its own design round after this one.

Revised on 2026-11-12 after the spec check, the design review (with probes), two second opinions and the user's picks
below. The rulings behind the revision are in .superpowers/sdd/2026-11-12-r0555/rulings-1.md (not tracked).

## The user's words

Their goals, verbatim:
- "I want this to be as light and as fast as possible... cause it is an backup solution, so it is designed to always in run the background. so every little bit will sum up to a lot over days month years."
- "simpler and smarter is better"
- "one of the core for reverberator is reuse existing linux features and easy browse / restore."

This round: "continue next phase please", then the pick "Fixes + lightness, one round (Recommended)". As offered:
- one spec for the four deferred fixes and the lightness items, since they touch the same commit and roll-forward code;
- built as small separate tasks, with the footprint measured first;
- the no-copy move into a new folder gets its own design round after. It is not in this round.

Their picks on this spec, 2026-11-12:

  version stays; the size limit can be passed until the next batch prunes, section 10).
- F4, a link whose path in the version reaches 4,096 bytes: "Leave that case out (Recommended)" (section 4).

## 1. Every name a cut batch recorded gets version n's entry back, at the scan (F1)

**Today.**
- `prepare_roll_forward()` (7022), at the scan, returns what the cut batch recorded in the previous version, version n (`give_back_folder_times()`, 6894: real folders, files and links, each of the kind it was), and marks the rows of the recorded files unchecked in a transaction of its own (`VaultManifest.mark_unchecked()`, 9072).
- `roll_forward_entries()` (7080) copies again each recorded name whose monitored path is a regular file now (`again`), trusted by the comparison and replayed as a modify.
- A recorded name it does not copy again keeps the cut batch's copy in the tree with an unchecked row: a file under an inner mount paused at the retry, one whose mount goes during the roll-forward's walk (`drop_unmounted_entries()`, 5769, drops the forced modify), one in a folder the walk cannot read (its rows are kept), and a name of another kind under a paused mount.
- The next full comparison that can see it reads it back by size, mtime and last 64 KiB. A copy all NUL that ends in 64 KiB of zeros passes; so does a page lost before the tail, and without a reboot the read comes from the page cache. Those are the three entries.

**The change: put version n's entries back before anything is compared.**
- A new scan step, `put_back_recorded(previous, tree, recorded)`, runs in `prepare_roll_forward()` right after `give_back_folder_times()`. It runs under the scan's locks and inside its VaultUnit (`get_vault_info()`, 7518), at every scan that finds a tree, before the attempt reads a row. For each name of `recorded`, in its order (a folder right before what is in it), the tree's entry there becomes version n's:
  - **a file or a link of version n:** nothing when the tree's entry is that inode already (same `st_dev` and `st_ino`); otherwise whatever the tree holds there goes (`remove_entry()`), and `link_or_copy(kept, tree's place)` (12618) puts version n's entry there, a link as itself;
  - **a real folder of version n:** nothing when the tree holds a real folder there; otherwise whatever the tree holds there goes, and a folder is made there (`os.mkdir()`). Its entries are recorded names of their own, which come back one by one after it: `record()` (13111) recorded such a folder whole (exchanged in, or every entry kept by a link) before the tree's folder could be replaced or removed;
  - **then, innermost first,** each recorded folder in the tree gets version n's folder's metadata (`copy_file_meta()` from the previous version's folder), as the links made in it moved its times and the cut batch may have changed its owner or mode. Version n's folder metadata is the previous version's, whose mtime `give_back_folder_times()` has just given back.
- **No staging and no rename.** The tree is no version until its commit; between the scan and the commit nothing reads it but the scan and the batch after it, and a restore of version n never reaches a recorded name through a forward link, as every folder above one is real in version n. A cut leaves the previous version as it was, so the next scan computes the same `recorded` and puts back again; a name left empty between its removal and its link is linked then. On a pool the link goes through the pool, as `put_back_forward_links()`'s links do, and `link_or_copy()` copies where the pool answers EXDEV between its disks.
- **Where hard links are refused** (`NO_HARD_LINK_ERRNOS`, 11401: EMLINK, a FUSE or network filesystem, EXDEV between a pool's disks), `link_or_copy()` copies: a new inode holding version n's bytes. When any put-back copied, the scan flushes the vault's disks through its own unit (`flush_or_fail()`) before it returns, so those copies are on the disk, heard through handles opened before they were written, before the attempt goes on. A failed flush raises JobFailure, which fails the scan and the attempt with it, and the next attempt puts back again.
- **Order in `prepare_roll_forward()`:** `remove_shadowed_links()`, `put_back_forward_links()`, `remove_mixed_names()`, `give_back_folder_times()`, `put_back_recorded()`. The transaction with `mark_unchecked()` goes, and `VaultManifest.mark_unchecked()` with it. `prepare_roll_forward()` returns `recorded` as before.
- **tests/test_tree_writes.py:** `USERS` gains `'put_back_recorded': {'remove_entry', 'copy_file_meta'}`, a scan step that writes the tree directly before any writer runs, as `remove_mixed_names()` does.
- **What stays in the roll-forward:**
  - `read_rows_from_tree()` (7048), which now reads the tree after the put-back: the row of each recorded name reads version n's entry, so nothing reads rows a second time;
  - the forced modify of each recorded name whose monitored path is a regular file (7123-7127): only it carries a change of the cut batch that a comparison cannot see (a rewrite at its size with its mtime set back);
  - the trusted set for those names (7117): it leaves their contents to that copy. Without it an attribute difference found at one would take the copy's place in `found` (the `again` loop passes over a path already found), and under Only Sync Attributes the replay would sync its metadata only;
  - `new_in_tree()` over a rebuilt manifest.
- **What it covers, with no case of its own:** a paused mount at the retry, a mount gone during the walk, a folder the walk cannot read, a name of another kind (a link, or a folder, that a file replaced, or the other way round), a move under a paused mount (the design review's probe B: `mv disk/a disk/b`, cut, retried paused, left the version with neither), and any later reason a recorded name is not replayed. Each holds version n's entry, under version n's row.
- **What it does not touch.** Creates of the cut batch have no record. With the manifest standing they have no row, and the roll-forward's sweep (`sweep_version_folder()`, 10607) removes those the comparison does not take. Over a rebuilt manifest no inner mount is remembered, so none is paused (the deferred entry of section 10).

**Why it is right (crash safety).**

| State a stop, a kill or a power cut leaves | How the next start finishes it |
|---|---|
| Cut inside the put-back: a name emptied and not linked yet, or a folder made and partly filled, its metadata not given yet | The previous version is unchanged, so `recorded` is the same; the next scan links what is missing, leaves what is version n's already, and gives every recorded folder its metadata again |
| Cut after the put-back, before the commit | The next scan finds version n's inodes there and leaves them |
| Power cut with some of the put-back lost | One of the two states above |
| Committed | Each recorded name holds version n's inode, whose bytes version n's commit flushed, or, on a vault that refuses hard links, a copy of it the scan flushed; its row is version n's, read from that entry |

- Version n keeps its record at a name put back: a real entry, the tree's inode (or the copy's original where hard links are refused). It reads right, and `measure_previous()` (7199) counts a shared inode for the tree only. V(n+1)'s change list does not name it, as V(n+1) holds there what version n held; the roll-forward's own entries, copies again included, are listed as today.
- The roll-forward always runs the commit flush (`do_backup()`, 6134).
- Nothing vouches for bytes no flush of their own unit covered, so a write error another program's sync saw has nothing left to hide.

**Tests** (each fails on main unless marked a pin):
1. tests/test_vault_units.py, `test_a_cut_batchs_copy_under_an_inner_mount_paused_at_the_roll_forward_is_read_at_the_next_full_comparison`, renamed for what it now checks and widened:
   - parameters as today (`stays` a pin, `paused_at_the_retry`, `goes_during_the_walk`), plus `unreadable_folder` (the file's monitored folder mode 000). `unreadable_folder` runs in Docker only, as uid 65534: as root a mode-000 folder reads, so the VM gate deselects it by name and no skip shows there;
   - right after the roll-forward, before the mount is back: the newest version's file has the previous version's record's `st_ino` and version n's bytes (main: the cut copy, all NUL);
   - its row is version n's record, with the unchecked flag version n had;
   - the next full comparison, with the mount back, reads nothing back for that rel (a recorder on `read_vault_record()`), copies it, and the newest version holds the file's bytes.
2. Other kinds, under a paused mount: a user's link the cut batch replaced by a file (the link comes back), a folder replaced by a file (the folder comes back whole, with version n's mode and times), a file replaced by a folder holding a new file (the file comes back, the folder goes).
3. The design review's probe B: under an inner mount, `mv disk/a disk/b` (a folder of files), the batch cut before its commit, then retried with the mount paused. The newest version holds `disk/a` as version n held it and no `disk/b`; its rows name `disk/a/*`; the row oracle (5.3) passes, and so does `view_truth.wrong_lists()` for V(n)'s list. Main holds neither, until the mount is back.
4. A vault that refuses hard links (`os.link` faked to raise EMLINK): the put-back copies, the scan flushes once through its unit (a recorder), and the newest version holds version n's bytes at the name.
5. tests/test_crash_harness.py, `test_no_copy_again_and_no_unchecked_marks_fails_the_oracle` becomes "no copy again and no put-back fails the oracle": with `roll_forward_entries()`'s copy again and `put_back_recorded()` both stubbed out, the oracle fails.
6. **Power-loss (the test VM),** tests/test_crash_power_loss.py, a new test in the shape of `test_a_power_cut_after_a_checkpoint_before_the_commit_flush_copies_an_attribute_changes_copy_again`:

   - the checkpoint, then the power cut before the commit flush;
   - the retry with that mount paused, then the next full comparison with it back;
   - the newest version holds the file's bytes after the retry and after the comparison. Main keeps it all NUL after both.
   - The page-cache case (no reboot) cannot be run in a container: test 1's assertion that the entry is version n's inode covers it, as nothing is read back.

**Cost.** Only at a roll-forward, at its scan: an lstat of each recorded name in the tree; an unlink and a link for each one the tree no longer holds as version n's inode (a folder: a mkdir, then its entries one by one); one `copy_file_meta()` per recorded folder; one flush when any put-back copied. A recorded folder the roll-forward then finds deleted costs one link per entry before its removal. Nothing on any other path. `prepare_roll_forward()` loses its transaction (about 5 fdatasyncs) per roll-forward.

## 2. A pool vault's handles open where the job vault is (F2)

**Today.** `VaultUnit.__init__()` (1967) opens, on a pool, an fd of each branch's root (`open_branch()`, 2019). `holding()` (2035) picks a handle by the `st_dev` of the job vault's folder on each branch, and raises `not_opened()` when no handle has it. A job vault folder on a branch that sits on a filesystem of its own (a mount nested under the branch, a btrfs subvolume) has a `st_dev` no handle has, so every sync raises and every attempt fails.

**The change.**
- `open_branch()` opens `os.path.join(branch, self.rel)`, or, when that is not there, its nearest existing parent, never above the branch.
- Branches whose handles share a `st_dev` keep one fd, as today.
- `holding()` is unchanged. A job vault folder made on a branch later lands on the filesystem of the nearest parent that existed, so its `st_dev` matches. A mount made at a folder on the way since the unit began has a `st_dev` no handle has, and `holding()` raises, as it does for a joined disk.
- **The restore takes the same rule.** `open_restore_disks()` (16095) opens each disk's branch root (`vault_disks(folder, roots=True)`), one handle per disk name. For a target whose folder on a branch is a nested mount, `syncfs` writes out the branch root's filesystem, not the one holding the target, and the restore says done. Now:
  - on each branch it opens the restore folder's place, or its nearest existing parent, never above the branch;
  - it keeps one handle per filesystem, by `fstat().st_dev`, as the daemon's unit does, with a disk's name kept for its messages (a disk whose branches lead to two filesystems gets two handles);
  - a branch the user cannot open is warned of once (`report.cannot_sync()`) and left out, and one that fails otherwise keeps its OSError for its syncs to fail with, as today;
  - `sync_restore()`'s check for a disk that joined goes by filesystem too, as `holding()` does: each branch the pool lists at the end whose folder is there (`os.stat()`) on a filesystem no handle is of fails the restore, as a joined disk does today. A branch left out at the claim as one the user cannot open is passed over, as today. This also catches a mount made at the folder's place on a branch while the restore ran, which today's check by disk name misses.
  - This is beyond the entry: Calls to confirm.

**Why it is right.** Linux reports a filesystem's writeback error to a syncfs through any fd of that filesystem opened before the error (the flush spec, section 2). An fd at the job vault's own folder, or at its nearest existing parent, is an fd of the filesystem that holds or will hold it. Nothing is stored; a cut closes the fds with the process.

**Tests** (each fails on main):
1. tests/test_pool_writer.py (or the flush round's tests/test_vault_units.py), on `harness.FakePool` with the errseq stand-in: a branch whose job vault folder is a symlink to a folder on /dev/shm, a stand-in for a nested mount, as `os.open()` and `os.stat()` follow it to another `st_dev`.
   - A batch commits (main fails with "is not on a filesystem this step opened").
   - `fail()` and `seen_elsewhere()` on the /dev/shm folder between the copies and the commit flush: VAULT WRITE ERROR, nothing commits. This pins that the handle is on that filesystem.
2. A branch whose folder above the job vault (`<branch>/mnt`) is a symlink to a folder on /dev/shm, the job vault below it missing on that branch when the unit opens, then a copy landing there: the sync goes through the handle opened at `<branch>/mnt`, with no error. Main raises, as its handle is the branch root's, on another filesystem.
3. A restore onto a FakePool target whose folder on a branch is such a symlink: `fail()` on /dev/shm, and the restore's sync reports the write error. Main says done.
4. A restore during which the restore folder's place on one branch becomes a symlink to a folder on /dev/shm, a copy landing there: the restore fails, naming the disk. Main says done.
5. **The test VM:** the same as test 1 with a real tmpfs mounted at the job vault's folder on a branch of a real mergerfs pool; and test 3 likewise.

**Cost.** None off a pool. On a pool of B branches: B opens at a deeper path (a few more path components looked up), once per unit; a restore's check stats the folder on each branch once, as today.

**Docs.** The entry goes. README line 54 goes.

## 3. One version per start (F3)

**Today.** In `backuper()` (4895):
- a batch resumed from the pending file at a start is `round_tripped`; it is replayed and verified on its own touched scopes, and commits a version;
- then `follow_up` (5095) runs a full comparison, which commits a second version when anything changed while the daemon was down;
- before any of it, `load_pending_transactions_for_resume()` walks the whole monitored tree (`get_monitor_path_most_recent_change_time()`, 3884) and replays the pending file only when the tree's newest mtime is at least 1 s older than the file; otherwise the tree is compared in full;
- a batch handed back after a failed attempt is never replayed: the job's next attempt starts from a fresh JobStartup with no pending file (none is written on a job failure), and appends a full scan, which absorbs it (5012-5014). That is one version already, a full comparison's. F3 leaves it as it is.

The live job's restart of 2026-11-10 made two versions a second apart. Round 7's rule, a resumed batch is always followed by a full comparison, decides from the downtime and not from the batch (docs/lessons.md, 2026-10-27).

**The change.** A resumed batch is checked against the whole tree, in its own version:
- **`backuper()`.** For a round-tripped batch:
  - `scan_folders` is emptied, as the whole tree covers them;
  - `matched_since` is `time.time_ns()`, taken before `do_backup()`, as for a full comparison;
  - `do_backup()` is told `whole=True`; `touched` stays the batch's own;
  - `follow_up` goes.
- **`do_backup()`, for every batch with no tree to roll forward,** in this order (F4 shares it; today the paused drop is an `elif` after the comparison of an empty batch, 6004-6011, so a batch it emptied returned "No differences" with nothing compared):
  1. `drop_untracked_deletes()` (4577), as today;
  2. the paused drop (`drop_entries_under()` of the paused folders), moved up from its `elif`;
  3. F4's check (section 4);
  4. a batch left with no entry is a batch with no entries. With `whole`, `touched` becomes `None`: a full comparison (`delta_generate_backup_entries()`, 10761, once, with folder times and `full_comparison_since()`). Otherwise the places it touched are compared, as today. `drop_unmounted_entries()` and F4's check follow;
  5. only then the no-differences path.
- **With entries left and `whole`,** `do_reverb_backup()`'s `verify()` (14077) compares the whole tree, as a full comparison compares it:
  - `TouchedScopes([''], [], None, full_comparison_since(vault_info_dict, manifest.matched))`, so extended attributes are compared from the bound a full comparison uses;
  - folders' mtimes, but not those of the folders the replay wrote into (`written.rels` at the time of the comparison): `settle()` gives those the monitored folders' times anyway, and a time compare would add an attrib row to the change list for each.
  - Its sweep (`sweep_version_folder()`) keeps the batch's own touched scopes, as on main. The tree is a fresh hand-over, holding version n's entries and what this batch writes; only the batch's own moves can leave a fallback's leftover, and the verification's fixes make no rename.
  - The roll-forward's verification, already whole, gets the folder times and the bound too (do_backup() passes `whole` for it), and keeps its whole sweep: the cut batch may have left anything.
- **The resume check goes.** `load_pending_transactions_for_resume()` replays the pending file without walking the tree: the replayed batch's version is now checked against the whole tree, which is what the check stood in for. A change made after the pending file was written is a difference like any other. `get_monitor_path_most_recent_change_time()` goes with it, and so does the loader's `skip_list` argument. The memory check and the check of rows sharing a time stay.

**Why it is right.**
- Round 7's rule stays met: every resumed batch has the whole tree compared before its version commits, with the bounds a full comparison uses. The replay first keeps the batch's moves as renames, which a comparison alone would turn into copies.
- `matched_since` taken before the batch holds: every change made before it is in the tree when the verification walks it, and every one after it comes as an event (the watcher is watching before the batch is taken: `startup.watching`).
- A stale pending file (one an earlier stop left, not loaded since, as "An older pending file replayed after a stop dropped changes" describes) replays what it holds, and the whole-tree check then finds everything that differs, as a full comparison would. The result is a full comparison's, with the pending moves kept as renames.
- **No new state, two parts removed (`follow_up`, the resume walk).** A stop, a kill or a power cut mid-batch leaves what it leaves today:
  - before the hand-over, the batch goes back to the queue, then to the pending file on a stop (the next start applies the same rule), or to the next attempt's full scan on a job failure;
  - after it, the roll-forward compares the whole tree.
- **The size limit.** What changed while the daemon was down is found by the whole-tree check, after the size estimate and the prunes, so that version can pass the vault's Backup Size Limit (or inode limit) by it, until the next batch prunes. The design review's probe F: limit 3,600,000 bytes and 2 MiB added while down left V0 to V2 at 4,194,306 bytes, where main's follow-up comparison pruned V0 first (3,145,730). The user approved it as a known limitation ("Keep it, accept the overshoot"; section 10).

**Tests** (each fails on main unless marked a pin):

4. 8. Pins, a resumed batch whose attempt fails: before the hand-over (a JobFailure at the size estimate), the next attempt's full scan makes one version; after it (a JobFailure at the commit flush), the roll-forward makes one version. As on main.

- The tests that pin the resume check change with it: tests/test_pending.py's `test_load_discard_when_monitor_not_older` (it now loads), tests/test_skip_list.py's `test_resume_check_ignores_changes_in_skipped_paths` and `test_pending_resumes_when_only_skipped_paths_changed`, and tests/test_io_errors.py's `test_resume_check_refuses_after_a_read_error` go with the walk.

**Cost.**
- **At a start with a batch pending:**
  - Saved: one version's hand-over (a skeleton with one forward link per root entry and the exchange), its change list (whose fsync is an f2fs checkpoint), its manifest commit (about 5 fdatasyncs), the current_version swap and the list's placement, under a Keep count one prune, and the resume check's walk of the monitored tree (an lstat of every entry).
  - Added: nothing. The whole-tree comparison is the follow-up's, moved into the batch, and the sweep keeps the batch's own scopes.
- **Measure in the test VM:**
  - an f2fs loop image, with a tree of the larger live job's shape (about 19,000 folders and 123,000 files, sized as the footprint run counted them);
  - a start with a one-file pending batch and one file changed while down;
  - main against the branch, alternating, three runs each, as round 22's benches ran;
  - wall time, the start's `lifetime_write_kbytes` delta and its foreground checkpoints (`cp_foreground_calls`).
  - Three runs, because the alternation is what cancels host drift.
- With nothing added, the branch should win on all three. If it costs more in any of them beyond its runs' spread, the build stops and reports. Writes and checkpoints weigh first, wall time second: the daemon's goal is to stay light over years, and a start is rare.

**Docs.**
- "A start with changes pending makes two versions", "A resumed batch of only untracked deletes walks the tree twice" and "An older pending file replayed after a stop dropped changes" go. The last one's miss that is left, a same-size rewrite that kept its mtime, is the whole-tree comparison's blind spot, which "A rewrite made while down that keeps size and mtime" already names.
- A new known limitation, approved: "A start with changes pending can pass the size limit until the next batch" (section 10).
- README line 16 becomes: "...; a batch resumed after a restart (one of scans only too) is replayed and then checked against the whole tree, as a full comparison checks it, before its version commits, so one version holds the batch and what changed while the daemon was down; a batch put back after a failed backup is compared whole by the next attempt." Lines 38 and 39 go. A line for the new limit (section 10).
- A lessons entry (section 11).

## 4. A batch whose every entry drops out is compared as one with none (F4)

**Today.** An entry the replay cannot apply is left out at the copy (`finish_copies()`, 8108):
- an unreadable file keeps its last copy, with an UNREADABLE line;
- a symlink whose text or path the vault's filesystem refuses is left out, with a NOT BACKED UP line (`link_too_long()`, 8088).

By then the tree is handed over, so the batch commits a version that changes nothing. A full comparison meets the same entries every time (the unreadable file's row keeps its old record; the left-out link has no row), so each start, interval or overflow makes one more empty version. Under Keep N each pushes the oldest out. An event batch of such a file alone does the same at every write.

**The change.** For every batch with no tree to roll forward, at step 3 of section 3's order (after the untracked deletes and the paused drop, before the no-differences path, the estimate, the prunes and the hand-over), and again on what the comparison of a batch with no entries found (step 4):
- **Would any entry change the version?** The check stops at the first entry that would, in three passes, cheapest first:
  1. A delete, a move, or a folder's entry (its path ends with /): it changes the version. No syscall.
  2. Every other entry (a create, a modify or an attrib of anything but a folder): an lstat of its monitored path:
     - a regular file `source_readable()` (7885) opens, or an entry of another kind (a FIFO, a socket, a device, which cp -a copies as itself): it changes the version;
     - a regular file it cannot open, or a path that cannot be looked at: it drops out, as the copy keeps the last copy. Under Only Sync Attributes an attrib of such a file drops out the same way: its record cannot vouch (the tail cannot be read), so the replay copies it, and the copy keeps the last copy (the design review's probe D);
     - a path gone: it drops out, as the replay passes over it; what it touched is compared below;
     - a symlink: pass 3.
  3. Only if every entry is still in doubt, each symlink entry is probed. It changes the version when the newest version (`latest_version_info.path`, the tree before the hand-over) holds an entry at its place, as leaving it out then removes that entry. Otherwise it changes the version unless the vault refuses its text: `os.symlink(text, <staging>/.link-probe-<uuid>)` answers ENAMETOOLONG. Staging is made first when it is not there (`os.makedirs(exist_ok=True)`), and the probe is unlinked at once. Any other error counts as "would change", and the copy says what it is.
- **When none would:** each entry is logged as the copy or the replay would log it, with the same UNREADABLE or NOT BACKED UP line (once per batch through `reported`), or, for a path gone, the replay's own line, and the batch is cleared.
  - At step 3, the cleared batch is a batch with no entries (section 3's step 4): the places it touched are compared (the whole tree for a resumed batch), and the check runs again on what that finds.
  - At step 4 (a full comparison's result, or the comparison of a cleared or collapsed batch), the cleared batch takes the no-differences path. With `reported` set, that path leaves the matched time where it is and, after L1, writes nothing.
- When one would, nothing changes from today: the others drop out at the copy as before.
- **A link whose path the vault refuses is left out of the check.** Its path in the new version reaching the vault's path limit (4,096 bytes on Linux) is not caught: the probe sits at a shorter path, and the new version's name is not known until it is made. Such a link, where no regular file's path in the version is as long (one would fail every backup, 8093), still makes one empty version per full comparison. The user's pick, "Leave that case out (Recommended)": the narrowed known limitation of section 10.

**Why it is right.**
- Each dropped entry is one the replay would have left as the version holds it. An unreadable file keeps its last copy, and a refused link with nothing at its place leaves nothing.
- A batch whose entries all dropped out is still compared where it touched: a change its collapse hid is found there, as main's verification finds it. The design review's probe H: a create of a file gone since, beside `create tmp; mv tmp f; rm f` with f in the vault, collapses to the create alone; the comparison of the touched places finds f deleted.
- A file readable at the check and not at the copy is today's case: one empty version, rare and right.
- The probe writes only into staging, which no reader reads and the scan empties, and only for a batch made of unreadable files and links. That it runs before `locks.take()` (6040) is no break of the rule at 5854, which keeps restores from reading the tree while it changes: the comparison already commits the manifest without the locks.
- No state is kept.

**Tests** (each fails on main unless marked a pin), in tests/test_long_links.py and tests/test_io_errors.py:
1. A full comparison whose only difference is an unreadable file, its size changed, as uid 65534 with mode 000:
   - no version;
   - the manifest's header change counter (bytes 24 to 27) unchanged (needs L1, task 3);
   - one UNREADABLE line.
2. The same for an unchanged unreadable file, which the comparison calls a modify when its hash cannot be read.
3. A full comparison whose only difference is a link the vault refuses for its text:
   - the probe faked by a fake of its own on `os.symlink` into staging (`refuse()` fakes only cp);
   - and, marked real, a long link on /dev/shm with the vault on an XFS basetemp;
   - no version, one NOT BACKED UP line.
4. An attrib under Only Sync Attributes of a mode-000 file (uid 65534): no version, one UNREADABLE line. Main commits a version with the copy as it was.
5. Probe H's batch: the version removes f (a pin on main; it fails on a check that skips the comparison of the touched places).
6. Pins:
   - an unreadable file beside a real change commits, as today;
   - a long link at a place where the newest version holds an older short link commits, the link gone from the new version (test_the_previous_version_keeps_its_own_link_of_that_name);
   - `test_a_full_comparison_meets_the_link_again_and_warns_again` still passes;
   - a link whose path in the new version reaches 4,096 bytes (a deep tree in the basetemp) still commits one version per full comparison: the narrowed limitation.
7. A one-file batch makes one lstat, one open and one close of its file before the estimate, and no probe (a recorder).

**Cost.** On a batch whose first entry is a delete, a move or a folder's: none. Otherwise one lstat, one open and one close of its first file: about 1.2 µs of CPU (the median of 7 runs of 20,000 on the host, a cached file), and no I/O, as the copy opens the same file right after. The probe runs only in a batch made of unreadable files and links. The spec check asked whether to run the check for full comparisons alone: it runs for every batch, as an event batch of a file the daemon cannot read (another user's mode-600 file written again and again) makes one empty version per write on main.

**Docs.** The entry narrows (section 10). README line 24 gains: "a full comparison that meets only files it cannot read, or only links whose text the vault refuses, makes no version; one that meets only a link whose path in the version reaches 4,096 bytes still makes one (a known limit)".

## 5. The lightness items

### 5.1 A batch with nothing to do commits nothing (L1)

**Today.** A batch whose events collapsed makes two sqlite commits and 10 fdatasyncs, in 321 syscalls:
- `delta_generate_backup_entries()` commits naming the version (10818), and `VaultManifest.commit()` (8809) always writes the `version` meta row;
- the no-differences path (6012-6023) then writes the skip fingerprint, the inner mounts and the matched time and commits again, whether they changed or not. `record_matched()` (8857) carrying the time over rewrites the same row.

**The change.**
- `VaultManifest.commit(version_path)` writes the `version` row only when it names another version. A transaction that wrote nothing to the main database then commits with no I/O: a probe with Python's sqlite3 in TRUNCATE mode left the header's change counter (bytes 24 to 27) and the journal file as they were across a transaction of reads and writes to a temp table (as `seen` is), and moved the counter for an `INSERT OR REPLACE` of the same value, which is what `commit()` does today (the design review ran it again on sqlite 3.46.1). Test 1 checks it on the real path.
- `set_skip_fingerprint()`, `set_inner_mounts()` and `record_matched()` write only a value that differs from the one recorded.
- **The matched time.** On the no-differences path it moves only after a full comparison (`touched is None`). A collapsed batch with no difference leaves it where it is: an older matched time is always true, and only widens the next full comparison's extended-attribute bound to the entries changed since then. Any committed version moves it as today.
- So a collapsed batch that reads nothing back commits nothing. One that reads a copy back commits that record, as it must.

**Why it is right.** Fewer writes, nothing new kept. A cut finds what the last commit left, and every value it carries is still true. The matched key's rule stays: "written only by `do_backup()`'s commits" (8852-8856).

**Tests** (each fails on main unless marked a pin):
1. A batch whose events collapsed (a file made and removed): the header change counter unchanged, and the journal file's size and mtime unchanged.
2. Pin: a full comparison with no difference makes one commit, the matched time moves.
3. Pin: a collapsed batch whose scope holds an unchecked copy commits its record.
4. Pin: a skip list change still commits its new fingerprint on the no-differences path.

**Cost.** Two commits (about 10 fdatasyncs) less for each collapsed batch, one for a no-difference full comparison.
- **Measure in the test VM:** `strace -f -c -e trace=fsync,fdatasync,syncfs` over 20 collapsed batches of the daemon, main against the branch.
- 20 batches show that the count per batch is the same every time, as it should be: it is set by the code path, not by timing.

### 5.2 No folder fsyncs off a pool after the commit point (L2)

**Today.** After the manifest's commit (6167), `do_backup()` fsyncs the job vault after `swap_current_version()` (6172), and `place_change_list()` (2155) fsyncs it after the rename. Each is an f2fs checkpoint: a one-file batch writes 455 KiB with 5 checkpoints, 418 KiB with 3 without them.

**The change.**
- In `do_backup()`, both fsyncs run only when the job vault is on a pool (`pool_guard.covers(job_vault)`, which `do_backup()` asks once as `on_pool` at 6066; the first version's path asks the guard the same way).
- Off a pool there is no fsync, and with it no mount table read (`fsync_vault_folder()`, 1878, reads one through `vault_disks()`).
- `place_change_list()` takes `sync`, which `do_backup()` passes as `on_pool`.
- `finish_r_commit()` (6851), the scan's finish of a commit a cut stopped, keeps both fsyncs on every filesystem: it runs once after a crash, and on a pool it is the step that puts the swap on its disk before the list is placed.

**Why it is right.** Once the manifest has committed V(n+1), a power cut can leave any mix of these, and the scan settles each:

| After the power cut | The scan |
|---|---|
| current_version still names V(n) | `move_current_version_forward()` |
| the list still in its private folder | `finish_r_commit()` places it |
| the previous list under its old name | `finish_previous_list()` renames it |

- The one state the scan refuses is a list that is nowhere: the private folder's removal kept and the rename that placed the list lost.
- A power cut leaves the state of one instant, a prefix of the batch's steps, and the removal comes after the rename. Keeping the removal without the rename would be the filesystem losing a file from a folder in use. On one filesystem that cannot happen:
  - ext4's and XFS's journals commit metadata in order;
  - an f2fs checkpoint is a snapshot of one instant, and its roll-forward recovery replays only fsynced files, never a folder's removal.
  - The sweeps below run it on all three.
- Before the commit point nothing changes: the change list's fsync, in a new private folder, is an f2fs checkpoint, which puts every change of the tree on the disk before the manifest's commit, as today.
- On a pool each disk keeps its own order, so both fsyncs stay.
- A vault on btrfs stays under its known limitation, "Vaults on btrfs": the crash promise does not cover it today, and nothing here is run there.

**What the operator sees.** Off a pool nothing after the commit point is fsynced. After a power cut within the filesystem's own commit interval (an f2fs checkpoint, 60 s by default; ext4's journal, 5 s; XFS's log, about 30 s), the version that batch made is listed by status, history and restore only once the daemon's next start has scanned the vault and placed its list (`finish_r_commit()`): until then `list_versions()` (14266) leaves out a version folder with no change list, and a restore of the version before reads right, through its forward links. Nothing is lost. A kill at that step leaves the same state today; L2 widens it to a power cut. This needs the user's OK as a known limitation: question 1 in section 14.

**Tests:**
1. Docker (fails on main): an off-pool one-file batch makes no `fsync_vault_folder()` call and no mount table read after the manifest's commit.
2. Pins: on FakePool both are made; a scan finishing a commit a cut stopped (`finish_r_commit()`) makes both, off a pool too.
3. **Power-loss, the test VM:**
   - `REVERB_CRASH_FULL=1` over `test_every_step_survives_a_power_loss` and `test_every_step_survives_a_power_loss_after_a_checkpoint` (`midway` and `just_before`), both `only_sync` values, every step, including the ones after the commit;
   - plus `test_a_power_loss_that_keeps_the_placement_and_loses_the_rename_is_finished`;
   - all must pass, with the row oracle of 5.3.
   - Over all its steps, the `just_before` sweep checkpoints the disk at every point of the batch and cuts one step later, so each state a checkpoint taken at any moment can keep is met, the ones after the commit point included.
4. **The same sweep on ext4 and on XFS, the test VM,** a gate of its own. The sweep takes the image's filesystem as a parameter (tests/scratch_images.py's `LoopImage` gains `mkfs.ext4` and `mkfs.xfs` beside `mkfs.f2fs`; only `LoopImage` and `needs_f2fs` there are bound to f2fs). The shutdown ioctl, `_IOR('X', 125, u32)` with flag 2 (no log flush), is the same call on all three, as the design review found. These runs also test design R's premise that the manifest's fsync carries the earlier renames on ext4 and XFS, which 5.3 leans on and the README so far only reasons.
5. Pin: the pool cut test (tests/test_pool_cut.py, the VM) still passes.

**Cost.** Two checkpoints and 37 KiB of the 455 KiB less for each committed batch on the live vaults.
- **Measure in the test VM:** an f2fs loop image, 20 one-file batches, main against the branch, alternating, three runs each.
- Read `cp_foreground_calls`, `cp_background_calls` and `lifetime_write_kbytes` of the image in /sys/fs/f2fs before and after.
- 20 batches, so that a background checkpoint (one per `cp_interval`, 60 s by default), counted apart, moves the mean by a few percent at most.

### 5.3 A move keeps its rows' records, and moves them only once the rename is made (L3, L7)

**Today.**
- `VaultManifest.move_tree()` (9029) and `move_file()` (9044) leave the moved rows unverified (`UNVERIFIED`, 8714, which also clears the dirty mark), so the verification reads each moved file back: lstat and 64 KiB. A rename of a folder of 2,000 files read 263.3 MB for a change that wrote 0.1 MB.
- `do_reverb_backup()`'s move branch moves the rows before `TreeWriter.rename()` (13238): "the move's rows are at dst already", so `rename()` records dst with `rows=False`.
- When the rename falls back to a copy, the target's rows are already gone. A record of the target, or of a folder above it, sized from its rows (`folder_usage()`, 13101, `rows=True`, as `remove_now()` from the sweep and `remove_queued()` call it) then counts too little, and the version before keeps a change list that says too little. The design review's run of fuzz seed 254, lists checked, shows it: `move_tree(c/n1/t/a/t/n2/n1/ -> c/n1/t/a/t/s/b/)` found no row under the source and wiped 6 under the target, the rename fell back, and `c/n1/t/a` was sized from its rows at 31,712 bytes and 48 inodes, where a walk gives 42,908 and 55; V20's list was short by 10.93 KiB and 7 inodes. Seed 4444 fails the same way; 372, 4492 and 14224 passed in that run.

**The change.**
- **Records follow their inode.** `move_tree()` and `move_file()` change the path only: each row keeps its record, its unchecked flag and its dirty mark. A row the replay vouched for earlier in the batch (dirty, with its record: `mark_vouched()`, 9000) stays vouched, so the commit reads its new metadata at the new path; a copy's dirty row stays a copy's. A moved folder's own row is still added again (`manifest.add()` after the move), as its metadata is synced. `mark_vouched()`'s docstring changes: `add()` wipes a record, a move carries it.
- **Rows move only after the rename.** The replay calls `move_tree()` / `move_file()` only after `writer.rename()` returned True.
  - `rename()` records dst with its own rows (`rows=True`, the default).
  - A fallback leaves the rows where they are. The undo branch after `copy_instead_of_move()` (which removed the rows `move_tree` put at the target) goes.
- **A moved file whose attributes the replay syncs** under Only Sync Attributes (`writer.file_meta()` after the rename) is marked vouched (`mark_vouched()`). The commit then reads its new metadata and keeps its hash (`take_dirty_records()`). Without Only Sync Attributes such a file is copied, as today.
- **`attribs_to_copy()` (10180)** passes the record of the row at the entry's place in the latest version, moved or not (today `record = None if moved`, 10221), as that row now travels with the inode to where the attrib applies.
- **Comments that said "a moved row is unverified"** are rewritten: `record_vouches()` (10158), `attribs_to_copy()`, the attrib replay's (13953-13955) and `move_tree()`'s docstring. A swap's leftover now carries the record of the inode actually at its place, as rows move with renames and only with them, so it vouches only when the monitored file matches that inode.
- **The fuzz checks lists again.** tests/test_watcher_fuzz.py drops `says_too_little()` and its filter (REVERB_WATCH_FUZZ_LISTS goes).

**Why it is right.**
- **The invariant:** every row's record describes the inode at its path in the version.
  - A rename keeps the inode, its bytes and its metadata.
  - The record moves with it, and only when it moved.
  - What the replay writes onto it afterwards is recorded at the commit (vouched, or dirty for a copy), wherever the row is by then.
- **The unchecked flag moves with the record,** so a copy not yet read back is read back at its new path.
- **After a cut before the commit,** the cut batch's rows roll back, and the roll-forward reads rows from the tree (`read_rows_from_tree()`).
- **After the commit point, a power cut cannot leave a committed record whose rename was lost:**
  - on f2fs the change list's fsync (a checkpoint, in its new private folder) put the renames on the disk before the manifest's commit;
  - on two renames the commit flush did;
  - on ext4 and XFS the manifest's fsync carries the earlier metadata in the journal, which the ext4 and XFS sweeps of 5.2 now run.
  - The row oracle below checks it under real power cuts.

**Tests:**
1. Docker (fails on main): a rename of a folder of 2,000 files reads none of them back (a recorder on `read_vault_record()`), and their rows keep their records, unchecked flags and dirty marks.
2. Docker (fails on main), for L7, built from fuzz seed 254's log: a batch whose replay moves a folder onto the place of a tracked folder T holding k entries, the rename falling back to a copy (its source not in the version), and later in the same batch removes T or a folder above it. `view_truth.wrong_lists()` is empty: the version before says the right size.    - If this test does not fail on main, the reading above is wrong, and the build reports back before fixing.
3. **A row oracle,** `rows_match_vault(job_vault)` in tests/vault_oracle.py. For each row of the newest version with a record and `unchecked = 0`, the entry at its path matches it:
   - kind, mode, uid and gid;
   - for a file: size, mtime and tail hash;
   - for a link: its text;
   - a folder's mtime is left out, as its row records the monitored one.
   - It runs after every retry in tests/test_crash_harness.py's kill points (Docker) and in the power-loss sweeps (the VM). It passes on main, where moved rows hold no record.
4. Pins:
   - a swap in one batch (`mv a t; mv b a; mv t b`) comes out right: the version and its rows match the monitored tree, and the oracle passes;
   - an attrib after a move in the same batch, under Only Sync Attributes, is right in the version and its row;

   - seeds 254, 372, 4444, 4492 and 14224 (round 22's teardown errors of this class) pass 3 of 3 alone, in containers;

**Cost.** A moved file is read back no more: 0 bytes where 263.3 MB was read for 2,000 files.
- **Measure:** `read_vault_record()` calls and `/proc/self/io` `rchar` of the batch, main against the branch, for that rename of a folder of 2,000 files.

**API.** The manifest's format does not change. The meaning of a moved row does:

### 5.4 One mount table for the batch after its waits, one after its walk (L4)

**Today.** A one-file batch through `backuper()` reads the mount table about 9 times, by reading the code:
- each of the two waits (`wait_for_path()`, 1229, through `vault_disk_problem()`, 4318);
- `PoolGuard()` (4356), once per path, as `pool_state()` (4210) reads it;
- `do_backup()` (5860);
- `drop_unmounted_entries()` after the verification (5777);
- `set_inner_mounts()` at the commit (6127, `current_mount_table()`);
- each `fsync_vault_folder()`.

The entry's measurement, of `do_backup()` alone with eight reads before 0.55.3, is 0.44 ms of CPU a read at 162 mounts.

**The change.**
- **One read for the batch, the latest before its work.** The backuper reads the table once at the top of its loop, into a one-item list that both waits take (`wait_for_path(..., table=)`; `vault_disk_problem()` takes a table). A wait's first poll uses the table in the list. A wait that has to poll again reads the table live and puts that read in the list. Once both waits returned, `PoolGuard(paths, mount_table)`, `compare_scanned_folders()` and `do_backup(mount_table=...)` take the table the list holds: the latest read, with no wait after it.
  - A table read before a wait that blocks would be stale. A pool unmounted when the loop began and mounted while the vault's wait polls would read as no pool: the guard would not cover the job vault, the unit would open one fd on the pool's mount, and L2 would drop a pool's fsyncs.
- **One read after the walk.** The table `drop_unmounted_entries()` reads after the walk is the one `set_inner_mounts()` takes at the commit, and the no-differences path's too. A disk mounted after the walk is remembered by the next batch.
- On a pool, the commit's two folder fsyncs read the table through `vault_disks()`, two reads more, as today (L2 keeps those fsyncs): they list the pool's branches after the commit. Off a pool a one-file batch reads the table twice; on a pool, four times.

**Why it is right.** Without a wait that blocks, the reads it replaces were a few milliseconds apart, so the shared table says the same. With one, the table taken is the wait's last read. Every check that must see the table after a walk still reads it then.

**Tests.**
- Docker (fails on main): a counter on `read_mount_table()` over one one-file batch through `backuper()` (the harness's job runner), off a pool, counts 2. The task first counts main's number and writes it in the handback.
- Pin (passes on main; fails with a table read before the waits): a batch whose vault pool (FakePool) is unmounted when the loop reads the table and mounted while the vault's wait polls. The batch's guard covers the job vault, and its unit opens a handle per branch.

**Cost.** Off a pool, about 7 reads less for each batch, about 3 ms of CPU at 162 mounts.
- **Measure:** the counter, and `timeit` of 1,000 `read_mount_table()` calls on the host's table for the cost of one (the median).

### 5.5 The inode estimate counts what design R adds, so no du (L5)

**Today.** `get_backup_size_inode()` (10916):
- subtracts, for each deleted folder, its inode count from `du --inodes -csP` (`get_path_inodes()`, 8456, one process per batch), and 1 for each deleted file;
- counts an inode for a create only: "we do not count inode change for attrib / modify / move events".

That rule comes from 0.54, whose versions were whole trees of links: a delete made the next version smaller, and a modify put a copy where a link was.

**On design R a delete frees nothing, and a copy adds an inode.**
- A deleted entry goes into the previous version as its record, and stays in the vault until that version is pruned.
- A modify's copy, and an attribute change that copies, puts a new inode in the tree, while the old one stays in the previous version as its record (`TreeWriter.copy()` records by a hard link first).
- A move keeps its inode.
- So the vault's inode count rises by one for each copy and each folder the batch makes, plus the links it makes, and falls by nothing. Today's estimate undercounts a batch by what it deletes and by what it modifies.

**The change.**
- Deletes count no inode.
- Each entry the replay copies (`copies()` in `get_backup_size_inode()`) counts its inodes wherever it counts its bytes: one for a file, a walk's for a folder, with the same nesting rule as the bytes (`sized_folders`). The carried-in and written adjustments below it follow the same rule.
- `get_path_inodes()` goes, and with it the batch's du process and `ARGUMENT_LIMIT`'s use here.
- tests/harness.py's own use of du stays (a test tool).
- **Hard links.** The replay copies each name on its own: a created folder is made folder by folder and each file in it is copied alone (`get_unskipped_size_inodes()`'s docstring, 10894), so a copied folder's hard-linked files become separate inodes in the vault, and the walk's count by name is what the copy adds. du's count by inode, which the entry's "Why" weighed, was of a deleted folder, which now counts nothing.

**Why it is right.** It is the change-list rule of docs/lessons.md 2026-11-06 ("When a stored number changes meaning, rework every formula that reads it"), applied to the formula 0.55 missed. The suite's rule for the estimate (written ≤ estimate ≤ what the vault grew by) holds for inodes too, as the links stay left out. Nothing is stored.

**Tests.**
- Fails on main: a batch that deletes a folder of K entries, creates M files and modifies P files estimates M + P inodes (main: M - K), and runs no du (a recorder on `multiCMD.run_command()`).
- Fails on main: the inodes that batch wrote, its new inodes in the tree (by `st_ino` against the version before, links left out), are at most the estimate: M + P, where main estimates M - K.
- Pin: the estimate is at most what the vault's inode count grew by.
- Tests that pin the old rule move to these.

**Cost.** One process (fork, exec, a walk of the deleted folder) less per batch that deletes a folder.

**Docs.**
- The entry goes.
- "Size estimates leave out a version's own small blocks" is unchanged: the links stay left out.
- Calls to confirm: under an inode limit, a batch that deletes or modifies prunes when it should, which can be a batch earlier than before.

### 5.6 The root's metadata is written only when it changed (L6)

**Today.** `record_root_meta()` (12545), through `TreeWriter.root_meta()` (13291), calls `setxattr` on the tree's folder every batch.

**The change.**
- It reads the folder's `ROOT_META_XATTR` first and skips the write only when the value is byte for byte the full record it would write (owner, mode, times and every extended attribute). Anything else, a failed read included, goes through the write as today.
- A trimmed record never equals the full one, so a root whose extended attributes do not fit goes through the write and its line as today, once per run (`ROOT_META_TROUBLE`, which a restart empties). A skip ends a trouble state with its line, as a write does.
- `hand_over()`'s copy of the record to the skeleton stays.

**Why it is right.** A record equal byte for byte is the same record. A skip never stands for a trimmed write, so the "trimmed" line after a restart is said as today. Nothing is stored.

**Tests.**
- Fails on main: a batch that leaves the root's owner, mode, times and xattrs as they were makes no `setxattr` of `ROOT_META_XATTR` on the tree (a recorder).
- Pins: a chmod of the root writes it; a record too big still writes the trimmed one once and says so once; after a restart (`ROOT_META_TROUBLE` emptied) with a trimmed record on the tree, the trimmed line is said once.

**Cost.** One `setxattr`, and the inode write it can cause, less for nearly every batch, for one `getxattr`.
- **Measure:** the recorder's count over 20 one-file batches.

### 5.7 The restore marker's recopy field and `--accept`'s first sync stay (L8)

Both exist: `recopy_way_out()` (15480), `refuse_accept_unsynced()` (16764), `marker_recopy()` (16750), and the sync before `hand_over_folders()` in `accept_restore()` (16546). Both still do a job, so neither goes.

- **"recopy" is still needed.** "unsynced" lasts from the claim to the run's sync. "recopy" lasts until every entry was copied again and a sync of them succeeded (`restore_entry()`'s docstring, 16240-16256).
  - A recopy run that fails one entry, say B, syncs and clears "unsynced", while B still holds what the killed run wrote, which nothing vouches for. "recopy" makes the next run copy everything again.
  - It also holds a recopy while a disk of the vault's pool is missing.
  - The two keys could become one with that longer lifetime, but that saves no I/O and rewrites the restore's most-reviewed code. Not this round.
- **`--accept`'s first sync is still needed on a pool.**
  - Its copies need no sync: `--accept` runs only over a marker with no record, so the run that wrote them synced them through handles open since its claim.
  - A 0.55.1 marker carries no record either, but no 0.55.1 restore can still be running, and a handle opened at `--accept` could not vouch for its copies anyway.
  - What the sync still does: a run stopped during its hand-over leaves folders' owners, modes and times unsynced (its stop syncs only before its own sync). On one filesystem the marker's removal cannot reach the disk before them. On a mergerfs pool each disk keeps its own order, and without this sync a power cut could keep the marker's removal on one disk and lose those folders' metadata on another, silently.
  - Off a pool it costs one syncfs per `--accept`, a command run by hand, and keeping one path for both is simpler than a branch.

**Docs.** No change.

### 5.8 A copy is recorded checked once its commit flushed it (L9)

**Today.** `record_dirty_entries()` records each file a batch copied as unchecked (`read_copied_record()`, 10262, unchecked 1). The next comparison that walks it reads it back (`compare_entry()`, 10327: an lstat and its last 64 KiB) and records it checked, a row write per copy. The mark stood for a copy whose bytes a crash could keep from the disk.

**Why it can go, after F1.** A pass over every writer of the flag:
- `read_copied_record()` at each commit: the only writer that sets it to 1 once F1 is built;
- `mark_unchecked()` at the scan: F1 removes it;
- `read_vault_record()`: 0 for every read-back, an unverified row's (moved rows on 0.55.4, a rebuilt or converted manifest's) among them;
- a copy made where hard links are refused (`keep_entry()`, 13026) sets `copies_unsynced`, and is flushed like any copy.

Since 0.55 every copy a version commits is flushed before its commit (6134-6140), through the handles its unit opened before the copy was written (VaultUnit), which hear every writeback error of the filesystem since. After F1 no cut copy stands at any name (each is copied again or holds version n's entry, and the scan flushed any put-back copy). So a mark is only ever written on a copy already on the disk, heard through such handles, and the read-back it asks for can find nothing the flush did not.

**The change.**
- `record_dirty_entries()` records each row with unchecked 0; `read_copied_record()` goes. A vouched row keeps its record's flag, as today.
- The read side stays: rows that 0.55.4 and older marked are read back once, as before, so the marks drain.
- The manifest's docstring ("A file copied by a backup stays unchecked until delta generation reads the copy back") and `compare_scopes()`'s are rewritten.

**Why it is right (crash safety).** A power cut after the commit cannot take a flushed copy's bytes: the disks' flush is the barrier. With L9 the row oracle (5.3), which checks rows with unchecked 0, covers every copy a batch made, so the power-loss sweeps of 5.2 (every step, f2fs, ext4 and XFS) and the kill points prove it.

**Tests.**
- Docker (fails on main): a batch that copies N files records them checked; the next full comparison reads none of them back (a recorder on `read_vault_record()`) and writes no row for them.
- Pin: a row marked unchecked as 0.55.4 marks it (set by hand) is read back once and recorded checked.
- Gate: the power-loss sweeps of 5.2 and the kill points, with the row oracle.

**Cost.** Per copied file, at the next comparison that walks it: one lstat, one 64 KiB read and one row write less.
- **Measure:** `read_vault_record()` calls and `rchar` of a full comparison after a batch of 1,000 copies, main against the branch.

**API.** The manifest's `unchecked` column keeps its meaning for a reader ("read this copy back"); the writer stops setting it. A 0.55.4 daemon reading a 0.55.5 manifest trusts its checked rows, as it trusts any. A lessons entry (section 11).

**An entry that narrows,** approved: "A full comparison that meets only what it leaves out commits a version" becomes:

> ### A full comparison that meets only a link too long for the version's paths commits a version
>
> - **Kind:** known limitation.
> - **What the operator sees:** a full comparison, such as the one at each start, whose only difference is a symlink whose path in the new version reaches the vault's path limit (4,096 bytes on Linux), where no regular file's path is as long, commits a version that changes nothing, with the link's NOT BACKED UP line. With Keep N Versions, each such version pushes the oldest one out. Unreadable files and links whose text the vault refuses no longer do this.
> - **Why:** the check that keeps such batches from committing probes a link's text in staging, at a shorter path; telling the path apart needs the new version's name, which is not known until it is made, and arithmetic on the vault's path limit for a rare link.
> - **Revisit when:** such a link is seen in a monitored tree.
> - **Approved:** 2026-11-12, "Leave that case out (Recommended)".

**A new known limitation,** approved (F3):

> ### A start with changes pending can pass the size limit until the next batch
>
> - **Kind:** known limitation.
> - **What the operator sees:** at a start that replays changes pending from the stop, what changed while reverberator was down is found by the whole-tree check that follows the replay, after the size estimate and its prunes, so that version can take the vault past its Backup Size Limit (or inode limit) by that much. The next backup's prune brings it back under. In a probe, a limit of 3,600,000 bytes and 2 MiB added while down left the vault at 4,194,306 bytes until the next batch.
> - **Why:** the check runs inside the replayed batch's version, so the pending moves stay renames and a start makes one version; 0.55.4 pruned first, in a second version, and made two versions at every such start.
> - **Revisit when:** a vault is kept close to its size limit and restarts with changes pending are frequent.
> - **Approved:** 2026-11-12, "Keep it, accept the overshoot".

**A deferred entry** (R12, the lost manifest and an unmounted inner disk, confirmed by the design review's probe A):

> ### A lost manifest stops an unmounted inner disk being paused
>
> - **Kind:** deferred.
> - **What the operator sees:** when a job's vault database is lost or unreadable (removed or damaged from outside; the daemon's own messages suggest removing it in some cases), it forgets which inner mounts it had seen. An inner disk unmounted at that moment then looks like an empty folder: the next comparison commits a version with that folder empty, with no "Inner mounts not mounted" line, and when the disk is mounted again every file is copied back. Under Keep N Versions or a size limit, the versions holding the disk's files can be pruned meanwhile, so a disk that never comes back can lose its backup.
> - **Why:** the inner mounts are recorded in the database only, so a rebuilt database has none to pause. The fix belongs at the source: the inner mounts recorded outside the database, with the version, so a rebuilt manifest pauses them too.
> - **Revisit when:** the round after 0.55.5.

## 11. Lessons entries

**The APIs the round touches, read and write sides:**
- **The manifest** (a storage format):
  - L3: the write side keeps records, flags and marks on moved rows; the read side is unchanged, and reads a 0.55.4 manifest's unverified moved rows as before.
  - L9: the write side records copies checked; the read side still reads back a row marked unchecked, so old marks drain.
  - L1: the `matched` and `version` meta rows are written less often, with the same meaning.
  - F1: the scan no longer writes the unchecked mark.
- **The versions a start makes** (agreed behaviour, README line 16), F3: one where there were two.
- **The pending file's replay** (agreed behaviour, README line 39), F3: replayed at every start, with no resume check; the whole-tree check in its version takes the check's place.
- **The alert lines** (firewatcher's patterns): unchanged. F4 logs the same UNREADABLE and NOT BACKED UP lines, from the check instead of the copy.
- **Unchanged:** the change list's format, the restore marker (L8), the rule file, every CLI flag and output.

- Changed: a move keeps its manifest rows' records, unchecked marks and dirty marks, and the rows move only once the version's rename is made; a fallback to a copy leaves them where they were.

## 15. The spec check's questions, answered

1. **Rows after a put-back.** The put-back runs at the scan, before `read_rows_from_tree()`, so the rows are read once, from version n's entries (section 1). Nothing reads rows again.
2. **A vault that refuses hard links.** The put-back copies, and the scan flushes those copies through its own unit before it returns (section 1); the roll-forward's commit flush covers them again.
3. **Version n at a name put back.** It keeps its record, a real entry sharing the tree's inode; V(n+1)'s list does not name it (section 1).
4. **F3's test 2.** A batch handed back after a failed attempt is never replayed: the next attempt's full scan absorbs it (5012-5014), one version on main already. F3 changes only the resumed batch; the test became pins for a failure before and after the hand-over (section 3, test 8).
5. **The sweep.** A resumed batch's sweep keeps the batch's own scopes, as nothing outside them can hold an entry no row tracks, so F3 adds no walk. The stop rule weighs writes and checkpoints first, then wall time (section 3).
6. **The resume check.** It goes (section 3): the whole-tree check in the replayed version is what it stood in for.
7. **Hard links in L5.** Each name is copied alone, so the walk's count by name is what the copy adds (5.5).
8. **L4 on a pool.** The commit's two fsyncs read the table twice more, as today: four reads a batch on a pool, two off it (5.4).
9. **Footprint.** Section 6 is unchanged until the report is in; the main session adds the candidates then.
- The check's misses: the footprint measured first (Calls to confirm), F4's per-batch cost (section 4), L2 on btrfs (5.2), L5's hard links (5.5).

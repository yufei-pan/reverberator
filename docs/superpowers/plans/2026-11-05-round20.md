# Round 20: design R with pools P2 (reverberator 0.55) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The user does not review this plan; open questions
> are in Calls to confirm at the end.

**Goal:** make the newest version the one real tree and older versions link forward, on one disk and on mergerfs pools,
convert live vaults once, and release 0.55 only after the pool cut test passes.

**Architecture:** one class, `TreeWriter`, becomes the only door to a version's tree and to the previous version's folder;
it records before it changes anything. `do_backup` hands the tree over, replays through the writer and commits at the
manifest; a cut batch is rolled forward by the normal batch path with the hand-over skipped. Readers walk components
themselves. The 0.54 writer keeps working behind a temporary constant until the suite has moved, then 802 lines go.

**Tech Stack:** Python 3.13 standard library (`ctypes` for `renameat2`, one line: no other way to reach the flag). Dev-only:
pytest, `mkfs.f2fs`, `f2fs_io`, `mount -o loop`, `mergerfs` (all present; needed only behind `REVERB_SCRATCH`).

**Spec:** `docs/superpowers/specs/2026-11-04-round19-vault-r-design.md`. Prototype to port rules from, not to copy:
`<scratchpad>/r19/design2/scripts/`
(`r2.py`, `crash.py`, `recheck.py`, `powerloss.sh`, `migrate.py`, `measure.py`). Line numbers below are at 344398f.

## What the spec leaves open, settled against the code

### S1. Which rules a vault gets

`vault_layout(job_vault, manifest) -> str`, one answer used by the scan, the start and the CLI:

| state | answer | what runs |
|---|---|---|
| manifest `layout`='r' | `'r'` | R scan |
| no `layout`, `.reverberator_staging` exists | `'converting'` | R scan, then the migration (a no-op for each version with no chain link), sizes pass, sets `layout` |
| no `layout`, no staging, versions exist | `'0.54'` | 0.54 rules, then `mkdir` staging, fsync the job vault, then the migration |
| no versions | `NEW_VAULT_LAYOUT` (`'r'` after Task 13) | V0 |

Why staging counts: `VaultManifest` discards an unreadable manifest, so `layout` can be lost. The 0.54 rules would then
`remove_orphan` a cut batch's tree, which is `rm -rf` of the only real tree. Staging is made after the 0.54 rules ran
and before anything else changes, so its presence means they must never run again. The migration on an R vault changes
nothing (forward links are no chain links: `parse_chain_text` needs the previous version's name), and the sizes pass is
right on R. With a lost manifest and a cut tree, `rebuild` lists T, and the rows are marked unchecked as in S4.

### S2. Locks around the scan: released before the wait for the monitored path

§2.8 says held "from the scan to its commit", but `backuper`'s `scan()` (line 4691) runs before the wait for the
monitored path (4702). Holding through that wait blocks every restore when the monitored disk died, the moment a restore is
wanted. So: `scan()` takes the locks, runs the 0.54 rules or R scan, the pool repairs, the roll-forward's preparation (S4 steps 1-4) and
the migration, then releases. The batch retakes them with `locks.take()` as any batch does. A restore between the two
reads exact versions, as preparation has run.

A scan can now finish a commit and empty staging, so every `get_vault_info` that can reach an R vault takes the locks: `scan()` already does, and `compare_scanned_folders` (4602) and `do_backup`'s own call, when they have no `vaultInfo`, must too. `get_vault_info(recalculate=True)` measures with `du`, which is wrong under §6; nothing but `tests/test_vault.py:50` calls it, so it goes in Task 16.

### S3. Commit reading in the R scan

R reads the manifest first (`read_job_vault` and `recorded_latest_version` prefer `current_version` today, line 6066). M is
the manifest's version, n the newest folder with a list.

| state | action |
|---|---|
| M = V<n+1>, its list in a private folder | finish: swap `current_version`, rename the previous list per `previous_list` if `from` still exists, place the list |
| M = V<n+1>, no list anywhere | refuse, as today (`JobFailure`: a missing disk may hide it) |
| M = V<n>, V<n+1> folder, no list, empty or all self-named | a skeleton: give P's folders their times (S4 step 2), then `remove_orphan`, so a cut between leaves nothing owing |
| M = V<n>, V<n+1> folder, no list, otherwise | the tree: keep, return in `VaultInfo.tree` |
| manifest lost (S1) | n and the orphan by the two rows above; a private list is discarded, the batch rolls forward |
| lone V0 orphan | removed; any other orphan is an error, as today |

`previous_list` is a JSON meta value `{"from": name, "to": name}`, written in the commit's transaction. `delta_generate_backup_entries`
commits naming its `version_path` (10476), which would falsely name T: roll-forward never calls it.

An all-self-named or empty folder is safe to remove after its exchange too: by the invariant no forward link in P leads
to an entry T does not hold, so P is whole.

### S4. Roll-forward is the normal batch with the hand-over skipped

Preparation, in the scan, under the locks, idempotent:
1. Walk P's real part. 2. Give each real folder its row's mtime, writing only where it differs.
3. `manifest.mark_unchecked(rows of the recorded paths)`, own transaction. A self-named link a cut exchange left needs no step:
the comparison and the sweep take it (Review 1).

Then `do_backup(vaultInfo with tree=T)`, once the monitored path is ready:
- `backup_entries` = a full `compare_scopes` reading T, plus each saved plain file modify, create or move it did not find while the monitored path is a regular file, replayed as a modify (a rewrite keeping size and mtime shows only to the watcher). No other saved entry: a saved file entry where a folder stands now failed the job on every attempt (Review 1). Never `delta_generate_backup_entries`.
- Retention loops as in a batch, counting the tree as the version being made; never prune P, never the last version.
- No `make_version_folder`, no hand-over. `TreeWriter(tree=T, previous=P)` as usual, so records are no-ops where P is real.
- `touched` is the whole tree, as P's root is always real and strays at the top need sweeping, so the verification sweeps it through `writer.remove`.
- Always commits, even with no entries. P's size comes from `measure_previous()` at commit (S7), not from counters.

Normal stop mid-batch (`backup_finished` False, line 5839): `manifest.rollback()`, T stays. The log line becomes
`Backup incomplete for <T>: the next attempt finishes it`. A stop is a roll-forward at the next start.

### S5. `record(rel, keep=True)` where T/rel is a folder

The spec's table exchanges the folder into P, so a failed copy loses the folder from the newest (README line 67 says it
stays). So: a file replacing a folder uses `hl_record(rel)`, and `place()` then removes T/rel with `replace_entry`. Same on a pool.

### S6. Inode estimate (spec §6 is wrong here)

§6 says the estimate before a batch is unchanged. `estimated_backup_inode = latest.inode + change` (5793) with
`vault_inodes + estimated_backup_inode > limit` counts the whole tree twice under R, as `vault_inodes` already holds it, and a
job whose tree passes half its inode limit prunes everything it may. In R: `estimated_backup_inode = change`, floored at 0. The size
loop is right as it is: `estimated_backup_size` is already the change.

### S7. Sizes at commit

`BatchSizes` counts into P at the primitives (spec §6). Commit computes `vault_size += p_size + t_size - old_newest.size`, the same for
inodes, and `vault_info_dict[n] = entry._replace(size=p_size, inode=p_inodes)`.

`manifest.size_under(folder)` sums rows for a folder exchange; it is right because P forwarding means nothing under it has changed in
this batch, so the rows are still version n's. `before_copy` reads the old row before `manifest.add`.

`measure_previous(P, T) -> (size, inodes)`: crash-only. Inode set of T's entries with `st_nlink > 1`; walk P's real part, count a file when its
inode is not in the set, 4 KiB and one inode per real folder, one inode per link. Equal to the counters by test (Task 8).

### S8. Readers

- The walk always applies the forward rule. The backward 0.54 text rule applies only when `layout` is not `'r'`. Spec §4.3's "No forward rule is used" would misread an R vault whose manifest was lost; forward text cannot occur in a 0.54 vault, so always-on is harmless.
- The next version comes from the link's text: a version name numbered k+1, and the rest equal to the prefix. That needs no list of versions, so T of a cut batch needs no change list to be walked.
- **History's "unchanged":** version k is unchanged at rel from k-1 when both walks land on the same inode (`same_inode`). A forward link lands there by construction, and a migrated version or a hard-link record by sharing the inode. The 0.54 test (`hop_rel`, a link to the same path in the older version) points the wrong way in R. A forwarded folder is not skipped: under Only Sync Attributes an attribute change exists only as a change list row, and skipping would drop that version from the folder's history. Moves come only from change list rows (`moved_from`).
- **Restore's folder walk:** `iter_tree_entries(resolved.path)` (14495) would treat a forwarded folder as a file. New `iter_version_entries(job_vault, number, rel)` yields parents before children, walking forward into the version a folder forwards to.

### S9. Manifest schema 3 is an in-place upgrade

`_open` drops the tables on an unknown schema (7929), so `_upgrade` takes 2 to 3 by changing only the meta value, and the schema 1 path continues to 3. `copy_version` and `monitor_paths` stay in the table, unused, until the later release. 0.54.1 reading schema 3 drops the tables: there is no downgrade (spec §7). `PRAGMA synchronous` stays FULL, pinned by a test, as the manifest commit is the commit point.

### S10. Kept code vs the removal list

Spec §8's lists conflict in four places. Settled: `manifest_monitor_paths` and `command_monitor_paths` go, as `decrement_stepper` reads the record itself when `monitor_paths` is None; `link_chain_end` goes and `xattrs_differ` (9987) reads T/rel directly; `prune_oldest` stays as the history-lock wrapper around the R prune, with the 0.54 stepper only for the §3.1 marker repair; a new `read_vault_layout_for_command(job_vault)` reads `layout` for the CLI with the retry `command_monitor_paths` had, read-only, built like `read_recorded_monitor_paths`.

A name that kept code needs (a constant such as `REFERENCED_COPY_THREADS`) stays until the later release; list it in the hand-back.

### S11. No exchange, and on a pool

`two_renames` is True when `pool_state(job_vault)` is not None. A plain filesystem finds out at its first exchange: `EINVAL`, `ENOSYS` or `ENOTSUP` from `rename_exchange` sets `writer.two_renames = True` and the hand-over moves its folder to `staging/skel-<V<n>>` and goes on as a pool does. `flush_vault_disks` works on any filesystem. All of §5's rules then apply.

On a pool, a record made inline (the monitored tree changed after the pre-record pass) sets `writer.needs_flush`; `writer.flush_if_needed()` runs before the change it guards. This is rare, and it closes the only unflushed gap in §5.

### S12. Fixtures that build vaults

- R vaults: real batches through `harness.run_backup`, as today. Hand-written R vaults for read edge cases use `tests/vaults.py` with the oracle's own `forward_text`.
- 0.54 vaults: `tests/legacy054.py` loads the real 0.54.1 module from `git show v0.54.1:reverberator.py` (a tag, as history gets rewritten after this branch merges and every hash changes) into a session temp folder and imports it as `reverberator054`; `build054(job, batches)` runs its `do_backup`. No 15K-line file is committed and the format is exact. It skips with a reason when the git object is missing. The fixture applies to the loaded module every patch `isolated_runtime` applies to `rv`, above all `sync_vault_filesystems`: the stub on `rv` does not reach a second module, and a real syncfs would flush the live ext4 under `/tmp`. A test proves it. `do_referenced_copy` is removed in Task 16, so this is the only way kept tests and migration tests get real 0.54 vaults.
- Hand-written `write_committed_version` vaults have no staging and no `layout`, so they still read as `'0.54'`. Most of `test_vault_scan` stays valid.

Design decision:
	When reverberator is in cold start, will not calculate hash to do space efficient move operations to vault.
	When restarting reverberator, will do one backup that will only handle create, modify, delete, attrib.
	The latest version's entries, with the size, mtime, mode, owner and tail hash of what the vault holds for each, are kept in .reverberator_manifest.sqlite in the job vault. Restarts compare the monitored tree against it, and read the vault only for entries it has no record of, and once for each file copied since the previous restart. A copy read back is recorded checked with no sync of its own, as every committed copy was flushed before its commit. Nothing is flushed as each copy is written: a commit flushes the batch's copies first, once per batch, so a version the vault database calls committed has its data on the disk. That flush, and every other sync of the vault, goes through handles the batch (or the scan, or the conversion) opened before its first write, one for each filesystem holding the job vault (syncfs on each disk of a mergerfs pool that holds it), so a write error that another program's sync met first is still heard, as Linux reports one to every handle open when it happened. A sync that fails commits nothing and fails the attempt, whose next attempt copies again what it changed.
	Each job may name a gitignore style Skip List File in its rule row. It is read at start, once the job's disks are ready, and applied to everything read from the monitored path and never to the vault. A job which has used patterns needs the value none to back up everything.
	Three rule columns after Skip List File are optional, and a rule file without them (12, 13 or 14 columns) is read as it is: missing or blank cells mean the defaults, and the daemon never writes them (a row it rewrites to fill in auto cells gets its first 12 cells written as before); --drop-sample-rule writes a sample whose header names all 15 columns and whose description rows stop at the 13th, the last with any effect. A cell that cannot be read logs an error naming the cell and its format, and the job runs with the default.
		13, Full Comparison Interval: a duration such as 1d, 12h, 30m, 45s or 1h30m, in w, d, h, m and s or their words (week, day, hr or hour, min or minute, sec or second, plural too), case ignored except that a bare M is refused (minute or month?), spaces allowed between a number and its unit and between groups, and a plain number in seconds; blank, 0, none, off and auto mean none, the default. When set, the job compares its whole tree with the vault that often, counted from the end of its last full comparison of any kind (a restart always makes one), which catches writes no event reports, such as through mmap. It starts within a few seconds of coming due, without waiting for the tree to be quiet, logging 'The full comparison interval (<N> s) has passed since the last one: comparing the whole tree'; a running batch delays it, and a job waiting for its vault postpones it.
		14, Chain Length and 15, Copy threads: kept so rule files that have them stay valid; from 0.55 neither has any effect, and any value is accepted without a line.
	Keep 1 Complete Backup (column 7) False is read as True from 0.55: a job's first version is always a complete copy, and the start logs one line saying so.
	A job name on more than one line of the rule file uses the last line, as TSVZ reads it. Each start logs one warning per such name, with its line numbers and the line used (Warning: Job name <name> is on lines <lines> of <rule file>: line <n> is used and the others are ignored.), or says that no line is used and the job does not run when the last one has only blank cells after the name. reverberator never removes those lines, and a row it fills in keeps such a name as written; status, history and restore do not warn.
	File names are anyone's to choose, and a name that is not UTF-8 (bad\xff.txt, say) is backed up like any other, and kept in the change lists and pending transactions so that its exact bytes come back (stored escaped, not as raw bytes). Wherever a name is shown, in a log line or the output of a command, it is escaped: a byte that is not UTF-8 appears as \xff, and a control character, such as a newline, a carriage return or an escape, as \x0a, \x0d or \x1b; in an ordinary log line a line break in a name continues on the next line indented by four spaces, while marker lines and command output show it as \x0a. No line reverberator logs holds more than 16384 bytes of text: a longer one is cut to fit, its notice included, never inside a character, and ends with the number of bytes left out, so that the journal, which splits a line longer than 48K, cannot start a record inside it. The daemon also writes every line its libraries print, and every traceback of a thread, whole: a line another thread has not finished waits until it is, so no marker can land inside one. A name can then neither drive a terminal nor start a log line of its own, so a file named like a marker cannot raise the alerts below.
	The newest version is a plain tree: its folders, files and your symlinks as the monitored tree was at that backup. Each older version holds as real entries only what the backup after it changed (files it replaced, removed or moved away, folders whose entries or metadata it changed), and everything else as one link to the same path in the version after it (../V<n+1>--<time>/<path>, a forward link), so a version costs what changed after it. Before a backup changes anything in the tree it moves the old state into the version before (a moved entry by hard links), so every committed version shows exactly what it held at every moment, a crash included (on a mergerfs pool or a filesystem with no exchange, once the next start's repair has run).
	The first 0.55 start of each job converts its vault once, before backing up: newest version first, each version holding links to an older one is rebuilt beside itself as a plain tree of hard links to the same copies and swapped in in one step, then each change list is renamed to what its version alone holds (one log line per version; a tree of about 180,000 files wrote about 0.95 GiB per version, and each of the next prunes removes such a version at about 0.7 GiB). A start cut off goes on where it stopped. There is no going back to 0.54. Until a job's conversion ends, a symlink of yours whose text has the shape of a 0.54 chain link reads, restores and converts as the file it names, not as a link.
	Runbook: a job that failed on names that are not UTF-8 under 0.39 may have left a pending-changes file with ? in its names. Deleting that job's .reverberator_pending_transactions.nsv before the first 0.40 start makes it compare its whole tree once.
	Change events waiting for a backup are kept compressed, events the backup would skip anyway are dropped as the queue grows, and the queue becomes one full scan only when memory runs short (stalls on memory, little available, or the queue holding a quarter of what is available).
	After each batch, every place its events touched is compared with the monitored tree and the new version is fixed before it is committed, so renames, saves through a backup file and folder swaps come out as they are in the tree; a batch resumed after a restart (one of scans only too), or put back after a failed backup, is followed by one full comparison.
	Changes made in one batch after a move, at the moved path or inside a moved folder (mv x d/x; chmod 600 d/x, or mv d e; echo new > e/new), are replayed after the move, so a folder is moved, not copied again, and a moved file's new mode, owner and extended attributes reach the new version. The comparison after each batch also checks the mode and owner (a symlink's own owner too) of what the batch touched, and the extended attributes of those the batch changed, by their ctime (a moved folder is one check, not one per file), and syncs what differs. A full comparison (at a start, after a failed backup, or when events were lost) also checks the extended attributes of the entries changed, by their ctime, since the vault last matched the whole tree (the last backup or comparison that saw all of it, recorded in the vault database), so an xattr-only change made while nothing watched is backed up too. It, and the comparison of a folder the watcher could not follow, also compares each folder's mtime, so a folder whose times alone moved while nothing watched (a file made and removed in it) gets them in the new version, its times only; a batch's own comparisons do not, so such a batch makes no version. Either check allows 10 s for a clock step. A sync of an entry's metadata into the vault also removes the extended attributes the monitored entry no longer has (setfattr -x, or an ACL removed by setfacl -b), so a restore does not bring them back; a monitored filesystem that keeps none (ENOTSUP, as mergerfs with xattr=nosys) leaves the vault's as they are.
	A file made or saved in a batch, or a folder made in it, that is then moved is copied once, to where the batch leaves it, through the folder moves and its own moves after it (echo new > f; mv f d/g; mv d D; mv D/g h copies h; a few rarer orders are a known limit below).
	A delete in a batch whose path held the source of a move made before it (mv d/g y; rm -r d) replays after that move, so what moved out is moved, not copied again; every other delete still replays before the batch's moves and copies, including one whose path a later folder move fills again (rm -rf site; mv site.new site; mv site/assets/x elsewhere).
	A move whose source, or the folder it goes into, the version does not hold (such as a file that moved on before its copy ran, or a move into a folder another move of the batch took) logs one warning (Not renaming <source> to <target>: its source or the folder it goes into is not in the version; copying it instead) and copies the entry (what that costs is a known limit below). A move into a new folder made at its own old place (mv D x; mkdir D; mv x D/D) is not tried: it logs one warning (Not renaming <source> to <target>: its new place is inside its old one in the version; copying it instead) and is copied the same way. Neither logs a traceback, and the comparison after the batch fixes the rest.
	Under Only Sync Attributes, an attribute-only change (chmod, chown, an xattr, touch) is synced onto the vault's copy only while the file's mtime is the one recorded. One whose mtime moved (touch, rsync -t, or a write through mmap, which raises no event and moves the mtime and ctime, not the size) copies the file once, in that version, so the mtime stays a true signal for later comparisons: a touch of a big unchanged file costs one copy.
	There, an attribute-only change that keeps the mtime (chmod, chown, an xattr) whose record vouches for the vault's copy (the file has the recorded size, mtime and last 64 KiB, and the vault's copy in the newest version the recorded size and mtime) is recorded at commit from that record's hash and the copy's new metadata, so one over a large tree reads no file data from the vault (a copy whose size or mtime changed by the commit is hashed as before). The copy keeps its checked or unchecked mark.
	The watcher watches each folder as its walk reaches it, before reading it, so a folder made during a cp -r or tar x is watched, and a folder moved within the tree is walked again at its new name. A batch carries the paths whose move-out is still waiting for its pair, and the check after it compares them, so a file moved into a new folder or out of the tree leaves its old place by the next batch at the latest. Its own delete, arriving later for a path the vault no longer tracks, is dropped, so it makes no version on its own. Events in a folder made during a batch, which the batch's copy of the folder holds, are recorded again once any batch is taken, the backuper's own take at a start too. A folder or file moved into a folder made in the same batch is copied whole, with no line in the log, even though the vault already holds it: under a size limit that copy can prune older versions (a move into a new folder that costs no copy waits for its own design).
	A symlink the monitored tree holds is backed up as itself; one whose text or path is longer than the vault's filesystem takes (on XFS, a text of 1,024 bytes and up) is left out of the version with a NOT BACKED UP line (a known limit). A link in a version is the vault's own only when its text is its own path in the version after it, which no backed-up symlink can be, as that version did not exist when it was backed up.
	Pruning renames the oldest version into .reverberator_staging, deletes it, then removes its change list; nothing links into the oldest version, so a prune cut off anywhere loses nothing of the others. Each job vault keeps a .reverberator_staging folder for the backup's own building, which the job's vault scan empties; leave it in place.

Known limits (each in docs/limitations.md):
	The vault database (.reverberator_manifest.sqlite) and the change lists are readable by any local user, and list every backed-up file name and size.
	A path in a version k versions older than the newest reaches its copy through up to k forward links, and every symlink in the vault's own path counts too, so browsing by hand fails with 'too many levels of symbolic links' in versions more than 40 back (about 20 while Docker changes mounts); restore and history follow them themselves.
	Before snapraid fix rebuilds a disk of a pool, stop reverberator (systemctl stop reverberator), and start it again once the fix ends: a replaced disk counts as there as soon as it is mounted, so jobs would resume while its files are still being restored.
	A write through mmap raises no inotify event. A file written only through mmap (a chat app's MMKV files) is backed up at its next normal write, a restart, or the job's Full Comparison Interval when one is set. Every comparison hashes a file's last 64 KiB, so a store before that tail (none, for a file of 64 KiB or less) is missed when it goes into a page still dirty from an earlier store (it moves no mtime) until the mtime next moves, or when the mtime is set back after it; and a copy a 0.46 or older daemon synced after such a store (old bytes under the new mtime) stays wrong until the file is written again.
	With a size limit, a backup can go over it until the next prune by about 4 KiB for each folder it touches and each folder above them (a chmod of 3,030 folders passed a limit by 11.64 MiB) or by a few KB for the version's xattr blocks. The links a backup makes are in no size record: about 4 KiB each on f2fs, so one file changed in a folder of 5,000 entries takes 20.6 MB of disk that status and the size limit do not see, until that version is pruned. With an inode limit it can go over by the links it makes, one for each entry of a folder that changes. A vault down to its only version, which is never removed, can pass it by the size of a change until the next backup prunes the older of the two.
	The pause on a missing pool disk tells a quickly swapped disk apart only on kernel 6.8 or newer, and notices a dying disk only once its filesystem fails or flags an error.
	An extended-attribute-only change made outside the watched folder (straight onto a disk of a pool, or a remote write on a network filesystem) is backed up only when the file next changes.
	A file rewritten in place while reverberator is down, at the same size, with its mtime set back and changed only before its last 64 KiB, is missed at the restart and kept wrong until it changes again; so is one rewritten while it ran, when a stop with the vault not there dropped its event.
	When reverberator fills a rule row's auto cells, it writes that row's resolved columns 1-12 back: a blank cell takes its #_defaults_# row value and an auto cell reverberator's own default, so a later edit of the defaults row no longer reaches that job: edit the job's own row, or clear its cells, to follow a changed default.
	A file edited while a full comparison runs is copied twice: into the comparison's version, and again by the next batch, from the edit's event.
	A pending file holding only a carried move-out's late delete, resumed at a restart, compares the whole tree twice (with no version).
	A stop while the vault is not there drops the queued changes, as the next start compares the whole tree; but a pending file an earlier stop left in the vault, not loaded since, may be replayed by a later start when every mtime in the tree is at least 1 s older than it, and that version then lacks the dropped attribute-only or mtime-keeping changes (chmod, chown, an xattr); the whole-tree comparison that follows the replay puts them in the next version, but misses a same-size rewrite that kept its mtime, as in the limit above.
	A vault on a disk mounted outside /etc/fstab (by hand, a systemd mount unit, autofs) is not checked for being mounted: a stop while it is unmounted writes its pending file on the bare mount point, and a start makes the Vault Path there (and then waits for the vault filesystem until a restart once the disk mounts without it); with an N/A or auto Vault File System Signature, the job backs up into the bare folder until the disk mounts, and those versions are hidden then and use the disk below's space, and an auto signature filled from such a folder is the disk below's, so once the disk mounts the job waits on the wrong signature until the cell is set back to auto. List such disks in /etc/fstab to have them checked.
	A disk mounted by hand (or by a systemd mount unit) under an fstab mount point that is not mounted does not count as there: a vault or monitored path on it waits with the FAILED: waiting marker naming the fstab point. Put the disk in /etc/fstab, or mount the fstab point first.
	A swap in one batch (mv a t; mv b a; mv t b) copies both entries again, two folders whole; a file swapped with a folder also logs one ERROR line (Not renaming … is a folder in the version …; doing delete & copy instead). The result is right.
	A folder renamed while a batch that holds a change inside it runs can leave that one version without the changed file, or without the folder; the next version is right.
	A disk that hangs while a renamed folder gets its watches hangs the job's backup too, with no wait shown in status; after a forced kill the next start compares the whole tree.
	A move whose source, or the folder it goes into, is not in place in the version when it replays, because of another change of the same batch (mv d e; mkdir e/sub; mv x e/sub/x copies x, and mv a/f g; mv a A; mv g h copies h), is copied once more with one warning, and its files are written to the vault again in full.
	A folder moved into a new folder made at its own old place in one batch (mv D x; mkdir D; mv x D/D) is copied whole once, with one warning; in the swap shape (mv site site.old; mv site.new site; mv site.old site/old) the replacing folder is copied whole too.
	A chmod or chown whose record vouches for the vault copy leaves the copy recorded checked: if a power loss or a write error loses the copy's new mode or owner just after the commit, the vault keeps the old ones, and restores give them, until the file next changes.
	The service unit waits up to ~5 min for the clock to sync before starting: a clock set back after start can hide extended-attribute-only changes made while nothing watched until the next batch.
	A database an application keeps writing (a SQLite file and its -wal, a PostgreSQL data folder) is copied file by file while it changes, so a version may hold a copy that lacks the newest changes or does not open. Back up a dump of it instead (as the app_db job does with pg_dump) and keep its live files out with the job's skip list.
	A vault on btrfs is not covered by the promise above that a crash leaves every committed version whole: it rests on the vault database's fsync also carrying the folder changes made before it to the disk, which power-cut tests confirm on f2fs and which should hold on ext4 and xfs by reasoning, and btrfs should not (reasoned, not run). A power cut at the wrong moment could make the next start refuse the vault, or finish a commit with a tree only partly changed.
	With Only Sync Attributes off, a power cut before a batch's flush ends can leave the copy of a file ending in 64 KiB of zeros all zeros in the newest version, when the batch only changed its attributes and the file is under an inner mount that is not mounted again at the next attempt; older versions keep the right copy.
	On a vault whose filesystem refuses hard links, the copy a batch makes to keep an older version's file is that file's only copy: a write error on it (with a VAULT WRITE ERROR line, or with none when another program's sync met the error first) can leave that older version's file wrong.
	A file whose copy was already lost before the upgrade (a 0.54 chain leading nowhere) stays a broken link in that version: the conversion logs one error line naming it, and after that a restore gives back the broken link with no FAILED line.
	The conversion runs on one thread, about two and a half minutes for a vault of five versions of about 93,000 entries each on an SSD with nothing cached, and some minutes more for a tree twice that size, and that job's backups wait for it, once.

Failure handling and log markers:
	A job that fails (an unreadable disk, a vault that is not ready, an error in a thread) is restarted by itself, while the other jobs keep running. The retry delay starts at 60 s, doubles on each failure, and stops at 1 h. It starts again from 60 s once an attempt has run for an hour before failing. While a disk the job needs is missing, the job waits for it, and logs a failure once the wait reaches 15 min, then once an hour while it lasts.
	mergerfs pools: when a job's vault or monitored path is on a mergerfs pool, every disk of the pool must be there. While one is not mounted or cannot be read, the job waits with the FAILED: waiting marker, whose reason names the disk (disk /mnt/vaults_data/a58 of pool /mnt/vaults is not mounted): it makes no backup, prune or commit, and no vault scan while a vault disk is out. Its watcher keeps queuing changes, which are backed up once the disk is back. A disk that drops during a backup stops its copies and fails the attempt before anything is deleted or committed. Once a wait that alerted ends, one line says the job goes on.
	A vault or monitored path on one disk, off any pool, is checked the same way: while its filesystem has failed (an f2fs whose checkpoint reports an error, an XFS shut down while still mounted), the job waits and pauses as for a pool's disk (disk /mnt/pool_disks/254 has failed: its f2fs checkpoint reports an error). An f2fs disk is found in /sys/fs/f2fs by its major:minor; one whose device the kernel removed while it stays mounted (disk /mnt/pool_disks/254 cannot be read: its device 8:208 is gone), or that /sys/fs/f2fs has no folder for, cannot be read, and the job waits for it; one whose folder has no checkpoint status (an old kernel) is warned of once and taken for whole.
	fstab mounts: a path's disk is not there either while /etc/fstab names a mount point at or above it (the longest one, matched by whole path components, so /mnt/backup does not cover /mnt/backup2) that is not mounted. Every wait for a job's vault or monitored path (at its start, before each batch, and the watcher's) checks both on every poll, and the job waits with the FAILED: waiting marker, whose reason reads /mnt/backup is not mounted (/etc/fstab names it): a bare folder left under the unmounted mount point is never backed up into, nor an empty monitored one backed up as everything deleted. Something other than a folder at the path reads <path> is not a folder. Every fstab entry counts alike (bind, noauto, nofail and mergerfs ones too), its escapes such as \040 decoded; a disk mounted some other way (a systemd mount unit, autofs, by hand) counts as there, as before, only when the nearest fstab mount point above it is mounted (below an unmounted one it waits too: put the disk in /etc/fstab, or mount the fstab point first), and a missing or unreadable fstab names nothing.
	The Vault Path is made by the job's start, inside that wait once its disk is there, so never under an unmounted fstab mount point or on a pool missing a disk, and never by reading the rule file; one that cannot be made fails the job, which retries. An auto Vault File System Signature, or an auto Monitoring File System Signature, is filled in only from a folder whose disk is there: otherwise the cell stays auto, with one warning at each reverberator start, until a later start finds such a folder (for a vault, the one the job's start made).
	A stop while the job's vault path is not a folder or its disk is not there writes no pending file, for a running job's queue or a failed one's: it logs one warning (Not saving <N> pending transactions: vault path <path> is not ready: <reason>; the next start compares the whole tree, or a full comparison request in place of the transactions, or does not exist or is not a folder in place of the reason), and the queued changes are dropped, as a start with no pending file compares the whole tree.
	On a mergerfs pool, whose folder fsync reaches no disk, the job vault is flushed on each disk that holds it, after current_version moves and after the change list is placed. On a pool or a filesystem with no exchange it is also flushed during a backup, after the tree is handed to the new version and between recording the old state and changing the tree (the hand-over leaves the version before it missing for those flushes, and history waits for it).
	Each job vault keeps a 0-byte .reverberator_manifest.sqlite-journal between backups (the vault database's journal, emptied rather than deleted after each write). It belongs there and is not a crash leftover; leave it in place.
	Each version folder stays the daemon's (root's, 0755, its own times), whatever the monitored root's owner, so no user can change the top level of committed versions. From 0.54 it keeps the monitored root's owner, mode, times and extended attributes as of its batch in one extended attribute of its own, trusted.reverberator.root (one line of JSON: {"v": 1, "uid", "gid", "mode", "atime_ns", "mtime_ns", "xattrs": {name: base64 of the value}}), which only root can read or write; a whole-job restore gives them to the job's top folder, and no trusted.reverberator.* name is ever given to a whole-job restore's top folder (a monitored folder that holds such a name, such as a copy of a vault made with rsync -aX as root, gets it back like any of its attributes). When the backup after it starts, the version before it gets a copy of the record. One that cannot be written (a vault filesystem without extended attributes, a full one) logs one error per job, not again while it keeps failing, and one info line when it works again; that version's whole-job restore gives the top folder the version folder's own, as it does when the record cannot be read or decoded (a warning says so). A root whose extended attributes do not fit in one attribute of the version folder (the record takes about 1.4 times their size, and a folder holds about 4 KiB on ext4 and f2fs) gets a record without them, saying so in one line: its owner, mode and times are kept, and its top folder gets none of the attributes.
	A failed read is never taken as a deletion, and a failed copy into the vault never commits a version. A path that cannot be read keeps its last backed-up copy.
	Each rm a delete runs in a new version is checked when the batch's commands are waited for, and so is the check after the batch removing an entry the version does not track: one that failed while the entry is still there fails the batch with FAILED: removing <path> from the version failed: <the error>; retrying in <N>s (for rm, its first error line, with (and N more) when it gave more), and no version is committed. The job keeps retrying with the growing delay, and makes no later version, until the entry can be removed. A failed rm whose entry is gone is no failure. A folder standing where a deleted file's row was is another row's entry and stays, with one line: Leaving <path>: a folder, another row's entry, is in its place in the version.
	The vault scan never deletes on a guess. Any error, a gap in the version numbers, a version folder that is a symlink, two folders with one number, or an entry named after a version folder that is not its change list (one that is not a regular file, whose name does not parse, or an editor or backup copy such as …nsv~), or a current_version that is no link (read when a version folder has no change list) makes the job skip its backup with a FAILED marker until the vault is put right by hand. An entry shaped like a change list that names no folder there is kept, with an error line, when a folder there has its number, and deleted, with an error line, when its number is below the oldest version's, as a removal cut short leaves it; any other, or one that is not a regular file, makes the job skip its backup with a FAILED marker. A version folder after the newest with no change list is removed only when it holds nothing but links to itself (a backup cut off before it began); otherwise it is the tree a cut backup was writing, and the job's next attempt finishes and commits it. A commit cut off after its database named the version is finished, not undone. Emptying a vault by hand to start it over needs a daemon restart.
	Problems that only a change of the rule or skip list can fix (a skip list that lost its patterns without none, a skip pattern that does not parse, two rows whose names become one job name, a name with no letters, digits, - or _ left once it is cleaned up) stop that job for good, and are not retried.
	Each of these is logged at error level, in exactly this form:
		reverberator job <name> FAILED: <reason>; retrying in <N>s       the job failed and will retry
		reverberator job <name> FAILED: waiting <N> min for <path>: <reason>       a disk the job needs is still missing
		reverberator job <name> UNREADABLE: <path>: <error>; keeping its last backed-up copy       a path could not be read, reported once per backup that meets it
		reverberator job <name> NOT BACKED UP: <path>: a symlink whose text or path is longer than the vault's filesystem takes; left out of this version       a symlink the vault cannot hold, reported once per backup that meets it
		reverberator job <name> STOPPED: <reason>       the job will not run again until its rule or skip list is fixed and reverberator restarted
		reverberator job <name> FAILED: cannot check the backup lock <path>: <error>; backup postponed       the file a restore waits on cannot be opened or locked, so the job is not backed up (its changes stay queued)
		reverberator job <name> FAILED: cannot check the restore lock <path>: <error>; backup postponed       the file that holds a restore's lock cannot be opened or locked, so the job is not backed up (its changes stay queued)
		reverberator job <name> FAILED: cannot check the history lock <path>: <error>; pruning postponed       the file history and restores hold cannot be opened or locked, so no version is removed and the vault keeps growing
		reverberator job <name> VAULT WRITE ERROR: disk <disk> failed a sync (<error>): nothing is committed past it, and the next attempt copies again what this one changed       a disk holding the job vault failed a write; logged by each attempt that meets it, then the job's FAILED line, so a disk that keeps failing alerts again at every retry of every job on it (after 60 s, then doubling up to once an hour)
		reverberator job <name> RECOVERED after <N> failed attempts       the job works again (informational)
		reverberator EXITING with error: <reason>       the daemon is exiting because of an error
	Exit codes: 0 after a signal (SIGTERM, SIGINT), 1 when the main thread fails, 3 when every job is STOPPED or the rule file is missing or holds no job. reverberator.service has RestartPreventExitStatus=3, so systemd does not restart a daemon that would only stop again. Keep that line if you write your own unit file.
	A job whose name has nothing left after cleanup (the name is used for its vault folder) is stopped with a STOPPED marker that calls the job row-<n>, so that the marker matches the alert patterns (n counts the rule rows reverberator keeps: comments, the defaults row and every row it ignores with a warning are left out, and a row repeating an earlier row's Job Name takes that row's place), and gives the name as written in the rule file, saying to rename it; it has no status file, and status shows it from the rule file; it never writes into the vault, nor makes its Vault Path. The marker for a lock that cannot be checked is logged after the same 15 min grace as a missing disk, then once an hour while the failure lasts; until then the daemon only logs, at error level, that it postponed the backup or the pruning.
	firewatcher/reverberator.regex holds the patterns for the alerting markers (FAILED, UNREADABLE, NOT BACKED UP, STOPPED, VAULT WRITE ERROR, EXITING); RECOVERED is left out. They match a marker only where a journal line's message starts (right after the first "]: ", past a color code or "[ERROR] " prefix), so a monitored file named like a marker, which shows up inside other lines, raises no alert. Copy it to /etc/firewatcher/patterns.d/reverberator.regex and restart firewatcher, which loads its patterns at start and follows the whole journal; 0.47 adds the VAULT WRITE ERROR pattern and 0.55.2 the NOT BACKED UP one, so copy it again when upgrading.
	Inner mounts: a mount point under a monitored path (read from /proc/self/mountinfo) is backed up while it is mounted. When it is unmounted, its folder is paused: nothing under it is recorded as deleted, its last backed-up contents stay in new versions, and events under it are dropped. When it is mounted again only that subtree is compared with the vault. To retire an inner disk for good, remove the mount point folder, or put files of its own in it; the pause then ends and the folder is backed up as what it now is.

Status, history and restore:
	reverberator status | history | restore: three commands that read the rule file and the vaults. They never write to a vault, its manifest or the rule file, and the daemon's own command line (reverberator [options] RULE_PATH) is unchanged.
	reverberator status [--rule PATH] [--state_dir DIR] [--json]: one block per job with its state (running, retrying, waiting for a disk or for a restore of the job to end, stopped, with the reason), its last backup, and its vault numbers (versions kept against the limit, the oldest kept, size and inodes against the limits; a vault that is not mounted is said to be). The daemon writes a small file per job into /run/reverberator after each state change and committed backup; the commands take --state_dir or REVERB_STATE_DIR to use another folder, the daemon only REVERB_STATE_DIR, so set the same REVERB_STATE_DIR for both or status will read the daemon as not running. status counts the daemon as running only when the pid it recorded is alive with the recorded start time, so after a kill or a reboot the jobs are shown as the last known state, marked so, never as healthy. The commands read the rule file the daemon recorded, whether or not it still runs; with no record, or to use another, give --rule PATH. They never fall back to a reverb_rule.tsv in the current folder.
	reverberator status --json prints the same as one JSON object on one line, for scripts and dashboards; both forms are made from the same data, so they cannot disagree, and exit alike (a usage error prints nothing on stdout). Times are seconds since the epoch, texts are escaped as in the text form, and jobs come in rule file order:
		{"daemon": {"alive", "pid", "version", "started_at", "rule_path"},
		 "jobs": [{"job", "state", "phrase", "last_known", "detail", "failures", "retry_at", "since", "last_backup", "last_version", "oldest_backup", "oldest_version", "versions", "keep",
		           "vault": {"path", "mounted", "error", "size", "size_limit", "inodes", "inode_limit"}}]}
	alive is whether the recorded daemon runs; pid, version (a string, such as "0.55") and started_at are those it recorded (null with no record; kept from its last run when it is not alive). state is starting, running, waiting, retrying, stopped, or unknown for a job with no status file; phrase is the state as the text shows it, and last_known says it is only the last known state (the daemon is not alive, or the record is older than this daemon run). failures counts the failed attempts in a row, retry_at is when a retrying job tries again, since when the state began. last_backup and last_version are the newest kept version's time and number, oldest_backup and oldest_version the oldest one's (null with no version); versions is how many are kept and keep the limit (0 for none). In vault, mounted is false for a vault folder that is missing or empty, the sizes and limits (0 for no limit) are null where the text shows no vault line, and error says why the vault could not be read (mounted and versions are then null). A job whose name has nothing left after cleanup is stopped, with vault null.
	reverberator history [--job NAME] [--files] PATH: when a file or folder changed in the versions the vault still keeps, newest first, including paths that no longer exist. PATH is a live path, absolute or relative to the current folder, under one job's monitored path (the longest match; --job NAME names the job, and PATH is then relative to its monitored path). For a file each line gives the version, time, event (create, modify, attrib, move with its source, delete) and size; for a folder, counts of what was created, modified and deleted under it, and --files lists the paths. The oldest kept version is shown as the oldest copy kept, not as a change. When one batch moves a folder and also moves a file through a name it overwrote or removed, history can name a place the file only passed through; restores are right. A path that was never backed up is said so, with the skip list pattern that matches it if there is one. A job vault that is not there is reported as The vault <path> is not there (is its disk mounted?), with exit code 1, not as never backed up.
	reverberator restore [--job NAME] [--version N | --at TIME] [--in-place] [--threads N] [--yes] [--accept] PATH [DEST]: copies a file, a folder, or a job's whole monitored path out of one version. The version is --version N, or the newest one at or before --at TIME (YYYY-MM-DD HH:MM[:SS] in local time, or a version folder's time; a bare YYYY-MM-DD means 00:00 at the start of that day, so it picks the last version made before that day began); with neither, the versions where the path differs are listed newest first and one is picked by number (one candidate is used and named). Without a terminal that is an error. Forward links are followed to the version holding the entry, user symlinks are restored as symlinks, and mode, owner, times and extended attributes are kept. With Only Sync Attributes a restored file carries the newest mode, owner and times its shared copy has, which are not necessarily those of the chosen version. A file is written under a temporary name and renamed once complete. An entry that is only a link into the monitored path (a referenced first version), a dangling chain in a vault not yet converted, an unreadable file or a failed copy is reported by path at the end, the rest still restores, and the exit code is 1. Each failure and warning is printed as it happens, so a restore with many of them does not hold them all in memory, and the summary at the end repeats the first 20 of each with their counts. The picker and the Continue? prompt are written to stderr, so they show on the terminal when the output is redirected. Progress is printed, and copies run in parallel, 4 at a time unless --threads N says otherwise, so a restore does not keep the vault disk from other jobs' backups.
	Destination: restore /a/b/proj /tmp/out creates /tmp/out/proj, and stops before writing when that name exists, unless it is this restore's own unfinished output. --in-place restores at the original path instead, first moving what is there to <name>.before-restore-<timestamp> next to it; nothing is overwritten. Names printed by the commands have control characters escaped. Restores refuse a destination on a path another user could change (a folder from / down that is owned by neither root nor you, or is group or other writable without the sticky bit), and a destination inside any job's vault; in place is also refused when the restored path would hold a vault, as moving it aside would take the vault along. In place is refused where another user owns or can write a folder above the restored path (for example a Nextcloud data tree owned by www-data): restore into a folder of your own, then move it in.
	Unfinished and failed restores: a folder restore puts a marker file (.reverberator-restore) at the top of its output, naming the job, path and version. Until the restore finishes or is accepted, its folders are owned by the user running the restore (usually root) and the target is private (0700); on success each folder gets its owner, mode and times, those the monitored folder had in that version (a folder with entries that no batch or full comparison from 0.54 on has made, changed or written into keeps, from the versions before, the time its entries were written into the vault: the first full comparison from 0.54 on, such as the one at start, gives every folder of the new version its own times; a whole job's top folder gets the monitored root's owner, mode, times and extended attributes as of that version, which its version folder keeps for it, and the version folder's own (root's, 0755, its own times) for a version made before 0.54, one whose vault filesystem keeps no extended attributes, or a restore run by a user other than root, who cannot read them), and the marker is removed. Running the same restore again (same job, path, version and place) continues it: entries already there with the vault copy's type, size and mtime are kept, the rest are copied. It never moves aside, replaces or deletes output it did not mark, and a marker of another job, path or version is refused. Ctrl-C, SIGTERM and SIGHUP stop a restore alike (one that is ignored when the restore starts, as nohup ignores SIGHUP, stays ignored): it first writes what it restored out to disk, saying so, which takes as long as the disk needs and cannot be cut short (a second Ctrl-C included); then the marker stays, and the same command picks up where it stopped, keeping what is there, unless the stopped run was itself copying everything again, or its write-out failed: then it copies everything again. A stop while the folders are being given their owners says to finish with --accept, as running it again would only copy over what is done. Only one run of the same restore is allowed at a time; a second is refused. When a restore leaves failures, the marker stays so a re-run retries just those, but a failure no rerun can fix does not hold it: a link the target's filesystem cannot hold (on XFS, a text of 1,024 bytes and up), an entry whose path it refuses as too long (a folder too deep, a file), a dangling chain and a link to the live file of a referenced backup are each named (while a disk of the vault's pool is missing, a dangling chain is retried instead, as the disk may hold what it leads to), and the restore finishes and exits 1. A restore syncs the target's disks before it hands the folders over and again before it ends. Every sync goes through a handle opened before the restore's first copy (on a mergerfs pool one for each disk), and a disk that joins the pool while it runs and holds the restore's folder fails it, as nothing can tell whether what landed there reached the disk (a folder restore is finished by running it again, which opens that disk too; for a file, move what was restored away and restore again). Until a sync succeeds, the marker records that what the target holds is not known to be on disk: after a kill, a crash or a power cut before then, or a sync that failed, the same restore run again copies everything again, and --accept is refused (exit 2) until such a run has finished and synced. A run again that copies everything again while a disk of the vault's mergerfs pool is missing (warned) keeps that record and leaves the target private, saying to run it again once the vault's disks are all there, as what the missing disk holds was not copied again. A run again that keeps failing for a cause it may fix (a file that cannot be copied, say) can never finish while the cause stays: the summary and --accept's refusal then say to fix the cause and run again, or to remove the target and restore it fresh when a restore made it (the marker says so), and otherwise (an existing folder, a job's root) to restore into a new folder instead, never to remove it; restore --accept PATH (with the same options) keeps the result as it is (it is refused, with exit code 2, when the target holds no unfinished restore of that path and version, as there is nothing to accept, and then changes nothing): it copies nothing, gives every folder its owner, mode and times (instead of the user running the restore), and removes the marker.
	Whole job: --in-place on a job's monitored path itself cannot move the root aside, so the root must be empty (an empty lost+found is fine) or hold its own unfinished restore, which covers a replaced disk, and must belong to the user running the restore (a root owned by another user is refused, not given to anyone); otherwise restore into a folder instead. It always shows which filesystem the root is on and asks Continue? [y/N] (--yes skips; without a terminal the question needs --yes). It refuses when that filesystem has less free space than the newest version took (it holds the whole tree; each older one what the backup after it changed), and warns that the restore may not fit when there is less than the versions from the chosen one up took together. Check the mount point it shows: with the disk not mounted, that would be the disk below it. A restore picked up again skips this check and its warning, as part of it is already in place. If the daemon runs that job, it will back the restore up as one large change.
	Retention and backups: a restore picks its version and asks Continue? without holding anything that backups wait for; it then waits for a running backup and holds the job's lock while it copies, and the daemon backs that job up only once it ends (one log line: Waiting for a restore of <job> to finish before backing up; the job's changes stay queued, and a stop of the daemon meanwhile keeps them as on any stop). A restore that starts while a backup waits waits for that backup, so restores cannot hold one off for ever, and it says Waiting for reverberator to finish a backup of <job>. history holds a lock of its own that only pruning waits for, as does a restore from its picker to its last copy: while either runs, or a pager shows the output of history, the daemon postpones pruning that job's oldest version, logging that it did. history runs beside a backup, and reads again what the backup changes under it. The locks are files in the state folder (job-<name>.backup.lock, job-<name>.restore.lock and job-<name>.history.lock), released by the system if the command is killed. While pruning is postponed (history, a restore at its picker or prompt, restores waiting behind a batch) the vault may pass its size limit or keep more versions than the limit. Backups wait, so a change reaches the vault only once the restore ends; status shows the job waiting, with the reason (a restore of <job> is copying, or the lock that cannot be checked), and no marker is raised for a long restore.
	Vault links: an older version's link is followed only when its text is exactly its own path in the version after it; nothing else in a version is ever followed. Browsing by hand: current_version and the newest version are plain trees; in older versions ls, cat and cp of a file work, find, du and rsync need -L to go into an unchanged folder, cp -a and rsync -a copy forward links as links, cp -aL and rsync -aL also follow your own symlinks, and rsync -a --copy-unsafe-links comes closest (forward links copied as what they name, your links inside the version kept as links, your links that leave it copied as what they point to). reverberator restore gives a faithful copy.
	Exit codes of the commands: 0 when everything asked for was shown or restored, 1 when anything failed, 2 for usage errors: a path under no job, no version chosen without a terminal, a destination refused, a path that was never backed up (for restore; history says so and exits 0), a rule file that is missing, a time for --at that is not one of the forms above, and --accept where no unfinished restore of that path and version is.
	history and restore still run while a disk of the vault's mergerfs pool is missing: they print a warning on stderr naming the disk, as what it holds is not shown, and exit 1 (2 still means a usage error, such as a path whose copies are all on the missing disk, which is reported as never backed up).

Design decision:
	When reverberator is in cold start, will not calculate hash to do space efficient move operations to vault.
	When restarting reverberator, will do one backup that will only handle create, modify, delete, attrib.
	The latest version's entries, with the size, mtime, mode, owner and tail hash of what the vault holds for each, are kept in .reverberator_manifest.sqlite in the job vault. Restarts compare the monitored tree against it, and read the vault only for entries it has no record of, and once for each file copied since the previous restart.
	Each job may name a gitignore style Skip List File in its rule row. It is read at start, once the job's disks are ready, and applied to everything read from the monitored path and never to the vault. A job which has used patterns needs the value none to back up everything.
	Change events waiting for a backup are kept compressed, events the backup would skip anyway are dropped as the queue grows, and the queue becomes one full scan only when memory runs short (stalls on memory, little available, or the queue holding a quarter of what is available).

Failure handling and log markers:
	A job that fails (an unreadable disk, a vault that is not ready, an error in a thread) is restarted by itself, while the other jobs keep running. The retry delay starts at 60 s, doubles on each failure, and stops at 1 h. It starts again from 60 s once an attempt has run for an hour before failing. While a disk the job needs is missing, the job waits for it, and logs a failure once the wait reaches 15 min, then once an hour while it lasts.
	A failed read is never taken as a deletion, and a failed copy into the vault never commits a version. A path that cannot be read keeps its last backed-up copy.
	Problems that only a change of the rule or skip list can fix (a skip list that lost its patterns without none, a skip pattern that does not parse, two rows whose names become one job name) stop that job for good, and are not retried.
	Each of these is logged at error level, in exactly this form:
		reverberator job <name> FAILED: <reason>; retrying in <N>s       the job failed and will retry
		reverberator job <name> FAILED: waiting <N> min for <path>: <reason>       a disk the job needs is still missing
		reverberator job <name> UNREADABLE: <path>: <error>; keeping its last backed-up copy       a path could not be read, reported once per backup that meets it
		reverberator job <name> STOPPED: <reason>       the job will not run again until its rule or skip list is fixed and reverberator restarted
		reverberator job <name> RECOVERED after <N> failed attempts       the job works again (informational)
		reverberator EXITING with error: <reason>       the daemon is exiting because of an error
	Exit codes: 0 after a signal (SIGTERM, SIGINT), 1 when the main thread fails, 3 when every job is STOPPED or the rule file is missing or holds no job. reverberator.service has RestartPreventExitStatus=3, so systemd does not restart a daemon that would only stop again. Keep that line if you write your own unit file.
	firewatcher/reverberator.regex holds the patterns for the alerting markers (FAILED, UNREADABLE, STOPPED, EXITING); RECOVERED is left out. They match a marker only where a journal line's message starts (right after the first "]: ", past a color code or "[ERROR] " prefix), so a monitored file named like a marker, which shows up inside other lines, raises no alert. Copy it to /etc/firewatcher/patterns.d/reverberator.regex, which firewatcher loads from the service's journal.
	Inner mounts: a mount point under a monitored path (read from /proc/self/mountinfo) is backed up while it is mounted. When it is unmounted, its folder is paused: nothing under it is recorded as deleted, its last backed-up contents stay in new versions, and events under it are dropped. When it is mounted again only that subtree is compared with the vault. To retire an inner disk for good, remove the mount point folder, or put files of its own in it; the pause then ends and the folder is backed up as what it now is.

Status, history and restore:
	reverberator status | history | restore: three commands that read the rule file and the vaults. They never write to a vault, its manifest or the rule file, and the daemon's own command line (reverberator [options] RULE_PATH) is unchanged.
	reverberator status [--rule PATH] [--state_dir DIR]: one block per job with its state (running, retrying, waiting for a disk, stopped, with the reason), its last backup, and its vault numbers (versions kept against the limit, the oldest kept, size and inodes against the limits; a vault that is not mounted is said to be). The daemon writes a small file per job into /run/reverberator after each state change and committed backup; set REVERB_STATE_DIR or --state_dir to use another folder (for the daemon and the commands alike). status counts the daemon as running only when the pid it recorded is alive with the recorded start time, so after a kill or a reboot the jobs are shown as the last known state, marked so, never as healthy. The commands read the rule file the daemon recorded, whether or not it still runs; with no record, or to use another, give --rule PATH. They never fall back to a reverb_rule.tsv in the current folder.
	reverberator history [--job NAME] [--files] PATH: when a file or folder changed in the versions the vault still keeps, newest first, including paths that no longer exist. PATH is a live path, absolute or relative to the current folder, under one job's monitored path (the longest match; --job NAME names the job, and PATH is then relative to its monitored path). For a file each line gives the version, time, event (create, modify, attrib, move with its source, delete) and size; for a folder, counts of what was created, modified and deleted under it, and --files lists the paths. The oldest kept version is shown as the oldest copy kept, not as a change. A path that was never backed up is said so, with the skip list pattern that matches it if there is one. A vault that is not mounted is said to be, not reported as never backed up.
	reverberator restore [--job NAME] [--version N | --at TIME] [--in-place] [--threads N] [--yes] [--accept] PATH [DEST]: copies a file, a folder, or a job's whole monitored path out of one version. The version is --version N, or the newest one at or before --at TIME (YYYY-MM-DD, YYYY-MM-DD HH:MM[:SS], local time, or a version folder's time); with neither, the versions where the path differs are listed newest first and one is picked by number (one candidate is used and named). Without a terminal that is an error. Chain links are followed to the real file, user symlinks are restored as symlinks, and mode, owner, times and extended attributes are kept. With Only Sync Attributes a restored file carries the newest mode, owner and times its shared copy has, which are not necessarily those of the chosen version. A file is written under a temporary name and renamed once complete. An entry that is only a link into the monitored path (a referenced first version), a dangling chain, an unreadable file or a failed copy is reported by path at the end, the rest still restores, and the exit code is 1. Progress is printed, and copies run in parallel (--threads).
	Destination: restore /a/b/proj /tmp/out creates /tmp/out/proj, and stops before writing when that name exists, unless it is this restore's own unfinished output. --in-place restores at the original path instead, first moving what is there to <name>.before-restore-<timestamp> next to it; nothing is overwritten. Names printed by the commands have control characters escaped. Restores refuse a destination on a path another user could change (a folder from / down that is owned by neither root nor you, or is group or other writable without the sticky bit), and a destination inside any job's vault. In place is refused where another user owns or can write a folder above the restored path (for example a Nextcloud data tree owned by www-data): restore into a folder of your own, then move it in.
	Unfinished and failed restores: a folder restore puts a marker file (.reverberator-restore) at the top of its output, naming the job, path and version. Until the restore finishes or is accepted, its folders are owned by root and the target is private (0700); on success each folder gets its owner, mode and times and the marker is removed. Running the same restore again (same job, path, version and place) continues it: entries already there with the vault copy's type, size and mtime are kept, the rest are copied. It never moves aside, replaces or deletes output it did not mark, and a marker of another job, path or version is refused. Only one run of the same restore is allowed at a time; a second is refused. When a restore leaves failures, the marker stays so a re-run retries just those; restore --accept PATH (with the same options) keeps the result as it is: it copies nothing, gives every folder its owner, mode and times, and removes the marker.
	Whole job: --in-place on a job's monitored path itself cannot move the root aside, so the root must be empty (an empty lost+found is fine) or hold its own unfinished restore, which covers a replaced disk; otherwise restore into a folder instead. It always shows which filesystem the root is on and asks Continue? [y/N] (--yes skips). It refuses when that filesystem has less free space than the recorded size of the version, so check the mount point it shows: with the disk not mounted, that would be the disk below it. If the daemon runs that job, it will back the restore up as one large change.
	Retention: while a restore runs it holds a lock for its job in the state folder (released by the system if the restore is killed), and the daemon postpones pruning that job's oldest version, logging that it did. Backups continue, so the vault may exceed its size limit until the restore ends.
	Vault links: a symlink in a version is taken as a link to the previous version's copy only when it names the version just before its own, and is followed only through real folders. Before 0.39 a move to another folder depth left links that pointed nowhere, and retention could delete the only copy behind one. Moves now rewrite the links they carry, and links broken earlier are read by history and restore and pruned correctly.
	Exit codes of the commands: 0 when everything asked for was shown or restored, 1 when anything failed, 2 for usage errors (a path under no job, no version chosen without a terminal, a destination refused).

Design decision:
	When reverberator is in cold start, will not calculate hash to do space efficient move operations to vault.
	When restarting reverberator, will do one backup that will only handle create, modify, delete, attrib.
	The latest version's entries, with the size, mtime, mode, owner and tail hash of what the vault holds for each, are kept in .reverberator_manifest.sqlite in the job vault. Restarts compare the monitored tree against it, and read the vault only for entries it has no record of, and once for each file copied since the previous restart. A comparison syncs the vault's disks once (syncfs on each disk of a mergerfs pool that holds the job vault) before it records any copy it read back as checked, and a failed sync keeps that comparison's copies unchecked, for a later comparison to read back again; nothing is flushed when copies are written.
	The kernel reports a disk's failed write only once, to the first sync that meets it, so a disk whose sync fails is remembered until the next reboot by a marker in the state folder (/run/reverberator, or $REVERB_STATE_DIR when set): vault-sync-failed-<the mount point of the disk's filesystem, percent-encoded, / as %2F>, as vault-sync-failed-%2Fmnt%2Fjank_data%2Fa58 for the filesystem mounted at /mnt/jank_data/a58 (the kernel reports the error once per mounted filesystem, so branches of a pool that are folders of one filesystem, and a job off the pool on that filesystem, share one marker), holding one line of JSON with the disk, the boot id and the error. While a marker of this boot stands, every comparison keeps the copies of each job whose vault is on that disk unchecked and reads their tails again, and after the reboot the restart's full comparison reads them back from the disk. To end a marker without a reboot once the disk is replaced, delete its file. A marker that cannot be written (a disk path too long for a file name, say) keeps the disk in memory until reverberator stops. Comparisons sync the vault's disks one at a time, so no other job's sync of the same disk gets past the error before it is marked.
	Each job may name a gitignore style Skip List File in its rule row. It is read at start, once the job's disks are ready, and applied to everything read from the monitored path and never to the vault. A job which has used patterns needs the value none to back up everything.
	Two rule columns after Skip List File are optional, and a rule file without them (12 columns) is read as it is: missing or blank cells mean the defaults, and the daemon never writes them (a row it rewrites to fill in auto cells gets its first 12 cells written as before); --drop-sample-rule writes a sample whose header and description rows name all 14 columns. A cell that cannot be read logs an error naming the cell and its format, and the job runs with the default.
		13, Full Comparison Interval: a duration such as 1d, 12h, 30m, 45s or 1h30m, in w, d, h, m and s or their words (week, day, hr or hour, min or minute, sec or second, plural too), case ignored except that a bare M is refused (minute or month?), spaces allowed between a number and its unit and between groups, and a plain number in seconds; blank, 0, none, off and auto mean none, the default. When set, the job compares its whole tree with the vault that often, counted from the end of its last full comparison of any kind (a restart always makes one), which catches writes no event reports, such as through mmap. It starts within a few seconds of coming due, without waiting for the tree to be quiet, logging 'The full comparison interval (<N> s) has passed since the last one: comparing the whole tree'; a running batch delays it, and a job waiting for its vault postpones it.
		14, Chain Length: the most links a path into the vault may meet (below). Blank or auto means 40, 0 or none means no limit, a whole number of 3 or more is itself, and a smaller one is read as 3, with an error line.
	File names are anyone's to choose, and a name that is not UTF-8 (bad\xff.txt, say) is backed up like any other, and kept in the change lists and pending transactions so that its exact bytes come back (stored escaped, not as raw bytes). Wherever a name is shown, in a log line or the output of a command, it is escaped: a byte that is not UTF-8 appears as \xff, and a control character, such as a newline, a carriage return or an escape, as \x0a, \x0d or \x1b; in an ordinary log line a line break in a name continues on the next line indented by four spaces, while marker lines and command output show it as \x0a. No line reverberator logs holds more than 16384 bytes of text: a longer one is cut to fit, its notice included, never inside a character, and ends with the number of bytes left out, so that the journal, which splits a line longer than 48K, cannot start a record inside it. The daemon also writes every line its libraries print, and every traceback of a thread, whole: a line another thread has not finished waits until it is, so no marker can land inside one. A name can then neither drive a terminal nor start a log line of its own, so a file named like a marker cannot raise the alerts below.
	A version links an unchanged file to the copy in the version before it, so after many versions a file reaches its real copy through a long chain of links. A job's Chain Length N (40 by default, the kernel's limit) is the most links a path into its vault may meet, two of them kept for the current_version link and a user's own link. A file is copied again from the vault into a new version once its chain would pass a threshold chosen from its name, from max(1, N-8) to N-2 links, so its copies come every max(1, N-8) + 1 to N-1 versions (33 to 39 at the default, its chains reaching 32 to 38 links). The spread by name keeps files from all being copied in one version only for N of about 10 and up: at a small N many or all files fall due together (at N = 3, every file every second version). A job keeping no more than max(1, N-8) + 1 versions (33 at the default) never copies again (a job with no limit on versions counts as keeping more), and with 0, no limit, chains grow as long as the versions kept and nothing is copied again. These copies are logged as recopy in the version's change list, are not shown by history or the restore picker (they are no change to the file), are checked like any other copy at the next comparison, and count toward the size limit. Lowering N makes every file whose chain is now too long due at the next version, all at once. reverberator follows chains of any length itself, and its comparisons walk vault links hop by hop, so the kernel's limit does not matter to it; tools that read the vault through the kernel do meet it: browsing the vault by hand (or any tool reading it through the kernel, such as cp) fails with "too many levels of symbolic links" for a file reached through more than 40 links, and through more than about 20 while mounts change on the host (Docker does this, and the kernel then counts links twice). On a host where the vault is read through the kernel, set the job's Chain Length (rule column 14) to about 20; where nobody browses or copies the vault by hand, 0 (no limit) saves the re-copies.
	The vault database is upgraded in place the first time 0.40 starts, without a full comparison, to record which version holds each file's real copy; a file whose record is still missing learns it from its chain the first time the files to copy again are worked out. Going back is not supported: an older reverberator does not know the new database, discards it and builds it again by reading the whole vault.
	Runbook: a job that failed on names that are not UTF-8 under 0.39 may have left a pending-changes file with ? in its names. Deleting that job's .reverberator_pending_transactions.nsv before the first 0.40 start makes it compare its whole tree once.
	Change events waiting for a backup are kept compressed, events the backup would skip anyway are dropped as the queue grows, and the queue becomes one full scan only when memory runs short (stalls on memory, little available, or the queue holding a quarter of what is available).
	After each batch, every place its events touched is compared with the monitored tree and the new version is fixed before it is committed, so renames, saves through a backup file and folder swaps come out as they are in the tree; a batch resumed after a restart (one of scans only too), or put back after a failed backup, is followed by one full comparison.
	Changes made in one batch after a move, at the moved path or inside a moved folder (mv x d/x; chmod 600 d/x, or mv d e; echo new > e/new), are replayed after the move, so a folder is moved, not copied again, and a moved file's new mode, owner and extended attributes reach the new version. The comparison after each batch also checks the mode and owner (a symlink's own owner too) of what the batch touched, and the extended attributes of those the batch changed, by their ctime (a moved folder is one check, not one per file), and syncs what differs. A full comparison (at a start, after a failed backup, or when events were lost) also checks the extended attributes of the entries changed, by their ctime, since the vault last matched the whole tree (the last backup or comparison that saw all of it, recorded in the vault database), so an xattr-only change made while nothing watched is backed up too. Either check allows 10 s for a clock step. A sync of an entry's metadata into the vault also removes the extended attributes the monitored entry no longer has (setfattr -x, or an ACL removed by setfacl -b), so a restore does not bring them back; a monitored filesystem that keeps none (ENOTSUP, as mergerfs with xattr=nosys) leaves the vault's as they are.
	Under Only Sync Attributes, an attribute-only change (chmod, chown, an xattr, touch) is synced onto the vault's copy only while the file's mtime is the one recorded. One whose mtime moved (touch, rsync -t, or a write through mmap, which raises no event and moves the mtime and ctime, not the size) copies the file once, in that version, so the mtime stays a true signal for later comparisons: a touch of a big unchanged file costs one copy.
	The watcher watches each folder as its walk reaches it, before reading it, so a folder made during a cp -r or tar x is watched, and a folder moved within the tree is walked again at its new name. A batch carries the paths whose move-out is still waiting for its pair, and the check after it compares them, so a file moved into a new folder or out of the tree leaves its old place by the next batch at the latest. Its own delete, arriving later for a path the vault no longer tracks, is dropped, so it makes no version on its own. Events in a folder made during a batch, which the batch's copy of the folder holds, are recorded again once any batch is taken, the backuper's own take at a start too.
	A symlink the monitored tree holds is backed up as a symlink and is never taken for the vault's own link to an older version, except one whose text is exactly its own path's link to the previous version, which only that path can be confused by. A version whose change list cannot be used (missing, empty, unreadable, or written under another monitored path) has its links of that form judged by their text alone, as before 0.44, and so does a link its change list cannot tell.
	Pruning hard-links the oldest version's copies into the next version and removes the oldest version only at the end, so a prune cut off anywhere loses nothing. On a filesystem without hard links it moves them, as before.
	Each job vault gets .reverberator_prune_salt at the job's first prune, a root-only 0600 file whose secret names pruning's temporary files. Leave it in place. A temp of it (.reverberator_prune_salt.tmp-*) that a kill left is removed by the job's next vault scan.
	A prune cut off between its hard link and its rename leaves a hidden .<hash>.reverberator-partial beside a link of the next version; the next prune uses and removes it, and a folder restore never writes it out (it is told by being the same file as a link beside it leads to).

Known limits (each in docs/limitations.md):
	The vault database (.reverberator_manifest.sqlite) and the change lists are readable by any local user, and list every backed-up file name and size.
	With keep-N at 40 or more, an unchanged user symlink is reached through more than 40 links by way of current_version/ (at 41 or more, through its own version folder too), so browsing the vault by hand gives "too many levels of symbolic links" for it; restore gives it back.
	Before snapraid fix rebuilds a disk of a pool, stop reverberator (systemctl stop reverberator), and start it again once the fix ends: a replaced disk counts as there as soon as it is mounted, so jobs would resume while its files are still being restored.
	A file written only through mmap raises no inotify event, so it is backed up at its next normal write or a restart; a chmod or chown of it in the same batch keeps its old bytes in that version (round 11 copies such a file when its mtime moved, and adds an optional scheduled full comparison).
	With a size limit, a backup can go over it until the next prune by a few KB (the new version's own folders, links and xattr blocks), or by the size of a file kept under a folder moved into a new folder; a vault keeping one version, whose only version is never removed, can pass it by the size of a change until a second version exists.
	The pause on a missing pool disk tells a quickly swapped disk apart only on kernel 6.8 or newer, and notices a dying disk only once its filesystem fails or flags an error.
	An extended-attribute-only change made outside the watched folder (straight onto a disk of a pool, or a remote write on a network filesystem) is backed up only when the file next changes.
	A file rewritten in place while reverberator is down, at the same size, with its mtime set back and changed only before its last 64 KiB, is missed at the restart and kept wrong until it changes again.
	After the reboot that ends a vault disk's failed-sync marker, the restart reads each unchecked copy back by its size, mtime and last 64 KiB, so a page lost in the middle of a file to the write error stays wrong until the file changes again.
	The service unit waits up to ~5 min for the clock to sync before starting: a clock set back after start can hide extended-attribute-only changes made while nothing watched until the next batch.

Failure handling and log markers:
	A job that fails (an unreadable disk, a vault that is not ready, an error in a thread) is restarted by itself, while the other jobs keep running. The retry delay starts at 60 s, doubles on each failure, and stops at 1 h. It starts again from 60 s once an attempt has run for an hour before failing. While a disk the job needs is missing, the job waits for it, and logs a failure once the wait reaches 15 min, then once an hour while it lasts.
	mergerfs pools: when a job's vault or monitored path is on a mergerfs pool, every disk of the pool must be there. While one is not mounted or cannot be read, the job waits with the FAILED: waiting marker, whose reason names the disk (disk /mnt/jank_data/a58 of pool /mnt/jank is not mounted): it makes no backup, prune or commit, and no vault scan while a vault disk is out. Its watcher keeps queuing changes, which are backed up once the disk is back. A disk that drops during a backup stops its copies and fails the attempt before anything is deleted or committed. Once a wait that alerted ends, one line says the job goes on.
	On a mergerfs pool, whose folder fsync reaches no disk, the job vault is flushed on each disk that holds it, after current_version moves and after the change list is placed.
	Each job vault keeps a 0-byte .reverberator_manifest.sqlite-journal between backups (the vault database's journal, emptied rather than deleted after each write). It belongs there and is not a crash leftover; leave it in place.
	A failed read is never taken as a deletion, and a failed copy into the vault never commits a version. A path that cannot be read keeps its last backed-up copy.
	The vault scan never deletes on a guess. Any error, a gap in the version numbers, a version folder that is a symlink, two folders with one number, or an entry named after a version folder that is not its change list (one that is not a regular file, whose name does not parse, or an editor or backup copy such as …nsv~), or a current_version that is no link (read when a version folder has no change list) makes the job skip its backup with a FAILED marker until the vault is put right by hand. An entry shaped like a change list that names no folder there is kept, with an error line, when a folder there has its number, and deleted, with an error line, when its number is below the oldest version's, as a removal cut short leaves it; any other, or one that is not a regular file, makes the job skip its backup with a FAILED marker. Emptying a vault by hand to start it over needs a daemon restart.
	Problems that only a change of the rule or skip list can fix (a skip list that lost its patterns without none, a skip pattern that does not parse, two rows whose names become one job name, a name with no letters, digits, - or _ left once it is cleaned up) stop that job for good, and are not retried.
	Each of these is logged at error level, in exactly this form:
		reverberator job <name> FAILED: <reason>; retrying in <N>s       the job failed and will retry
		reverberator job <name> FAILED: waiting <N> min for <path>: <reason>       a disk the job needs is still missing
		reverberator job <name> UNREADABLE: <path>: <error>; keeping its last backed-up copy       a path could not be read, reported once per backup that meets it
		reverberator job <name> STOPPED: <reason>       the job will not run again until its rule or skip list is fixed and reverberator restarted
		reverberator job <name> FAILED: cannot check the restore lock <path>: <error>; pruning postponed       the file that holds a restore's lock cannot be opened or locked, so no version is removed and the vault keeps growing
		reverberator job <name> VAULT WRITE ERROR: disk <disk> failed a sync (<error>); its copies stay unchecked until a reboot       a disk holding the job vault failed a write, logged once per marker (see the sync marker above)
		reverberator job <name> VAULT WRITE ERROR: disk <disk> failed a sync (<error>); cannot record it until a reboot (<marker error>), so it is remembered only until reverberator stops       the same, when the marker cannot be written
		reverberator job <name> RECOVERED after <N> failed attempts       the job works again (informational)
		reverberator EXITING with error: <reason>       the daemon is exiting because of an error
	Exit codes: 0 after a signal (SIGTERM, SIGINT), 1 when the main thread fails, 3 when every job is STOPPED or the rule file is missing or holds no job. reverberator.service has RestartPreventExitStatus=3, so systemd does not restart a daemon that would only stop again. Keep that line if you write your own unit file.
	A job whose name has nothing left after cleanup (the name is used for its vault folder) is stopped with a STOPPED marker that calls the job row-<n>, so that the marker matches the alert patterns (n counts the rule rows reverberator keeps: comments, the defaults row and every row it ignores with a warning are left out, and a row repeating an earlier row's Job Name takes that row's place), and gives the name as written in the rule file, saying to rename it; it has no status file, and status shows it from the rule file; it never writes into the vault (an auto signature can still create an empty Vault Path folder, as for any row). The marker for a restore lock that cannot be checked is logged after the same 15 min grace as a missing disk, then once an hour while the failure lasts; until then the daemon only logs, at error level, that it postponed pruning.
	firewatcher/reverberator.regex holds the patterns for the alerting markers (FAILED, UNREADABLE, STOPPED, VAULT WRITE ERROR, EXITING); RECOVERED is left out. They match a marker only where a journal line's message starts (right after the first "]: ", past a color code or "[ERROR] " prefix), so a monitored file named like a marker, which shows up inside other lines, raises no alert. Copy it to /etc/firewatcher/patterns.d/reverberator.regex and restart firewatcher, which loads its patterns at start and follows the whole journal; 0.47 adds the VAULT WRITE ERROR pattern, so copy it again when upgrading.
	Inner mounts: a mount point under a monitored path (read from /proc/self/mountinfo) is backed up while it is mounted. When it is unmounted, its folder is paused: nothing under it is recorded as deleted, its last backed-up contents stay in new versions, and events under it are dropped. When it is mounted again only that subtree is compared with the vault. To retire an inner disk for good, remove the mount point folder, or put files of its own in it; the pause then ends and the folder is backed up as what it now is.

Status, history and restore:
	reverberator status | history | restore: three commands that read the rule file and the vaults. They never write to a vault, its manifest or the rule file, and the daemon's own command line (reverberator [options] RULE_PATH) is unchanged.
	reverberator status [--rule PATH] [--state_dir DIR] [--json]: one block per job with its state (running, retrying, waiting for a disk, stopped, with the reason), its last backup, and its vault numbers (versions kept against the limit, the oldest kept, size and inodes against the limits; a vault that is not mounted is said to be). The daemon writes a small file per job into /run/reverberator after each state change and committed backup; the commands take --state_dir or REVERB_STATE_DIR to use another folder, the daemon only REVERB_STATE_DIR, so set the same REVERB_STATE_DIR for both or status will read the daemon as not running. status counts the daemon as running only when the pid it recorded is alive with the recorded start time, so after a kill or a reboot the jobs are shown as the last known state, marked so, never as healthy. The commands read the rule file the daemon recorded, whether or not it still runs; with no record, or to use another, give --rule PATH. They never fall back to a reverb_rule.tsv in the current folder.
	reverberator status --json prints the same as one JSON object on one line, for scripts and dashboards; both forms are made from the same data, so they cannot disagree, and exit alike (a usage error prints nothing on stdout). Times are seconds since the epoch, texts are escaped as in the text form, and jobs come in rule file order:
		{"daemon": {"alive", "pid", "version", "started_at", "rule_path"},
		 "jobs": [{"job", "state", "phrase", "last_known", "detail", "failures", "retry_at", "since", "last_backup", "last_version", "oldest_backup", "oldest_version", "versions", "keep",
		           "vault": {"path", "mounted", "error", "size", "size_limit", "inodes", "inode_limit"}}]}
	alive is whether the recorded daemon runs; pid, version and started_at are those it recorded (null with no record; kept from its last run when it is not alive). state is starting, running, waiting, retrying, stopped, or unknown for a job with no status file; phrase is the state as the text shows it, and last_known says it is only the last known state (the daemon is not alive, or the record is older than this daemon run). failures counts the failed attempts in a row, retry_at is when a retrying job tries again, since when the state began. last_backup and last_version are the newest kept version's time and number, oldest_backup and oldest_version the oldest one's (null with no version); versions is how many are kept and keep the limit (0 for none). In vault, mounted is false for a vault folder that is missing or empty, the sizes and limits (0 for no limit) are null where the text shows no vault line, and error says why the vault could not be read (mounted and versions are then null). A job whose name has nothing left after cleanup is stopped, with vault null.
	reverberator history [--job NAME] [--files] PATH: when a file or folder changed in the versions the vault still keeps, newest first, including paths that no longer exist. PATH is a live path, absolute or relative to the current folder, under one job's monitored path (the longest match; --job NAME names the job, and PATH is then relative to its monitored path). For a file each line gives the version, time, event (create, modify, attrib, move with its source, delete) and size; for a folder, counts of what was created, modified and deleted under it, and --files lists the paths. The oldest kept version is shown as the oldest copy kept, not as a change. A path that was never backed up is said so, with the skip list pattern that matches it if there is one. A vault that is not mounted is said to be, not reported as never backed up.
	reverberator restore [--job NAME] [--version N | --at TIME] [--in-place] [--threads N] [--yes] [--accept] PATH [DEST]: copies a file, a folder, or a job's whole monitored path out of one version. The version is --version N, or the newest one at or before --at TIME (YYYY-MM-DD HH:MM[:SS] in local time, or a version folder's time; a bare YYYY-MM-DD means 00:00 at the start of that day, so it picks the last version made before that day began); with neither, the versions where the path differs are listed newest first and one is picked by number (one candidate is used and named). Without a terminal that is an error. Chain links are followed to the real file, user symlinks are restored as symlinks, and mode, owner, times and extended attributes are kept. With Only Sync Attributes a restored file carries the newest mode, owner and times its shared copy has, which are not necessarily those of the chosen version. A file is written under a temporary name and renamed once complete. An entry that is only a link into the monitored path (a referenced first version), a dangling chain, an unreadable file or a failed copy is reported by path at the end, the rest still restores, and the exit code is 1. Each failure and warning is printed as it happens, so a restore with many of them does not hold them all in memory, and the summary at the end repeats the first 20 of each with their counts. The picker and the Continue? prompt are written to stderr, so they show on the terminal when the output is redirected. Progress is printed, and copies run in parallel, 4 at a time unless --threads N says otherwise, so a restore does not keep the vault disk from the daemon's backups.
	Destination: restore /a/b/proj /tmp/out creates /tmp/out/proj, and stops before writing when that name exists, unless it is this restore's own unfinished output. --in-place restores at the original path instead, first moving what is there to <name>.before-restore-<timestamp> next to it; nothing is overwritten. Names printed by the commands have control characters escaped. Restores refuse a destination on a path another user could change (a folder from / down that is owned by neither root nor you, or is group or other writable without the sticky bit), and a destination inside any job's vault; in place is also refused when the restored path would hold a vault, as moving it aside would take the vault along. In place is refused where another user owns or can write a folder above the restored path (for example a Nextcloud data tree owned by www-data): restore into a folder of your own, then move it in.
	Unfinished and failed restores: a folder restore puts a marker file (.reverberator-restore) at the top of its output, naming the job, path and version. Until the restore finishes or is accepted, its folders are owned by the user running the restore (usually root) and the target is private (0700); on success each folder gets its owner, mode and times and the marker is removed. Running the same restore again (same job, path, version and place) continues it: entries already there with the vault copy's type, size and mtime are kept, the rest are copied. It never moves aside, replaces or deletes output it did not mark, and a marker of another job, path or version is refused. Ctrl-C, SIGTERM and SIGHUP stop a restore alike: the marker stays, and the same command picks up where it stopped. A stop while the folders are being given their owners says to finish with --accept, as running it again would only copy over what is done. Only one run of the same restore is allowed at a time; a second is refused. When a restore leaves failures, the marker stays so a re-run retries just those; restore --accept PATH (with the same options) keeps the result as it is (it is refused, with exit code 2, when the target holds no unfinished restore of that path and version, as there is nothing to accept, and then changes nothing): it copies nothing, gives every folder its owner, mode and times (instead of the user running the restore), and removes the marker.
	Whole job: --in-place on a job's monitored path itself cannot move the root aside, so the root must be empty (an empty lost+found is fine) or hold its own unfinished restore, which covers a replaced disk, and must belong to the user running the restore (a root owned by another user is refused, not given to anyone); otherwise restore into a folder instead. It always shows which filesystem the root is on and asks Continue? [y/N] (--yes skips; without a terminal the question needs --yes). It refuses when that filesystem has less free space than the oldest kept version took in the vault (that version holds the whole tree; the others only what changed after it), and warns that the restore may not fit when there is less than all the kept versions up to the chosen one took together. Check the mount point it shows: with the disk not mounted, that would be the disk below it. A restore picked up again skips this check and its warning, as part of it is already in place. If the daemon runs that job, it will back the restore up as one large change.
	Retention: while a restore runs it holds a lock for its job in the state folder (released by the system if the restore is killed), and the daemon postpones pruning that job's oldest version, logging that it did. history holds the same lock for as long as its output is being written, so pruning waits for it too, and while a pager shows the output of history, nothing is pruned. Backups continue, so the vault may exceed its size limit until the restore ends.
	Vault links: a symlink in a version is taken as a link to the previous version's copy only when it names the version just before its own, and is followed only through real folders. Before 0.39 a move to another folder depth left links that pointed nowhere, and retention could delete the only copy behind one. Moves now rewrite the links they carry. A link broken earlier is copied again in the newest version by the next full comparison (as at the first start of 0.39), is read by history and restore in older versions, and becomes a real copy when retention prunes the version it points into.
	Exit codes of the commands: 0 when everything asked for was shown or restored, 1 when anything failed, 2 for usage errors: a path under no job, no version chosen without a terminal, a destination refused, a path that was never backed up (for restore; history says so and exits 0), a rule file that is missing, a time for --at that is not one of the forms above, and --accept where no unfinished restore of that path and version is.
	history and restore still run while a disk of the vault's mergerfs pool is missing: they print a warning on stderr naming the disk, as what it holds is not shown, and exit 1 (2 still means a usage error, such as a path whose copies are all on the missing disk, which is reported as never backed up).
